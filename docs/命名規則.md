# 命名規則（profile）

命名規則是**獨立、可跳過**的 JSON 檔。不套用時系統完整可用：設備類型依廠牌與收集到的資料判斷，分群依連線關係。

命名規則只能做兩件事：

1. **建模前**把名稱對應到正式名稱：`alias`（別名）、`stripDomain`（去掉網域）
2. **建模後**加註解：`classify`（類型、角色、站點）、`group`（分群）、`label`（顯示名稱）；選用的 `zones`（L4 zone 標籤）也是註解，但只在查詢時使用（見下方「zones」）

它**不能**新增、刪除或改變任何事實（介面、鏈路、VLAN、位址）。基準的 `meta.profile` 會記錄使用了哪一份規則、版本與內容雜湊（[設計說明 §5.2](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)）。

## 格式

命名規則是 `schema` 為 `ssot-profile/1` 的 JSON。完整範例直接看專案附帶的檔案，不在這裡另寫一份，以免和實際檔案走樣：

- [`profiles/floor-device-naming.json`](../profiles/floor-device-naming.json)：JSON 範例，格式即使用者自備規則檔的格式。
- [`profiles/site-naming.js`](../profiles/site-naming.js)：內建規則。內容是同一種 JSON 物件，只是包成 `<script>` 以便 `file://` 直接載入。

| 欄位 | 說明 |
|---|---|
| `match` | 正規表示式（預設不分大小寫，可用 `flags` 改） |
| `kind` | `firewall`、`switch`、`router`、`host`、`unknown`；第一個符合的規則生效 |
| `role`、`site`、`value` | 可用 `$1`、`$2` 帶入比對到的群組 |
| `id`、`version` | 規則識別與版本；基準的 `meta.profile` 會記錄這兩個值與全文的雜湊。`id` 應與檔名相同；修改內容時一併提高 `version`，比較容易分辨是哪一份 |
| `stripDomain`、`alias` | 建模前：去掉名稱中第一個 `.` 之後的網域、把舊名稱對應到正式名稱 |
| `group`、`label` | 建模後：分群名稱與畫面顯示名稱，`match` 比對到時以 `value` 產生 |
| `zones` | 選用：L4 zone 標籤的陣列，只在查詢時使用，見下方「zones」 |
| `name` | 選用：這份規則的名稱（字串），顯示在「建立基準」的選單與「⚙ 設定 → 命名規則」的清單（`S.profile.nameOf`）。不影響標註 |
| `description` | 選用：一句說明，顯示在「⚙ 設定 → 命名規則」的清單；沒有時依有哪些規則推出一句（`S.profile.describe`）。不影響標註 |

**`name` 和 `label` 的差別**：`name` 是**這份規則**叫什麼（例如「樓層_設備型號_編號」），只用於顯示；`label` 是**每台設備**的顯示名稱規則 `{ match, value }`，會寫進基準的註解。

- **規則名稱寫在 `name`**。舊的寫法是把最上層的 `label` 寫成字串當名稱（內建的 `site-naming.js` 仍這樣寫，仍可使用）；但同一份規則若也要顯示名稱規則，兩個 `label` 會撞名，`JSON.parse` 只保留後面那一個，名稱就不見了（`floor-device-naming.json` 第 2 版就是這樣，清單的「名稱」顯示「—」）。
- **衝突會明確報錯**：載入命名規則檔時，同一個物件裡有重複的鍵（例如兩個 `label`）就失敗並列出位置（`S.profile.parse`）；`name` 和字串的 `label` 同時存在、`label` 不是字串也不是 `{ match, value }`、`name` 不是字串時，也會失敗（`S.profile.compile`）。
- 名稱的取法（`S.profile.nameOf`）：有 `name` 用它；沒有時用字串的 `label`；都沒有時沒有名稱。物件的 `label` 不是名稱。

**比對順序**：`classify` 由上往下比對，**類型（`kind`）與角色（`role`）各自採用第一個有給值的規則**。所以較明確的規則要排在前面。例如 `TPE_CORE_RT_01` 要先用第三段 `RT` 判斷為路由器，再讓 `CORE` 的規則只提供角色；若 `CORE` 的規則排在前面又帶了 `kind`，路由器就會被判成交換器。

**分隔符號**：同一份規則的 `classify`、`group`、`label` 應接受相同的分隔符號（例如都用 `[_-]`），否則同一台設備會只有一部分被標註。

### zones（選用，2.11.0 新增）

給 L4 的 zone 用的標籤：把網段標成使用者指定的 zone，例如管理 VLAN 標成 `MGMT`。格式：

```json
"zones": [
  { "on": "vlan", "match": "^MGMT$", "zone": "MGMT" },
  { "on": "interface", "match": "dmz", "flags": "i", "zone": "DMZ" },
  { "on": "subnet", "match": "^10\\.9\\.", "zone": "LAB" }
]
```

| 欄位 | 說明 |
|---|---|
| `on` | 比對的對象：`vlan`（網段所在 VLAN 的 ID 文字與 VLAN 名稱）、`interface`（設定這個網段的已收集設備的介面名稱與說明）、`subnet`（網段文字，例如 `10.0.10.0/24`） |
| `match`、`flags` | 正規表示式，和其他段一樣預設不分大小寫 |
| `zone` | zone 名稱，非空字串；可用 `$1`、`$2` 帶入比對到的群組 |

- **第一條符合的生效**：每個網段由上往下比對，用第一條符合的規則。
- **只在查詢時使用，不進 Snapshot**：建立基準時只驗證、不使用 `zones`；查詢 zone 與 zone 矩陣時（`Q.zones`、`Q.zoneMatrix` 等，見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)）以 `profile` 參數傳入。命名規則的標籤是使用者寫下的意圖，優先於其他 zone 來源，而且**不標示為推論**。`meta.baselineKey` 依命名規則的全文計算，所以改了 `zones` 再重新建立基準，基準鍵也會不同。
- **要傳入建立基準時用的同一份命名規則**：查詢時核對 `id`、`version` 與內容雜湊是否和基準的 `meta.profile` 相同，不同、建立基準時沒有套用命名規則，或基準沒有記錄雜湊（2.11.0 以前建立）時，丟出 TypeError（規則見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)）。
- **改了 `zones` 卻沒改 `version`，L4 查詢會被擋下**：內容雜湊和基準記錄的不同。要用同一份命名規則重新建立基準；修改命名規則時也一併提高 `version`。
- **有驗證**：`zones` 不是陣列、`on` 不是上面三種、`zone` 不是非空字串、`match` 不是有效的正規表示式時，載入命名規則就會失敗，錯誤訊息列出所有問題（和其他段相同）。

## 使用方式

- 在「建立基準」對話框的「命名規則」選單選擇，或選「載入命名規則檔（JSON）…」。載入過的規則會儲存在這個瀏覽器。
- 「⚙ 設定 → 命名規則」把內建的與載入過的分開列出（id、名稱、說明、來源、目前的基準是否使用），可以載入命名規則檔、下載範本、匯出任一份、移除載入過的，並看每一份對目前基準的套用結果（見下方「維護流程」）。
- 專案附帶兩份規則，副檔名代表用法：

  | 檔案 | 用法 | 名稱格式 |
  |---|---|---|
  | `profiles/site-naming.js` | **內建**：`index.html` 自動載入，直接出現在選單 | 站點_層級_類型_編號（`TPE_CORE_RT_01`），相容三段的站點_角色_編號 |
  | `profiles/floor-device-naming.json` | **使用者載入**：用「載入命名規則檔（JSON）…」選取，也是自備規則的範本 | 樓層_設備型號_編號（`3F_hAP_01`、`B1F-RB5009`） |

- 要新增內建規則，照 `site-naming.js` 的方式放在 `profiles/`，並在 `index.html` 加一行 `<script>`。
- `tests/core/profile.js` 會用範例資料與代表名稱檢查這兩份規則的標註結果；修改規則時請一併更新測試（測試由 `tests/run.js` 載入執行）。

## 維護流程

### 撰寫

1. 從「⚙ 設定 → 命名規則 → 下載範本」取得最小範本（每一段各有一個範例、帶 `description`），或複製 `profiles/floor-device-naming.json`。
2. 把 `id` 改成和檔名相同，`name` 寫這份規則的名稱、`description` 寫適用的名稱格式（例如「站點_類型_編號」）。不要再用字串的 `label` 當名稱（見上方「`name` 和 `label` 的差別」）。
3. 依上方「格式」的欄位表填寫：先用 `stripDomain`、`alias` 把同一台設備的不同寫法對到同一個正式名稱，再寫 `classify`（較明確的規則排前面）、`group`、`label`。分隔符號在每一段保持一致。
4. 只寫需要的段落：沒有 `group` 時分群照常依連線關係，沒有 `classify` 時類型照常依收集到的資料判斷。

### 驗證

1. 在「⚙ 設定 → 命名規則」按「載入命名規則檔（JSON）…」。格式有誤時（JSON 不合法、同一個物件裡有重複的鍵、`kind` 不在允許的值內、正規表示式錯誤、`name`／`label` 衝突、`zones` 格式不對）會列出全部問題，不會加入清單。
2. 在同一頁的「套用結果」選這份規則，看它對**目前基準**的結果（`S.profile.compile(json).coverage(Q)`，只讀基準、不改寫）：
   - **對上幾台**：至少得到一個註解（類型、角色、站點、分群或顯示名稱）的設備數，另列已收集設備的台數。
   - **各欄位的分布**：每個類型、角色、站點、分群各有幾台；分群名稱拼錯或層級沒切對，在這裡最容易看出來。
   - **沒對上的名稱**：先列 20 筆，可展開全部；未收集、只由鄰居或 ARP 得知的設備會註明。這些名稱就是要補規則的對象（或刻意不標註的設備）。
   - 目前的基準不是用這份規則建立時，結果是依基準中的名稱預覽（名稱已經過建立時那一份規則的 `alias`／`stripDomain`）；以這份規則重新建立基準後才是實際結果。
3. 結果符合預期後，在「建立基準」對話框選這份規則重新建立基準。

### 測試

附帶在 `profiles/` 的規則由 `tests/core/profile.js` 檢查。修改這些規則或新增一份時，照既有案例加測試：

- 代表名稱的標註：`S.profile.compile(json).annotate(名稱)` 應得到的 `{ kind, role, site, group, label }`（見「附帶的 JSON 命名規則範例可載入」）。
- 用範例資料建立基準時，類型不應被規則改錯，也不改變應收集的資料（C02）（見「附帶的命名規則檔可載入」）。
- 套用結果：`S.profile.coverage(json, S.query(snapshot))` 的 `matched`、`unmatched`、`fields`（見「命名規則套用結果」）。

測試使用 `tests/lib.js` 的 `build(text, { profile })`（固定時間），執行 `npm run test:core -- --grep 命名規則`。

### 版本與相容

- **改了規則就提高 `version`**。基準的 `meta.profile` 記錄 `id`、`version` 與全文雜湊；`zones` 查詢、新舊基準比對與工作包都以它確認是不是同一份規則。
- **基準鍵會改變**：`meta.baselineKey` 依命名規則的全文雜湊計算（[設計說明 §5.2](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)）。同一份收集檔換了命名規則（或改了內容）再建立，基準鍵不同，處理紀錄會把它當成**新的一輪**（[ADR-002](架構決策/002-處理紀錄放在基準之外.md) 的修訂、[ADR-005](架構決策/005-版本升級規則.md)）。漂移偵測仍以 `inputHash` 判斷，同一份收集檔只算一次觀察。
- **`alias`、`stripDomain` 會改變設備鍵**，涉及那台設備的 findingKey 也跟著改變（[ADR-003](架構決策/003-findingKey的組成.md)）：處理紀錄中舊鍵的項目在新一輪會判為消失（可判定時成為已修好），新鍵的項目判為新出現。只改 `classify`、`group`、`label` 不改變設備鍵，但類型改變可能讓依類型判斷的檢查結果不同。
- 新舊基準比對遇到兩份的命名規則不同時，會提示差異可能來自命名規則，不是網路改變。

### 移除與分享

- **分享**：在「⚙ 設定 → 命名規則」按該列的「匯出」，下載 `<id>.json`；對方用「載入命名規則檔（JSON）…」載入。工作包也會附上建立基準時用的那一份。
- **移除**：只有載入過的可以移除（會先確認），內建的不能移除。和內建同 id 的載入規則會蓋過內建的那一份，移除後恢復內建的。
- 移除目前基準正在用的規則**不影響已建立的基準**（基準裡的註解與 `meta.profile` 不變）；之後建立基準時就不能再選它，需要時再載入一次。要用 `zones` 做 L4 查詢時仍需要同一份規則，移除前可以先匯出。
