# 多層網路架構圖 實作規格書

> L2（VLAN／MAC＋L1）・L3（IP／Route）・L4（SLB＋ACL＋Service）　草案 v0.4（2026-10-24）

## 0. 文件狀態

v0.2 依 topo-mikrotik 修訂當時的現況（Snapshot `ssot-snapshot/2`、`S.VERSION` 2.0.0）修訂；之後各項「狀態」隨實作更新。v0.3 依工具版本 2.8.0（Snapshot 仍為 `ssot-snapshot/2`）更新狀態，並把原本的 P2／P3 改為使用者決定的新排程 M1／M2／M3（見 [§11](#11-實作階段)）。目前的版本以 `src/core/ns.js` 的 `S.VERSION`、`S.SCHEMA` 為準，各版變更見[版本紀錄](版本紀錄.md)。修訂方式如下：

- 原有需求全部保留，每項加上「本工具對應」與「狀態」。
- 與工具現行架構衝突的需求，改寫為可行的版本，原需求移到「範圍外」並說明原因。詳見 [§10](#10-與現行架構的衝突與決策)。

狀態代號：

| 代號 | 意義 |
|---|---|
| **已有** | 已實作，可在 Snapshot 或查詢介面取得 |
| **部分** | 已有一部分，缺口寫在說明欄 |
| **P1** | 第一階段，已完成（2.2.0），見 [§11](#11-實作階段) |
| **M1／M2／M3** | 規劃在 M1（L2／L3 視圖）、M2（L4）、M3（VRF）實作，見 [§11](#11-實作階段) |
| **未排程** | 原本排在 P2，但不在 M1–M3 的範圍內，尚未排入時程 |
| **範圍外** | 本工具（MikroTik RouterOS 專用、離線、一次建立）不實作 |

v0.2 的 P2、P3 已不再使用：P2 的 L2 domain 已完成，其餘分到 M1（VLAN 篩選、埠層級 L2 圖、L3 子網圖）與 M3（VRF）；P3 未完成的部分改為 M2。逐項對照見 [§11](#11-實作階段)。

本工具的資料來源只有 RouterOS CLI 輸出（`detail without-paging`），收集方式見 [收集清單與輸入格式.md](收集清單與輸入格式.md)。資料模型見 [設計說明.md §5.2](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)，檢查規則見 [基準檢查規則.md](基準檢查規則.md)。

## 1. 範圍與設計原則

| 原則 | 說明 | 本工具對應 |
|----|----|----|
| 分三層、各一張圖 | L2、L3 為拓樸圖；L4 不畫成拓樸，改為 zone 矩陣＋查詢 | L2 拓樸圖已有；L3 圖 M1；L4 矩陣 M2 |
| 層間以錨點銜接 | L1 port ← MAC ← IP ← (IP, proto, port)，每層只往下一層對應 | 埠 ← MAC ← IP 已有（bridge host、ARP） |
| 存規則、不存結果 | 可達性於查詢時計算，不預算全對全矩陣 | 與現有「Snapshot 存事實、查詢時計算」一致 |
| 預設聚合、點選展開 | 主視圖以 zone 為單位，下鑽至 IP、port、路徑 | L2 圖已採用（終端群組收合、雙擊展開） |
| Workload 不在主流程 | 作為可選對應表，僅在端點需展開時查詢 | 範圍外 |
| 一次建立、可重現 | 同一份輸入一定得到同一份結果，不做增量合併 | v0.2 新增；沿用工具既有原則 |
| 可離線 | 不需後端與執行期網路連線；查詢為 JS 函式 | v0.2 新增；沿用工具既有原則 |

## 2. 共用資料模型

### 2.1 核心實體

| Device | device_id | hostname, role(switch/router/fw/slb/host), vendor, mgmt_ip | 共用 | `devices`：`key`、`hostname`、`kind`、`manufacturer`、`mgmtIp`；`kind` 沒有 slb（RouterOS 無 SLB） | 已有 |
| Interface | (device_id, ifname) | type(phy/lag/svi/sub), admin/oper, mac, lag_parent | L1/L2 | `interfaces`：`type`（`physical`／`lag`／`vlan` 等）、`enabled`／`status`、`hwMac`、`lag` | 已有 |

| Vlan | (domain, vlan_id) | name, l2_domain | L2 | `vlans` 以設備內的 VLAN ID 為鍵；`l2_domain` 對應「VLAN 區塊」：`Q.vlan(id).domains` 依兩端都帶此 VLAN 的鏈路與推論鏈路，把帶這個 VLAN 的設備分成互不相連的區塊，鍵為 `<VLAN ID>@<區塊內第一台設備>`；`Q.vlan(id, 區塊鍵)` 只取其中一塊。是推論，查詢時計算、不存進 Snapshot；分塊規則只有一份（`S.infer.vlanSpan`），A02、V06、A06 只比較同一塊內的位置（見[設計說明 §5.3](設計說明.md#53-關鍵推論)） | 已有（推論） |
| PortVlan | (ifname, vlan_id) | mode(access/trunk), native, allowed_list | L2 | 介面的 `mode`（access／tagged）、`pvid`（native）、`untaggedVlans`＋`taggedVlans`（allowed）、`frameTypes`、`ingressFiltering` | 已有 |
| MacEntry | (device, vlan, mac) | ifname, type(dynamic/static), last_seen | L2 | `macs[].seen`（`{ep, vlan, static}`）；type 取自 bridge host 的 `D`（dynamic）旗標；RouterOS 沒有 age 欄位，`last_seen` 只能用設備收集時間 | 已有 |
| Vrf | (device, vrf) | rd, 對應 zone | L3 | `vrfs`（`/ip vrf print` 或 export 的 `/ip vrf`，依設定順序；`members` 是歸到這個 VRF 的介面）、`interfaces[].vrf`／`vrfBasis`；路由以 `routing-table` 對應（`routes[].vrf`），VRF 介面當閘道也有處理；rd 未收集（手冊的 `/ip vrf` 只有 `name`、`interfaces`，rd 不在這個選單）（見 [ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)、[設計說明 §5.2「VRF 與路由表」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)） | 已有（資料層與畫面，3.0.0） |
| IpAddr | (vrf, ip) | prefix, ifname, role(primary/vip/hsrp/vrrp) | L3 | `ipAddresses`（`vrf` 一定有值，鍵是 `K.inVrf(ip, vrf)`：main 不加後綴，其他 VRF 加 `@<VRF>`）；`role`：VRRP 介面上的位址為 `vrrp`；hsrp 為 Cisco 專有，不適用 | 已有（vrf 3.0.0） |
| Subnet | (vrf, prefix) | gateway, vlan_id, zone_id | L3 | `prefixes`（直連網段，每個 VRF 的每個網段一筆，`key` 是網段鍵）、`vlan`（網段在 VLAN 介面上時）；gateway 以 DHCP 網路設定（`dhcpNetworks`，含 `vrf`）為依據；zone_id 由 `Q.zones().subnets[].zone` 查詢（不存進 Snapshot） | 部分（vrf 3.0.0） |
| ArpEntry | (device, vrf, ip) | mac, ifname | L3→L2 錨點 | `arps`（`vrf`：設備回報的 `vrf=`，沒有時取介面的 VRF） | 已有（vrf 3.0.0） |
| Route | (device, vrf, prefix) | next_hop, out_if, protocol, AD, metric, ecmp_group | L3 | `routes`：`routingTable`、`vrf`、`nh[]`（ECMP；各有 `vrf`、`vrfBasis`）、`proto`、`distance`（AD）、`blackhole`；策略路由的 `routingTables`、`routingRules`；metric 與 ecmp_group 未收集 | 部分（vrf 3.0.0） |
| Zone | zone_id | name, type(dmz/db/mgmt/oa...), 來源(fw/vrf/tag/derived) | L4 | 由 `/interface list`、VRF、子網推導；WAN／LAN：`firewallZones` 由名稱含 WAN／LAN 的 `/interface list` 推論（標示為推論，2.7.0）；其他 zone：`Q.zones` 依命名規則標籤、interface list、VLAN、網段推導（推論，查詢時計算、不存進 Snapshot，2.11.0，見 [§5.4](#54-zone-定義m2)）；3.0.0 起 zone 依 VRF 分開（非 main 的 id 加 `@<VRF>`），VRF 本身不是 zone 的來源 | 部分；zone 已有（查詢與畫面），依 VRF 分開（資料層，3.0.0） |
| Rule | (acl_id, seq) | action, src/dst(obj ref), proto, port_range, stateful, hit_count | L4 | `firewallRules`：export 的 `/ip firewall filter`／`nat`／`raw` 與 `/ipv6 firewall filter`／`raw`，保留 chain 內順序（position）、比對條件原文（address-list 只存名稱，不展開）與來源行；hit_count 為規則的 `stats`（`print stats` 的 bytes／packets，依序對到 export 的規則，對不上時整個表不採用，見 [F09](基準檢查規則.md#f09)） | 已有（2.7.0；hit_count 2.11.0） |
| AclBinding | (device, ifname, dir) | acl_id, default_action | L4 | RouterOS 以 chain＋`in-interface`／`out-interface`（或 interface list）表達；目前保留在規則的比對條件中，檢查時展開 interface list 判斷（內建 chain 預設接受），沒有獨立的綁定實體 | 部分（2.7.0） |
| NatRule | (device, seq) | type(snat/dnat/pat), match, translate, 生效順序(pre/post filter) | L4 | `/ip firewall nat`；RouterOS 的 dstnat 在 filter 前、srcnat 在 filter 後。目前 nat 規則存在 `firewallRules`（`table: nat`，`to-addresses`／`to-ports` 在 `params`）；F04 依 dstnat 後的位址與埠再走 forward 判斷；`/ipv6 firewall nat` 未解析 | 部分（2.7.0） |
| SlbVip | (vip, proto, port) | pool_id, snat_mode, persistence | L4 | RouterOS 無 SLB | 範圍外 |
| PoolMember | (pool_id, ip, port) | weight, health | L4 | 同上 | 範圍外 |
| Service | (ns, ip, proto, port) | process, app_tag, 來源(ss/scan) | L4 | 需主機收集 | 範圍外 |
| RuleSet | hash | 正規化後的主機規則範本，主機只存參照 | L4 | 需主機收集 | 範圍外 |

### 2.2 跨層錨點

| 對應 | 來源資料 | 用途 | 狀態 |
|----|----|----|----|
| MAC → 交換器 port | MacEntry（排除 uplink/trunk 學到的 MAC） | 終端定位、L2 圖顯示端點 | 已有（終端埠判定，見 [基準檢查規則.md A02](基準檢查規則.md#a02)） |
| IP → MAC | ArpEntry | L3 節點接回 L2 位置 | 已有（`Q.findIp`） |

| VIP → Pool member | SlbVip / PoolMember | L4 路徑分段 | 範圍外 |
| (ns, IP) → 宿主 | Workload（可選） | 主機 filter、Docker DNAT 歸屬 | 範圍外 |

唯一識別一律帶 VRF 或 namespace，以處理位址重疊。本工具 3.0.0 起，位址與網段的鍵帶 VRF（`K.inVrf`：main 不加後綴，其他 VRF 加 `@<VRF>`），所有路由表的路由都是事實（見 [§4.1](#41-資料收集)）。

## 3. L2 視圖（VLAN／MAC＋L1）

### 3.1 資料收集

| 項目 | 原方法 | 原頻率 | 本工具（RouterOS CLI） | 狀態 |
|----|----|----|----|----|
| 鄰居（L1） | SNMP LLDP-MIB / CDP-MIB、gNMI、控制器 API | 每日＋事件觸發 | `/ip neighbor print detail without-paging` | 已有 |
| LAG | IEEE8023-LAG-MIB、設定檔解析 | 每日 | export 的 `/interface bonding` | 已有（成員的運作狀態取自 `/interface print`；聚合層級的彙總未排程，原 P2） |
| VLAN / trunk allowed | Q-BRIDGE-MIB、設定檔 | 每日 | export 的 bridge VLAN、`/interface bridge vlan print detail` | 已有 |
| MAC 表 | Q-BRIDGE-MIB dot1qTpFdb、CLI | 每 15–60 分 | `/interface bridge host print detail without-paging` | 已有 |

收集頻率：本工具是一次建立的離線基準，不排程收集。定期收集可用 `tools/collect.sh` 搭配外部排程，每次產生一份獨立的基準；不做跨次合併（見 [§10](#10-與現行架構的衝突與決策)）。

### 3.2 處理規則

| 規則 | 狀態 |
|----|----|
| 同一條線由兩端或控制器重複回報時合併為一條 Link | 已有（鏈路鍵與兩端無關） |
| LAG 成員收斂為一條邏輯鏈路，成員數與狀態作為屬性 | 部分：圖上已將同兩台設備的鏈路併成一條線，成員數已有（`lagMembers`）；成員狀態彙總未排程（原 P2） |
| 端點定位：MAC 只在 access port（或非 uplink 的 port）出現才視為直連；同一 MAC 出現於多台交換器時取無 LLDP 鄰居的那個 port | 已有（終端埠：單一 MAC、無 LLDP／CDP 鄰接到已收集網路設備） |
| 一個 port 上 MAC 數超過門檻（如 \>5）標記為「下掛未管理交換器或 hypervisor」 | 已有：[A04](基準檢查規則.md#a04) |
| （v0.2 新增）Wi-Fi 客戶端定位：MAC 表無法判斷客戶端連在哪台 AP，改依 AP 關聯表（registration table）確認，沒有時依證據強度推定並標示依據 | 已有（`macs[].wifi`，見 [收集清單與輸入格式.md §4](收集清單與輸入格式.md#4-routeros-特有的行為與限制)）；CAPsMAN 的 CAP 與實體 AP 對應待實機驗證 |

### 3.3 呈現

| 元素 | 表示方式 | 狀態 |
|----|----|----|
| 容器 | 交換器／路由器，內含 port | 已有：L2 埠圖的設備框（`Q.portGraph`，[設計說明 §5.2「L2 視圖的查詢」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)，畫面見[使用說明「② 檢視」](使用說明.md#step-view)），以 ELK 的 port 排列 |

| 連線 | 實體鏈路；LAG 加粗；顏色或標籤顯示 trunk allowed VLAN | 部分：LAG 有獨立類別線型；allowed VLAN 顯示在鏈路詳情 |

## 4. L3 視圖（IP／Route）

### 4.1 資料收集

| 項目 | 原方法 | 本工具（RouterOS CLI） | 狀態 |
|----|----|----|----|
| 介面 IP、VRF | IP-MIB、設定檔、gNMI | export 的 `/ip address`、`/ip address print detail`（RouterOS 7 的 `vrf=`）；VRF 為 `/ip vrf print detail`（collector 在 RouterOS 7 自動收集）或 export 的 `/ip vrf` | 已有（VRF 3.0.0） |
| 路由表 | IP-FORWARD-MIB、CLI（show ip route vrf all）、gNMI AFT | `/ip route print detail without-paging`：所有路由表（`routing-table`），VRF 的路由表與只用於策略路由的路由表都是事實；策略路由另讀 export 的 `/routing table`、`/routing rule`、`/routing settings`、mangle 的 mark-routing | 已有（其他路由表 3.0.0） |
| ARP | IP-MIB ipNetToPhysical | `/ip arp print detail without-paging` | 已有 |
| 閘道 VIP | HSRP/VRRP MIB、設定檔 | export 的 `/interface vrrp`（RouterOS 只有 VRRP） | 已有（`ipAddresses[].role`） |

### 4.2 處理規則

| 規則 | 狀態 |
|----|----|
| 子網依 (VRF, prefix) 建立，gateway 取 SVI 或 HSRP/VRRP VIP | 部分：`prefixes` 依 (VRF, prefix) 建立並帶 VLAN（3.0.0）；gateway 取自 DHCP 網路設定 |
| 跨子網的節點只取「有路由能力」的設備（有 forwarding、有路由表）；主機多網路卡不視為路由，避免誤判 | 已有（路徑追蹤只沿有路由表的設備前進） |
| 路徑計算：逐跳查 longest-prefix match，ECMP 展開為多條；結果存為 path 物件供 L4 繼承 | 已有（`src/query/trace.js`，含遞迴下一跳） |
| 非對稱路徑：提供 dst→src 反向路徑，供無狀態 ACL 檢查回程 | 已有（路由追蹤同時列出回程並標示非對稱） |

### 4.3 呈現

| 元素 | 表示方式 | 狀態 |
|----|----|----|
| 容器 | VRF，內含子網 | 已有（3.0.0）：`Q.subnetGraph` 以 VRF 為容器，子網、節點、邊與路由都有 `vrf`，不同 VRF 的同一個網段是不同的子網節點，設備在每個有位址的 VRF 各一個節點（id 為「設備鍵@VRF」，main 不加後綴；[設計說明 §5.2「L3 子網圖」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)）；畫面在有兩個以上的 VRF 時，每個 VRF（含 main）畫成一個框（[設計說明 §11「L3 與 VRF」](設計說明.md#11-檢視層架構)、[使用說明「L3 子網圖」](使用說明.md#層級設備l2-埠l3-子網l4-可達性)） |
| 節點 | 子網；路由設備為跨子網的連接點 | 已有：L3 子網圖（`Q.subnetGraph`，[設計說明 §5.2「L3 子網圖」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)） |
| 連線 | 路由器介面所連的子網；靜態路由／預設路由以虛線標示 | 已有：位址邊；「顯示路由」以虛線箭頭畫出靜態路由與預設路由（`routes: true`） |

### 4.4 檢查項目

<a id="52-規則正規化p3"></a>

### 5.2 規則正規化（M2）

本工具對應（部分，2.7.0）：比對條件正規化（清單值排序）、以區間與集合判斷規則涵蓋（F01）、first-match 與內建 chain 預設接受，集中在 `S.infer.fw`；address-list 不展開，interface list 展開成介面集合後比較。

- 統一為 Rule(seq, action, src_set, dst_set, proto, port_range,
  stateful)，錨點為 (device\|host, interface, in/out)。

- 不展開 object-group（RouterOS 為 address-list、interface list）；比對時用集合運算（BDD 或 interval set）。

- 每台設備標註語意：first-match／block-priority、預設 action、NAT 相對於
  filter 的順序。RouterOS 為 first-match；chain 結尾未命中時預設接受。

- 主機規則正規化後取 hash 存成 RuleSet，主機只存參照（範圍外）。

<a id="53-可達性計算p3"></a>

### 5.3 可達性計算（M2）

本工具對應（已有（查詢與畫面），2.11.0）：`Q.reach(src, dst, { proto, port })` 沿 L3 路徑逐跳套用 raw prerouting → dstnat（改寫後重新查路由）→ filter input／forward／output → srcnat，輸出 allow／deny／unknown、每段位址、命中與決定的規則、NAT 改寫；無法判斷時列出原因代碼，不猜（[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)）。單台設備內「從 WAN 進來的新連線」的判斷（2.7.0）仍供 F03–F05、F07 使用。主機的 OUTPUT／INPUT 與 Service 範圍外；VRF 與策略路由的查詢與畫面已支援（3.0.0，`{ vrf }`；L4 的可達性查詢可選 VRF）。

查詢 (src, dst, proto, port) 時：

- 取 L3 路徑；沿途依序套用各介面 in/out 的 AclBinding。

- 遇到 NAT/SLB：改寫位址，以新位址重新向 L3 取下一段路徑（本工具只處理 NAT）。

- 套用來源主機 OUTPUT、目的主機 INPUT（容器再加宿主 FORWARD）（範圍外）。

- 比對目的 Service；無狀態設備另檢查回程路徑（Service 範圍外）。

- 輸出：允許／拒絕、決定性規則、每段位址、是否有服務監聽。

<a id="54-zone-定義p3"></a>

### 5.4 Zone 定義（M2）

| 優先 | 來源 | 本工具對應 |
|----------|------------------------------------|----|
| 1 | 用途標籤 | 命名規則的 `zones` 標籤 |
| 2 | 防火牆 zone、VRF | RouterOS `/interface list`；VRF 不是獨立的來源，3.0.0 起每個 zone 只含同一個 VRF 的網段（非 main 的 zone id 加 `@<VRF>`） |
| 3 | VLAN | VLAN |
| 4 | 子網 | `prefixes` |
| — | 規則等價類（用於驗證 1–4 的分組） | 規則正規化後計算 |

用途標籤排在防火牆 zone 之前（使用者 2026-10-24 決定）：命名規則是使用者明確寫下的意圖，比由 interface list 推論出來的分組優先。

MGMT 獨立成 zone；SLB VIP 歸屬其所在 zone；zone 判斷以 NAT 後位址為準。

本工具對應（已有（查詢與畫面），2.11.0）：`Q.zones`、`Q.zoneOf`；L4 畫面的「zone 的依據」列出每個 zone 與網段的來源、依據與「推論」標示。每個網段依上表的順序取第一個有結果的來源：① 命名規則的 `zones` 標籤 → ② interface list（同時屬於多個清單時取成員最少的）→ ③ VLAN（各設備不一致時取多數）→ ④ 網段本身；每個網段記錄依據（`basis`）與其他來源的結果（`alternatives`），可用來檢查分組。矩陣的目的 zone 以 NAT 後的位址為準。規則等價類用在矩陣的代表位址（見 [§7](#7-資料量控制)），不另作 zone 來源。

MGMT 要獨立成 zone 時，以命名規則的標籤指定（例如 `{ "on": "vlan", "match": "^MGMT$", "zone": "MGMT" }`，[命名規則](命名規則.md#zones選用2110-新增)）。細節見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)。

<a id="55-下鑽層級p3"></a>

### 5.5 下鑽層級（M2）

本工具對應（已有（查詢與畫面），2.11.0）：L0 是 `Q.zoneMatrix`，L1／L2 是 `Q.zoneCell`（結果相同的來源併成一列，並列出牽涉的規則），L3 是對某個代表位址呼叫 `Q.reach`。依 [ADR-014](架構決策/014-L4-zone矩陣在查詢時計算.md)（已接受）：L0 也在查詢時計算並快取，不存進 Snapshot；大型資料以 `Q.zoneMatrixSteps` 分段計算。L0–L3 的畫面在拓樸圖工具列的「L4 可達性」：矩陣是 HTML 表格（`table role="grid"`），可切服務、矩陣／表格與匯出 CSV，點格子依序下鑽到 L1 位址組、L2 牽涉的規則與 L3 逐跳路徑（[設計說明 §11](設計說明.md#11-檢視層架構)、[使用說明「L4 可達性」](使用說明.md#l4-可達性)）。L2 的「監聽」需 Service 資料，範圍外。

| 層級 | 觸發 | 列 × 欄 | 格子內容 | 計算 |
|----|----|----|----|----|
| L0 | 主視圖 | src zone × dst zone | 全通/全擋/部分/異質；可切 service 類別 | 查詢時計算並快取，大型資料分段計算（依 [ADR-014](架構決策/014-L4-zone矩陣在查詢時計算.md)） |
| L1 | 點 zone 格 | src IP 群組 × dst IP | 允許 port 數或異質 | 即時 |
| L2 | 點 IP 格 | dst port 列表 | 允許/監聽/決定規則/差異狀態 | 即時 |
| L3 | 點 port | 路徑追蹤 | 逐段設備、命中規則、NAT/SLB 改寫、主機 filter | 即時 |

<a id="56-格子狀態定義p3"></a>

### 5.6 格子狀態定義（M2）

| 狀態 | 條件 |
|----------|-----------------------------------------------------------|
| 全通 | zone 內所有成員對該 service 類別允許 |
| 全擋 | 全部拒絕 |
| 部分 | 部分 IP 或 port 允許 |
| 異質 | 同 zone 成員的結果不一致（zone 切分錯誤或主機規則不一致） |
| 多開 | 允許但無服務監聽，或不在 Dependency 清單（需 Service 資料，範圍外） |
| 漏開 | 有服務監聽／有 Dependency，但被拒絕（需 Service 資料，範圍外） |

<a id="57-呈現規則p3"></a>

### 5.7 呈現規則（M2）

本工具對應（部分，2.11.0）：L0 對角線（zone 內）以虛線外框單獨標示；L1 的來源依結果合併成組，同一格有其他結果時，全部拒絕的組預設收起；dst-nat 的入口在 L1 標出改寫後的位址，L3 逐跳列出 NAT 改寫前後的位址。從異質格下鑽時只顯示造成差異的 IP：已有，L1 預設只列出造成差異的組（依 `Q.zoneCell` 的 `groups[].divergent` 判斷，定義見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)），可切換顯示全部，造成差異的服務另標「≠ 差異」。L2 連續允許的 port 合併為區間：尚未實作（本工具的 L2 列出牽涉的規則）。

- L0 對角線（zone 內）單獨標示，主要受主機 filter 影響。

- L1 src 端合併結果相同的 IP 為群組；dst 保留個別 IP；全擋列欄預設隱藏。

- L2 連續允許的 port 合併為區間。

- 從「異質」格下鑽時，L1 預設只顯示造成差異的 IP。

- SLB/NAT：L1 顯示 VIP，L3 顯示改寫前後兩段（本工具只有 NAT）。

<a id="58-規則整理產出p3"></a>

### 5.8 規則整理產出（M2）

本工具對應（部分，2.7.0）：被遮蔽規則（F01）、重複規則（F02）已實作；永不命中規則：hit_count 已解析（2.11.0，規則的 `stats`），規則詳情已顯示命中次數（對不上 export 時說明原因，見 F09），沒有 finding（計數器是收集當下的累積值，0 不代表規則沒有用）；過寬規則只涵蓋 WAN 可連入的放行（F03）與 IPv6 只限目的埠的放行（F05）。

整理結果可直接轉成修正 patch（2.8.0，`S.remediate.plan`，見[設計說明 §9](設計說明.md#9-修正-patchssot-patch1)）：F01、F02（以及固定來源埠放行的 F06）是 auto 等級，以 `disabled=yes` 停用規則，產生每台設備的套用、回復與驗證 `.rsc`；工具只產生文字，不連線套用（[ADR-001](架構決策/001-工具維持唯讀.md)）。F03 是 choice 等級，目前不產生指令、列出原因。

- 被遮蔽規則（shadowed）、重複規則、永不命中規則（搭配 hit_count；需收集 `/ip firewall filter print stats`）。

- 過寬規則（any/any、port range 過大）。

- 主機 RuleSet 範本數量與偏離基準的主機清單（範圍外）。

## 10. 與現行架構的衝突與決策

本工具的既有原則見 [設計說明.md §2](設計說明.md#2-原則)：一次建立、可重現、可離線、只吃 RouterOS 輸出。下列需求與之衝突，v0.2 先採「建議做法」，**待確認**。

| 原需求 | 衝突 | 建議做法（v0.2 採用） |
|----|----|----|
| 定期收集（每日、每 15–60 分）、`last_seen`、依設定變更增量重算 | 基準是一次建立的 Snapshot，沒有時間序列；增量合併違反可重現 | 每台設備記錄收集時間；需要歷史時保留多份基準，已由新舊基準比對（`S.compare.snapshots`）處理（見 [設計說明.md §8](設計說明.md#8-比對獨立模組)）。2.8.0 起，跨輪次的處理狀態與收斂摘要記在基準之外的處理紀錄（`ssot-ledger/1`，見 [設計說明.md §10](設計說明.md#10-處理紀錄ssot-ledger1)），以 `meta.baselineKey` 判斷是否同一輪；每一輪仍是一份獨立的基準，不合併 |
| SNMP、gNMI、控制器 API、多廠牌、Linux／Windows／K8s／雲端規則、SLB、Workload | 本工具是 MikroTik RouterOS 專用版，只吃 CLI 輸出 | 列為範圍外；需要時另建多來源版本（可參考多廠牌版 topo-ssot） |
| HTTP API（/l2/locate 等） | 無後端、可離線 | 以 `SSOT.query()` 的 JS 函式提供相同查詢 |

## 11. 實作階段

使用者在 2026-10-24 決定 P1 之後的排程：原本的 P2、P3 改為 M1、M2、M3，三項都排在畫面的版面重整之後。整體順序是 findingKey 區分 facet → A12 修正指令 → 版面重整第一階段（資料中心與工作包）→ 版面重整第二階段（中間工作畫面）→ **M1** → 版面重整第三階段（上方流程步驟）→ **M2** → **M3**。

| 階段 | 內容 | 負責 | 前置條件 | 狀態 |
|----|----|----|----|----|
| P1：補齊 L2／L3 子集 | 設備收集時間、MAC 類型、`frame-types`／`ingress-filtering`、LAG 成員狀態、路由 distance 與黑洞路由、VRRP 角色、子網閘道與 vlan_id；新檢查：allowed／native 不一致、孤立 VLAN、單埠 MAC 過多、路由迴圈、黑洞路由、子網無閘道、閘道不在子網、ARP 無對應子網；反向路徑追蹤 | — | — | **已完成（2.2.0）**；LAG 成員狀態彙總與子網無閘道未排程 |
| M1：L2／L3 視圖 | 依 VLAN 篩選、圖上持續標示承載鏈路（VLAN 區塊已算出，見 [§3.3](#33-呈現)）；埠層級 L2 圖（ELK 的 port）；L3 子網圖（先不分 VRF，資料結構預留 vrf） | 主要是 frontend；資料已有 | 版面重整第二階段（中間工作畫面）完成 | **已完成（2.10.0）**：查詢（`Q.vlanIds`、`Q.vlanCarriers`、`Q.portGraph`、`Q.subnetGraph`）與畫面（層級切換、VLAN 篩選、L2 埠圖、L3 子網圖）；VRF 容器在 M3 |
