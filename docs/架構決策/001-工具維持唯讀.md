# ADR-001：工具維持唯讀，修正 patch 只產生文字

- **狀態**：已接受
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

基準找出問題之後，使用者希望修正時看得到要下的指令，並能一次處理單台或多台設備。

工具原本的定位是：

- 網站：由 RouterOS CLI 輸出建立基準的離線工具。`index.html` 的 Content-Security-Policy 以 `connect-src 'none'` 禁止執行期網路連線（開發原則第 11 條）。
- 收集器：`tools/collect.sh` 是唯一會連到設備的部分，只用系統 SSH 收集輸出（開發原則第 13 條）。

要讓修正「做得到」，可以讓工具直接套用到設備，也可以只產生文字、交給使用者執行。

## 決策

- 不提供連線或套用到設備的功能，也不做 `tools/apply.sh`。
- 修正 patch 由核心 [src/remediate/patch.js](../../src/remediate/patch.js) 產生：
  - `S.remediate.plan(Q, selection)` 產生 `ssot-patch/1` 純 JSON 計畫，只讀基準的事實，相同輸入得到相同結果。
  - `renderRsc`、`renderRollback`、`renderVerify`（多台用 `files`）把計畫轉成每台設備的 `.rsc` 文字。檔頭註明只是文字，工具不會連線或改設定。
- 每台設備有三個檔案：
  - **套用**：所有前置檢查都在任何變更之前。前置檢查以 `:if ([:len [find where …]] != 預期筆數) do={ :error … }` 確認條件只找到預期的規則。RouterOS 的 `/import` 逐行執行到第一個錯誤為止、沒有交易，所以前置檢查失敗時不會改到任何設定。
  - **回復**：依基準的 `before` 值倒序還原，同樣先做前置檢查。
  - **驗證**：每個變更一條 `print where`，並以註解寫出預期結果。
- 用 `find where` 的條件找規則，不用規則編號。條件可能符合多條規則時不產生指令，改列為 manual 並說明原因。
- `.rsc` 只含 ASCII：字串中的非 ASCII 位元組寫成 `\XX`，註解中的非 ASCII 字元寫成 `<U+XXXX>`。中文說明放在計畫的 note、risk、warnings。
- 目前只實作 auto 等級（F01、F02、F06 以 `disabled=yes` 停用規則）。choice 與 manual 等級，以及找不到規則、已停用等情況，放進 `skipped` 並附原因。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 只產生文字，由使用者自己執行 | 維持離線與唯讀；使用者可以逐行審查；結果可重現，可用黃金檔測試 | 套用、確認都要使用者自己做 | **採用** |
| B. 網站直接連線套用 | 操作最少 | 違反離線契約（`connect-src 'none'`）；瀏覽器要處理憑證；核心會依賴網路 | 不採用 |
| C. 新增 `tools/apply.sh` 以 SSH 套用 | 可以沿用收集器的 SSH 與 key | 工具從唯讀變成可寫，需要有寫入權限的帳號；要處理部分套用、連線中斷與回復，責任與風險大很多 | 不採用 |
| D. 只顯示處理建議，不產生指令 | 最簡單 | 使用者要自己組指令，容易抄錯條件 | 不採用；manual 等級仍是這種做法 |

## 後果

### 變容易的

- 使用者可以用唯讀帳號收集、用自己的流程審查與套用，工具不需要任何寫入權限。
- 計畫與 `.rsc` 可重現，可以用黃金檔測試（`tests/golden/sample-patch*`）。
- 套用失敗的範圍可預期：前置檢查不通過時一行設定都不會改。

### 變困難的

- 是否修好要靠重新收集、再建立基準來確認（見 [ADR-002](002-處理紀錄放在基準之外.md) 的處理紀錄）。
- 設備上的設定已經和基準不同時，前置檢查會中止，使用者要先重新收集。
- 多台設備的執行順序、套用中途失敗後的處理，都要使用者自己判斷。

### 之後要回頭看的

- 第三階段計畫的自動回復 scheduler 包裝（變更觸及管理介面或路徑時預設加上）與多台執行順序提示，尚未實作。
- CLI `tools/patch.js` 計畫與 `tools/baseline.js` 合併成一支，結束碼的設計見 [ADR-002](002-處理紀錄放在基準之外.md)。
