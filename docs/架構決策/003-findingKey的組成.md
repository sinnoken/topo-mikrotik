# ADR-003：findingKey 的組成

- **狀態**：已接受
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

新舊基準比對、修復追蹤、修正 patch 的選取與處理紀錄，都要判斷「這兩份基準裡的 finding 是不是同一個問題」。finding 本身沒有 id 以外的識別欄位，而訊息文字、證據行號在兩份基準之間常會改變（輸入多了一行、訊息改了措辭）。

## 決策

- findingKey 定義在 [src/query/query.js](../../src/query/query.js)，以 `Q.findingKey(f)`（或 `S.query.findingKey`）取得：

  ```js
  JSON.stringify([f.id].concat(U.uniq(f.entities.map((e) => e.type + ':' + e.key)).sort(U.cmp)))
  ```

  也就是規則 id 加上去重、排序後的實體（`type:key`）。以 JSON 陣列字串表示，避免分隔符號與鍵的內容混淆。
- **不含**訊息、證據、行號、嚴重度與 finding 在基準中的順序。訊息改寫或輸入行號改變時，同一個問題仍對得上。
- **碰撞**：同一份基準內，id 與實體都相同、只差訊息的 finding 會得到同一個鍵。已知的情況：
  - 同一台設備的多段 I01、I02、I03（I03 的實體只有設備）；
  - 沒有設備標頭的 I01（實體為空）；
  - 同一台設備對同一個鄰居 ID 的多筆 R02。
- **比對以多重集合處理**：`S.compare.snapshots`（[src/compare/compare.js](../../src/compare/compare.js)）把每個鍵對應到一組 finding，同一個鍵先配對訊息相同的，其餘依基準中的順序配對，配不到的才算新增或消失。
- 其他使用者對碰撞的處理：
  - 處理紀錄（[ADR-002](002-處理紀錄放在基準之外.md)）：同一個鍵只有一個項目，碰撞的 finding 共用同一個狀態。
  - 修正 patch：以鍵選取時，同一個鍵的每一筆都會選到；同一條規則只停用一次（`same-target`）。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. id＋排序後的實體 | 訊息與行號改變不影響；實體已是 canonical key | 同一份基準內可能碰撞 | **採用**，碰撞以多重集合處理 |
| B. 再加上訊息 | 幾乎不碰撞 | 訊息改一個字就對不上，處理紀錄的狀態全部失效 | 不採用 |
| C. 再加上證據的行號 | 不碰撞 | 輸入多一行就全部對不上 | 不採用 |
| D. 每條檢查自訂穩定鍵 | 每條規則都能精準區分 | 規則分散在各檢查，容易不一致，違反單一事實來源 | 不採用 |

## 後果

### 變容易的

- 改寫 finding 訊息（例如補充說明、調整措辭）不會影響比對與處理紀錄。
- 同一個鍵在比對、修復追蹤、修正 patch 與處理紀錄之間通用。

### 變困難的

- 實體鍵的規則變成長期契約。`src/core/keys.js` 的正規化、命名 profile 的 canonicalize，或防火牆規則鍵（設備＋位址族＋表＋chain＋比對條件）改變時，相關的 findingKey 會跟著改變：舊項目在處理紀錄中會被判為消失、新項目判為新出現。這類修改要在報告中說明對處理紀錄的影響。
- 防火牆規則鍵含比對條件，所以使用者修改規則的條件後，同一條規則的 finding 會變成另一個鍵。
- 碰撞的 finding 在處理紀錄中無法分開處理，例如同一台設備的兩段 I03 只能一起標為可接受。

### 之後要回頭看的

- 碰撞的規則是否補上可以區分的實體（例如 I03 依區塊區分），要和處理紀錄的相容性一起評估：補上之後，舊的鍵都會改變。**已處理**：沒有改實體，而是為 12 條規則加上 facet，見下方「修訂」。I01、I03 仍會碰撞。
- 「finding 所屬設備」目前有兩份實作：`Q.findingDevice`（query.js）與 `V.remediation.findingDevice`（src/view/remediation.js），規則相同。畫面應改為呼叫查詢介面。**已處理**：畫面的實作已移除，分組、匯出與修正計畫都呼叫 `Q.findingDevice`，只剩一份。

## 修訂

### 2026-10-24：findingKey 加入 facet（2.9.0）

- **原因**：同一組 id＋實體可能產生多筆 finding，例如同一組設備的 A12「DNS 伺服器不同」與「NTP 伺服器不同」。兩筆共用一個鍵，處理紀錄與修正計畫無法分開處理。
- **修改**（2278c28）：
  - finding 新增選用欄位 `facet`，標示這筆檢查的是哪一個項目。值只取自設定項目的固定字樣與正規化後的設定值，不取自訊息、設備名稱或行號。
  - findingKey 改為：

    ```js
    JSON.stringify([f.id].concat(f.facet != null ? ['facet:' + f.facet] : [], 排序並去重的 'type:key'…))
    ```

    facet 固定放在第 2 個元素，不參與排序；entity 的 type 不會是 `facet`（有測試），所以不會和實體混淆。沒有 facet 的規則，鍵和之前完全相同。
  - 上表的選項 D（每條規則自訂鍵）**部分採用**：不讓各檢查自訂整個鍵，而是由 `CATALOG`（[src/check/catalog.js](../../src/check/catalog.js)）統一宣告哪些規則有 facet 以及格式，`add()`（[src/check/checks.js](../../src/check/checks.js)）強制檢查：有宣告的規則每筆都要有 facet，沒宣告的都不能有，不一致時丟錯。規則仍集中在一處，沒有違反單一事實來源。
  - 有 facet 的 12 條規則：I02、V06、V07、A02、A07、A08、A10、A11、A12、R02、R05、R06。各規則的取值見[基準檢查規則「每筆結果的內容」](../基準檢查規則.md#每筆結果的內容)。
  - 新增 `Q.findingBaseKey(f)`（也可用 `S.query.findingBaseKey`）：不含 facet 的鍵，也就是 2.9.0 之前的 findingKey。
- **碰撞清單改為**：
  - 同一台設備的多段 I01、I03，以及沒有設備標頭的 I01（這兩條依輸入區塊產生，不是檢查項目，所以不加 facet）；
  - facet 也分不開的少數情況：同一台設備重複設定同一個 DHCP 網段（R05），同一介面重複連到同一個 router-id（R02）。

  這些仍以多重集合處理，處理紀錄中仍共用同一個狀態。
- **處理紀錄的轉換**：舊的鍵等於新 finding 的 `findingBaseKey`。舊鍵的項目要對應到 facet 不同的每一筆，這個轉換由 workflow 實作（[ADR-002](002-處理紀錄放在基準之外.md)）。**已處理**：處理紀錄依 `S.ledger.KEY_MIGRATIONS` 轉換舊鍵（`facet-split`，見 ADR-002 的「修訂」）；新舊基準比對時，只要任一邊有某條規則的 finding 沒有 facet，那條規則在兩邊都退回用 `findingBaseKey`（見[設計說明 §8](../設計說明.md#8-比對獨立模組)）。
- **不變的部分**：鍵不含訊息、證據、行號、嚴重度與順序；實體部分的組成不變；比對以多重集合處理；鍵以 JSON 陣列字串表示。
- **版本**：升為 2.9.0（minor，見 [ADR-005](005-版本升級規則.md)）。
