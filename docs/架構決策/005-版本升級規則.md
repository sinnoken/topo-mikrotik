# ADR-005：版本升級規則

- **狀態**：已接受
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

畫面會把上一次建立的基準連同輸入存在瀏覽器裡，下次開啟時還原。解析器或檢查改了之後，還原的舊基準仍是舊的解析結果，使用者會以為修正沒有生效。

需要一個規則決定什麼時候改版本號，讓已儲存的基準在需要時以新程式重建。

## 決策

- 版本號 `S.VERSION` 與 Snapshot 格式 `S.SCHEMA` 定義在 [src/core/ns.js](../../src/core/ns.js)，寫進每份基準的 `meta.version`、`meta.schema`。
- **解析結果改變就升 minor**（例如 2.7.0 → 2.8.0）。「解析結果」指同一份輸入建出的 Snapshot 內容：事實、推論、finding 或欄位改變。
- 畫面還原時（`App.restore`，`src/view/app.js`）：
  - 版本或 schema 不同、而且有儲存的輸入時，用儲存的輸入重新建立基準，並告知「程式已更新，已用儲存的輸入重新建立基準」。
  - schema 不同、又沒有儲存輸入時，告知格式不相容，請使用者重新建立。
- **只新增 CATALOG 欄位時不升版**。CATALOG 的常見原因與處理（`causes`、`action`）不複製到 finding、不進 Snapshot（見 [ADR-006](006-規則目錄與判斷分開.md)），改了不影響已儲存的基準。
- **Snapshot 結構的破壞性改變才改 `S.SCHEMA`**，並升 major（2.0.0 改為 `ssot-snapshot/2`）。
- 每次升版都在[設計說明的版本紀錄](../設計說明.md#版本紀錄)寫一筆。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 解析結果改變就升 minor | 規則簡單；已儲存的基準一定會以新程式重建 | 版本號增加得快 | **採用** |
| B. 只有使用者要求時才升版 | 版本號少 | 容易忘記，使用者看到過時的結果 | 不採用 |
| C. 依程式內容自動算版本（例如核心檔案的雜湊） | 不會忘記 | 改註解、改文字也會觸發重建；版本號沒有意義，無法對照版本紀錄 | 不採用 |
| D. 每次開啟都重建 | 不需要版本號 | 大型網路每次開啟都要重算；浪費使用者時間 | 不採用 |

## 後果

### 變容易的

- 解析器修正後，使用者不需要手動重新載入輸入。
- 從 `meta.version` 可以知道一份基準是哪一版程式建的。

### 變困難的

- 每次改解析或檢查都要判斷是否改變 Snapshot，並在同一次修改中升版與寫版本紀錄。
- 舊版的基準 JSON 檔（使用者匯出、在「比對」載入的）沒有輸入可以重建。schema 相同時 `S.compare.snapshots` 照常比對，不提示版本不同，所以新版本新增的檢查會顯示成「新出現」，看起來像網路變了。
- 升版後以同一份輸入重建，`inputHash` 不變，處理紀錄的 `advance` 會視為同一輪而略過（見 [ADR-002](002-處理紀錄放在基準之外.md)）。**已處理**：處理紀錄改用 `meta.baselineKey` 判斷（ADR-002 的「修訂」）。基準鍵含 major.minor 版本，所以升 minor 會改變基準鍵、成為新的一輪；升 patch 號不會，符合「patch 版不改變 Snapshot」的規則。

### 之後要回頭看的

- 比對兩份版本不同的基準時，是否要明確提示「版本不同，部分差異可能來自程式更新」。**已處理**：`S.compare.snapshots` 的回傳值新增 `warnings`，版本（`kind: 'version'`）或命名規則（`kind: 'profile'`）不同時照常比對並提示；畫面在比對結果上方與「只看新出現的」旁邊顯示。
- patch 號（第三碼）何時使用。過去的 2.5.1 改變了推論結果（有推論鏈路的埠不再判為終端埠）卻只升 patch 號；依這份決策，之後這種修改要升 minor，patch 號留給不改變 Snapshot 的修正。
