# ADR-006：規則目錄 catalog.js 與判斷 checks.js 分開

- **狀態**：已接受
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

每條檢查規則除了判斷邏輯，還有給使用者看的資訊：標題、嚴重度、類別、需要的資料，以及常見原因與處理方式。這些文字會出現在詳情、規則清單、匯出的 CSV 與 Markdown，也要和[基準檢查規則](../基準檢查規則.md)一致。

如果文字散在各檢查函式或畫面裡，就會有多份各自走樣。

## 決策

- [src/check/catalog.js](../../src/check/catalog.js) 是規則目錄 `CATALOG`：每條規則的 `severity`、`cat`、`title`、`data`、`evidenceLimit`、`causes`、`action`。
- [src/check/checks.js](../../src/check/checks.js) 只負責判斷，以規則 id 對應目錄。`catalog.js` 必須先載入（`tools/core-files.js` 的順序），否則 `checks.js` 直接丟出錯誤。
- **causes／action 只有一個來源**：只放在 `CATALOG`，不複製到 finding，也不進 Snapshot。
- **畫面只透過 `V.remediation.advice(id)` 讀取 causes／action**（`src/view/remediation.js`）。它每次從 `S.check.CATALOG` 讀取，回傳 `{ action, causes }`；詳情、規則清單與匯出都用它。規則的標題、嚴重度與類別，畫面直接讀 `S.check.CATALOG`。
- `tests/docs.js` 檢查 `CATALOG` 與 `docs/基準檢查規則.md` 一致：每條規則都有章節、總覽表的標題與嚴重度相同、「常見原因」的條數與 `causes` 相同、有「處理」。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 文字寫在 checks.js 各檢查旁邊 | 判斷與說明放在一起 | 檔案變得很大；畫面要讀說明就得依賴判斷程式 | 不採用 |
| B. causes／action 複製到每筆 finding | 匯出的 Snapshot 自帶說明 | Snapshot 變大且重複；改一個字就改變 Snapshot，要升版（見 [ADR-005](005-版本升級規則.md)） | 不採用 |
| C. 目錄與判斷分開，畫面經由單一函式讀取 | 單一來源；文字修改不影響 Snapshot；有測試檢查與文件一致 | 新增規則要改目錄、判斷與文件三處 | **採用** |
| D. 說明只寫在文件，畫面讀取 Markdown | 文件就是來源 | `file://` 開啟時不能讀取其他檔案；文件格式變成程式的契約 | 不採用 |

## 後果

### 變容易的

- 修改常見原因或處理方式不需要升版，已儲存的基準也會顯示新的文字。
- 所有畫面與匯出顯示同一份文字。

### 變困難的

- 新增規則要同時改 `catalog.js`、`checks.js` 與 `docs/基準檢查規則.md`，漏改會被 `tests/docs.js` 擋下。
- 舊基準顯示的是目前版本的說明，不是建立當時的說明。

### 之後要回頭看的

- 檢查參數的預設值、型別與範圍也打算宣告在 `CATALOG`（見 [ADR-009](009-檢查參數的設定位置.md)）。
- 修正 patch 的說明與風險（`src/remediate/patch.js` 的 `DISABLE`）是修正專屬的文字，和規則的處理方式不同層，所以不放在 `CATALOG`。但畫面 `src/view/remediation.js` 的 `DISABLE_FIX` 和它有一份重複的說明，要隨畫面改用核心 patch 一起移除（見 [ADR-001](001-工具維持唯讀.md)）。

## 待辦

- frontend：移除 `DISABLE_FIX` 的重複說明（併入 ADR-001 的待辦）。
