# ADR-007：GitHub Pages 只發布畫面需要的檔案

- **狀態**：已接受
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

`main` 分支會部署到 GitHub Pages，讓使用者不必下載就能使用。repo 中有很多不屬於畫面的檔案：測試、文件、收集器、去識別化工具、agent 定義、測試資料（含去識別化的真實設備輸出）。

本專案沒有 build 步驟（零相依、`file://` 直接開啟），所以不能靠打包工具決定要發布哪些檔案。

## 決策

- [.github/workflows/deploy-pages.yml](../../.github/workflows/deploy-pages.yml) 先跑 `npm test`，通過後才部署。
- 只複製 git 追蹤的 `index.html`、`assets/`、`src/`、`profiles/`、`samples/`、`vendor/`；`tests/`、`docs/`、`tools/`、`.claude/` 等不上站。
- **部署前檢查檔案是否都存在**：`index.html` 中每個 `src="…"`、`href="…"` 引用的本機檔案，以及 `src/view/graph/elk-layout.js` 的 `ENGINE_SRC`（動態載入的 ELK），都必須在網站目錄裡，缺少任何一個就停止部署。找不到 `ENGINE_SRC` 也停止部署。
- 上線後在真實瀏覽器確認 ELK 能載入、不該發布的路徑是 404（[發布前檢查表 §10](../發布前檢查表.md#10-github-pages-上線後)）。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 發布整個 repo | 最簡單 | 測試資料、工具與文件都公開在網站上；網站內容和畫面無關 | 不採用 |
| B. 加入 build 步驟（bundler）產生網站 | 只發布實際用到的程式 | 破壞零相依；網站和 `file://` 開啟的版本不同 | 不採用 |
| C. 列出畫面需要的目錄，部署前檢查引用都存在 | 不需要 build；網站和本機開啟的是同一批檔案；漏複製會在部署前被擋下 | 新增頂層目錄時要改 workflow | **採用** |

## 後果

### 變容易的

- 網站與本機以 `file://` 開啟的是同一批檔案。
- 漏掉檔案時部署失敗，不會發布一個打不開的網站。
- 新增的核心檔案放在 `src/` 下就會發布（例如 `src/remediate/`、`src/ledger/`），不必改 workflow。

### 變困難的

- 畫面需要新的頂層目錄時，要記得改 workflow 的目錄清單。
- 檢查只涵蓋 `index.html` 的 `src`／`href` 屬性與 `ENGINE_SRC`。之後若有其他執行期才載入的檔案，要另外加進檢查。

### 之後要回頭看的

- **站點／分群層級的拓樸檢視**：分層版面（ELK）超過 `App.ELK_MAX`（1500 台網路設備）就不執行，改用內建版面。更大的網路需要先依站點或分群收合的檢視。這會影響要發布的畫面資產（例如是否還需要整包 ELK），屆時一併檢視本決策。

## 待辦

- 無。
