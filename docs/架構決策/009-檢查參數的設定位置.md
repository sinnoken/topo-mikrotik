# ADR-009：檢查參數的設定位置

- **狀態**：提議
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

有些檢查與推論用固定的門檻或比對規則，不同網路的合理值不一樣：

- A04「單一埠學到過多 MAC」：`src/check/checks.js` 的 `MANY_MACS = 5`，超過 5 個外部 MAC 才列出。
- 防火牆的 WAN／LAN 分類：`src/model/infer.js` 的 `WAN_LIST`、`LAN_LIST` 正規式，決定哪些 interface list 算 WAN、LAN（[設計說明 §5.3](../設計說明.md#53-關鍵推論)）。這是推論，F03–F08 都依賴它。

處理紀錄的規則品質統計（[ADR-002](002-處理紀錄放在基準之外.md) 的 `ruleStats`）會指出誤報率高的規則，接下來就需要能調整參數。參數會改變 finding，所以必須和基準一起被記錄，才能保持可重現與可比對。

`S.build` 目前的選項只有 `profile`、`expectedData`、`now`（`src/pipeline.js`）。

## 決策（建議）

建議採用選項 **B**：

- 參數宣告在 `CATALOG`（見 [ADR-006](006-規則目錄與判斷分開.md)）：每個可調參數寫出預設值、型別與範圍，例如 A04 的門檻（整數，下限 1）。WAN／LAN 清單名稱的正規式屬於推論，不屬於單一規則，要另外決定宣告在哪裡（例如 F08 或另一個推論參數表）。
- `S.build(sources, { checkParams })` 接受參數；`ssot-checks/1` 只是把這個選項存成檔案。
- **不合法的值直接報錯**：型別不對、超出範圍、正規式無法編譯、不認得的參數名稱，都丟出錯誤並列出全部問題，不改用預設值（與命名 profile 的 `compile` 相同）。
- **實際使用的參數記錄在 `meta.checkParams`**，包括沒有指定、採用預設值的參數，讓基準可以重現。
- **新舊比對時參數不同要明確提示**：`S.compare.snapshots` 在兩份基準的 `meta.checkParams` 不同時說明哪些參數不同，因為部分差異可能來自參數，不是網路改變。
- 參數只影響推論與檢查，不改寫事實。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 放在命名 profile（`ssot-profile/1`） | 已有檔案格式與載入流程 | 命名 profile 只能 canonicalize 或加註解，不能改變事實與檢查（開發原則第 6 條）；命名與檢查的調整混在同一個檔案 | 不建議 |
| B. 新增 `ssot-checks/1` 設定檔，底層用 build 選項 | 檢查參數有自己的格式，可以保存、分享、放進版本控制；畫面與 CLI 共用 | 多一種長期保存的格式（見 [ADR-010](010-schema版本與轉換規則.md)） | **建議** |
| C. 只用 build 選項 | 最簡單 | 使用者無法保存與分享；畫面與 CLI 各自處理，容易不一致 | 不建議；B 的底層仍是 build 選項 |

## 後果

### 變容易的

- 依規則品質統計調整門檻，不必改程式。
- 從基準就能知道當時用了哪些參數。

### 變困難的

- `meta` 新增欄位，Snapshot 格式要跟著更新；第一次加入時要升版（見 [ADR-005](005-版本升級規則.md)）。
- 正規式參數要防範效能問題（回溯過多），驗證時要限制寫法或長度。

### 之後要回頭看的

- 處理紀錄的冪等性原本只看 `inputHash`（只涵蓋輸入文字），之後改為 `meta.baselineKey`（見 ADR-002 的「修訂」）。檢查參數會改變 finding，所以採用時**要把實際使用的參數加進 baselineKey 的組成**：放在組成陣列的最後（`src/pipeline.js` 的 `baselineKey`），不影響既有欄位的意義。參數不同、輸入相同的兩份基準因此是不同的一輪。

## 待辦

- 使用者：決定採用哪個選項。
- 採用 B 時：data-model 實作 `checkParams`、`meta.checkParams` 與比對提示；frontend 加上載入設定檔；docs 更新設計說明、基準檢查規則（各規則的可調參數）。
