# ADR-016：文件分工：每個主題只有一個說明處

- **狀態**：已接受
- **日期**：2026-10-24
- **決策者**：使用者

## 背景

開發原則要求「一份資訊只寫在一處，其他地方用連結」（[.github/copilot-instructions.md](../../.github/copilot-instructions.md) 的「文件同步對照」）。實際上同一個主題常寫在三、四處，每次修改都要同步好幾份，漏改的地方就和程式走樣。

2026-10-24 整理文件前的檢視結果：

- **檢查結果 CSV 的欄位**：README 的「使用」、設計說明 §14 與發布前檢查表 6.1 各寫一份。這一輪加上 `facet` 欄時，三份都要改。
- **處理紀錄的畫面行為**：README 的「畫面」、設計說明 §14 與 §16、發布前檢查表第 5 節都有描述，詳略不同。
- **分層版面（ELK）**：README 的「中：拓樸圖」、設計說明 §9「規模」與 §12「未知對端」的「版面」、`CLAUDE.md` 的架構段都寫到上限與載入方式。
- **SSH 收集器**：README 的「SSH 批次收集」和收集清單 §0 寫了同樣的指令與選項。
- **開發指令**：README 的「開發」與 `CLAUDE.md` 的「指令」各有一份。
- **還沒做的功能**：設計說明 §11「尚未做」、路線圖與規格書各寫一份。
- **版本紀錄**：放在設計說明的最後，和「現在怎麼運作」混在一起，設計說明因此超過 650 行。
- **設計說明的章節順序**：未知對端（§12）、修正 patch（§15）、處理紀錄（§16）依加入的時間排在後面，讀者看不出上游、下游與檢視層的關係。
- **發布前檢查表**：443 行，一個瀏覽器要跑很久；其中不少項目（狀態轉換、分組、比對結果）已經由冒煙測試檢查，手動重驗只是重複。

## 決策

- **每個主題只有一個說明處**，其他文件只寫一句摘要並連結過去。各份文件回答什麼問題、不寫什麼，以 [docs/README.md](../README.md) 的「分工原則」與「各份文件」為準，本 ADR 不另列一份。
- **這次整理（文件整理第一步）**：
  - 設計說明依「原則 → 上游（輸入、模型與推論、命名規則、檢查）→ 下游（比對、修正 patch、處理紀錄）→ 檢視層架構 → 附錄」重排。檢視層只寫架構，畫面操作暫時集中在其中一節（§12），等使用說明建立後移過去。
  - 版本紀錄移到 [docs/版本紀錄.md](../版本紀錄.md)；「尚未做」併入[路線圖](../路線圖.md)；設計說明各留一行連結。
  - README 只留快速開始、功能一覽與文件連結；開發相關的說明移到 [docs/開發指南.md](../開發指南.md)，收集器的細節只寫在收集清單 §0。
  - 發布前檢查表的主清單只列真實瀏覽器才測得到的項目，並寫出冒煙測試（`tests/ui-smoke.js`）已涵蓋的步驟名稱；原本的詳細步驟移到同一份文件的附錄，不刪除。
- **章節編號改變時保留舊錨點**：在新標題前加 `<a id="舊錨點"></a>`，因為其他文件、ADR 與程式註解可能以舊的 § 編號或錨點引用。文件中的引用一併改成新的節號；程式註解由負責的 agent 之後順手更新，舊錨點讓它們在那之前仍然有效。
- 已有測試檢查一致性的配對（`CATALOG` 與基準檢查規則、兩份 skill、`ownership.json` 與 agent 定義）維持現狀。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 維持現狀，修改時逐份同步 | 不用搬動文件 | 每次修改要找出三、四處；漏改就走樣，這一輪的 `facet` 欄就是例子 | 不採用 |
| B. 每個主題只有一個說明處，其他地方連結 | 修改只改一處；讀者知道該看哪一份 | 要搬動內容、改章節編號，舊連結要保留錨點；讀者有時要多點一次連結 | **採用** |
| C. 由程式產生文件（例如 CSV 欄位、規則表） | 文件不會和程式走樣 | 需要產生器與 build 步驟，只適用於表格類的內容；說明與取捨仍要人寫 | 不採用；已有的一致性測試保留 |

## 後果

### 變容易的

- 改一個行為時只改一份文件，其他文件的連結不用動。
- 設計說明的章節順序對應資料流（上游 → Snapshot → 下游 → 檢視層），新功能有明確的位置。
- 發布前的手動檢查縮短到一個瀏覽器約 15 分鐘，主清單寫明哪些已由冒煙測試涵蓋。

### 變困難的

- 讀者有時要在兩份文件之間跳轉，例如從 README 的功能一覽連到設計說明的畫面操作。
- 設計說明的章節編號改變，舊錨點要一直保留；新增章節時也要避免和舊錨點同名。
- 在使用說明建立之前，設計說明 §12（畫面操作）與 §11（檢視層架構）、檢查表附錄之間仍有部分重複。

### 之後要回頭看的

- **使用說明**：等版面重整第一階段（資料中心＋工作包）完成、畫面的分頁穩定後，新增 `docs/使用說明.md`，把設計說明 §12、檢查表附錄中的畫面操作集中過去（[路線圖「文件整理第二步」](../路線圖.md#文件整理第二步使用說明)）。**已處理**（版面重整 3 之後）：新增[使用說明](../使用說明.md)，依流程步驟 ①–⑤ 排列，是畫面操作唯一的說明處；設計說明 §12 只留一行連結並保留舊錨點。發布前檢查表的附錄是檢查步驟（操作加上預期結果），保留在檢查表，畫面的說明改連到使用說明。
- **連結檢查**：這次用一次性的腳本檢查指向 `docs/` 的相對連結與錨點。是否把它加進 `tests/docs.js`，等使用說明建立、文件結構穩定後再決定。
- **程式註解中的舊節號**：`src/` 的註解只引用 §5.3，這次沒有改變；之後若有程式註解引用改了編號的章節，由負責的 agent 更新。
