# ADR-020：設計說明拆出畫面架構與查詢介面兩份文件

- **狀態**：提議
- **日期**：2026-11-06
- **決策者**：使用者（已授權「文件必要的時候也能重構」；這份拆分方式待確認）

## 背景

[ADR-016](016-文件分工每個主題只有一個說明處.md) 定下「每個主題只有一個說明處」，並把設計說明依「原則 → 上游 → 下游 → 檢視層架構 → 附錄」重排。之後幾輪功能都往設計說明加內容，3.3.0 時已有 1344 行：

- **§11 檢視層架構約 310 行**，加上 §11.6 規模共約 340 行：`App.round`、流程步驟、抽屜、store、拓樸圖的層級、L4、各面板、theme、CSS token、拓樸版面、終端與匯出。讀核心的人要捲過整段，改畫面的人則要在核心的章節之間找。
- **§5.2 的查詢函式約 170 行**：`Q.*` 與 `S.query.*` 的參數與回傳，夾在 Snapshot 的欄位表與推論規則之間。下游（workflow）與畫面（frontend）最常查的就是這一段，但 agent 定義與 CLAUDE.md 只能寫「見設計說明 §5.2」，讀者要自己在 300 行裡找函式。
- 兩段都是同一個主題的唯一說明處，沒有重複；問題是長度與讀者不同，不是內容走樣。

## 決策

- 設計說明 §11 的全文移到新的 [docs/畫面架構.md](../畫面架構.md)，依內容分成 9 節（邊界與本輪的資料、流程步驟與頁首、樣式與儲存、拓樸圖的層級與 L4、各面板的資料來源、theme、拓樸版面、終端的畫法、匯出）。§11.6 規模涵蓋核心、查詢與畫面，留在設計說明，改為第 12 節。
- 設計說明 §5.2 中的查詢函式（IP 與搜尋、VRF 與路由表的查詢、L3 網段圖、L2 視圖、防火牆命中次數與 L4、檢查結果與覆蓋、靜態查詢、選取鍵與唯讀政策）移到新的 [docs/查詢介面.md](../查詢介面.md)。Snapshot 的欄位、推論規則與判斷依據（例如 VRF 的歸屬、下一跳的擁有者）仍在設計說明。
- 搬移時不改寫內容的意義，只改標題、節號與連結；同時把舊說法換成畫面的現行用字（例如「單側觀察」改為「只有一端資料」、「子網」改為「網段」、「未知對端」改為「終端埠」）。
- 設計說明原位置留一段連結，並依 ADR-016 保留舊錨點（`11-檢視層架構`、`111-資料來源與檢視狀態`…`116-規模`、`9-規模`、`12-畫面操作` 等），其他文件的引用改成新位置。
- 各份文件的分工仍以 [docs/README.md](../README.md) 的「分工原則」為準，這次在表中加入兩份新文件；`.github/copilot-instructions.md` 的「文件同步對照」與 docs agent 的對照表同步更新。
- 兩份新文件在 `docs/` 底下，所有權沿用 `ownership.json` 的 `docs/`（歸 docs agent）；查詢函式的實作仍歸 data-model，新增函式時由 data-model 在報告的「文件影響」中列出。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 維持一份設計說明，只加目錄 | 不搬動內容，連結不變 | 長度不變，下游與畫面的讀者仍要捲過核心的章節 | 不採用 |
| B. 拆出畫面架構與查詢介面兩份 | 依讀者分開：核心、查詢介面、畫面各一份；每份 150–900 行 | 要改連結、保留舊錨點；同一個功能（例如 VRF）的欄位與查詢分在兩份文件 | **採用（提議）** |
| C. 依功能拆成多份（VRF、L4、處理紀錄、工作包…） | 每份很短 | 跨功能的模型與查詢分散，「每個主題只有一個說明處」的主題界線變得不清楚；連結更多 | 不採用 |

## 後果

### 變容易的

- 改畫面的人只讀畫面架構與使用說明；改下游或畫面要找查詢函式時，直接看查詢介面。
- 設計說明回到核心的資料流（輸入 → 模型與推論 → 檢查 → 下游），約 900 行。
- agent 定義與 CLAUDE.md 可以直接指向 `docs/查詢介面.md`，不必寫「§5.2 的某一段」。

### 變困難的

- VRF、L4 這類功能的說明分在三份文件：規則在設計說明，函式在查詢介面，畫面在畫面架構，讀者要多點一次連結。
- 設計說明要多保留一批舊錨點；新增章節時要避開它們。

### 之後要回頭看的

- 連結檢查：這次仍以一次性的腳本檢查全 repo 的 Markdown 相對連結與錨點（ADR-016 的「之後要回頭看的」）。文件結構穩定後，再決定是否加進 `tests/docs.js`。
- 版本紀錄與已接受的 ADR 中的歷史敘述仍寫「設計說明 §11」等舊節號，連結靠舊錨點指到原位置的連結段落，不改寫。

## 待辦

- 使用者：確認這份拆分方式（決定後把狀態改為「已接受」或「已否決」）。
- data-model：之後新增或修改查詢函式時，在報告的「文件影響」寫出要改查詢介面的哪一節。
- frontend：「文件影響」改寫成畫面架構的節號。
