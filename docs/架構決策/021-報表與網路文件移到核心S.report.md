# ADR-021：報表與網路文件移到核心（S.report），畫面與 CLI 共用

- **狀態**：已接受
- **日期**：2026-11-06
- **決策者**：使用者（已實作並合併：0af6a26 報表、3523bcb 網路文件）

> 這份是**補記**：決定在實作時就已做出，當時沒有寫 ADR。這裡記錄既成的決定與理由，不改變程式。

## 背景

- 檢查結果的 CSV 與 Markdown 報表原本寫在畫面的 `src/view/export.js`。排程 CLI（`tools/baseline.js`）也要輸出同樣的報表；如果在 CLI 另寫一份，兩份的欄位、跳脫、排序與用語（嚴重度、處理狀態、「與多數不同」）一定會慢慢走樣。
- `src/view` 是畫面層，依賴 DOM，CLI 在 Node 中只載入核心檔案（`tools/core-files.js`，經 `tests/load.js`），用不到畫面的程式。
- 之後加入的網路文件（站點說明書：設備清單、IP 規劃、VLAN 表、埠表、未結案事項）也有同樣的需求：畫面資料中心的下載與 CLI 的 `sitedoc.md`／`sitedoc.csv` 要逐字相同。
- 核心已有上下游的單向依賴（[CLAUDE.md](../../CLAUDE.md) 的「單向依賴」、[ADR-013](013-新增workflow-agent依上下游分工.md)）：下游只透過 `SSOT.query(snapshot)` 讀基準、不改寫，上游不呼叫下游。

## 決策

- **報表的文字只在核心產生一次**：新增 `src/report/`，屬於核心的下游模組（與 `compare/`、`remediate/`、`ledger/`、`workpack/` 同一層），列在 [tools/core-files.js](../../tools/core-files.js)，載入在 `S.ledger` 之後。
  - [src/report/report.js](../../src/report/report.js)：檢查結果的 CSV 與 Markdown（`S.report.findingsCsv`、`findingsMarkdown`），以及報表用語的單一來源（`SEV_TEXT`、`STATUS_TEXT`、`DEVIATION_LABEL`、`NO_MAJORITY`）。
  - [src/report/sitedoc.js](../../src/report/sitedoc.js)：網路文件（`S.report.siteDocTables`、`siteDocMarkdown`、`siteDocCsv`），加在 `S.report` 上。
  - 函式與參數見[設計說明第 3 節](../設計說明.md#3-模組)。
- **只透過查詢介面讀基準**：`S.report` 只用 Q 與 `S.query.rule`／`S.query.rules`，處理狀態用 `S.ledger.isPending`；處理紀錄是使用者的資料，由呼叫端以 `opts.ledgerOf` 傳入。不碰 DOM、不改寫基準；上游與其他下游不呼叫 `S.report`。由 `tests/workflow/report.js` 的單向依賴測試檢查。
- **畫面與 CLI 都呼叫同一份**：畫面的匯出（`src/view/export.js`）與處理建議、狀態文字（`src/view/remediation.js`）直接引用 `S.report` 的成員，不另寫一份；CLI 的 `findings.csv`／`findings.md`／`sitedoc.md`／`sitedoc.csv` 也由它產生。
- **畫面的邊界允許 `S.report`**：`tests/ui/boundary.js` 的 `VIEW_S_ALLOW` 加入 `report`（0af6a26；[ADR-018](018-畫面只透過Q與S.query讀資料.md) 的允許清單，見該 ADR 的「修訂」）。
- **歸 workflow agent**：`src/report/` 列在 [ownership.json](../../.claude/agents/ownership.json) 的 workflow，測試在 `tests/workflow/report.js`、`tests/workflow/sitedoc.js`，預期輸出在 `tests/workflow/fixtures/report/`、`tests/workflow/fixtures/sitedoc/`。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 報表留在畫面，CLI 另寫一份 | 不必搬程式 | 兩份文字一定會走樣；CLI 的輸出沒有和畫面比對的依據 | 不採用 |
| B. CLI 載入畫面的 `src/view/export.js` | 只有一份 | CLI 要模擬 DOM 或拆開畫面檔；畫面層變成 CLI 的依賴，違反「核心不碰畫面」的方向 | 不採用 |
| C. 移到核心下游 `src/report/`，畫面與 CLI 都呼叫它 | 一份文字；沿用既有的下游邊界與測試方式；可用固定情境的預期輸出逐字檢查 | 多一個核心目錄，畫面邊界清單多一個成員；報表用語改由核心提供，畫面同名的常數要引用它 | **採用** |

## 後果

### 變容易的

- 畫面的匯出與 CLI 的報表逐字相同，改一處兩邊一起變；預期輸出（`tests/workflow/fixtures/`）可以直接當規格檢查。
- 報表用語（嚴重度、處理狀態）只有一份，畫面與報表的說法一致。
- 之後新增其他報表時，位置與邊界已經確定：放在 `src/report/`，只讀 Q。

### 變困難的

- 報表的變更歸 workflow，畫面只負責按鈕與下載；同時改報表內容與畫面時要依「workflow → frontend → docs」的順序。
- 報表依賴查詢介面，報表需要新的資料時要先由 data-model 新增查詢函式。

### 之後要回頭看的

- `tools/patch.js`（修正 patch 的 CLI）仍在規劃中；若它也要輸出報表類的文字，沿用這個做法放進核心下游，不在 CLI 另寫。
- 附註（2026-11-07，3.9.0）：主管摘要 `S.report.managerSummary`（ba65ace）在呼叫時另用 `S.remediate.levelOf`（處理方式的等級：要先選擇的 `choice`、可直接產生指令的 `auto`）與 `Q.exposureSummary`，不另寫一份等級或計數規則；沒有用 `S.compare`，也沒有用 `S.remediate.plan`。`S.remediate` 也是下游、載入在 `S.report` 之前，所以這是下游讀下游，單向依賴不變（上游仍不呼叫下游）。上方決策中「`S.report` 只用 Q 與 `S.query.rule`／`S.query.rules`，處理狀態用 `S.ledger.isPending`」的列舉因此不完整；之後若下游之間的呼叫再增加，再決定是否另開 ADR 規定下游之間的依賴方向。
