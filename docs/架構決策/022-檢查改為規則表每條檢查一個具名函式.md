# ADR-022：檢查改為規則表，每條檢查一個具名函式

- **狀態**：已接受
- **日期**：2026-11-06
- **決策者**：使用者

## 背景

[src/check/checks.js](../../src/check/checks.js) 的 `run(M, ctx)` 原本是一個約 330 行的閉包，從 I01 到 L01 依序寫在裡面。跨設備一致性（V06、V07、A06–A12、R06、L02）、防火牆（F01–F08）、命中次數（F09）和管理面（F10–F14）各是一個函式，由 `run` 在中途呼叫。共用的輔助（設備名稱、鏈路排序、代表證據、VLAN 區塊、直連網段、MAC 來源）散在閉包各處，在哪裡第一次用到，就定義在哪裡。

這樣的結構有幾個問題：

- 看不出某個 id 由哪一段負責。要找 R02，得在 C01、R05 和一致性檢查之間翻找；新增檢查時也不知道該插在哪裡。
- 共用的前置計算和只有一條檢查用到的索引混在一起，看不出哪些是共用的；改一條檢查時，容易動到別條。
- 沒有辦法檢查「每個 `CATALOG` id 都有實作，也沒有實作 `CATALOG` 沒有的 id」。漏了實作，只有在範例資料剛好沒產生那個 finding 時才會被發現。
- 之後還要加 F 類和 L 類的檢查，閉包會繼續變長。

[ADR-006](006-規則目錄與判斷分開.md) 已經把規則目錄（`CATALOG`）和判斷分開；這份 ADR 決定的是判斷這一側的結構。

## 決策

- `checks.js` 的 `RULES` 是規則表。每一筆是 `{ ids, name, fn }`，`fn(X, add)` 是具名函式，只產生 `ids` 中的 finding。表依各筆第一個 id 在 `CATALOG` 中的順序排列。
- **每個 `CATALOG` id 恰好屬於一筆**：
  - 載入 `checks.js` 時由 `verifyRules` 檢查。漏列、重複、`CATALOG` 沒有的 id、順序不對，都直接丟錯。
  - 執行時，`run` 傳給 `fn` 的 `add` 會擋下不屬於這一筆的 id。
  - [tests/core/checks-table.js](../../tests/core/checks-table.js) 另外檢查同樣的條件，也檢查函式名稱不重複、每一筆都不可改動，並確認範例資料中每一筆規則都有產生 finding。
- **一筆一條檢查**。只有共用前置計算、或彼此有排除關係的檢查才合成一筆：
  - R01／R03／R04：共用同一次下一跳解析，每個下一跳只歸入其中一種。
  - V06／V07、A06／A07、A10／A11：各組共用同一份屬性、網段或設定清單。
  - F01–F08：共用同一份規則清單與 WAN 路徑模擬；F05、F06 已列的規則，F03 不再列。
  - F10–F14：共用同一份管理面設定與 WAN 可達性判斷。
- **共用前置計算集中在 `prep(M, ctx)`**，每次 `run` 只建立一次，傳給每個 `fn`（即 `X`）。內容包括：
  - 設備與介面名稱、證據排序。
  - 排序後的鏈路與代表證據。
  - 區塊與設備的對應、VLAN 區塊分組、PVID。
  - 各設備的直連網段、MAC 來源。
  - 跨設備一致性共用的分組與多數決（`consistencyKit`，放在 `X.cc`）。

  只有一條檢查用到的索引，留在那條檢查的函式裡。
- **輸出不因此改變**：
  - finding 的順序只由 `run` 最後的排序決定。同一個 id 的 finding 在各自的函式內依原本的順序產生，所以規則表的順序不影響結果。
  - 重構前後比對了 10 份輸入的 Snapshot（範例資料、1000 台的壓力資料與 `tests/fixtures`；見提交 a86e2d6），去掉 `meta.createdAt`、`meta.timing` 後逐字相同，所以不升版（[ADR-005](005-版本升級規則.md)）。
- `S.check` 新增 `RULES`，給測試和文件對照。表中每一筆與它的 `ids` 都已凍結，不可改動。其他成員（`run`、`coverage`、`hopOwner`、`resolveNextHop` 等）不變。

## 考慮過的選項

| 選項 | 優點 | 缺點 | 結論 |
|---|---|---|---|
| A. 維持一個大閉包，只加段落註解 | 不用改程式 | 上述問題都還在；無法檢查 id 與實作的對應 | 不採用 |
| B. 每個 id 一個檔案（`src/check/rules/*.js`） | 檔案小，衝突少 | 核心檔案從 2 個變成約 35 個，`tools/core-files.js` 和 `index.html` 的載入順序都要同步改；共用前置計算還要另外放一個檔案 | 不採用；同一個檔案內的規則表已經夠清楚 |
| C. 把判斷寫在 `CATALOG` 裡（`CATALOG[id].check = fn`） | 目錄與判斷一一對應 | 違反 [ADR-006](006-規則目錄與判斷分開.md)：目錄要依賴判斷程式，畫面讀目錄時也會帶進判斷 | 不採用 |
| D. 每個 id 一定一個函式，不合併 | 對應最單純 | R01／R03／R04 要解析三次下一跳，F01–F08 要多次模擬 WAN 路徑，1000 台時會變慢；F03 還要知道 F05、F06 的結果 | 不採用 |
| E. 同一個檔案內的規則表，共用前置計算的才合併，載入時檢查對應 | 對應清楚，可以自動檢查；效能不變；載入順序不變 | 合成一筆的那幾個函式仍然比較長 | **採用** |

## 後果

### 變容易的

- 找某個 id 的判斷：看 `RULES` 就知道是哪個函式。
- 新增檢查：在 `CATALOG` 加一筆後，如果忘了在 `RULES` 加對應的函式，載入時就會丟錯，不必等範例資料剛好觸發。
- 每條檢查的函式只讀 `X` 和自己的索引，改它不會動到其他檢查的前置計算。

### 變困難的

- 新的共用前置計算要放進 `prep`（或 `consistencyKit`），不能就地定義；放進去之前，要先確認真的有兩條以上的檢查共用。
- 合成一筆的檢查（F01–F08、F10–F14）仍然是一個較長的函式。要再拆，得先把彼此的排除關係（例如 F05、F06 已列的規則 F03 不再列）改成明確的前置計算。

### 之後要回頭看的

- 有了規則表，[ADR-009](009-檢查參數的設定位置.md) 的檢查參數（例如 A04 的門檻）可以依規則傳入，不必再找散在各處的常數。
- 如果之後要讓使用者停用某些檢查，可以在 `run` 依規則表略過；但要先決定被略過的檢查在 `Q.ruleStatus` 怎麼呈現。
