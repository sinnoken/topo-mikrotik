# 查詢介面（SSOT.query）

畫面與下游模組（比對、修正 patch、處理紀錄、工作包、報表）只透過查詢介面讀基準：`Q = SSOT.query(snapshot)` 的函式，以及不需要 Snapshot 的靜態函式 `S.query.*`（[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）。實作在 `src/query/`（歸 data-model）。這份文件列出各函式的參數與回傳；Snapshot 的欄位、推論規則與判斷依據寫在[設計說明 §5](設計說明.md#5-模型)，畫面怎麼使用這些函式見[畫面架構](畫面架構.md)。

本文件原本是設計說明 §5.2 中的查詢段落，內容沒有改變（[ADR-020](架構決策/020-設計說明拆出畫面架構與查詢介面.md)）。需要新的查詢函式時，由 data-model 加入並更新這裡。

## 1. IP 位址與搜尋

vrf 參數的共通規則：省略表示不指定；給了就必須是 `Q.vrfs()` 中的名稱，否則丟出 TypeError，不猜。位址與前綴的欄位見[設計說明 §5.2「IP 位址與前綴」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)。

- `Q.ipOwner(ip, vrf)`：擁有這個 IP 的介面鍵（管理 IP 為「設備|」），沒有時為 null。省略 vrf 時 `ip` 可以直接是位址鍵（`10.0.0.1`、`10.0.0.1@cust-a`），沒有 `@` 就是 main。
- `Q.findIp(ip, vrf)`：一個 IP 在基準中的資料 `{ ip, vrf, vrfs, owner, owners: [{ vrf, ep }], arps, macs, subnets, locations }`。省略 vrf 時列出所有 VRF 的結果，`vrfs` 是有結果的 VRF，`owner` 是第一個擁有者（main 優先，再依 VRF 名稱）；`ip` 無效時為 null。
- `Q.ipsOf(ep)`
- `Q.addressesOf(ep)`
- `Q.subnets()`：所有設備自有的直連網段 `{ ep, dev, net, len, ip, vrf, prefix（網段鍵） }`；`Q.subnetsOf(dev, vrf)` 是其中一台設備的（給 vrf 時只取那個 VRF）。
- `Q.prefixes()`
- `Q.ipEntries()`／`Q.prefixEntries()`：每個 VRF 中不重複的 IP、每個 VRF 的每個網段各一列，多了 `key`（位址鍵或網段鍵）與 `vrf`；網段內的 IP 數只算同一個 VRF 的。
- `Q.search(text, limit)`：頁首的搜尋，回傳 `[{ type, key, label, … }]`，最多 `limit`（預設 20）筆。`type` 是 `mac`、`ip`、`subnet`、`vlan`、`device` 或 `interface`。
  - `device` 的 `label` 是原名（同 `Q.devName`）；畫面顯示時改用 `Q.devLabel(key)`。
- `Q.devName(key)`：設備名稱原值（`label` 或 `name`；找不到設備時回傳鍵），用於鍵比對、排序與匯出（CSV／Markdown 的設備欄）。
- `Q.devLabel(key)`：畫面給人看的設備名稱（詳情標題、清單的設備欄、修正計畫的「依設備」選單、搜尋結果、拓樸圖節點的提示）。通常與 `Q.devName` 相同；沒有收集（`collected: false`）且名稱是 IPv4 位址（`S.ip.isIp`）的設備，加上得知它的鄰居協定，例如 `172.31.255.2（OSPF 鄰居）`。協定是事實：碰到這台設備的 `links[].protocols`，加上以它為 `peerDev` 的 `ospfAdjacencies`（記為 OSPF），依 LLDP、CDP、MNDP、OSPF 的順序以「／」列出；都沒有時寫「（鄰居）」。不改 Snapshot 欄位。寫法只在 `S.check.discoveryLabel` 定義，C01 的訊息也用它（放在 check：訊息在 check 產生，query 可依賴 check，反過來不行）。
  - 只回傳結構化欄位，不回傳顯示用的副標；副標由畫面的 `A.searchSub`（`src/view/app-toolbar.js`）以 `V.TERMS`、`V.KIND`、`V.IFC_TYPE`、`V.ifcState` 組成。各類型多出的欄位以 `query.js` 中 `search` 的註解為準（例如 `ip` 的 `owner`、`macs`、`heard`、`vrfs`，`vlan` 的 `devices`、`vlanDomains`，`interface` 的 `match`、`ifType`、`status`）。
  - VLAN 接受純數字（不以 0 開頭，避免 MAC 片段被當成 VLAN）或「vlan 30」「VLAN30」，範圍 1–4094。
  - 完整的 MAC、IP 與 VLAN ID 各一筆；IP 前綴（例如 `10.1.`、`10.1`）先列以它開頭的直連網段（`subnet`，`key` 是含 VRF 的網段鍵，同 `Q.subnetGraph` 的網段 id），再列 IP；MAC 前綴（任一分隔符，或不寫分隔符但含 `a-f`）列出以它開頭的 MAC。只有數字時不當成 MAC 前綴，留給 VLAN 與 IP。
  - `ip` 的 `key` 是不含 VRF 的位址（不分 VRF），同一個位址在多個 VRF 合成一筆，`vrfs` 列出所在的 VRF（副標在 main 時不寫）。
  - 設備依名稱；介面先比名稱（`match: 'name'`），再比描述（`match: 'desc'`）。
- `Q.subnetGraph(opts)`：L3 網段圖（M1），見[第 3 節](#3-l3-網段圖)。

## 2. VRF 與路由表

- `Q.vrfs()`：基準中出現的 VRF 名稱（設定、位址、ARP 與路由），main 在最前、其餘依名稱；只用 main 的網路是 `['main']`。
- `Q.vrfsOf(dev)`：這台設備的 `vrfs` 設定，依設定順序。
- `Q.routesOf(dev, vrf)`：這台設備的路由；給 vrf 時只取那個 VRF 的路由表（只用於策略路由的路由表 `vrf` 為 null，不會被選到）。`Q.routesInTable(dev, table)`：某張路由表的路由，不論是不是 VRF。
- `Q.routingTables()`、`Q.routingRules()`：Snapshot 的 `routingTables`、`routingRules`。
- `Q.policyOf(dev)`：`{ tables, rules（啟用中的 rule，依順序）, marks（啟用中的 mark-routing）, policyRules（沒寫時是預設順序）, custom（改過 policy-rules）, any（有任何會改變查表的設定） }`，凍結。
- `Q.hopOwner(dev, ip, vrf)`：見[設計說明 §5.2「VRF 與路由表」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)的「下一跳的擁有者」。

## 3. L3 網段圖

`Q.subnetGraph({ nodes, hearsay, routes })` → `{ subnets, nodes, edges, routes, omitted }`。網段節點、設備或介面節點，以及「在這個網段有位址」的邊。

- **VRF 是容器**（[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）：每個網段、節點、邊與路由都有 `vrf`（main 也寫出），不同 VRF 的同一個網段是不同的網段節點。id 用 `K.inVrf`：main 不加後綴（和加入 VRF 之前相同），其他 VRF 加 `@<VRF>`。
  - 設備模式時，一台設備在每個有位址的 VRF 各一個節點，id 是「設備鍵」或「設備鍵@VRF」；介面模式時介面只屬於一個 VRF，id 就是介面鍵。
  - 推論的邊（鄰居宣告的位址、管理 IP）只接到同一個 VRF 的已知網段；管理 IP 視為 main。重疊網段（`overlaps`）、DHCP 網路的閘道也只在同一個 VRF 內對應。

- **參數**：`nodes` 為 `'device'`（預設，每台設備一個節點）或 `'interface'`（每個介面一個節點；管理 IP 的節點 id 是「設備鍵|」）。`hearsay` 預設 true，加入推論的邊：鄰居宣告的位址（`basis: 'neighbor'`）與沒有列在介面位址的管理 IP（`basis: 'mgmt'`），都只以最長相符接到已知網段，不產生新網段。`routes` 預設 false，為 true 時加入靜態路由（含黑洞）與預設路由；目的網段不是已知網段時，新增 `basis: 'route'` 的網段節點。
- `subnets[]`：`{ id, prefix, net, len, family, vrf, basis（connected／route）, vlan, vlans, eps, devices, routers, gateways, overlaps, duplicateIps }`。`routers` 是接在這裡的路由設備，`gateways` 是 DHCP 網路設定的閘道（`{ ip, dev, src }`）。
  - `overlaps`：和這個網段互相包含的其他網段 id（例如 `10.0.0.0/16` 與 `10.0.1.0/24`）。`routes` 為 true 時，路由新增的網段（例如彙總路由）也參與比對；預設路由 /0 包含所有網段，不列。
  - `duplicateIps`：同一個 IP 設在這個網段的多個介面上（VRRP 位址除外，鄰居宣告的不算）。
- `nodes[]`：`{ id, type, dev, ep, name, label, kind, collected, vrf, subnets, router, routerBasis, multihomed, hostAddresses }`。`hostAddresses` 是 /32 的自有位址（loopback 等，不形成網段）。
  - **路由設備是推論**：接到 2 個以上的網段，而且有路由表資料（`routerBasis: 'routes'`），或設備類型是路由器或防火牆（`'kind'`）。只是多張網卡的主機不算（`multihomed` 為 true、`router` 為 false）。interface 節點的 `router` 是所屬設備的值。
- `edges[]`：`{ id, subnet, node, dev, eps, addresses: [{ address, ip, ep, role, hearsay, seenBy, src }], basis（address／neighbor／mgmt）, inferred, vrf }`。`inferred` 為 `basis` 不是 `address`。
  - **管理 IP 的邊以 `seenBy` 追溯**：`mgmtIp` 在 Snapshot 沒有來源行，所以 `src` 是設備的 `src`（只由鄰居看到的設備為空），`seenBy` 列出看到這台設備的已收集設備。
- `routes[]`：`{ id, dev, node（設備模式時是這台設備在這個 VRF 的節點 id，介面模式為 null）, subnet（目的網段 id，同一個 VRF）, prefix, len, default, proto, distance, blackhole, nh（含 `vrf`、`vrfBasis`）, via（下一跳所在、這台設備在閘道的 VRF 直連的網段 id）, routingTable, vrf, src }`。interface 模式也接在設備上。
  - 只畫 VRF 的路由表（`routes[].vrf` 不是 null）。只用於策略路由的路由表不屬於任何 VRF 容器，不畫，筆數在 `omitted.policyRoutes`。
- **已知的限制**：同一個 VRF 中的同一個網段即使在不同站點，也會併成同一個網段節點。
- **只有 IPv4**：核心沒有收集 IPv6 的 prefix 與路由，所以網段與路由都是 IPv4。

## 4. L2 視圖

M1 新增。

- `Q.vlanIds()`：基準中出現的所有 VLAN ID（VLAN 定義與介面的 PVID／untagged／tagged），由小到大。VLAN 篩選的選項用。
- `Q.vlanSummary()`：VLAN 的三種數法（凍結）`{ ids, domains, definitions }`。`ids` 是 VLAN 定義中相異的 VLAN ID 數（同 `Q.inventory().counts.vlanIds`）；`domains` 是各 ID 不相連區塊的合計（同 `Q.vlan(id).domains`，推論）；`definitions` 是各設備的 VLAN 定義筆數（同 `meta.stats.vlans`）。畫面不自己重算，避免三種數字混用。
- `Q.vlanCarriers(vid, domain)`：承載這個 VLAN 的鏈路，VLAN 篩選時高亮用；給 `domain`（`Q.vlan` 的區塊鍵，見 [設計說明 §5.3「VLAN 區塊」](設計說明.md#53-關鍵推論)）時只含那一塊。回傳 `{ id, domain, devices, links, counts: { carry, partial, oneSide, inferred }, eps }`。
  - `links[]`：`{ key, kind（link／inferred）, status, inferred, hearsay, reason, a, b, src }`，依 status（下表的順序）再依鍵排序。`kind` 表示用 `Q.getLink` 還是 `Q.getInferredLink` 取回原始實體；`inferred` 為 true 表示這一列是推論；`hearsay` 表示鏈路本身只有只有一端資料。判斷依據和 `Q.vlan` 相同：兩端的有效 VLAN（介面本身加上所屬聚合的 PVID／untagged／tagged）。

    | status | 意義 | 事實或推論 |
    |---|---|---|
    | `carry` | 兩端都帶這個 VLAN | 事實 |
    | `partial` | 兩端都有 VLAN 資料，只有一端帶（兩端不一致，V01）；只含 `vlansDiff` 中的 VLAN，例如單臂路由的實體埠對上 PVID 1 不算 | 事實 |
    | `oneSide` | 只有一端帶，另一端無從得知；`reason` 是 `unfiltered`（任一端在未開 vlan-filtering 的 bridge 上，VLAN 原樣轉送；就是 `Q.vlan(id).transparent`，參與區塊劃分；未過濾的 bridge 串接時，中間那條鏈路兩端的 `has` 都是 null）、`peer-uncollected`（對端沒有收集）、`peer-no-vlan-data`（對端沒有 VLAN 設定資料）或 `hearsay`（鏈路是只有一端資料）。後三種不參與 `Q.vlan` 的區塊劃分 | 推論 |
    | `inferred` | 推論鏈路，已收集的各端都帶這個 VLAN（同 `Q.vlan(id).inferred`） | 推論 |

  - `a`／`b`：`{ ep, dev, port, has, via, mode, collected, vlanData }`。`has` 為 true／false 是事實（這台設備有 VLAN 設定資料）；為 null 表示無從得知（沒有收集、沒有 VLAN 資料，或這一端是 `vlanUnfiltered`）。`via` 是帶這個 VLAN 的位置：`self`（介面本身）、`lag`（所屬聚合介面）或 `member`（推論鏈路記在聚合上，由成員埠帶）；`mode` 是 `tagged`、`untagged` 或 `both`。
  - `eps`：帶這個 VLAN 的鏈路端點（`has` 為 true），排序後的 ep 鍵。
  - 只算介面鄰接（LLDP／CDP）；MNDP 只證明同一廣播網域，不列入。
  - VLAN 子介面讓 parent 以 tagged 承載（停用的不算；parent 是 bridge 時只有 bridge 本身帶），和 V01 相同，所以單臂路由的實體埠也會被高亮。規則與已知的限制見[設計說明 §5.2「介面」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)的「VLAN 子介面讓 parent 承載」「vlan-filtering」與「已知的限制」。
- `Q.portGraph({ lag, ports, inferred, devices })`：埠層級的 L2 圖（給 ELK 的 port），回傳 `{ devices, ports, edges, omitted }`。
  - **參數**：`lag` 為 `'collapse'`（預設，聚合成員併進聚合埠，成員列在 `members`）或 `'expand'`（成員各自是埠，`lag` 指向所屬聚合）；`ports` 為 `'linked'`（預設，只列有邊的埠）或 `'all'`（另列範圍內已收集設備的實體、聚合與無線介面）；`inferred` 預設 true，是否包含推論鏈路；`devices` 是設備鍵的陣列，給了就只取至少一端在其中的邊（另一端的設備也會出現，`focus` 為 false）。
  - `devices[]`：`{ id, label, kind, collected, focus, ports, bridges: [{ ep, name, ports, vlanIfcs }] }`。**bridge 不是埠**，放在 `devices[].bridges`，列出它的埠與掛在它上面的 VLAN 介面。
  - `ports[]`：`{ id（ep 鍵）, dev, name, ifc, unknown, type, rawType, status, enabled, hearsay, lag, members, bridge, mode, pvid, vlans, subIfcs, unknownPeer, macCount, edges }`。**VLAN 子介面不是埠**，列在掛載的埠（或其成員）的 `subIfcs`。推論鏈路未收集端的未知埠，`ifc` 為 null、`unknown` 為 true。
  - `edges[]`：`{ id, a, b（埠 id，a < b）, aDev, bDev, links, inferredLinks, count, evidence, inferred, cls, vlansCommon, src }`。`evidence` 依強弱是 `adjacency`（有雙側的 LLDP／CDP 介面鄰接）、`hearsay`（只有只有一端資料，推論）、`inferred`（只有推論鏈路，推論）；`inferred` 為 `evidence` 不是 `adjacency`。
  - 只算 interface-adjacency 的鏈路。`omitted` 是沒有畫成邊的筆數：`domainOnly`（MNDP 鏈路，只證明同一廣播網域，不當直連）、`sameDevice`（收合後兩端是同一個埠）、`inferred`（`inferred` 為 false 時略過的推論鏈路）。
- **共通規則**（`vlanCarriers`、`portGraph`、`subnetGraph`，以及 `vlanIds`）：第一次呼叫時才計算，依參數快取，同樣的參數第二次呼叫直接回傳同一個物件；回傳的物件是 Q 新建的，深層凍結。`portGraph`、`subnetGraph` 的參數值不認得時丟出 TypeError；`vlanCarriers` 的 vid 轉成數字比對。

## 5. 防火牆命中次數與 L4

M2（2.11.0）新增；判斷規則見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)。

- `Q.firewallStats()`：Snapshot 的 `firewallStats`（事實）；`Q.firewallStatsOf(devKey)`：其中這台設備的表。
- `Q.subnetsOf(devKey, vrf)`：`Q.subnets()` 中屬於這台設備的直連網段，順序相同；給 vrf 時只取那個 VRF 的。凍結的陣列。
- `S.trace(Q, src, dst, { ttl, vrf })`：路由追蹤（推論）。每一跳在它的 VRF 查路由（含策略路由），下一跳寫了 `@<VRF>` 時在那個 VRF 解析閘道，下一台從擁有閘道位址的 VRF 繼續。回傳 `{ ok, src, dst, vrf, start, reached, status, unverified, hops: [{ dev, vrf, via, table, rule, route, proto, ecmp, next }], ends: [{ dev, vrf, status, note, path }], edges }`；`ends[].status` 另有策略路由的 `policy`（查哪一張路由表不明）與 `policy-drop`（rule 丟棄）。
  - 走到未收集的設備（起點、中途或終點，目的不在它的直連網段時）以 `ends[].status` 為 `unverified` 停下：沒有它的路由表，不能判斷是否抵達，不算斷掉。
  - `status` 是整體結果：`reached`（至少一支抵達）、`unverified`（沒有抵達，而且每一支都停在未收集的設備）或 `unreachable`（其他）；`unverified` 是停在未收集設備的設備鍵（去重、依出現順序）。`error` 與 `ends[].note` 等文字中的 VRF 在 main 時省略，與 `K.inVrf` 相同；只用 main 的網路時，trace 與 reach 的文字和 2.11.0 相同（`tests/core/vrf.js`，fixture `tests/fixtures/vrf/trace-2.11-main-only.json`）。
- **vrf 的決定**（`S.trace` 與 `Q.reach` 共用 `S.trace.pickVrf`）：給了就用，不是基準中的 VRF 時丟出 TypeError；沒給時依來源位址：只在一個 VRF（擁有它，或它落在那個 VRF 的直連網段）時用那個 VRF，不在任何 VRF 時是 main，在多個 VRF（位址重疊）時回傳 `{ ok: false, error, vrfs }`，請使用者指定，不猜。
- `Q.reach(src, dst, opts)`：從 src 到 dst 的新連線能不能通（推論）。`opts`：`{ proto（預設 tcp）, port（tcp、udp 必填，1–65535 的整數；沒有埠的協定要省略）, vrf（選用，見上方「vrf 的決定」；有 entry 時是入介面的 VRF，給了不同的 vrf 丟出 TypeError）, entry（選用：封包進入的介面鍵，來源不在任何網段時用）, disabledRules（選用：當作停用的規則鍵，估計停用的影響用） }`。回傳 `{ ok, src, dst, proto, port, vrf, entry, verdict（allow／deny／unknown）, final（NAT 後的 `{ dst, port }`，各路徑不同時為 null）, natApplied, start, reasons, notes, decisive, paths: [{ verdict, hops, end }], assumptions }`；`hops[].vrf` 是封包在那台設備所在的 VRF。`reasons` 只在 unknown 時有值，其他結果的同類說明放在 `notes`。位址不是有效的 IPv4 時回傳 `{ ok: false, error }`，來源在多個 VRF 時另有 `vrfs`；參數不合法時丟出 TypeError。
- `Q.zones(opts)`：每個 IPv4 直連網段的 zone（推論），每個 VRF 分開。`opts`：`{ profile（選用：建立基準時用的命名規則 JSON，核對方式見 §5.3）, sources（選用：要用的來源，`subnet` 一定包含） }`。回傳 `{ zones: [{ id, name, source, inferred, basis, subnets, devices, vrf }], subnets: [{ prefix, key（網段鍵）, net, len, vrf, zone, source, inferred, basis, detail, alternatives, eps }] }`。非 main 的 VRF，zone 的 id 加上 `@<VRF>`（`K.inVrf`），名稱加上「（VRF <VRF 名稱>）」；main 的 id 與名稱和加入 VRF 之前相同。
- `Q.zoneOf(ip, opts)`：IP 所屬的 zone（那個 VRF 最長相符的直連網段）`{ zone, subnet, key, vrf, source, inferred }`；不在任何網段時為 null。VRF 由 `opts.vrf` 指定；沒有指定時依位址決定（同上方「vrf 的決定」），位址在多個 VRF 時丟出 TypeError，請指定 vrf。
- `Q.zoneMatrix(opts)`：zone 矩陣 L0，含所有 VRF 的 zone。`opts` 是 `Q.zones` 的參數，另加 `services`（`[{ proto, port }]`，預設是 `S.query.l4Services()` 加上 dst-nat 規則的目的埠）。回傳 `{ vrf（固定為 null）, vrfs（有 zone 的 VRF）, zones, services, cells: [{ src, dst, diagonal, status（allow／deny／partial／unknown／empty）, counts, services, heterogeneous, rule, rules, ruleCount, reasons }], stats }`。
- `Q.zoneMatrixSteps(opts)`：`Q.zoneMatrix` 的分段計算（generator，用法像 `S.steps`）。參數同 `Q.zoneMatrix`；每一段 yield `{ stage（reps／evaluate／summary）, done, total }`（`total` 是上限，只用來顯示進度），跑完時的回傳值與 `Q.zoneMatrix(opts)` 是同一個物件。分段的方式見 [設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)。
- `Q.zoneCell(srcZone, dstZone, opts)`：矩陣的明細（L1／L2）：一格的摘要，加上 `groups`（目的 × 結果相同的來源代表併成一列，每組有 `dst, srcs, services, status, counts, srcDevices, divergent, divergentServices`）與 `ruleDetails`（牽涉的規則）。`divergent` 表示這一組造成格子異質，`divergentServices` 是造成差異的 service（定義見 §5.3）。L3 是對某個來源代表與目的呼叫 `Q.reach`。zone 不存在時丟出 TypeError。
- `Q.ruleImpact(key, opts)`：規則的影響：`{ rule（含 stats）, shadowed（F01）, duplicate（F02）, findings, cells, total, paths, truncated, ifDisabled }`，`ifDisabled` 是停用這條規則時結果改變的路徑。`opts` 同 `Q.zoneMatrix`，另加 `limit`（列出的路徑數上限，預設 50）。沒有這條規則時為 null。
- 不需要 Snapshot 的靜態查詢：`S.query.l4Services()`（矩陣預設的 service）、`S.query.zoneSources()`（zone 來源與優先順序）、`S.query.reachAssumptions()`（判斷的前提，每次 `Q.reach` 都附在 `assumptions`）、`S.query.reachReasonCodes()`（原因與結束代碼的清單，見 §5.3）。
- 共通規則：第一次呼叫 L4 函式時才建立計算引擎（`src/query/trace.js` 的 `S.reach.engine`）；結果依參數快取在記憶體，回傳的物件深層凍結，不寫進 Snapshot（[ADR-014](架構決策/014-L4-zone矩陣在查詢時計算.md)）。

## 6. 檢查結果與覆蓋

- `Q.findingKey(f)`：finding 的穩定鍵，見[設計說明 第 8 節](設計說明.md#8-比對獨立模組)。
- `Q.findingBaseKey(f)`（也可用 `SSOT.query.findingBaseKey`）：不含 facet 的鍵（id＋實體），也就是 2.9.0 之前的 findingKey；沒有 facet 的 finding 與 `Q.findingKey` 相同。給處理紀錄等轉換舊鍵用。
- `Q.findingDevice(f)`：finding 所屬的設備鍵。取第一個 `device` 實體；沒有時，取第一個能對到設備的介面、鏈路一端、防火牆規則、管理服務或設備自有的 IP。都對不到（例如沒有設備標頭的 I01、只涉及 MAC 或 VLAN 的檢查）時為 null。畫面的分組、匯出與修正 patch 都用它。
- `Q.coverage()`：Snapshot 的 `coverage[]`（每台設備收集了哪些資料、缺漏與收集失敗），沒有時為空陣列。處理紀錄用它判斷能不能判定已修好。
- `Q.coverageOf(devKey)`：該設備的覆蓋列（`coverage()` 的一個元素）；沒有這台設備時為 null。
- `Q.coverageSummary()`：收集完整度的唯一數字來源（凍結）`{ devices, collected, missing, network, networkCollected, hosts }`。
- `Q.coverageGap(row)`：覆蓋列（`Q.coverage()` 的元素）是否「已收集但有缺漏」：已收集，且缺少應收集的資料或有指令收集失敗（只有失敗也算）。這是唯一的判斷：`coverageSummary().missing` 是它的台數，畫面的覆蓋率表（「有缺漏」篩選、排序、標紅）也呼叫它。
  - `devices`、`collected`：全部設備與已收集的台數。
  - `network`、`networkCollected`：應收集的網路設備與其中已收集的台數。範圍和 C01／C02 相同，都用 `S.check.expectsCollection`（已收集的設備，加上未收集但不是主機的設備）；`network − networkCollected` 等於 C01 的筆數。
  - `hosts`：不在收集範圍的主機（只由鄰居或 ARP 得知），`network + hosts = devices`。
  - `missing`：已收集、但缺少必要資料或有收集失敗的台數，等於 C02 的筆數。
- `Q.pendingSummary(isPending)`：「待處理」的唯一數字來源（凍結）`{ error, warn, info, total, handled }`。`isPending(f)` 判斷一筆 finding 是否仍待處理（畫面傳入以 `S.ledger.isPending` 判斷處理紀錄狀態的函式；省略時全部算待處理），不是函式時丟出 TypeError；不認得的嚴重度丟出 RangeError。
  - `error`、`warn`、`info`：各嚴重度仍待處理的筆數。
  - `total`＝`error`＋`warn`：步驟列「研判」、基準狀態卡與「驗證」改善趨勢所說的「待處理」，不含提醒。
  - `handled`：已處理的錯誤與警告筆數；提醒不算進 `total` 與 `handled`。
- `Q.ruleStatus()`：每項檢查的結果 `{ id, severity, cat, title, hint, count, missing, status }`，`status` 是 `found`（有發現）、`pass`（需要的資料有收到且沒有發現）或 `nodata`（需要的資料沒有任何已收集設備提供），`missing` 是缺少的資料組；`hint` 同 `S.query.rule(id).hint`。依檢查代碼排序。
- `Q.findings()`：全部 finding，依 Snapshot 的順序；陣列位置就是 idx。`Q.finding(idx)`：第 idx 筆，不是有效索引時為 null。
- `Q.findingIndexesByKey(key)`：findingKey 等於 key 的 idx，由小到大；findingKey 可能碰撞，所以是陣列，沒有時為空陣列。`Q.findingIndexByKey(key)`：第一筆的 idx（碰撞時取 Snapshot 順序的第一筆），沒有時為 -1。
- `Q.findingsByRule(id)`：某項檢查（例如 `'C01'`）的 finding，依 Snapshot 的順序；沒有時為空陣列。
- `Q.deviationsOf(devKey)`：這台設備被多數決判定與多數不同（列在 `finding.deviation.deviating`，推論）的 finding 索引，依 Snapshot 的順序；沒有時為空陣列。與多數不同的設備不一定是那筆 finding 的實體，所以另建索引，不併入 `Q.findingsFor`。
- `Q.blocksOf(devKey)`：屬於某設備的輸入區塊（`blocks[].devKey`），依輸入順序；沒有時為空陣列。`Q.block(id)`：一個區塊，沒有時為 null。`Q.blockAt(file, line)`：包含 file 第 line 行的區塊（同 `Q.block` 的物件），不在任何區塊內（例如設備標頭、註解行）或沒有這個檔案時為 null。
- `findingIndexesByKey`、`findingsByRule`、`deviationsOf`、`blocksOf` 與 `coverageOf` 的索引，以及 `coverageSummary`、`vlanSummary` 的結果，在第一次呼叫時才建立（1000 台規模下多數畫面用不到）；回傳的陣列凍結。

## 7. 不需要 Snapshot 的靜態查詢

`S.query.*`（[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）：

- `S.query.rule(id)`：一項檢查的目錄資料（凍結）`{ id, severity, cat, title, data?, evidenceLimit?, facet?, causes, action, hint }`；不認得的 id 為 null。`causes`／`action`／`hint` 只經 `S.report.advice` 使用（`src/report/report.js`；畫面是 `V.remediation.advice`，匯出的報表也用它，見[畫面架構 §5](畫面架構.md#5-各面板的資料來源)）。
  - `hint` 是處理提示：`action` 的第一句（到第一個「。」，含句號），沒有 `action` 時為 null。`CATALOG` 不另存一份；[基準檢查](基準檢查.md)每項檢查「處理」的第一句必須和它相同（`tests/docs.js`）。
- `S.query.rules()`：所有檢查（凍結的陣列），依 `CATALOG` 的宣告順序（匯出的附錄依這個順序）。
- `S.query.dataLabel(t)`：資料類別（設備的 `data`、coverage 的 `data`／`missing`、收集失敗的 `dataTypes`）的顯示名稱；不認得時原樣回傳。
- `S.query.adapterLabel(id)`：解析器（`meta.adapters`、`blocks[].adapters` 的 adapter id）的顯示名稱；不認得時原樣回傳。
- `S.query.metaOf(json)`：還沒建立查詢介面的 Snapshot JSON（瀏覽器儲存或使用者匯入的檔案）的 `meta`；不是物件或沒有 `meta` 物件時為 null。用來先判斷 schema／版本是否相容，再決定要 `S.query` 還是重建。
- 檢查目錄是**目前程式**的目錄，不是建立那份基準時的目錄（[ADR-006](架構決策/006-規則目錄與判斷分開.md)），所以放在 `S.query` 而不是 Q。`S.query.findingKey`、`S.query.findingBaseKey` 也在這裡。
- `S.util.fmtVlans(ids)`：VLAN 清單的精簡文字，例如 `[10, 11, 12, 20]` → `"10-12,20"`（輸入要先由小到大排序，例如 `S.util.ifcVlans` 的結果）。核心訊息與畫面共用；`S.check.fmtVlans` 指向同一個函式。

## 8. 選取鍵與唯讀政策

依 [ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)：

- **選取鍵**：同一份基準內，finding 以 idx 指定（`Q.finding(idx)`）。idx 只在同一份 Snapshot 內有效；跨基準（處理紀錄、新舊比對、修正計畫）用 findingKey，再以 `Q.findingIndexByKey`／`findingIndexesByKey` 換回 idx。不直接用 findingKey 當選取鍵，因為它可能碰撞。
- **唯讀**：Snapshot 本身靠約定唯讀，`S.query` 不複製也不凍結它。Q 的衍生索引（上面的凍結陣列）與檢查目錄（`CATALOG`、`DATA_LABEL`、`S.query.rule`／`rules`）凍結，呼叫端改不壞。畫面不改寫基準由冒煙測試以深層凍結的基準確認（[開發指南 §3](開發指南.md#3-測試)）。
