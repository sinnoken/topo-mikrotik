# 查詢介面（SSOT.query）

畫面與下游模組（比對、修正 patch、處理紀錄、工作包、報表）只透過查詢介面讀基準：`Q = SSOT.query(snapshot)` 的函式，以及不需要 Snapshot 的靜態函式 `S.query.*`（[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）。實作在 `src/query/`（歸 data-model）。這份文件列出各函式的參數與回傳；Snapshot 的欄位、推論規則與判斷依據寫在[設計說明 §5](設計說明.md#5-模型)，畫面怎麼使用這些函式見[畫面架構](畫面架構.md)。

本文件原本是設計說明 §5.2 中的查詢段落，內容沒有改變（[ADR-020](架構決策/020-設計說明拆出畫面架構與查詢介面.md)）。需要新的查詢函式時，由 data-model 加入並更新這裡。

## 1. IP 位址與搜尋

vrf 參數的共通規則：省略表示不指定；給了就必須是 `Q.vrfs()` 中的名稱，否則丟出 TypeError，不猜。位址與前綴的欄位見[設計說明 §5.2「IP 位址與前綴」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)。

- `Q.ipOwner(ip, vrf)`：擁有這個 IP 的介面鍵（管理 IP 為「設備|」），沒有時為 null。省略 vrf 時 `ip` 可以直接是位址鍵（`10.0.0.1`、`10.0.0.1@cust-a`），沒有 `@` 就是 main。
- `Q.findIp(ip, vrf)`：一個 IP 在基準中的資料 `{ ip, vrf, vrfs, owner, owners: [{ vrf, ep }], arps, macs, subnets, locations }`。省略 vrf 時列出所有 VRF 的結果，`vrfs` 是有結果的 VRF，`owner` 是第一個擁有者（main 優先，再依 VRF 名稱）；`ip` 無效時為 null。
- `Q.ipsOf(ep)`
- `Q.addressesOf(ep)`
- `Q.subnets()`：所有設備自有的直連網段 `{ ep, dev, net, len, ip, vrf, prefix（網段鍵） }`；`Q.subnetsOf(dev, vrf)` 是其中一台設備的（給 vrf 時只取那個 VRF）。
- `Q.prefixes()`
- `Q.ipEntries()`／`Q.prefixEntries()`：每個 VRF 中不重複的 IP、每個 VRF 的每個網段各一列，多了 `key`（位址鍵或網段鍵）與 `vrf`；網段內的 IP 數只算同一個 VRF 的。
- `Q.search(text, limit)`：頁首的搜尋，回傳 `[{ type, key, label, … }]`，最多 `limit`（預設 20）筆。`type` 是 `mac`、`ip`、`subnet`、`vlan`、`device` 或 `interface`。
  - `device` 的 `label` 是原名（同 `Q.devName`）；畫面顯示時改用 `Q.devLabel(key)`。
- `Q.devName(key)`：設備名稱原值（`label` 或 `name`；找不到設備時回傳鍵），用於鍵比對、排序與匯出（CSV／Markdown 的設備欄）。
- `Q.devLabel(key)`：畫面給人看的設備名稱（詳情標題、清單的設備欄、修正計畫的「依設備」選單、搜尋結果、拓樸圖節點的提示）。通常與 `Q.devName` 相同；沒有收集（`collected: false`）且名稱是 IPv4 位址（`S.ip.isIp`）的設備，加上得知它的鄰居協定，例如 `172.31.255.2（OSPF 鄰居）`。協定是事實：碰到這台設備的 `links[].protocols`，加上以它為 `peerDev` 的 `ospfAdjacencies`（記為 OSPF），依 LLDP、CDP、MNDP、OSPF 的順序以「／」列出；都沒有時寫「（鄰居）」。不改 Snapshot 欄位。寫法只在 `S.check.discoveryLabel` 定義，C01 的訊息也用它（放在 check：訊息在 check 產生，query 可依賴 check，反過來不行）。
  - 只回傳結構化欄位，不回傳顯示用的副標；副標由畫面的 `A.searchSub`（`src/view/app-toolbar.js`）以 `V.TERMS`、`V.KIND`、`V.IFC_TYPE`、`V.ifcState` 組成。各類型多出的欄位以 `query.js` 中 `search` 的註解為準（例如 `ip` 的 `owner`、`macs`、`heard`、`vrfs`，`vlan` 的 `devices`、`vlanDomains`，`interface` 的 `match`、`ifType`、`status`）。
  - VLAN 接受純數字（不以 0 開頭，避免 MAC 片段被當成 VLAN）或「vlan 30」「VLAN30」，範圍 1–4094。
  - 完整的 MAC、IP 與 VLAN ID 各一筆；IP 前綴（例如 `10.1.`、`10.1`）先列以它開頭的直連網段（`subnet`，`key` 是含 VRF 的網段鍵，同 `Q.subnetGraph` 的網段 id），再列 IP；MAC 前綴（任一分隔符，或不寫分隔符但含 `a-f`）列出以它開頭的 MAC。只有數字時不當成 MAC 前綴，留給 VLAN 與 IP。
  - `ip` 的 `key` 是不含 VRF 的位址（不分 VRF），同一個位址在多個 VRF 合成一筆，`vrfs` 列出所在的 VRF（副標在 main 時不寫）。
  - 設備依名稱；介面先比名稱（`match: 'name'`），再比描述（`match: 'desc'`）。
- `Q.subnetGraph(opts)`：L3 網段圖（M1），見[第 3 節](#3-l3-網段圖)。

## 2. VRF 與路由表

- `Q.vrfs()`：基準中出現的 VRF 名稱（設定、位址、ARP 與路由），main 在最前、其餘依名稱；只用 main 的網路是 `['main']`。
- `Q.vrfsOf(dev)`：這台設備的 `vrfs` 設定，依設定順序。
- `Q.routesOf(dev, vrf)`：這台設備**作用中**的路由；給 vrf 時只取那個 VRF 的路由表（只用於策略路由的路由表 `vrf` 為 null，不會被選到）。`Q.routesInTable(dev, table)`：某張路由表作用中的路由，不論是不是 VRF。3.8.0 起 `routes[]` 也有非作用中的路由（`active: false`），這兩個函式、`Q.subnetGraph` 的路由與路由追蹤都不含它們（沒有 `active` 欄位的舊基準全部視為作用中）。
- `Q.allRoutesOf(dev)`（3.8.0）：這台設備的所有路由，含非作用中的，依 Snapshot 的順序（凍結）；設備詳情的路由表用。
- `Q.dhcpClientsOf(dev)`、`Q.pppoeClientsOf(dev)`（3.8.0）：這台設備的 `dhcpClients`、`pppoeClients`（凍結的陣列，元素是 Snapshot 本身的那一筆）；`Q.ospfOf(dev)`：`{ areas, templates }`（`ospfAreas`、`ospfInterfaceTemplates`，同一台回傳同一個凍結物件）。欄位見[設計說明 §5.2「對外與路由網域的設定」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)；索引在第一次呼叫時才建立。
- `Q.routingTables()`、`Q.routingRules()`：Snapshot 的 `routingTables`、`routingRules`。
- `Q.policyOf(dev)`：`{ tables, rules（啟用中的 rule，依順序）, marks（啟用中的 mark-routing）, policyRules（沒寫時是預設順序）, custom（改過 policy-rules）, any（有任何會改變查表的設定） }`，凍結。
- `Q.routesIncomplete(dev)`（3.10.0）：這台設備的路由表收集不完整（`coverageOf(dev).incomplete` 含 `route`：路由表的指令收集失敗，例如逾時只收到前面一部分；事實）。3.10.0 以前的基準沒有 `incomplete`，改看 `failures[].dataTypes`。是路由視圖的成員（`S.trace.ROUTING_VIEW`）：查不到符合的路由時，路徑追蹤與可達性回不明，不當成沒有路由（[設計說明 §5.3「路由表收集不完整」](設計說明.md#53-關鍵推論)）。
- `Q.hopOwner(dev, ip, vrf)`：見[設計說明 §5.2「VRF 與路由表」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)的「下一跳的擁有者」。
- **對外邊界、對外入口與路由網域**（3.8.0，推論；判斷規則見[設計說明 §5.3「對外邊界與路由網域」](設計說明.md#對外邊界與路由網域380-新增)）：
  - `Q.boundaries(dev)`：Snapshot 的 `boundaries`，不給 dev 時是全部設備，給了是那台（凍結的陣列，元素是 Snapshot 本身的那一筆，不要修改）。`Q.boundaryOf(ep)`：某個介面的那一筆；沒有任何證據時為 null（視為 internal）。
  - `Q.wanEntries(dev)`：對外入口 `[{ dev, ep, vrf, hasIfc, wanList }]`（凍結），是 WAN 清單成員（在前）與 `external` 邊界的聯集，和檢查用的 `M.wanEntries` 同一個函式（`S.infer.fw.wanEntries`）。不給 dev 時是全部設備（依 `firewallZones` 的設備順序）；沒有比對環境（沒有 `/export`）的設備為空陣列。
  - `Q.routingDomains()`：Snapshot 的 `routingDomains`（凍結）。`Q.routingDomainOf(prefixKey)`：網段鍵（`K.inVrf(網段, vrf)`，同 `prefixes[].key` 與 `Q.subnetGraph` 的網段 id）所屬的網域；不是直連網段時為 null。

## 3. L3 網段圖

`Q.subnetGraph({ nodes, hearsay, routes })` → `{ subnets, nodes, edges, routes, omitted }`。網段節點、設備或介面節點，以及「在這個網段有位址」的邊。

- **VRF 是容器**（[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）：每個網段、節點、邊與路由都有 `vrf`（main 也寫出），不同 VRF 的同一個網段是不同的網段節點。id 用 `K.inVrf`：main 不加後綴（和加入 VRF 之前相同），其他 VRF 加 `@<VRF>`。
  - 設備模式時，一台設備在每個有位址的 VRF 各一個節點，id 是「設備鍵」或「設備鍵@VRF」；介面模式時介面只屬於一個 VRF，id 就是介面鍵。
  - 推論的邊（鄰居宣告的位址、管理 IP）只接到同一個 VRF 的已知網段；管理 IP 視為 main。重疊網段（`overlaps`）、DHCP 網路的閘道也只在同一個 VRF 內對應。

- **參數**：`nodes` 為 `'device'`（預設，每台設備一個節點）或 `'interface'`（每個介面一個節點；管理 IP 的節點 id 是「設備鍵|」）。`hearsay` 預設 true，加入推論的邊：鄰居宣告的位址（`basis: 'neighbor'`）與沒有列在介面位址的管理 IP（`basis: 'mgmt'`），都只以最長相符接到已知網段，不產生新網段。`routes` 預設 false，為 true 時加入作用中的靜態路由（含黑洞）與預設路由；目的網段不是已知網段時，新增 `basis: 'route'` 的網段節點。
- `subnets[]`：`{ id, prefix, net, len, family, vrf, basis（connected／route）, vlan, vlans, eps, devices, routers, gateways, overlaps, duplicateIps }`。`routers` 是接在這裡的路由設備，`gateways` 是 DHCP 網路設定的閘道（`{ ip, dev, src }`）。
  - `overlaps`：和這個網段互相包含的其他網段 id（例如 `10.0.0.0/16` 與 `10.0.1.0/24`）。`routes` 為 true 時，路由新增的網段（例如彙總路由）也參與比對；預設路由 /0 包含所有網段，不列。
  - `duplicateIps`：同一個 IP 設在這個網段的多個介面上（VRRP 位址除外，鄰居宣告的不算）。
- `nodes[]`：`{ id, type, dev, ep, name, label, kind, collected, vrf, subnets, router, routerBasis, multihomed, hostAddresses }`。`hostAddresses` 是 /32 的自有位址（loopback 等，不形成網段）。
  - **路由設備是推論**：接到 2 個以上的網段，而且有路由表資料（`routerBasis: 'routes'`），或設備類型是路由器或防火牆（`'kind'`）。只是多張網卡的主機不算（`multihomed` 為 true、`router` 為 false）。interface 節點的 `router` 是所屬設備的值。
- `edges[]`：`{ id, subnet, node, dev, eps, addresses: [{ address, ip, ep, role, hearsay, seenBy, src }], basis（address／neighbor／mgmt）, inferred, vrf }`。`inferred` 為 `basis` 不是 `address`。
  - **管理 IP 的邊以 `seenBy` 追溯**：`mgmtIp` 在 Snapshot 沒有來源行，所以 `src` 是設備的 `src`（只由鄰居看到的設備為空），`seenBy` 列出看到這台設備的已收集設備。
- `routes[]`：`{ id, dev, node（設備模式時是這台設備在這個 VRF 的節點 id，介面模式為 null）, subnet（目的網段 id，同一個 VRF）, prefix, len, default, proto, distance, blackhole, nh（含 `vrf`、`vrfBasis`）, via（下一跳所在、這台設備在閘道的 VRF 直連的網段 id）, routingTable, vrf, src }`。interface 模式也接在設備上。
  - 只畫 VRF 的路由表（`routes[].vrf` 不是 null）。只用於策略路由的路由表不屬於任何 VRF 容器，不畫，筆數在 `omitted.policyRoutes`。
- **已知的限制**：同一個 VRF 中的同一個網段即使在不同站點，也會併成同一個網段節點。
- **只有 IPv4**：核心沒有收集 IPv6 的 prefix 與路由，所以網段與路由都是 IPv4。

## 4. L2 視圖

M1 新增。

- `Q.vlanIds()`：基準中出現的所有 VLAN ID（VLAN 定義與介面的 PVID／untagged／tagged），由小到大。VLAN 篩選的選項用。
- `Q.vlanSummary()`：VLAN 的三種數法（凍結）`{ ids, domains, definitions }`。`ids` 是 VLAN 定義中相異的 VLAN ID 數（同 `Q.inventory().counts.vlanIds`）；`domains` 是各 ID 不相連區塊的合計（同 `Q.vlan(id).domains`，推論）；`definitions` 是各設備的 VLAN 定義筆數（同 `meta.stats.vlans`）。畫面不自己重算，避免三種數字混用。
- `Q.vlanCarriers(vid, domain)`：承載這個 VLAN 的鏈路，VLAN 篩選時高亮用；給 `domain`（`Q.vlan` 的區塊鍵，見 [設計說明 §5.3「VLAN 區塊」](設計說明.md#53-關鍵推論)）時只含那一塊。回傳 `{ id, domain, devices, links, counts: { carry, partial, oneSide, inferred }, eps }`。
  - `links[]`：`{ key, kind（link／inferred）, status, inferred, hearsay, reason, a, b, src }`，依 status（下表的順序）再依鍵排序。`kind` 表示用 `Q.getLink` 還是 `Q.getInferredLink` 取回原始實體；`inferred` 為 true 表示這一列是推論；`hearsay` 表示鏈路本身只有只有一端資料。判斷依據和 `Q.vlan` 相同：兩端的有效 VLAN（介面本身加上所屬聚合的 PVID／untagged／tagged）。

    | status | 意義 | 事實或推論 |
    |---|---|---|
    | `carry` | 兩端都帶這個 VLAN | 事實 |
    | `partial` | 兩端都有 VLAN 資料，只有一端帶（兩端不一致，V01）；只含 `vlansDiff` 中的 VLAN，例如單臂路由的實體埠對上 PVID 1 不算 | 事實 |
    | `oneSide` | 只有一端帶，另一端無從得知；`reason` 是 `unfiltered`（任一端在未開 vlan-filtering 的 bridge 上，VLAN 原樣轉送；就是 `Q.vlan(id).transparent`，參與區塊劃分；未過濾的 bridge 串接時，中間那條鏈路兩端的 `has` 都是 null）、`peer-uncollected`（對端沒有收集）、`peer-no-vlan-data`（對端沒有 VLAN 設定資料）或 `hearsay`（鏈路是只有一端資料）。後三種不參與 `Q.vlan` 的區塊劃分 | 推論 |
    | `inferred` | 推論鏈路，已收集的各端都帶這個 VLAN（同 `Q.vlan(id).inferred`） | 推論 |

  - `a`／`b`：`{ ep, dev, port, has, via, mode, collected, vlanData }`。`has` 為 true／false 是事實（這台設備有 VLAN 設定資料）；為 null 表示無從得知（沒有收集、沒有 VLAN 資料，或這一端是 `vlanUnfiltered`）。`via` 是帶這個 VLAN 的位置：`self`（介面本身）、`lag`（所屬聚合介面）或 `member`（推論鏈路記在聚合上，由成員埠帶）；`mode` 是 `tagged`、`untagged` 或 `both`。
  - `eps`：帶這個 VLAN 的鏈路端點（`has` 為 true），排序後的 ep 鍵。
  - 只算介面鄰接（LLDP／CDP）；MNDP 只證明同一廣播網域，不列入。
  - VLAN 子介面讓 parent 以 tagged 承載（停用的不算；parent 是 bridge 時只有 bridge 本身帶），和 V01 相同，所以單臂路由的實體埠也會被高亮。規則與已知的限制見[設計說明 §5.2「介面」](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)的「VLAN 子介面讓 parent 承載」「vlan-filtering」與「已知的限制」。
- `Q.portGraph({ lag, ports, inferred, devices })`：埠層級的 L2 圖（給 ELK 的 port），回傳 `{ devices, ports, edges, omitted }`。
  - **參數**：`lag` 為 `'collapse'`（預設，聚合成員併進聚合埠，成員列在 `members`）或 `'expand'`（成員各自是埠，`lag` 指向所屬聚合）；`ports` 為 `'linked'`（預設，只列有邊的埠）或 `'all'`（另列範圍內已收集設備的實體、聚合與無線介面）；`inferred` 預設 true，是否包含推論鏈路；`devices` 是設備鍵的陣列，給了就只取至少一端在其中的邊（另一端的設備也會出現，`focus` 為 false）。
  - `devices[]`：`{ id, label, kind, collected, focus, ports, bridges: [{ ep, name, ports, vlanIfcs }] }`。**bridge 不是埠**，放在 `devices[].bridges`，列出它的埠與掛在它上面的 VLAN 介面。
  - `ports[]`：`{ id（ep 鍵）, dev, name, ifc, unknown, type, rawType, status, enabled, hearsay, lag, members, bridge, mode, pvid, vlans, subIfcs, unknownPeer, macCount, edges }`。**VLAN 子介面不是埠**，列在掛載的埠（或其成員）的 `subIfcs`。推論鏈路未收集端的未知埠，`ifc` 為 null、`unknown` 為 true。
  - `edges[]`：`{ id, a, b（埠 id，a < b）, aDev, bDev, links, inferredLinks, count, evidence, inferred, cls, vlansCommon, src }`。`evidence` 依強弱是 `adjacency`（有雙側的 LLDP／CDP 介面鄰接）、`hearsay`（只有只有一端資料，推論）、`inferred`（只有推論鏈路，推論）；`inferred` 為 `evidence` 不是 `adjacency`。
  - 只算 interface-adjacency 的鏈路。`omitted` 是沒有畫成邊的筆數：`domainOnly`（MNDP 鏈路，只證明同一廣播網域，不當直連）、`sameDevice`（收合後兩端是同一個埠）、`inferred`（`inferred` 為 false 時略過的推論鏈路）。
- **共通規則**（`vlanCarriers`、`portGraph`、`subnetGraph`，以及 `vlanIds`）：第一次呼叫時才計算，依參數快取，同樣的參數第二次呼叫直接回傳同一個物件；回傳的物件是 Q 新建的，深層凍結。`portGraph`、`subnetGraph` 的參數值不認得時丟出 TypeError；`vlanCarriers` 的 vid 轉成數字比對。

## 5. 防火牆命中次數與 L4

M2（2.11.0）新增；判斷規則見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)。

- `Q.firewallStats()`：Snapshot 的 `firewallStats`（事實）；`Q.firewallStatsOf(devKey)`：其中這台設備的表。
- `Q.mgmtOf(devKey)`（3.4.0 新增）：這台設備的管理面設定，即 Snapshot `mgmtSettings` 的那一筆（欄位見[設計說明 §5.2](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)）；沒有 export 的設備為 null。
  - 設備層：`export` 是 `full`（有整機 `/export`）或 `partial`（只有 `/ip export` 這類部分 export，或沒有指令標記的段落）；`version` 是設備版本（`/system resource` 優先，其次 export 抬頭的「by RouterOS x」，都沒有時為 null）；`versionInRange` 是版本在預設值表範圍內 true、範圍外 false、版本不明 null。
  - 每一項：`basis` 是 `export`（有寫出的欄位）、`default`（全部以出廠預設值補上，推論）或 `none`（全部沒有資料）；`defaulted` 是以預設值補上的欄位；`unknown` 是沒有資料的欄位（值為 null）；`reason` 是 `unknown` 的原因——`not-exported`（部分 export 沒有包含這個選單）或 `version`（版本不在預設值表範圍，不推定），`unknown` 是空的時為 null；`src` 是 export 的行。版本不明時照用預設值。
  - 任何欄位都可能是 null（沒有資料），呼叫端要能處理。`snmp.communities` 可能是 null（部分 export 又沒有 community 的設定），原因在 `snmp.communitiesReason`；每個 community 也有 `defaulted`／`unknown`。DNS 與 SOCKS 有 `vrf`（預設 main）。
  - F13 的 facet 平常是 community 名稱；同一台有同名且啟用中的 community 時是「名稱#內容雜湊前 8 碼」。
  回傳 Snapshot 本身的物件（不凍結、不複製），不要修改；依設備的索引在第一次呼叫時才建立。F10–F14 的判斷見[基準檢查「管理面加固」](基準檢查.md#管理面加固f10f14)。
- `Q.policyBaseline(devKey)`（3.7.0 新增）：這台設備的狀態式骨架（回程的前提，推論），IPv4 filter 的 input、forward 各一列；判斷規則見[設計說明 §5.3「防火牆」](設計說明.md#53-關鍵推論)，F15 依它判斷（[基準檢查 F15](基準檢查.md#f15)）。沒有設定資料（`/export`）的設備為 null。每一列是 `{ chain, rules, established, invalidDrop, defaultAction, returnSafe, src }`：
  - `rules`：chain 本身啟用中的規則數（不含 jump 進去的）。
  - `established`：`{ status, rule, path, conditional, shadowed, blockedFrom }`。`status` 是 `accept`（一定走得到的放行，accept 或 `fasttrack-connection`）、`policy`（沒有規則決定，內建 chain 預設放行）或 `drop`（先被一定命中的丟棄擋下）；`shadowed` 是排在那條丟棄之後、走不到的 established 放行；`conditional` 是只在部分條件下放行的規則。
  - `established.blockedFrom`：`[{ rule, path, interfaces }]`，排在決定 established 的規則之前、只以介面為條件的丟棄（從這些介面進來的回程不保證；`interfaces` 是入介面，只限出介面或清單展開不了時為 null）。有值時 `returnSafe` 為 false。
  - `invalidDrop`：`{ status（drop／accept／policy）, rule, path, explicit }`，`explicit` 表示決定結果的規則明確比對 `connection-state`。
  - `defaultAction`：`{ action（drop／reject／tarpit／accept）, scope（all：沒有條件；interface：只以介面為條件；null：預設放行）, policy（true 表示沒有這種規則，是內建 chain 的預設放行）, rule }`。
  - `returnSafe`：false 表示已建立連線的回程封包可能被丟棄（F15 的條件）。
  - `rule` 是規則鍵（用 `Q.getFirewallRule` 取得規則），`path`（經過的 jump 規則）、`conditional`、`shadowed` 是規則鍵陣列；`src` 是依據的規則行 `[[block, line]]`，依序、不重複。
  第一次查詢某台設備時才計算，結果深層凍結並快取。
- **位址清單**（3.10.0；判斷規則見[設計說明 §5.3「防火牆」](設計說明.md#53-關鍵推論)的「位址清單」與「位址集合的登錄表」）：
  - `Q.addressListsOf(devKey)`：這台設備的 `addressLists`（依位址族 ip → ipv6、名稱；欄位見[設計說明 §5.2](設計說明.md#52-實體snapshotmodelschema-ssot-snapshot2)），凍結；沒有時為空陣列。`static` 為 true 時 `Q.reach` 與 F 檢查依項目判斷，false 時 `reasons` 列出可能有動態來源的原因。
  - `Q.addressListOf(devKey, family, name)`：一份清單（`family` 是 `ip` 或 `ipv6`）；基準裡沒有（export 沒有項目，也沒有寫入它的設定）時為 null，判斷時不明。
  - `S.query.addressListReasons()`：可能有動態來源的原因（凍結的 `[{ code, source, label }]`，`source` 是 `entry`（清單的項目）或 `writer`（寫入清單的來源）），即判斷用的 `S.infer.fw.ADDRESS_LIST_DYNAMIC`；`reasons` 是其中的 `code`。
  - `Q.addressSet(id)`（3.11.0）：位址集合登錄表（判斷用的同一份，推論用的索引，不在 Snapshot）的一筆 `{ id, kind, dev, family, static, reasons, src, size, ranges }`，深層凍結；`kind` 是 `address-list`、`rule-address`、`service` 或 `routing-rule`（id 的寫法見設計說明），`size` 是合併後的區段數，`ranges` 是 `[[起, 迄]]` 的位址文字（依位址排序）；可能有動態來源的清單與無法判斷的字面值，`size`、`ranges` 為 null。沒有這個 id 時為 null。A10 的 `deviation.groups[].list` 是 `address-list` 的 id。
- `Q.subnetsOf(devKey, vrf)`：`Q.subnets()` 中屬於這台設備的直連網段，順序相同；給 vrf 時只取那個 VRF 的。凍結的陣列。
- `S.trace(Q, src, dst, { ttl, vrf })`：路由追蹤（推論）。每一跳在它的 VRF 查路由（含策略路由），下一跳寫了 `@<VRF>` 時在那個 VRF 解析閘道，下一台從擁有閘道位址的 VRF 繼續。回傳 `{ ok, src, dst, vrf, start, starts, startBasis, reached, status, unverified, hops: [{ dev, vrf, via, table, rule, route, proto, ecmp, next }], ends: [{ dev, vrf, status, note, path, reason?, assumption? }], edges }`；`ends[].status` 另有策略路由的 `policy`（查哪一張路由表不明，`assumption` 是對到的前提 `policy-routing` 或 `mark-routing`）與 `policy-drop`（rule 丟棄）。路由追蹤的前提是 `S.query.traceAssumptions()`，結束狀態對到的前提是 `S.query.traceEndStatuses()`（見下方「不需要 Snapshot 的靜態查詢」）。`opts.ttl` 給了要是正整數，否則丟出 TypeError；預設 `S.trace.TTL`（32）。
  - **和 L4 共用走法**（3.8.0）：起點、逐跳、迴圈、TTL、送往外部都是 `S.trace.walker`，和 `Q.reach` 相同（規則見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)）。
  - **起點**：`starts` 是所有起點（同一個依據有多台閘道時每一台都是），`start` 是第一台；`startBasis` 是依據（`S.query.reachStartBases()` 的值，或來源是網路設備自己的位址時的 `device`）。
  - **送往外部**（3.8.0）：經對外介面（`Q.boundaryOf` 為 external）送往不在基準的下一跳、目的也不在基準時，`ends[].status` 與 `hops[].next[].status` 是 `egress`；出介面只是可能對外（possible）時仍是 `unknown-nh`，另有 `reason: 'egress-possible'`，`note` 寫出弱證據。
  - 走到未收集的設備（起點、中途或終點，目的不在它的直連網段時）以 `ends[].status` 為 `unverified` 停下：沒有它的路由表，不能判斷是否抵達，不算斷掉。路由表收集不完整（`Q.routesIncomplete`）的設備查不到符合的路由時也是 `unverified`，另有 `reason: 'route-data-incomplete'`（3.10.0）；`Q.reach` 在這種情況是不明，原因代碼同名。
  - `status` 是整體結果：`reached`（至少一支抵達）、`external`（沒有抵達，但有分支送往外部，3.8.0）、`unverified`（沒有抵達，而且每一支都停在未收集的設備）或 `unreachable`（其他）；`unverified` 是停在未收集設備的設備鍵（去重、依出現順序）。`error` 與 `ends[].note` 等文字中的 VRF 在 main 時省略，與 `K.inVrf` 相同；只用 main 的網路時，trace 與 reach 的文字和 2.11.0 相同（`tests/core/vrf.js`，fixture `tests/fixtures/vrf/trace-2.11-main-only.json`）。
- **vrf 的決定**（`S.trace` 與 `Q.reach` 共用 `S.trace.pickVrf`）：給了就用，不是基準中的 VRF 時丟出 TypeError；沒給時依來源位址：只在一個 VRF（擁有它，或它落在那個 VRF 的直連網段）時用那個 VRF，不在任何 VRF 時是 main，在多個 VRF（位址重疊）時回傳 `{ ok: false, error, vrfs }`，請使用者指定，不猜。
- `Q.reach(src, dst, opts)`：從 src 到 dst 的新連線能不能通（推論）。`opts`：`{ proto（預設 tcp）, port（tcp、udp 必填，1–65535 的整數；沒有埠的協定要省略）, vrf（選用，見上方「vrf 的決定」；有 entry 時是入介面的 VRF，給了不同的 vrf 丟出 TypeError）, entry（選用：封包進入的介面鍵，來源不在任何網段時用；也可以是沒有介面紀錄的對外入口，VRF 用入口的 VRF）, disabledRules（選用：當作停用的規則鍵，估計停用的影響用） }`。回傳 `{ ok, src, dst, proto, port, vrf, entry, verdict（allow／deny／unknown）, final（NAT 後的 `{ dst, port }`，各路徑不同時為 null）, natApplied, start, reasons, notes, decisive, paths: [{ verdict, hops, end, route, filter }], assumptions }`；`hops[].vrf` 是封包在那台設備所在的 VRF。分層結果（3.8.0，定義見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)的「結果分層」）：`paths[].route` 是 `{ status（reached／no-route／blackhole／policy-drop／loop／unknown）, code, reasons }`，`paths[].filter` 是 `{ status（allow／deny／unknown，路由沒到時 n/a）, rule（擋下的規則；預設丟棄時 `{ key: null, policy: true }`）, reasons（filter、nat、assumption 層的原因） }`。`reasons` 只在 unknown 時有值，其他結果的同類說明放在 `notes`。回程未保證（推論，判斷方式見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)）：那一跳（forward 或 input）另有 `hops[].returnUnsafe`＝`{ chain, rule（規則鍵）, interfaces（介面鍵陣列；所有介面都算時為 null） }`，沒有時不加這個欄位；結果是 allow 時，允許的路徑上每個這樣的跳在 `notes` 加一筆 `{ code: 'return-not-guaranteed', dev, message, rule（規則參照）, chain, interfaces }`，結果仍是 allow。位址不是有效的 IPv4 時回傳 `{ ok: false, error }`，來源在多個 VRF 時另有 `vrfs`；參數不合法時丟出 TypeError。
- `Q.zones(opts)`：每個 IPv4 直連網段的 zone（推論），每個 VRF 分開。`opts`：`{ profile（選用：建立基準時用的命名規則 JSON，核對方式見 §5.3）, sources（選用：要用的來源，`subnet` 一定包含） }`。回傳 `{ zones: [{ id, name, source, inferred, basis, subnets, devices, vrf }], subnets: [{ prefix, key（網段鍵）, net, len, vrf, zone, source, inferred, basis, detail, alternatives, eps }] }`。非 main 的 VRF，zone 的 id 加上 `@<VRF>`（`K.inVrf`），名稱加上「（VRF <VRF 名稱>）」；main 的 id 與名稱和加入 VRF 之前相同。
- `Q.zoneOf(ip, opts)`：IP 所屬的 zone（那個 VRF 最長相符的直連網段）`{ zone, subnet, key, vrf, source, inferred }`；不在任何網段時為 null。VRF 由 `opts.vrf` 指定；沒有指定時依位址決定（同上方「vrf 的決定」），位址在多個 VRF 時丟出 TypeError，請指定 vrf。
- `Q.zoneMatrix(opts)`：zone 矩陣 L0，含所有 VRF 的 zone。`opts` 是 `Q.zones` 的參數，另加 `services`（`[{ proto, port }]`，預設是 `S.query.l4Services()` 加上 dst-nat 規則的目的埠，3.8.0 起再加上「網路設備（管理）」各目的設備自己開著的服務）。回傳 `{ vrf（固定為 null）, vrfs（有 zone 的 VRF）, zones, services, cells: [{ src, dst, diagonal, status（allow／deny／partial／unknown／empty）, incomplete（有允許又有無法判斷）, counts, deniedBy, services, heterogeneous, rule, rules, ruleCount, reasons }], stats（另有 externalEntries（外部來源的入口數，和暴露清單同一份入口）、deviceTargets）, ipv6（IPv6 在用的設備 [{ dev, src }]） }`。`deniedBy`（3.8.0）是 `{ noRoute, filter }`，拒絕的組合中路由沒到與防火牆擋下各幾筆，合計等於 `counts.deny`；`cells[].services[]` 也各有一份。`zones` 另含虛擬 zone（`virtual: true`）：`external`「外部（Internet）」與只當目的的 `self`「網路設備（管理）」（`dstOnly: true`，`cells` 沒有這一列）；`Q.zoneCell` 也接受這兩個 id。代表位址另有 `peer`（zone 內同網段用的第二個位址），外部來源有 `entry`。`Q.reach` 的逐跳另有 `conntrack`（`new`／`untracked`）。
- `Q.zoneMatrixSteps(opts)`：`Q.zoneMatrix` 的分段計算（generator，用法像 `S.steps`）。參數同 `Q.zoneMatrix`；每一段 yield `{ stage（reps／evaluate／summary）, done, total }`（`total` 是上限，只用來顯示進度），跑完時的回傳值與 `Q.zoneMatrix(opts)` 是同一個物件。分段的方式見 [設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)。
- `Q.zoneCell(srcZone, dstZone, opts)`：矩陣的明細（L1／L2）：一格的摘要（含 `deniedBy`），加上 `groups`（目的 × 結果相同的來源代表併成一列，每組有 `dst, srcs, services, status, counts, srcDevices, divergent, divergentServices`）與 `ruleDetails`（牽涉的規則；3.7.0 起每列有 `verdict`，是這條規則或 chain 預設動作的結果（`policy` 列就是預設動作），只因條件無法判斷才列入的規則為 null）。`divergent` 表示這一組造成格子異質，`divergentServices` 是造成差異的 service（定義見 §5.3）。L3 是對某個來源代表與目的呼叫 `Q.reach`。zone 不存在時丟出 TypeError。
- `Q.exposure(opts)`（3.7.0 新增；畫面在 L4 的頂端使用，經 `Q.exposureSteps` 分段計算）：從 WAN 進來連得到什麼（暴露清單，推論），分成路由器本身、dst-nat、直接路由三段；判斷方式見[設計說明 §5.3「暴露清單」](設計說明.md#暴露清單370-新增)。`opts` 是 `Q.zones` 的參數，另加 `maxEvaluations`（判斷次數上限，預設 200000；3.8.0 之後由 400000 調降，拒絕依 service 等價類共用之後 1000 台約 8 萬次）與 `maxSources`（每台入口設備的外部區段數上限，預設 16）；不是正整數時丟出 TypeError。回傳：
  - `status`：`ok`、`no-wan`（沒有可辨識的對外入口：WAN 清單成員與 `external` 邊界都沒有）或 `no-external-address`（外部的代表位址都在基準內）；不是 ok 時 `message` 寫出原因。
  - `wan`：`{ entries: [{ dev, ep, vrf }], devices }`，入口設備與入口介面。入口（3.8.0）是有 `/export` 的設備上 `Q.wanEntries` 與 `Q.boundaries` 中 `external` 介面的聯集，含沒有介面紀錄的成員，和 `Q.zoneMatrix` 的外部 zone 相同。`external`：`{ representative（外部代表位址，和矩陣的外部 zone 相同）, byDevice: [{ dev, sources: [{ ip, range }], sourceCount, truncated }] }`，每台入口設備切出的外部區段；status 不是 ok 時為 null。
  - `services`：`[{ id, proto, port, range, origins }]`，`origins` 是候選服務的來源：`default`（預設服務）、`filter`（從入口進來的放行規則的目的埠，也取 IPv6 filter input／forward 的放行規則）、`dst-nat`、`ip-service`、`mgmt`。`ip-service`、`mgmt` 取自第 1 段每台目的設備自己開著的服務（啟用中的 `/ip service`；`Q.mgmtOf` 開著的 DNS、SNMP、Web Proxy、SOCKS、Bandwidth Server），和 `Q.zoneMatrix` 的「網路設備（管理）」同一份（3.8.0）。
  - `self`、`dnat`、`routed`：各 `{ rows, counts: { candidates, allow, unknown, deny, natted, notEvaluated } }`。只列允許與無法判斷的組合，拒絕的只計數；`natted` 是被 dst-nat 改寫、改列到別段的組合；`notEvaluated`（3.8.0）是判斷次數上限用完、一次都沒判斷到的組合，不算 `candidates`，也不算拒絕（3.8.0 之後 IPv4 也計入，歸段方式見[設計說明「暴露清單」的限制](設計說明.md#暴露清單370-新增)）。IPv6 的列（見下方「IPv6 的列」）併在 `self`、`routed` 的 `rows` 與 `counts` 裡。每列：
    - 位址族：`family`（`ipv4`／`ipv6`）。
    - 位置：`dev`（self 段是目的設備，其他段是入口設備）、`via`（只有 self 段的 IPv4 列：經別台入口設備進來時是 `{ dev, ep }`，入口就在目的設備上時為 null；IPv6 的 self 列為 null；其他段沒有這個欄位）、`entries`（給出這個結果的入口介面）、`entry`（給 `Q.reach` 的入口介面）、`inInterface`（它的介面名稱）、`src`（判斷這一列用的外部代表位址）、`dst`（`K.inVrf` 的鍵）、`ip`、`vrf`（self 段是目的位址的 VRF，其他段是入口的 VRF）。
    - 分層（3.8.0）：`route`、`filter`，由這一列的代表判斷（同 `src`、`entry`）展開的路徑彙整，形狀同 `Q.reach` 的 `paths[].route`／`filter`；路徑的路由層結果不只一種時 `route.status` 是 `unknown`（`branches-differ`）。IPv6 的列 `route` 為 null，`filter.rule` 為 null。
    - 服務：`service`、`proto`、`port`、`portRange`（null 或 `[a, b]`）、`serviceName`（self 段：`/ip service` 的名稱，或 dns、snmp、web-proxy、socks、bandwidth-server；其他段為 null）。
    - 結果：`verdict`（`allow`／`unknown`）、`incomplete`（允許，但有些來源或入口無法判斷）、`reasons`（unknown 的原因代碼；allow 的列只有 `return-not-guaranteed` 或 IPv6 的 `no-ipv6-firewall`，否則是空陣列）、`returnUnsafe`（`[{ dev, chain, rule（規則鍵）, interfaces }]`，這一列的代表判斷（和 `Q.reach(src, ip, { entry })` 相同）路徑上回程未保證的跳，沒有時是空陣列；IPv6 的列一律空）、`allowedFrom`（`{ kind: any／limited, ranges, text }`，允許的外部來源）、`rule`（決定結果的規則；預設放行時是 `{ key: null, policy: true, table, chain }`；可能是 null）、`findingKeys`（相關檢查的 findingKey：規則的 F03／F04（IPv6 的列另有 F05）、`/ip service` 的 F07、設備的 F10、F13、F14，已排序）。
    - 目的：`target`（self 段是設備鍵，其他段是網路設備鍵或網段鍵）、`zone`（`Q.zones` 的 zone id，self 段為 `self`）；`nat`（dnat 段一定有：`{ from: 公網:埠, to: 內部:埠, rule }`；routed 段只在內部又被 NAT 時才有）、`dstAny`（dnat 段：dst-nat 沒有限制 `dst-address`／`dst-address-list`）、`subnet`（routed 段：代表位址所屬的網段鍵）。
    - IPv6 的列（`family: 'ipv6'`，只看邊界路由器）：欄位同上，`zone` 為 null（self 段為 `self`），`vrf` 是 main，沒有 `nat`；routed 段另有 `subnet`（網段文字，`target` 相同）、`dstRange`（`[起, 迄]`，這一列代表的目的區段）與 `dstAny`（決定的放行沒有 `dst-address`／`dst-address-list`，或預設放行：整個區段的主機都暴露）。`src` 是 IPv6 的外部代表位址。
    - 排序：入口設備的列在前（self 段另有經入口連到的其他設備）→ 設備（自然排序）→ 位址族（IPv4 在前）→ 位址 → VRF → `services` 的順序，與輸入順序無關。
  - `denied`：`{ self, dnat, routed }`，各段拒絕的組合數。`deniedBy`（3.8.0）：`{ self, dnat, routed }`，各 `{ noRoute, filter, notNatted }`，合計等於 `denied` 的同一段：路由沒到（含 dst-nat 改寫成私有位址又送回外部的）、防火牆擋下（IPv6 的拒絕都算這裡）、dst-nat 寫明的位址但這個服務沒被改寫。`noWan`：`[{ dev, findingKey }]`，有防火牆規則卻判斷不出 WAN 的設備（F08）。`noFirewall`：已收集、不是主機、有預設路由卻沒有 `/export` 的設備（推論為可能的邊界路由器）。
  - `ipv6`：`{ status, message, devices, evaluated, missing }`。`devices` 同 `Q.zoneMatrix` 的 `ipv6`；`evaluated` 是判斷了 IPv6 的入口設備鍵；`missing` 是 `[{ dev, reason: 'no-address'｜'disabled' }]`，在用 IPv6 卻沒有 IPv6 位址、或 IPv6 停用的入口設備。`status`：`edge-only`（至少一台入口設備有 IPv6 位址並判斷了，只看邊界路由器）、`no-ipv6-address`（沒有入口設備有 IPv6 位址的事實）、`no-wan`（沒有 WAN 入口）、`not-evaluated`（IPv4 的外部代表位址不可用，`status` 為 `no-external-address`）。`message` 是給畫面照列的說明。**目前 Snapshot 沒有 IPv6 位址的事實**（`/ipv6 address` 只當作 IPv6 在用的證據），所以實際資料上是 `no-ipv6-address`，IPv6 的列只在 `ipAddresses` 有 IPv6 的項目時才會出現。`limits`：`{ evaluations（含 IPv6）, maxEvaluations, truncated }`。`assumptions`：`Q.reach` 的前提（路由層＋L4）之後附加兩條暴露清單專用的前提（`S.query.exposureAssumptions()`：`exposure-source-ranges`、`wan-member-no-interface`，見下一條），只出現在暴露清單的結果，`Q.reach` 不含。
  - IPv4 的每一列與 `Q.reach(src, ip, { proto, port, entry })` 的結果一致（測試逐列核對）；IPv6 的列沒有對應的 `Q.reach`（`Q.reach` 只接受 IPv4）。
  - 附加的兩個前提：外部來源依入口設備的規則（`src-address`、展開的 `src-address-list`、`/ip service` 的 available-from、`/routing rule`）切區段，經入口連到另一台網路設備本身時另依那台目的設備的規則切，路徑上其他設備依來源位址的規則不切，所以 `allowedFrom` 可能偏寬（`exposure-source-ranges`）；沒有介面紀錄的 WAN 清單成員（只有 `/ip address` 與 list member）也算入口，VRF 視為 main（`wan-member-no-interface`）。3.8.0 起矩陣的外部 zone 也收這種入口，兩者相同。
- `Q.exposureSteps(opts)`：`Q.exposure` 的分段計算（generator），每一段 yield `{ stage（prepare／evaluate／summary）, done, total }`，回傳值與 `Q.exposure(opts)` 相同；參數不合法的 TypeError 在第一次 `next()` 時丟出。
- `Q.exposureSummary(opts, exposure)`（3.9.0 新增）：暴露清單的結論（推論），畫面 L4 頁首與主管摘要（`S.report.managerSummary`）共用同一份分組、計數與結論句，畫面不自己分組（定義在 `src/query/reach-exposure.js` 的 `S.reach._.exposureSummary`）。`opts` 同 `Q.exposure`；`exposure` 是已算好的 `Q.exposure(opts)` 結果（例如 `Q.exposureSteps` 跑完的值），省略時呼叫 `Q.exposure(opts)`；依 exposure 的結果物件快取。回傳（深層凍結）：
  - 計數有兩種單位，欄位分開、不混用：
    - **服務**（`unit: '服務'`）：分組後的列數。同一台設備、同一個服務、結果、允許來源、依據與入口都相同的列併成一列（例如設備每個介面位址的 icmp）。`total: { allow, unknown }` 與各段的 `allow`、`unknown` 用這種單位，結論句也只用它。
    - **組合**（目的位址 × 服務，未分組）：`combos: { allow, unknown, deny, notEvaluated }`，各段的 `combos` 是 `{ candidates, allow, unknown, deny, natted, notEvaluated }`（即 `Q.exposure` 各段的 `counts`）。拒絕與沒判斷的沒有列，只有這種單位。
  - `sections`：`{ self, dnat, routed }`，各 `{ allow, unknown, groups, combos, deniedBy }`。`groups` 是 `[{ row（第一列）, index（它在 `rows` 的位置）, ips（併進來的位址，依 rows 的順序）, entryDev }]`，允許在前、再無法判斷，同結果內保留 `Q.exposure` 的順序；第 1 段（`self`）再依目的設備分組（有允許的設備在前，同一類裡入口設備在前），`entryDev` 是目的設備是不是入口設備，其他段為 null。`deniedBy` 同 `Q.exposure` 的同一段。
  - `status`、`message`：同 `Q.exposure`。`noFirewall`：沒有 `/export` 的可能邊界路由器（設備鍵）。`truncated`：判斷次數用完（`limits.truncated`）。
  - `sentence`：結論句，例如「從外部進來，連得到 N 個服務：網路設備本身 a 個、轉送到內部 b 個、直接路由 c 個。」，另接無法判斷的服務數與沒有防火牆資料的設備；`status` 不是 ok 時寫出原因。數字的千分位不依執行環境的 locale。
- `Q.ruleImpact(key, opts)`：規則的影響：`{ rule（含 stats）, shadowed（F01）, duplicate（F02）, findings, cells, total, paths, truncated, ifDisabled }`，`ifDisabled` 是停用這條規則時結果改變的路徑。`opts` 同 `Q.zoneMatrix`，另加 `limit`（列出的路徑數上限，預設 50）。沒有這條規則時為 null。
- `Q.assumptionUse()`：這份基準用得到哪些判斷的前提（推論，查詢時計算並快取，不進 Snapshot；判斷方式見[設計說明 §5.3「L4 可達性與 zone」的「判斷的前提」](設計說明.md#l4-可達性與-zone2110-新增)）。深層凍結的陣列，路由層、L4、暴露清單的前提依序每條一筆 `{ code, layer, status（affects／missing-data／not-used／always）, devices（設備鍵，自然排序）, ruleKeys（防火牆規則鍵）, count, unit（rules／devices；count 為 0 時 null） }`。畫面只列 `affects` 與 `missing-data` 的。
- 不需要 Snapshot 的靜態查詢：`S.query.l4Services()`（矩陣預設的 service 的基本清單）、`S.query.zoneSources()`（zone 來源與優先順序）。
  - 判斷的前提（凍結，每條 `{ code, layer, short, detail, message }`，`message` 同 `detail`）：`S.query.traceAssumptions()`（路由層，L3 路由追蹤與 L4 共用，即 `S.trace.ASSUMPTIONS`）、`S.query.reachAssumptions()`（只有 L4 自己的防火牆層與推論假設；3.8.0 之後不再含路由層）、`S.query.exposureAssumptions()`（暴露清單另有的兩條）。`Q.reach` 的 `assumptions` 是前兩份接起來，`Q.exposure` 的是三份接起來。
  - `S.query.reachDefinition()`：L4 的判斷方式（一句話）。`S.query.reasonAssumptions(code, reason?)`：一個原因實際對到的前提 code（凍結的陣列；給了原因物件時依它的 `keys`、`assumption` 對得更準；不是前提造成的是空陣列；代碼不在 `reachReasonCodes()` 時丟出 TypeError）。`S.query.traceEndStatuses()`：`S.trace` 的 `ends[].status` 對應的前提 `[{ status, assumption, reasons? }]`。
  - `S.query.reachReasonCodes()`（原因與結束代碼的清單 `[{ code, kind, layer, note, assumption }]`，`layer` 是 `route`／`filter`／`nat`／`assumption`，`assumption` 是對到的前提 code、可能有多條時是陣列、不是前提造成的是 null，見 §5.3）與 `S.query.reachStartBases()`（3.8.0：閘道推定的依據，凍結的 `['dhcp', 'next-hop', 'default-route', 'routes', 'subnet']`，即 `Q.reach` 的 `start.basis` 與 `S.trace` 的 `startBasis` 可能的值；`S.trace` 另有 `device`）。
- 共通規則：第一次呼叫 L4 函式時才建立計算引擎（`S.reach.engine`，`src/query/reach.js` 與 `reach-eval.js`、`reach-zones.js`、`reach-matrix.js`、`reach-exposure.js` 五個檔；L3 的路由追蹤 `S.trace` 與共用的走法 `S.trace.walker` 在 `src/query/trace.js`）；結果依參數快取在記憶體，回傳的物件深層凍結，不寫進 Snapshot（[ADR-014](架構決策/014-L4-zone矩陣在查詢時計算.md)）。

## 6. 檢查結果與覆蓋

- `Q.findingKey(f)`：finding 的穩定鍵，見[設計說明 第 8 節](設計說明.md#8-比對獨立模組)。
- `Q.findingBaseKey(f)`（也可用 `SSOT.query.findingBaseKey`）：不含 facet 的鍵（id＋實體），也就是 2.9.0 之前的 findingKey；沒有 facet 的 finding 與 `Q.findingKey` 相同。給處理紀錄等轉換舊鍵用。
- `Q.findingDevice(f)`：finding 所屬的設備鍵。取第一個 `device` 實體；沒有時，取第一個能對到設備的介面、鏈路一端、防火牆規則、管理服務或設備自有的 IP。都對不到（例如沒有設備標頭的 I01、只涉及 MAC 或 VLAN 的檢查）時為 null。畫面的分組、匯出與修正 patch 都用它。
- `Q.coverage()`：Snapshot 的 `coverage[]`（每台設備收集了哪些資料、缺漏與收集失敗），沒有時為空陣列。處理紀錄用它判斷能不能判定已修好。
- `Q.coverageOf(devKey)`：該設備的覆蓋列（`coverage()` 的一個元素）；沒有這台設備時為 null。
- `Q.coverageSummary()`：覆蓋率的唯一數字來源（凍結）`{ devices, collected, missing, network, networkCollected, hosts }`。
- `Q.recognizedDevices()`：認到的設備（`devices()` 的子集合，順序相同）：已收集，且有至少一類資料（`data`）或有收集失敗的紀錄（`coverageOf(key).failures`）。內容都認不得、也沒有收集失敗紀錄的設備（例如 `files-v1` 以檔名當設備名、卻沒有任何可辨識資料）在建立時就不會成為設備（3.6.0 起）；這裡另外排除「辨識成功但 0 列」的設備（例如只有空的 print 區塊），它們會建立為已收集、資料為空。這是唯一的判斷：CLI 的「沒有認到任何設備的資料」（結束碼 2）用它，建立前的預檢用同一個判斷的 `S.query.preflightRecognized`。
- `Q.coverageGap(row)`：覆蓋列（`Q.coverage()` 的元素）是否「已收集但有缺漏」：已收集，且缺少應收集的資料或有指令收集失敗（只有失敗也算）。這是唯一的判斷：`coverageSummary().missing` 是它的台數，畫面的覆蓋率表（「有缺漏」篩選、排序、標紅）也呼叫它。
  - `devices`、`collected`：全部設備與已收集的台數。
  - `network`、`networkCollected`：應收集的網路設備與其中已收集的台數。範圍和 C01／C02 相同，都用 `S.check.expectsCollection`（已收集的設備，加上未收集但不是主機的設備）；`network − networkCollected` 等於 C01 的筆數。
  - `hosts`：不在收集範圍的主機（只由鄰居或 ARP 得知），`network + hosts = devices`。
  - `missing`：已收集、但缺少必要資料或有收集失敗的台數，等於 C02 的筆數。
- `Q.pendingSummary(isPending)`：「待處理」的唯一數字來源（凍結）`{ error, warn, info, total, handled }`。`isPending(f)` 判斷一筆 finding 是否仍待處理（畫面傳入以 `S.ledger.isPending` 判斷處理紀錄狀態的函式；省略時全部算待處理），不是函式時丟出 TypeError；不認得的嚴重度丟出 RangeError。
  - `error`、`warn`、`info`：各嚴重度仍待處理的筆數。
  - `total`＝`error`＋`warn`：步驟列「研判」、基準狀態卡與「驗證」改善趨勢所說的「待處理」，不含提醒。
  - `handled`：已處理的錯誤與警告筆數；提醒不算進 `total` 與 `handled`。
- `Q.ruleStatus()`：每項檢查的結果 `{ id, severity, cat, title, hint, count, missing, status }`，`status` 是 `found`（有發現）、`pass`（需要的資料有收到且沒有發現）或 `nodata`（需要的資料沒有任何已收集設備提供），`missing` 是缺少的資料組；`hint` 同 `S.query.rule(id).hint`。依檢查代碼排序。
- `Q.findings()`：全部 finding，依 Snapshot 的順序；陣列位置就是 idx。`Q.finding(idx)`：第 idx 筆，不是有效索引時為 null。
- `Q.findingIndexesByKey(key)`：findingKey 等於 key 的 idx，由小到大；findingKey 可能碰撞，所以是陣列，沒有時為空陣列。`Q.findingIndexByKey(key)`：第一筆的 idx（碰撞時取 Snapshot 順序的第一筆），沒有時為 -1。
- `Q.findingsByRule(id)`：某項檢查（例如 `'C01'`）的 finding，依 Snapshot 的順序；沒有時為空陣列。
- `Q.deviationsOf(devKey)`：這台設備被多數決判定與多數不同（列在 `finding.deviation.deviating`，推論）的 finding 索引，依 Snapshot 的順序；沒有時為空陣列。與多數不同的設備不一定是那筆 finding 的實體，所以另建索引，不併入 `Q.findingsFor`。
- `Q.blocksOf(devKey)`：屬於某設備的輸入區塊（`blocks[].devKey`），依輸入順序；沒有時為空陣列。`Q.block(id)`：一個區塊，沒有時為 null。`Q.blockAt(file, line)`：包含 file 第 line 行的區塊（同 `Q.block` 的物件），不在任何區塊內（例如設備標頭、註解行）或沒有這個檔案時為 null。
- `findingIndexesByKey`、`findingsByRule`、`deviationsOf`、`blocksOf` 與 `coverageOf` 的索引，以及 `coverageSummary`、`vlanSummary` 的結果，在第一次呼叫時才建立（1000 台規模下多數畫面用不到）；回傳的陣列凍結。

## 7. 不需要 Snapshot 的靜態查詢

`S.query.*`（[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）：

- `S.query.rule(id)`：一項檢查的目錄資料（凍結）`{ id, severity, cat, title, data?, evidenceLimit?, facet?, causes, action, hint }`；不認得的 id 為 null。`causes`／`action`／`hint` 只經 `S.report.advice` 使用（`src/report/report.js`；畫面是 `V.remediation.advice`，匯出的報表也用它，見[畫面架構 §5](畫面架構.md#5-各面板的資料來源)）。
  - `hint` 是處理提示：`action` 的第一句（到第一個「。」，含句號），沒有 `action` 時為 null。`CATALOG` 不另存一份；[基準檢查](基準檢查.md)每項檢查「處理」的第一句必須和它相同（`tests/docs.js`）。
- `S.query.rules()`：所有檢查（凍結的陣列），依 `CATALOG` 的宣告順序（匯出的附錄依這個順序）。
- `S.query.preflightRecognized(pre)`：建立前的預檢（`S.preflight` 的結果）中認到的設備（`pre.devices` 的子集合，順序相同）；和 `Q.recognizedDevices()` 同一個判斷（有至少一類 `dataTypes` 或 `failures` 大於 0）。輸入畫面的「認到 N 台設備」與是否允許建立都用它。
- `S.query.dataLabel(t)`：資料類別（設備的 `data`、coverage 的 `data`／`missing`、收集失敗的 `dataTypes`）的顯示名稱；不認得時原樣回傳。
- `S.query.boundaryLabel(kind)`（3.8.0）：對外邊界證據種類（`boundaries[].evidence[].kind`）的顯示名稱，例如 `default-route` 是「預設路由的出介面」；和檢查訊息用同一份（`S.infer.BOUNDARY_LABEL`）。不認得的種類為 null。
- `S.query.adapterLabel(id)`：解析器（`meta.adapters`、`blocks[].adapters` 的 adapter id）的顯示名稱；不認得時原樣回傳。
- `S.query.mgmtDefaults()`：管理面設定的出廠預設值表（凍結的 `S.MGMT_DEFAULTS`）：各項的預設值、適用版本 `routerOS`（線上手冊 7.24–7.26，顯示用的文字）、`versions`（`{ text: '7.24–7.26', from: [7, 24], to: [7, 26] }`，含兩端；設備版本在範圍外時不用這張表推定）與手冊網址 `manual`。畫面說明「預設（未在 export 中）」時用它。
- `S.query.metaOf(json)`：還沒建立查詢介面的 Snapshot JSON（瀏覽器儲存或使用者匯入的檔案）的 `meta`；不是物件或沒有 `meta` 物件時為 null。用來先判斷 schema／版本是否相容，再決定要 `S.query` 還是重建。
- 檢查目錄是**目前程式**的目錄，不是建立那份基準時的目錄（[ADR-006](架構決策/006-規則目錄與判斷分開.md)），所以放在 `S.query` 而不是 Q。`S.query.findingKey`、`S.query.findingBaseKey` 也在這裡。
- `S.util.fmtVlans(ids)`：VLAN 清單的精簡文字，例如 `[10, 11, 12, 20]` → `"10-12,20"`（輸入要先由小到大排序，例如 `S.util.ifcVlans` 的結果）。核心訊息與畫面共用；`S.check.fmtVlans` 指向同一個函式。
- 命名規則對基準的套用結果 `S.profile.coverage(json, Q)` 與說明 `S.profile.describe(json)` 不是查詢函式（屬於命名規則模組，只讀 Q），參數與回傳見[設計說明第 6 節](設計說明.md#6-命名規則profile)。

## 8. 選取鍵與唯讀政策

依 [ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)：

- **選取鍵**：同一份基準內，finding 以 idx 指定（`Q.finding(idx)`）。idx 只在同一份 Snapshot 內有效；跨基準（處理紀錄、新舊比對、修正計畫）用 findingKey，再以 `Q.findingIndexByKey`／`findingIndexesByKey` 換回 idx。不直接用 findingKey 當選取鍵，因為它可能碰撞。
- **唯讀**：Snapshot 本身靠約定唯讀，`S.query` 不複製也不凍結它。Q 的衍生索引（上面的凍結陣列）與檢查目錄（`CATALOG`、`DATA_LABEL`、`S.query.rule`／`rules`）凍結，呼叫端改不壞。畫面不改寫基準由冒煙測試以深層凍結的基準確認（[開發指南 §3](開發指南.md#3-測試)）。
