# 畫面架構（檢視層）

這份文件寫檢視層（`src/view/`、`assets/app.css`、`index.html`）的架構與資料的去向：狀態放在哪裡、資料從哪個查詢函式來、哪些東西不進基準。

- 核心（輸入、模型與推論、檢查、比對、修正 patch、處理紀錄、工作包）見[設計說明](設計說明.md)；畫面用到的查詢函式見[查詢介面](查詢介面.md)。
- 畫面怎麼操作只寫在[使用說明](使用說明.md)，這裡不重複；約 1000 台時的耗時見[設計說明 §12「規模」](設計說明.md#12-規模)。
- 本文件原本是設計說明 §11，內容沒有改變，只重新分節（[ADR-020](架構決策/020-設計說明拆出畫面架構與查詢介面.md)）。

## 1. 邊界與本輪的資料

檢視層是 `src/view/` 底下的一般 `<script>`，在 `index.html` 中排在核心、命名規則、嵌入的範例與收集指令（`samples/collect-commands.js`）之後載入。

- **只讀基準**：畫面只透過 `SSOT.query(snapshot)`（Q）與 `S.query.*` 的靜態查詢（[查詢介面](查詢介面.md)）讀取 Snapshot 與檢查目錄，不讀 Snapshot 的欄位、不讀內部模型 M，也不改寫 Snapshot（[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）。比對、修正計畫與處理紀錄的結果都由核心（`S.compare`、`S.remediate`、`S.ledger`）產生，畫面只負責選取、排版與下載。
  - **允許使用的 `S.*` 成員**以 `tests/ui/boundary.js` 的邊界掃描（`VIEW_S_ALLOW`、`VIEW_S_ONLY`）為準，目前是：查詢 `query`、`trace`、`util`、`keys`；常數 `VERSION`、`SCHEMA`、`LINK_SCOPE`、`KIND_LABEL`；輸入 API `build`、`buildAsync`、`inputHashOf`、`preflight`（建立前的預檢，[設計說明 第 4 節](設計說明.md#4-輸入)）、`profiles`、`samples`、`collectCommands`（收集指令清單），以及只允許一個成員的 `S.readers.PASTE`、`S.profile.compile`；下游 `compare`、`remediate`、`ledger`、`workpack`、`zip`、`report`（[ADR-021](架構決策/021-報表與網路文件移到核心S.report.md)）；畫面自己的 `view`、`store`。
  - 禁止的寫法：`S.check.*`（改用 `S.query.rule`／`rules`／`dataLabel`、`S.util.fmtVlans`）、`S.adapters`（改用 `S.query.adapterLabel`）、計算的成員名稱 `S[…]`、從 `S` 解構，以及讀 `snap.`／`snapshot.` 的欄位（`findings`、`meta`、`coverage`、`blocks`、`model` 等，改用 Q 的函式；還沒建立 Q 的 JSON 用 `S.query.metaOf`）與 `Q.snapshot`。
  - 畫面需要新的資料時，由 data-model 新增查詢函式，畫面不繞過。
- **收集指令的唯一來源**：每台設備要收集的指令只定義在 `tools/collector-commands.sh`。`tools/embed-sample.js`（`npm run sample` 也會執行）把它轉成 `samples/collect-commands.js`（`S.collectCommands`：`default`、`optional` 兩組 `{ id, command }`），設定的「收集與建立基準」直接列出（整個畫面只在這裡出現一次，歡迎畫面以按鈕開啟這個分類），畫面不另寫一份。沒有重新產生時核心測試會失敗（`tests/core/generated.js`），每個指令也要有解析器認得。
- **建立前的預檢**（`src/view/app-input.js`）：輸入對話框以 `S.preflight` 顯示認到的設備與無法辨識的段落（[設計說明 第 4 節](設計說明.md#4-輸入)）。打字停下 400 ms 才重算（約 1000 台的預檢約需數百毫秒），選檔、載入範例與換命名規則時立即重算；建立前若輸入在預檢後被改過（例如程式直接寫入文字框）會再預檢一次。0 台設備時停用「建立基準」；預檢本身丟出錯誤時不擋建立，由建立回報同樣的錯誤。清單最多列 200 筆。剪貼簿不可用時明說，請使用者手動選取，不靜默失敗。
  - 建立失敗、命名規則檔載入失敗與預檢的錯誤，都轉成中文原因，寫在對話框的狀態列（`#input-status`，`role="status"`），不用 `alert`：訊息本來是中文（核心與命名規則丟出的錯誤）時原樣使用，`SyntaxError` 說明不是有效的 JSON，其他（程式錯誤）改用中文說明並附原訊息。
- **本輪的資料集中在 `App.round`**（`src/view/app.js`）：`{ sources, profile, expectedData, snapshot, Q, expected: { name, data, error }, origin: { kind, name?, createdAt? }, get ledger() }`。
  - `sources` 是收集檔 `[{ name, text }]`（順序決定 inputHash）；`profile` 是建立基準時用的命名規則；`expectedData` 是 `S.build` 的建立選項（畫面稱「各類設備應收資料」，目前只會由工作包帶入）；`snapshot`、`Q` 是基準與它的查詢介面。
  - `expected` 是比對用的預期資料（畫面稱「預期現況」；`ssot-expected/1`；無法解析時 `data` 為 null、`error` 寫原因），沒有時為 null。
  - `origin` 是這份基準怎麼來的：`kind` 為 `build`、`restore` 或 `workpack`，由工作包帶回時另有工作包的檔名與建立時間。
  - `ledger` 是唯讀的 getter，讀的是 `src/view/app-ledger.js` 的狀態（處理紀錄停用時為 null）；處理紀錄的停用、轉換與寫入 store 仍由 app-ledger.js 管理。
  - 只能經 `A.load(snap, positions, inputs)`（換基準，可以同時換輸入，不會出現基準換了、收集檔還是舊的中間狀態）、`A.setRoundInputs(inputs)`（只換輸入）與 `A.clearRound()`（「清除」）改變。`App.snap`、`App.Q`、`App.sources`、`App.profileJson` 改為它的唯讀存取器，直接指定在嚴格模式下會丟錯。
  - 選取、展開、版面、縮放與位置是檢視狀態，不放在 `App.round`。上一輪的基準（新舊基準比對的舊基準）也不在這裡，仍在 `src/view/panels/baseline-diff.js` 的記憶體中，因為它在工作包沒有角色。

## 2. 流程步驟、頁首與抽屜

- **流程步驟與中間的工作畫面**（`src/view/app-panes.js`，版面重整 3）：頁首的流程步驟（輸入、檢視、研判、修正、驗證）取代原本的左側五個分頁與中間四個分頁。每一步同時決定左側清單與中間的工作畫面；右側的詳細資料不變。

  | 步驟 | 左側 | 中間 |
  |---|---|---|
  | 輸入（`input`） | —（資料中心蓋住主畫面） | 資料中心：本輪的輸入、覆蓋率與輸出 |
  | 檢視（`view`） | 清單（`#pane-inventory`：設備、介面、IP、網段、MAC、VLAN） | 拓樸圖 |
  | 研判（`triage`，預設） | 檢查結果（`#pane-findings`） | 拓樸圖 |
  | 修正（`fix`） | 沒有，中間全寬 | 修正計畫（`#view-patch`，「要修正哪些」在它自己的左欄） |
  | 驗證（`verify`） | 沒有，中間全寬 | 驗證（`#view-verify`）：本輪變化 `#round-body`、處理紀錄 `#ledger-body`、修正追蹤 `#tracking-body`、改善趨勢 `#trend-body`、比對 `#compare-body` |

  - **狀態**：`App.step` 是主畫面那一步（「檢視」到「驗證」，預設「研判」）；資料中心開著時目前的一步是「輸入」（`A.currentStep()`），關閉後回到 `App.step`。`App.centerView` 是中間的工作畫面：`graph`、`patch` 或 `verify`。步驟與工作畫面都是檢視狀態，不存進 store；store 的鍵沒有變。
  - **切換**：`App.showStep(step, { focus, scroll, workspace, opener, section })`。「輸入」開啟資料中心（`section` 是要捲到的區塊，`opener` 是開啟它的按鈕）；其他步驟先關閉資料中心再切換。`focus` 為 true 時焦點移到這一步的標題（「檢視」、「研判」是左側清單的標題 `#left-title`，「修正」、「驗證」是工作畫面的標題）；為字串時移到「驗證」的區塊（`round`、`ledger`、`tracking`、`trend`、`compare`）或 `graph`（畫布）；省略時焦點不動。`scroll` 只捲到同樣的目標、不移焦點。`workspace` 是窄螢幕要顯示的工作區，預設有左側清單時先看清單，否則看工作畫面。
  - **其他模組的入口**：`App.showView(view, { focus })` 換成對應的一步：`graph` 是「在圖上定位」（目前不在拓樸圖時，回到上一次看圖的「檢視」或「研判」），`patch` 是「修正」，`verify` 是「驗證」，`compare`、`trend` 是「驗證」並捲到那個區塊。搜尋與路由追蹤用它回到拓樸圖。
  - **步驟列**（`A.renderSteps`）：`<nav>` 中的按鈕，目前的一步是 `aria-current="step"`。每一步寫出狀態文字（「輸入」已收集台數、「檢視」拓樸圖的層級、「研判」待處理筆數、「修正」已選項目、「驗證」處理紀錄的第幾輪與復發數），不只靠顏色。沒有基準時停用的步驟寫「建立基準後」；窄螢幕（`A.isNarrowScreen`，重繪步驟列時判斷）五格等寬，改寫「—」，完整說法在按鈕的 `title`。沒有基準時「修正」、「驗證」以 `aria-disabled` 停用（仍可聚焦與朗讀原因），點了以提示列說明；停在「修正」、「驗證」時清除基準會回到「研判」（`A.syncSteps`）。
  - **工作畫面的疊放**：「修正」、「驗證」疊在 `#stage` 上的拓樸圖（`#view-graph`）上面，同一格：畫布的大小不變，切換時不重新排列，位置、縮放與選取都保留，PNG 照常匯出。拓樸圖被蓋住時設為 `inert`。「修正」、「驗證」沒有左側清單，左欄寬度為 0（記住的寬度不變）。只重繪目前顯示的工作畫面（`A.renderCenter`）。
  - **點選**：在「修正」、「驗證」點選檢查結果或比對的項目時，步驟不切換，詳情在右側顯示；圖的選取也更新。
  - **層級切換**仍在拓樸圖的工具列，「檢視」和「研判」都看得到；「檢視」的步驟狀態寫出目前的層級。
  - **窄螢幕**：三個工作區依流程排列（左側清單 → 中間的工作畫面 → 詳細資料），標籤跟著目前的一步（`A.syncWorkspaces`）；「修正」、「驗證」沒有清單工作區。圖的上方只有兩列（`assets/app.css`，純 CSS）：頁首只留流程步驟（品牌名稱只給螢幕閱讀器，「資料中心」按鈕隱藏，因為它和「輸入」是同一個畫面）；搜尋與 ⚙（設定）以絕對定位放在工作區列的右端，搜尋框平常縮成圖示，聚焦時展開蓋住這一列。資料中心或設定開著時（`#app.hub-open`／`.settings-open`）兩者隱藏，由畫面上的「回到…」「關閉」離開。
  - **觸控的說法**：操作提示（`#hint`）與歡迎畫面的步驟各有滑鼠與觸控兩份文字（`.for-mouse`／`.for-touch`），依 `pointer: coarse` 顯示其中一份。
  - **資料中心就是「輸入」**：它是蓋住整個主畫面的另一層，有自己的 `inert`、Esc 與焦點規則（見[第 5 節](#5-各面板的資料來源)「資料中心」）。設定（⚙）是同一種另一層，和資料中心互斥（見下方「設定畫面」）。
- **頁首、選單與通知**（`src/view/app-toolbar.js`、`src/view/app.js`）：
  - 頁首只有流程步驟、搜尋、資料中心與 ⚙（`#btn-settings`，開啟設定畫面，不是下拉選單）；原本的「⋯」選單拿掉了：配色、清除基準與程式版本移到設定，路由追蹤與匯出 PNG 移到拓樸圖的工具列。原本的基準摘要列（`#baseline-summary`）與頁尾（`#footer`）拿掉了，摘要改在右側的基準狀態卡（見下方「基準狀態卡」）。
  - 下拉選單（工具列的「版面 ▾」「顯示 ▾」）共用 `A.bindMenu(btn, menu, place)`：按鈕有 `aria-haspopup`、`aria-expanded`；項目是 `menuitem`、`menuitemradio`（版面模式）或 `menuitemcheckbox`（力導向、主機、終端、分群，`A.setChecked` 同時改 `aria-checked` 與 class `on`）。有 `data-keep` 的項目按了不關閉。`A.closeMenus()` 關閉全部，切換層級、開啟路由追蹤、開啟設定與清除基準時呼叫。工具列的選單與路由追蹤表單放在 `.grp` 外面（`.grp` 會裁切），開啟時以 `placeUnder` 對齊按鈕，放不下時往左移。
  - 版面模式（`App.LAYOUT_MODES`：`elk`、`builtin`）只經 `A.setLayoutMode(mode)` 改變：存進 store 的 `'layoutMode'`，同步「版面 ▾」的勾選與設定「一般」的單選，不重新排列；「版面 ▾」選了之後另外按一次「重新排列」。工具列的選擇就是預設版面，沒有另一個「只這次」的值。
  - 工具列的右端是「路由追蹤…」（`#btn-trace`，`aria-haspopup="dialog"`，每一層都顯示）與「匯出 PNG」（`#btn-png`，`layer-only`，L4 隱藏）；`#btn-trace`、`#btn-png` 的 id 與行為沿用，沒有基準時由 `A.renderAll` 停用。
  - 路由追蹤是「路由追蹤…」下方的小對話框（`#trace-pop`，`role="dialog"`，在 `#toolbar` 裡）；按鈕再按一次關閉，Esc 或點外面關閉後焦點回到按鈕（`A.closeTrace`），開啟時 `A.placeTrace` 對齊按鈕並設 `aria-expanded`。`App.openTrace` 在中間不是拓樸圖（「修正」「驗證」）或窄螢幕不在拓樸圖工作區時，先 `App.showView('graph')`，表單才看得到。來源與目的的輸入框共用 `#trace-ips` 的 datalist，選項是 `Q.ipEntries()` 的每個位址（多個 VRF 只列一次並註明 VRF），換基準時才重建。「⇅ 對調」（`#trace-swap`）只交換兩個輸入框的值，不自動追蹤，焦點留在按鈕。說明文字寫「等價多路徑」，畫面不寫 ECMP（有測試）。
  - 通知（`A.banner`）在圖的下方中央，`role="status"`；給了 `ms` 時淡出。`A.banner` 回傳這則通知的 token；沒有 `ms` 的通知（設備圖的「分層版面計算中…」）由發出者在工作取消或結束時以 `A.bannerClear(token)` 收起，已換成別的通知時 token 不同、不會收掉別人的。設備圖的分層版面被取消（改快速版面、換基準、清除）時由 `A.cancelElk()` 遞增 `App.layoutToken` 並收起「計算中」，通知才不會一直被當遮擋物。
  - **Esc 一次只關最上層**：頁面層級的 Esc 只有一個 document 監聽（`app.js` 的 `bindEscape`），各層以 `A.onEscape(層, fn)` 登記，`fn` 處理了就回傳 `true`；依 `ESC_ORDER`（選單 → 路由追蹤 → 資料中心 → 設定 → 抽屜）只交給第一個處理的層，不依各 `bind*` 的註冊先後。元素自己的 Esc（輸入框、VLAN 標示、畫布、原生對話框）在元素上處理並停止傳遞。操作提示（`#hint`，`A.syncHint`）只在有基準、看的是拓樸圖時顯示，同一次開啟頁面只出現一次，約 6 秒後淡出。
- **窄螢幕的詳情抽屜**（`src/view/app-panes.js`）：窄螢幕在拓樸圖（工作畫面工作區）選取時，`#right` 以底部抽屜疊在圖上，圖仍可操作；內容仍是同一個 `#detail`。
  - 狀態是檢視狀態，存在 `#main[data-sheet]`（`half`／`full`），不進 store。`#right` 是 `role="region"`、不鎖焦點；`#sheet-bar` 有把手、標題、展開與收起。
  - `App.select` 呼叫 `A.openSheetFor()`：窄螢幕、中間是拓樸圖、而且不在「詳細資料」工作區時，切到工作畫面並開抽屜（已開時維持高度）；從清單工作區來時焦點移到抽屜標題。其他情況照原本切到「詳細資料」工作區。`A.closeSheet()` 在取消選取、換基準、清除、切到其他工作區或中間不是拓樸圖時呼叫；焦點在抽屜內時移到「工作畫面」工作區按鈕。
  - 拖曳把手放開時，高度低於 `closeBelow`（`#main` 的 20%）收起、高於 `fullAbove`（65%）展開成全高，其餘回到半高；移動不到 `tapPx` 算點一下（三者是 `app-panes.js` 模組內的常數 `SHEET`，不掛在 `A` 上）。拖曳完緊接著的 click 不算點一下，下一輪就清掉，之後用鍵盤按把手照常切換。Esc 最後才輪到抽屜（`A.onEscape` 的 `ESC_ORDER`）：選單、路由追蹤、資料中心、設定處理過的 Esc 不會再收抽屜；輸入框、對話框與搜尋選單裡的 Esc 也不收。
  - 抽屜、工具列與通知以 `GraphView.setOccluders` 登記（抽屜、工具列與通知的 `max` 是 `V.GraphView.LIMITS.OCCLUDER.pinned`，全高的抽屜超過它就不計），全圖、聚焦與 `reveal` 讓開它們（見[第 7 節](#7-拓樸版面)「畫布」）。

## 3. 樣式、儲存與檢視狀態

- **樣式的唯一來源**：顏色、線型、透明度與 Canvas 字型都定義在 `src/view/theme.js`（[第 6 節](#6-樣式theme)）。
- **儲存集中在 `src/view/store.js`**：IndexedDB 資料庫 `topo-mikrotik` 的 `kv`；無法使用 IndexedDB 時退回記憶體，畫面會提示。存了哪些鍵、中文名稱、用途、清除時會失去什麼，只定義在 `S.store.KEYS`（每一項 `{ key, label, purpose, loss, kind: 'data'|'pref', where: 'indexedDB'|'localStorage', critical?, check(v) }`；`critical` 是無法從收集檔重建的資料，`check` 是還原備份時的格式檢查）。設定「本機資料」的清單、清除與備份都依它，冒煙測試掃描 `src/view` 以字面值存取的鍵都在 `KEYS` 裡。使用的鍵：
  - `last`：最後一次的基準、輸入（收集檔、命名規則、`expectedData`）與節點位置，由 `A.saveLast` 從 `App.round` 寫入；「清除基準」只刪這個鍵。
  - `ledger`：處理紀錄（`critical`；舊版的 `acks` 轉換後刪除，見[第 5 節](#5-各面板的資料來源)）。
  - `layout`、`layoutMode`：左右欄寬度與版面模式（`pref`）。
  - `profiles`：使用者載入的命名規則。
  - `meta:updatedAt`：store 自己記錄的各鍵最後更新時間（`set`／`del` 在同一筆交易裡更新）；不是資料，不出現在 `keys()`、`inventory()` 與備份。舊版寫入的鍵沒有時間。
  - **函式**：既有的 `get`／`set`／`del`／`available` 語意不變。另有 `keys()`（存著的資料鍵，排序，不含 meta）、`sizeOf(v)`（JSON 序列化後的 UTF-8 位元組數）、`inventory()`（`{ storage: 'indexedDB'|'memory', themeStorage: 'localStorage'|'memory', items }`，`items` 先依 `KEYS` 的順序列出每一項（沒有資料的 `present` 為 false），再列不認得的鍵（`kind: 'other'`），每一項有 `bytes`、`updatedAt`）、`clear(k)`（`'theme'` 改呼叫 `theme.clear()`；不認得的鍵也可以清）、`resetPrefs()`（只清 `pref` 的鍵，回傳清了哪些）。
  - **備份 `ssot-localdata/1`**（`S.store.BACKUP_SCHEMA`，畫面層的格式，不進核心）：`exportAll(now)` 回傳 `{ schema, version: S.VERSION, exportedAt: now, items: { 鍵: 值 } }`，含 `KEYS` 中存著的鍵（含配色，不含不認得的鍵）；時間由呼叫端傳入。`validateBackup(obj, extra)` 回傳 `{ ok, errors, keys }`，檢查 schema、`items`、不認得的鍵與每個鍵的 `check`（處理紀錄用 `S.ledger.validate`），`extra` 是呼叫端另外的檢查（畫面用它確認版面名稱在 `App.LAYOUT_MODES` 內）。`restore(obj, extra)` **全有或全無**：不合法時回傳 `{ ok: false, errors }`、一筆都不寫；合法時 IndexedDB 的鍵在同一筆交易寫回（中途失敗時整筆不寫入並丟出錯誤），之後才寫配色，回傳 `{ ok: true, keys, warnings }`。備份裡沒有的鍵不動。基準（'last'）能不能還原只由 `S.store.lastRestorable(v)` 判斷（`{ ok, reason, meta, rebuild }`），備份檢查與 `App.restore`（回傳 `{ loaded, reason }`）、`A.savePositions` 共用；無法載入時以 `A.resetBaselineView()` 收起畫面上的基準並以通知說明。`S.store.revision()` 在本頁寫入後加一，本機資料分類依它快取各鍵的大小。還原或清除後 `V.settings.profiles.syncSaved()` 讓 `S.profiles` 跟上 store，`A.resetPendingAcks()` 清掉記憶體中待轉換的舊確認標記。
  - 例外：配色偏好（`S.store.theme`，`system`／`light`／`dark`）放在 localStorage 的 `topo-mikrotik:theme`。首次繪製前就要知道深淺，IndexedDB 是非同步的，等它讀回來畫面已經以系統的深淺畫過一次；這是很小的顯示偏好，不是基準或處理紀錄。鍵與合法值只定義在 store.js；讀到不合法的值時忽略（不改寫）、以 `console.warn` 告知並退回跟隨系統，寫入不合法的值丟 `RangeError`；localStorage 無法使用時記在記憶體（這次有效）並以通知說明不會保留。`S.store.theme.clear()` 刪除偏好，回到跟隨系統。
- **檢視狀態不進基準**：畫布上的節點位置、選取、展開、縮放、篩選、修正計畫的選取與新舊比對的結果，都不寫回 Snapshot。
  - 設備圖的節點位置（`'last'.positions`）與 `'layout'` 的格式都不變。L2 埠圖與 L3 網段圖的位置與縮放**只放在記憶體**（`App.layers`），不另外佔 store 的鍵：這兩層可以由 ELK 重新算出來，而且埠的 id 會隨聚合收合與焦點改變，存起來還要處理失效。
- **版面引擎**：內建版面與分層版面（ELK）共用 `src/view/graph/layout.js` 的分群與分層，見[第 7 節](#7-拓樸版面)。

## 4. 拓樸圖的層級與 L4

- **拓樸圖的層級**（`src/view/app-layers.js`，M1）：設備圖、L2 埠圖（`Q.portGraph`）、L3 網段圖（`Q.subnetGraph`）共用同一張畫布 `App.graph`，切換時換掉圖資料；L4 可達性（M2）也是工具列的一層，但不是畫布，見下方「L4 可達性」。app-layers.js 負責層級切換、VLAN 篩選，以及 L2／L3 的圖資料、版面與標示；設備圖的資料仍在 app-graph.js。
  - **狀態**（都是檢視狀態，不寫進基準）：`App.layer`（`device`／`l2`／`l3`／`l4`）；`App.devicePos`（設備圖的位置，存進 store 的 `'last'`）；`App.layers`（L2／L3 的圖資料、位置與縮放，鍵是「層級＋選項」，例如 L2 的聚合收合、全部的埠、範圍與焦點；換基準或清除時清空）；`App.layerJob`（L2／L3 背景版面的工作，測試可以等待）；`App.vlanFilter`（`{ id, domain, pinned }`，VLAN 篩選；`pinned` 是在工具列的 VLAN 選單選的）；`App.L2_MAX`（300）。
  - **L2 的選項**：`#btn-l2-lag`、`#btn-l2-ports` 在 `A.bindLayers` 時移進「顯示 ▾」（`#view-menu`），成為 `data-layers="l2"` 的勾選項目（`menuitemcheckbox`、`data-keep`，狀態以 `A.setChecked` 寫 `aria-checked`）；範圍選單留在工具列。`A.showLayer` 只在層級改變時收起選單，同一層重畫（切換這兩個選項）時選單不關。
  - **疊在圖上的說明**：圖例展開時 `#legend` 加上 `open`，CSS 以 `.legend.open ~ .hint` 讓操作提示讓位；圖例最高 `min(55%, 100% - 130px)`，內容在框內捲動。層級說明 `#layer-note` 放在圖例按鈕（`--control-h`）上方，最高 30%，太長時捲動。
  - 切換層級（`App.showLayer`）時，各層的平移與縮放分開保存、不互相覆蓋；選取保留，在新的一層重新標示。只有設備圖拖曳後的位置寫進 store。
  - **VLAN 篩選**：`App.vlanFilter` 在每一層都持續標示；選 VLAN 時也會設為篩選。在 VLAN 選單選的（`pinned`）保留到取消；由檢查結果、搜尋或詳情的連結選 VLAN 順帶設的不是使用者主動要的，`App.select` 選其他東西時一起取消，否則之後選的設備看起來像帶著自己的 VLAN 標示。基準中沒有的 VLAN（`Q.vlanIds()` 沒有，例如搜尋到「基準中沒有這個 VLAN」）只開詳情，不設成篩選：選單沒有這個選項，圖上也沒有可標的。只有由選取帶入的篩選（沒有 `pinned`）工具列才有 `#vlan-chip`（「VLAN n ✕」，L4 不顯示）；選單選的由選單本身標示、用選單的「不篩選」取消，不並排第二個標示。`#vlan-chip` 由 `A.syncLayerUi` 一起同步；按它或在它上面按 Esc 呼叫 `A.clearVlanFilter()`：選取的是 VLAN 時一起取消選取，否則保留選取、只重新標示，焦點移到 VLAN 選單。標示來自 `Q.vlanCarriers`（`A.vlanMarks`）：設備圖標在設備對的線上，L2 標在埠對埠的邊上，同一條線有多條鏈路時取最需要注意的狀態（只有一端帶 > 承載 > 推論承載 > 只有一端可確認）；L3 標出屬於這個 VLAN 的網段。換基準時（`A.resetLayers`），由選取帶入的篩選隨選取一起清掉；選單選的在新的基準沒有這個 VLAN 時取消。VLAN 選單只顯示釘選的篩選：由選取帶入的篩選時選單維持「不篩選」，使用者在選單選這個 VLAN 時值才會改變、觸發 `change` 而改為釘選。
  - **換基準與清除的選取**：`A.load` 與「清除」在新的圖資料換上畫布後呼叫 `A.resetSelection()`：`App.sel` 清空，畫布的選取環、高亮、疊加與與多數不同的外圈一起清掉，抽屜收起；釘選的 VLAN 篩選由 `App.select(null, { refresh: true })` 依新的基準重新標示。
  - **L2 的大型資料**：埠讓 ELK 的計算量比設備圖大很多，所以 `App.L2_MAX`（300 台）低於 `App.ELK_MAX`。超過時只畫焦點設備與它的鄰居，並停用「整張圖」。焦點是選取的設備；沒有選取時，取鏈路最多的路由器、防火牆或交換器。選了不在圖上的設備時，改以那一台為中心重畫（`A.recenterL2`）。
  - **L3 與 VRF**（M3，[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）：L3 的設備節點 id 是 `Q.subnetGraph` 的 `n.id`（設備鍵，main 以外是「設備鍵@VRF」，`K.inVrf`），節點另存 `dev`（設備鍵）與 `vrf`；路由的箭頭從路由表所在的節點（`r.node`）出發。基準中用到的 VRF（依 `Q.vrfs()` 的順序，main 在最前）有兩個以上時，分群改依 VRF（群名是 `V.vrfText`），不再沿用設備圖的分群；只有 main 時分群與加入 VRF 之前相同。main 以外的節點標籤寫「名稱（VRF）」，只改顯示，id 仍是 `K.inVrf` 的鍵。`index.nodesOfDev` 是設備鍵 → 這台設備在圖上的節點（每個 VRF 一個），選取設備、檢查結果的實體與路由追蹤的標示都經由它找節點；介面與 IP 用 `nodeAt(設備, vrf)` 取它所屬 VRF 的節點。`info` 另有 `vrfs`、`byVrf` 與 `omitted.policyRoutes`（沒畫的策略路由路由數，來自 `Q.subnetGraph` 的 `omitted`）。路由追蹤在 L3 依每一跳與下一跳的 VRF 連到對應的節點；L2 與設備圖仍用 `t.edges`。
  - **IP 的選取**：`{ type: 'ip', key, vrf }`，由 `V.ipSel(key, vrf)` 產生（`src/view/dom.js`）。`vrf` 為 null 代表不分 VRF（搜尋、沒有 `@` 的比對項目：詳情列出所有 VRF，在多個 VRF 時請使用者選擇）；省略 `vrf` 時從位址鍵（`K.splitVrf`，例如檢查結果的實體）取出，沒有 `@` 就是 main。詳情以 `Q.findIp(ip, vrf)` 查詢；`vrf` 不在目前的基準中（換了基準）時改為不分 VRF 並說明。
  - **只用 main 時畫面不變**：VRF 的選單、欄位、框與標示都以 `Q.vrfs().length > 1`（或 zone 矩陣的 `vrfs`、這台設備的 VRF 設定）判斷，只有 main 時不出現，有冒煙測試（「只有 main 的網路：…」）。
  - **VRF 相關的共用定義**（`src/view/dom.js`）：`V.fillVrfSelect(select, vrfs, value)`（路由追蹤與 L4 共用的 VRF 選單：第一個選項「依來源位址決定」的值是空字串，不傳 vrf，由查詢層依來源決定；`value` 不在清單中時回到第一個選項）、`V.vrfText`、`V.TRACE_END`（`S.trace` 的結束狀態文字，含 `policy`、`policy-drop`）、`V.IFC_VRF_BASIS`（`interfaces[].vrfBasis` 的文字；`V.IFC_VRF_INFERRED` 列出推論的依據，目前是 `export`）、`V.NH_VRF_BASIS`（`routes[].nh[].vrfBasis` 的文字）。可達性的原因代碼 `policy-routing`、`policy-drop` 加進 `V.REACH_REASON`。
  - **路由追蹤的 VRF**（`src/view/app-select.js`）：`App.openTrace(src, dst, vrf)` 的 `vrf` 是預先選好的 VRF，省略時保留選單目前的值；`A.syncTraceVrf(value)` 依 `Q.vrfs()` 決定選單顯示與否並填入選項。`S.trace` 回傳 `{ ok: false, vrfs }`（來源在多個 VRF）時，畫面不猜，留著視窗並在 `#trace-msg` 請使用者選擇。回程的 VRF：去程抵達（`reached`）的 VRF 只有一個時用它，否則用選單選的。選取是 `{ type: 'trace', result, reverse, vrf }`，`vrf` 是使用者指定的（沒指定時為 null）。
- **L4 可達性**（`src/view/panels/l4.js`，M2）：zone 矩陣、每一格的明細（位址組、牽涉的規則、逐跳路徑）與可達性查詢。資料全部來自查詢層（`Q.zoneMatrixSteps`、`Q.zoneMatrix`、`Q.zoneCell`、`Q.reach`、`Q.zones`，以及 `S.query.l4Services`、`reachAssumptions`、`reachReasonCodes`；[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)），畫面不自己判斷規則或路由。操作見[使用說明「檢視」](使用說明.md#step-view)。
  - **疊在畫布上**：L4 的內容在 `#view-l4`，選了 L4 時疊在畫布上、工具列下面（層級切換仍在工具列，Tab 順序在矩陣之前）。`App.showLayer('l4')` 不換畫布的資料、不記縮放；畫布設為 `inert`，圖例與操作說明不顯示，回到其他層級時照原樣還原。只對畫布有用的工具列群組（VLAN 篩選、全圖、「版面 ▾」「顯示 ▾」）在 L4 隱藏；工具列的「匯出 PNG」也在 L4 隱藏（從資料中心按時以提示列說明），「路由追蹤…」照常顯示。
  - **入口與介面**：`V.l4`（`show`、`zoneOpts`、`state`、`openCell`、`openGroup`、`runReach`、`rerunWithVrf`、`timings`、`runs`、`MATRIX_MAX`）。`V.l4.state()` 另有 `vrf`（矩陣的來源 VRF 篩選，空字串是全部）與 `reachVrfs`（可達性查詢的來源在多個 VRF 時可以選的 VRF，否則為 null）；`V.l4.rerunWithVrf(App, vrf)` 以同一個請求換 VRF 重新查詢。
  - **VRF**（M3）：可達性查詢的 VRF 選單在 `Q.vrfs()` 有兩個以上時出現，選了才以 `{ vrf }` 傳給 `Q.reach`；`Q.reach` 回傳 `vrfs` 時（來源在多個 VRF）畫面列出選擇的按鈕，不猜。從位址組開啟逐跳路徑時帶上代表位址的 `vrf`。矩陣的 VRF 篩選依 `Q.zoneMatrix` 的 `vrfs`（兩個以上才出現），只篩來源 zone（列），目的 zone（欄）全部保留，所以跨 VRF 的格子照樣看得到；表格檢視與 CSV 共用同一個篩選。`V.l4.runs(Q)` 是這份基準上各服務分段計算的紀錄（`{ ms, wallMs, steps, maxStepMs, maxGapMs }`：計算本身、含讓出的總時間、段數、一段最久佔住主執行緒多久、兩段之間最長的間隔），大型冒煙測試讀它。`App.l4Job` 是矩陣的計算，`App.l4ImpactJob` 是規則詳情的「計算 L4 影響」，都是 Promise，測試可以等待。
  - **「在圖上定位」**（搜尋、路由追蹤，`App.showView('graph')`）在 L4 時改回設備圖，因為矩陣沒有圖。
  - **匯出**：L4 不匯出 PNG（`A.exportPng` 以提示列說明），矩陣改用 L4 畫面的「下載 CSV」（目前的服務，每一格一列，開頭有 UTF-8 BOM、換行 CRLF，儲存格經 `V.exporter.csvCell` 處理）。
  - **版面順序**：判斷的前提（只寫一句摘要，逐條的 `S.query.reachAssumptions()` 收在預設收合的「看全部 N 條前提」）→ zone 矩陣 → 可達性查詢 → 明細與 zone 的依據；矩陣在查詢之前，首屏先看到矩陣。
  - **矩陣用 HTML 表格**：`<table role="grid">` 加 CSS 自製，不用 SVG 或 Canvas。理由是可及性：鍵盤（roving tabindex，只有目前的格子在 Tab 順序裡）、螢幕閱讀器（每格的 `aria-label` 寫出狀態、筆數與代表規則）與強制色彩都比較容易做好。
  - **顏色**：取自 `theme.l4`（[第 6 節](#6-樣式theme)），五種狀態一律有符號與文字（`V.L4_STATUS`），不只靠顏色。部分允許是琥珀色（亮暗兩組都對格子底色與畫布底色 ≥ 3:1，冒煙測試檢查色相，不和拒絕、無法判斷同色）；「＋?」（`.l4-inc`）、IPv6 提示（`.l4-ipv6-note`）、連線追蹤的說明（`.l4-ct`）有各自的樣式。
  - **L4 的用語**（都在 `src/view/dom.js`，畫面不另寫一份）：`V.L4_STATUS`（格子狀態與 `Q.reach` 的結果）與 `V.L4_STATUS_TIP`（各狀態的說明）；`V.L4_INCOMPLETE`「部分無法判斷」（格子、組與服務的 `incomplete`：有確定的允許、又有無法判斷的組合，接在狀態文字後面，矩陣的格子另加「＋?」，表格、明細與 CSV 的狀態欄用同一段文字）；`V.L4_VERDICT`（逐跳規則的結果，中文在前、RouterOS 原值在括號，nat 沒有命中的 `none` 是「不改寫」）；`V.L4_CONNTRACK`（逐跳的連線追蹤狀態 `hops[].conntrack`，目前只有 `untracked`）；`V.ZONE_SOURCE`（zone 的來源，含虛擬 zone 的 `virtual`）；`V.REACH_REASON`（原因與結束代碼，含 `service-refused`、`service-unknown`、`egress-wan`、`hairpin-no-srcnat`；沒有對照的代碼由 `V.reachReason` 原樣顯示並標「沒有說明」）；`V.REACH_START`、`V.REACH_START_BASIS`（可達性的起點與閘道的推定依據；冒煙測試掃描 `reach.js` 的 `srcLocation` 中 `basis` 的字面值，每一個都要有中文名稱）。規則的位置寫「chain 內第 N 條」，是 chain 內從 1 起算的序號，不是 print 的編號。
  - **虛擬 zone**（外部（Internet）、網路設備（管理），規則見[設計說明 §5.3「L4 可達性與 zone」](設計說明.md#l4-可達性與-zone2110-新增)）：只在 `Q.zoneMatrix` 的 `zones`，不在 `Q.zones`，所以 zone 名稱先查 `Q.zones`、找不到再查矩陣的 `zones`。`dstOnly` 的 zone（網路設備（管理））只當欄、不當列；外部 zone 的 VRF 是 main，照來源 VRF 篩選。
  - **IPv6 提示**：矩陣只算 IPv4；`Q.zoneMatrix` 的 `ipv6` 有設備時，矩陣上方寫出這些設備與「IPv6 未納入」，請使用者看 F05／F07，避免把「全部拒絕」誤讀成安全。
  - **上限**：矩陣最多畫 `MATRIX_MAX`（60）個 zone，超過時只有表格檢視；表格檢視最多列 3000 格，完整內容在 CSV。明細的表格最多列 300 筆。
  - **檢視狀態**：服務、檢視方式（矩陣／表格）、開啟哪一格的明細、「收起全部拒絕的組」與結果不一的格子的「顯示全部」都只在記憶體，不存進 store，換基準時清掉。矩陣與規則影響的計算結果由查詢層快取；畫面記下這份基準算過哪些服務，再開時直接畫、不顯示忙碌提示。規則影響的結果依基準與規則保留，到換基準為止。
  - **第一次計算**：用 `Q.zoneMatrixSteps` 分段計算（[設計說明 §5.3](設計說明.md#l4-可達性與-zone2110-新增)）。先顯示忙碌提示，稍後才開始；段與段之間以 `setTimeout(0)` 讓出主執行緒，所以計算期間畫面仍可操作。同時最多一個計算；只換檢視方式時沿用進行中的計算。換服務、換基準或離開 L4 時以 `it.return()` 放棄，不畫過期的結果，查詢層也不留快取；離開 L4 而放棄的，回到 L4 時重新計算。狀態列只寫 zone、代表位址、dst-nat 入口與判斷次數，不寫計算時間與是否使用快取（計算紀錄仍留在 `V.l4` 的除錯介面，大型冒煙測試用它印出時間）。
  - **進度的可及性**：說明文字放在狀態列（live region），只朗讀一次；進度條（`role="progressbar"`）每段更新 `aria-valuenow` 與 `aria-valuetext`（階段與筆數，例如「第 2／3 段：逐一判斷 …」），畫面上的數字設為 `aria-hidden`，不在 live region 反覆朗讀。
  - **結果不一的格子**（`heterogeneous`，畫面標「≠ 結果不一」）：明細的位址組預設只列 `groups[].divergent` 的組，可切換顯示全部；造成差異的服務（`divergentServices`）在按鈕上另標「≠ 差異」文字，不只靠顏色。結果一致的格子仍是全部拒絕的組預設收起。
  - **命名規則**：建立基準時用的命名規則（`App.profileJson`）有 `zones` 段時，才以 `profile` 參數傳給查詢層（`V.l4.zoneOpts`，規則影響共用）。核對失敗時（[設計說明 §5.3](設計說明.md#l4-可達性與-zone2110-新增)）不套用 `zones` 段（zone 改由其他來源決定），並在狀態列與「zone 的依據」寫出核心的錯誤訊息，不靜默改用別的分法。

## 5. 各面板的資料來源

下列都是檢視狀態、使用者的資料或衍生輸出，不改寫基準：

- **處理紀錄（取代確認標記）**：使用者對每個 finding 的決定與歷程，資料模型與規則在核心 `S.ledger`（[設計說明 第 10 節](設計說明.md#10-處理紀錄ssot-ledger1)），畫面接線在 `src/view/app-ledger.js`。
  - 存在 store 的獨立鍵 `'ledger'`，和基準 `'last'` 分開：按「清除」不影響它，重新建立同一份網路的基準時仍然有效。
  - 每次建立或還原基準後，以目前時間呼叫 `S.ledger.advance` 推進一輪；同一份基準（基準鍵相同）已推進過時不顯示本輪變化。
  - **舊確認標記的轉換**：啟動時 store 沒有 `'ledger'`、但有舊的 `'acks'`（`{ findingKey: { at, kind, note } }`）時，先記下，等第一份基準載入時以 `S.ledger.fromAcks` 轉換（含推進一輪），提示列顯示轉換的筆數。`'ledger'` 寫入成功後才刪除 `'acks'`；寫入失敗時保留 `'acks'`，下次開啟再轉換一次。store 已經有 `'ledger'` 時不讀 `'acks'`。
  - **無法使用時停用**：store 中的 `'ledger'` 格式不正確（`S.ledger.validate` 不通過），或舊確認標記無法轉換時，處理紀錄停用：不寫入 store、不丟資料，畫面說明原因與錯誤。可以匯出原資料、匯入正確的處理紀錄，或以空白的處理紀錄重新開始（舊的 `'acks'` 保留不刪）。
  - **匯出與匯入**：入口在資料中心（「驗證」的處理紀錄只留「在資料中心匯出或匯入…」）。匯出 `ledger-<目前時間>.json`（停用時匯出 store 中的原資料；檔名由 `A.ledgerFileName` 產生，工作包共用）。匯入先以 `S.ledger.validate` 檢查，不合法時列出全部錯誤（原本只列 30 筆）、目前的處理紀錄不變；合法時等使用者確認後**整份覆蓋**目前的處理紀錄（只覆蓋、不合併），再以目前的基準推進一輪。
  - **待處理與已處理**：處理紀錄的狀態是 open、regressed，或不在處理紀錄中時算待處理；其餘（scheduled、accepted、false-positive、fixed）算已處理。已處理的錯誤與警告不計入步驟列「研判」、基準狀態卡與「驗證」改善趨勢的「待處理」（`A.problemCounts`，數字來自 `Q.pendingSummary(A.isPending)`，錯誤＋警告、不含提醒），狀態卡註明另有幾項已處理，另有復發、因收集失敗而無法判斷、接受風險到期的提示，點一下到「驗證」的本輪變化。
  - **變更狀態**：檢查結果每筆訊息下方的「處理狀態」（`aria-expanded` 標出是否展開）開啟編輯欄位；不叫「處理」，和檢查上方的處理提示「處理：…」區分。狀態選單只列目前的狀態與 `S.ledger.USER_TO` 允許的轉換，另有備註；選「接受風險」時要填豁免原因（畫面要求必填）與到期日（預設 `S.ledger.WAIVER_DAYS` 天後，日期以 UTC 0 時計）。儲存交給 `S.ledger.set`；不合法的變更（例如把仍出現在最新一輪基準的項目標為已修好）在欄位下方顯示核心的錯誤訊息，資料不變。
  - 已處理的項目依狀態各列一組（已排定修正、接受風險、誤報、已修好，預設收合）；有標為誤報的檢查時，另列「誤報率最高的檢查」（`S.ledger.ruleStats`，最多 5 條）。詳情的檢查結果列出狀態、豁免原因與到期日、備註。
- **「驗證」裡的處理紀錄**（`src/view/panels/ledger.js`）：數字全部來自核心（`S.ledger.summary` 與 `advance` 的結果），畫面只排版與畫圖。`V.ledgerPane.render` 畫本輪變化、處理紀錄與修正追蹤，`V.ledgerPane.renderTrend` 畫改善趨勢；原本左側的處理紀錄分頁與它的摘要已經拿掉。工作畫面夠寬時（`@container` ≥ 880px），本輪變化與處理紀錄在左欄（sticky），修正追蹤、改善趨勢與比對在右欄。
  - **處理紀錄**（`#ledger-body`）：各狀態的筆數與機制說明收在預設收合的「各狀態的筆數與說明」（狀態的 chip 只在本輪變化上色）；豁免沒寫原因時提醒補上（例如由舊確認標記轉換而來）；匯出與匯入的入口（在資料中心）。
  - **本輪變化**（`#round-body`）：新出現、已修好、復發、接受風險到期、因收集失敗而無法判斷的筆數與清單（每組最多列 300 筆）；「新出現」含提醒（`Q.findingIndexByKey` 對到的 finding 為 info），和 `Q.pendingSummary` 的待處理口徑不同，有提醒時在數字旁寫「（含提醒 N）」並以 title 說明；目前基準有這一筆時，點一下定位。和上一輪的基準版本不同時，提示新出現的可能來自新版檢查。同一份基準已推進過（例如重新開啟頁面）時說明沒有新的變化。第一輪（`A.ledgerRoundIndex() === 0`）沒有上一輪可比對，不列數字 chip，改寫「第一輪，沒有可比對的上一輪」與記進處理紀錄的筆數（含提醒時寫明）。
  - **修正追蹤**（`#tracking-body`）：已排定修正（`scheduled`）的項目（標示目前基準仍有或沒有），以及累計已修好的項目，上方有三個數字（已排定修正、目前基準仍有、累計已修好）。取代 2.7.0 在新舊基準比對上方的修復追蹤。
  - **改善趨勢**（`#trend-body`）：上方的數字卡是待處理（`A.problemCounts()` 的 `total`，即 `Q.pendingSummary`，附錯誤與警告各幾筆）、提醒（`info`）、最新一輪的接受風險、覆蓋率與終端埠；復發只在本輪變化顯示，這裡不重複。只有一輪時只列數字卡；兩輪以上畫三張小倍數折線圖（SVG，一張圖一個軸）：「未結案（含提醒）」（`S.ledger.summary` 的 `pending`，不分嚴重度，所以不叫待處理）、復發與已豁免的筆數、覆蓋率（已收集／應收集）、終端埠數（處理紀錄的 `unknownPeers`）。顏色與線型取自 `theme.trend`。
    - 線寬 1.5 的細線，三條線另以圓形、方形、三角形標記區分；圖例與 tooltip 的樣本也畫出同樣的線與外形，不只靠顏色。
    - 線尾寫出名稱與數值（只有一條線的圖只寫數值）；數值相同的線，線尾文字往下錯開，不會疊在一起。
    - 滑過或聚焦一輪時，tooltip 顯示輪次、該輪的建立時間與每條線的數值。
    - x 軸標籤在輪數多時間隔顯示（第一輪與最後一輪一定顯示）。
    - 鍵盤：每張圖只有一個 Tab 停點（最後一輪），←、→、Home、End 切換輪次；每一輪有朗讀用的說明。
    - 保留「表格檢視」，列出同樣的數字；表格寬於畫面時在自己的框內捲動。
- **修正計畫**（「修正」的工作畫面 `#view-patch`，`src/view/panels/patch.js`；原本是對話框 `#dlg-patch`）：計畫與 `.rsc` 文字全部由核心 `S.remediate` 產生（[設計說明 第 9 節](設計說明.md#9-修正-patchssot-patch1)），畫面只負責選取、預覽與下載。
  - 從步驟列的「修正」、「研判」步驟檢查結果的「修正計畫…」，或防火牆畫面的「在修正計畫中開啟」開啟（`App.openPatch` 切到「修正」）。點選檢查結果時留在「修正」，詳情在右側。
  - 重繪會重建全部的元素：展開的規則記在 `state.open`，重繪後仍展開；焦點在有 `data-patch-focus` 的元素上時，重繪後回到同一個元素。換了基準時 `state.open` 和選取一起清空。
  - 工作畫面本身的寬度 ≥ 880px 時（`@container`，不是視窗寬度），「要修正哪些」與計畫分成左右兩欄，左欄 sticky；較窄時上下排。
  - 選取：依檢查、依設備（「加入這台的全部」）、逐筆勾選（每條最多列 200 筆），或「全部清除」。
    - 依檢查寫成「類別 ▸ 檢查標題」：類別與標題取自 `S.query.rule`（檢查目錄，目錄沒有的代碼歸「未登錄的檢查」、標題用代碼），類別依 `S.query.rules()` 的順序，每類是預設收合的 `<details>`（標題寫出檢查數與已選幾項，展開狀態記在 `state.cats`）；類別內可產生指令的檢查排前面，點一下選取或取消這項檢查的全部。畫面上寫檢查標題，代碼只放在 `title` 與 `data-rule-id`；計畫的每一項與「沒有產生指令的項目」也一樣。
    - 逐筆勾選收在「逐筆勾選（N 項檢查）」：預設收合、有展開的檢查時展開，使用者切換後記在 `state.picks`。逐筆勾選以 findingKey 為單位，facet 不同的（例如同一組設備的 A12 DNS 與 NTP）各自一列，並標示比對對象；仍共用一個鍵的只有依輸入區塊產生的 I01、I03。選取是 findingKey 的集合，只在記憶體，不存進 store；換了基準（inputHash 不同）時清空。
  - 計畫：依設備列出每一項的修改前（證據的原文，可開啟原始輸出）與修改後（這一項的套用指令，取自 `S.remediate.renderRsc`），以及說明、風險與警告。每台設備可切換檢視套用、回復、驗證三個檔案，複製或下載目前檢視的那一份。上方只有一個主要的「下載全部（N 個檔案）」（每台三個 `.rsc`，加上總表 `patch-summary-<建立時間>-<N>dev.md`，不分設備台數），只下載總表收在「其他格式 ▾」。「本工具只產生文字」的說明只在計畫開頭寫一次。沒有產生指令的項目依原因分組列出。
  - **choice 的選擇**（目前是 A12）：`plan.choices` 每筆以 radio 列出選項。選擇存成 findingKey → 選項 id，和選取一樣只在記憶體、不存進 store，換了基準時清空；只把選取範圍內的選擇以 `S.remediate.plan(Q, selection, { choices })` 交給核心重新產生計畫，畫面不自己組指令。選項已不存在（核心丟出 RangeError）時清掉選擇、改回預設，並以 banner 說明。
  - 選擇的標題只寫檢查名稱，代碼與類別放在 `title`；檢查結果的訊息用一般文字色，後面另有「看這筆檢查結果」連結（`V.remediation.findingRef` 的 `label`）。多數選項只以「推論」chip 標示推論，核心選項文字中的「（推論：N 台中 M 台，…）」顯示成「（N 台中 M 台：…）」。
  - 唯讀提示「本工具只產生文字，不會連線或改動任何設備。」是 `<details class="patch-readonly">` 的摘要：寬螢幕預設展開，窄螢幕預設收合成一行；使用者切換後記在 `state.note`。
  - **「不修改」**：核心不碰處理紀錄（[設計說明 第 9 節](設計說明.md#9-修正-patchssot-patch1)），由畫面呼叫 `App.setLedger`（`S.ledger.set`）把這筆標為 accepted，附原因與到期日。處理紀錄停用，或目前狀態依 `S.ledger.USER_TO` 不能改為 accepted 時，只顯示說明、不顯示表單；已經是 accepted 時顯示豁免內容。

- **比對在「驗證」**：預期現況比對與新舊基準比對的結果都在「驗證」的比對（`#compare-body`，`V.lists.compare`），各一張卡片；點一列在右側詳情開啟該項目，步驟不切換。原本左側「比對」分頁的摘要已經拿掉；摘要改在資料中心的「上一輪的基準」「預期現況」兩列。
- **新舊基準比對的結果不保存**：舊基準是使用者載入、之前匯出的 Snapshot JSON；比對結果與舊基準的查詢介面只放在記憶體（`src/view/panels/baseline-diff.js`），不寫進 store。比對結果上方逐筆列出核心的 `warnings`（版本、命名規則不同）。

- **防火牆畫面的修正**：設備的防火牆畫面有「修正（停用規則）」一節，列出指向規則、而且核心有修正方式（`S.remediate.levelOf` 不是 manual）的檢查結果。計畫由 `S.remediate.plan` 產生：可產生指令的列出套用指令、find 的依據、風險與警告，可複製；不能產生的（例如 F03 要選擇處理方式、F02 的 find 無法區分）列出核心給的原因。定位到某條規則時只列這條、預設展開，否則列這台設備的全部、預設收合。完整的 `.rsc` 在中間的修正計畫。
- **devices.csv 草稿**（`V.remediation.devicesCsvDraft`）：由 C01（只被鄰居發現、沒有收集資料的網路設備）產生 `tools/collect.sh` 的設備清單，格式 `name,address,user,port,extra`。
  - `address` 依序取設備的管理 IP、鄰居回報的位址；`user` 一律是佔位值 `CHANGE_ME`（`collect.sh` 擋不下佔位值，檔頭註解會提醒先改成實際的 SSH 帳號）；`port` 為 22，`extra` 留空。
  - 不能直接使用的設備寫成註解列（開頭 `#`，`collect.sh` 會略過）並註明原因：沒有任何位址、位址含空白或逗號、名稱不符合 `collect.sh` 的名稱規則，或名稱重複。修正後移除 `#` 即可。
  - 檔頭註解另寫基準建立時間、輸入指紋，以及建議先執行 `tools/collect.sh devices.csv --dry-run`。

## 6. 樣式（theme）

所有顏色、線型、透明度與字型集中在 `src/view/theme.js`，Canvas 繪圖與圖例都讀它（圖例分「設備／終端／鏈路／鏈路註記／標示」五類，預設收合，說明文字放提示；外形、鏈路色、線寬、虛線、弱證據透明度與標示色由 theme 產生，有測試比對）；CSS 的設備類型、嚴重度色與它的一致性也有測試。鏈路依速率是同一色相由淺到深的色階，線寬隨速率遞增（1G → 10G → 40G，聚合最粗）；1G 是由介面名稱推估的分類，不代表實際協商速率，圖例提示會說明此限制。「只有一端資料」（hearsay）是點線、「推論鏈路」是長虛線，兩者只改線型與透明度，保留速率色；只有 MNDP 的設備對不畫線。選取或 hover 高亮時維持完整不透明度。一般 UI 採冷白背景與一致的圓角、控制項高度及陰影層級；操作按鈕依優先級呈現，狀態 chip 使用對應色彩及邊框，清單表格使用斑馬列與 hover 高亮，互動元件提供鍵盤焦點樣式，並尊重減少動態效果的系統偏好。

- **theme 的內容**（配色以 dataviz 的 validator 在亮色、底色 `#f8fafc` 驗證）：
  - 狀態色（`sev`、`mark.bad`／`good`）只表示狀態，而且一律搭配外形或文字；類別色（設備、連線、廠商）不用紅、橘黃、綠。
  - `text`：文字色（body、muted、err、warn、ok、info），對其底色至少 4.5:1，與 `assets/app.css` 的對應變數一致。防火牆的動作色與比對的 effect 色都取自它。
  - `sevShape`：嚴重度的外形，錯誤是方形、警告是三角形；節點右上角、連線中點與圖例共用（`V.sevMark`）。比對的 effect 標籤前也加上同樣的外形（`diff.effectSev`）。
  - `multi`：同一對設備有多條鏈路時，線加寬（`widen`）並在中間留一條底色細縫（`gap`），看起來是雙線。
  - `font`：Canvas 的字型清單（`sans`、`mono`）與 CSS 的 `--font-sans`、`--font-mono` 是同一串（拉丁字型在前、繁中字型在後，有測試）；`weight`（`normal` 400、`strong` 600）；畫布字級是螢幕 px：設備名稱 `labelPx`（13）、分群名稱 `groupPx`（13）、埠名 `portPx`（12，設備圖的埠名任何縮放都固定這個大小；L2 埠圖的埠名隨縮放、最大不超過它，滑過或選取時固定它），節點內的小字（廠商縮寫、數量）在螢幕上小於 `minPx`（11）時不畫。過長的節點標籤與埠名截斷加「…」。
  - `mark`：圖上的標示色（選取、滑過、搜尋、路由追蹤）與狀態色 `bad`／`good`；`unverified` 是路由追蹤停在未收集設備的中性灰（無法驗證，不是錯誤）。
  - `sev`：嚴重度的標記色（error `#d93025`、warn `#c27a00`），與 CSS 的 `--sev-error`、`--sev-warn` 一致，對白底與表面色至少 3:1（有測試）。
  - `canvas.deviation`：與多數不同的虛線外圈（顏色、線寬、虛線、外擴距離，以及圖例的 `label`／`tip`），比選取與高亮更外圈，顏色和狀態色、選取、滑過、搜尋、追蹤都不同；縮小時線寬與虛線保持螢幕上可見。`canvas.group.labelBg` 是分群標籤的底色，蓋住底下的連線，文字對它至少 4.5:1。
  - `canvas.surface`：畫布底色（與 `--surface` 相同）。每次繪圖先填滿，所以匯出的 PNG 不是透明背景；多條鏈路的中縫也用它。
  - `vlan`：VLAN 篩選的四種線型：`carry` 實線、`inferred` 長虛線（同推論鏈路）、`partial` 錯誤色實線加垂直短刻度（`ticks`：沿線每 `gap` 一道、全長 `len`、粗 `w`）並在中點加錯誤外形（方形）、`oneSide` 淡色點線。都保留外形或線型，不只靠顏色。
    - `partial` 的錯誤色與 `carry` 的正常色在紅綠色盲下分不出來（validator 的 CVD 檢查 deutan ΔE 5.0 不通過），所以顏色不變，改以線型與外形作第二種編碼；設備圖、L2 埠圖、圖例與 PNG 匯出都有刻度。
    - 不用雙線，是因為會和「多條鏈路」（`multi`）的雙線撞在一起；不用鋸齒線，是因為在短邊上不好辨認。其他線型都是沿線方向的虛線、點線或雙線，垂直的刻度不會和它們混淆。
  - `l2`：L2 埠圖的設備框（`box`，外框用設備類型色，未收集的用虛線）與埠（`port`，聚合埠較寬，推論鏈路未收集端的未知埠用虛線）。
  - `l3`：L3 網段圖的網段長條（`subnet`，只由路由得知的目的網段用虛線外框）、路由（`route`，虛線加箭頭）、網段重疊（`overlap`，警告文字色的虛線，中點加警告外形）與重疊、重複 IP 的標籤（`badge`）。
  - `trend`：處理紀錄趨勢圖的線色、外形標記、格線與座標軸色，以及線型 `lineWidth`（1.5）、`markerSize`（外形標記的半徑 3）、`markerRing`（標記外圈的底色環 1.5）。待處理、復發、已豁免三色以 dataviz 的 validator 檢查全部通過，色覺差異模擬下最差的 ΔE 是 18.4。
  - `l4`：L4 zone 矩陣與可達性的五種狀態（`status`，鍵和 `Q.zoneMatrix` 的格子 `status`、`Q.reach` 的 `verdict` 相同），每種有符號色 `mark`、底色 `bg` 與符號 `glyph`；另有格子的文字色（`text.body`）、「≠ 結果不一」的徽章（`badge`）、對角線（zone 內）的虛線外框（`diagonal`）與焦點色。
    - allow（✓）、deny（✕）、partial（◐）的 `mark` 以 dataviz 的 validator 檢查全部通過，色覺差異模擬下最差的 ΔE 是 13.2（deutan）。
    - unknown（?）與 empty（–）刻意用中性色：「無法判斷」與「沒有可算的組合」不是一種結果。empty 另加斜線底紋（`hatch`），和 unknown 的實心灰底分開。
    - 格子的文字對每種底色至少 4.5:1，符號對格子底色與畫布底色至少 3:1。強制色彩模式下底色被系統色取代，狀態仍靠符號與文字辨識，焦點改用 `Highlight` 的 outline。
  - 其他：防火牆畫面的動作色、停用規則透明度與定位列（`firewall`），新舊比對的 effect 色與新暴露底色（`diff`）。
- **字級與 CJK 排版**（`assets/app.css` 的 `:root`）：
  - 字級是整數階梯，窄螢幕不縮小：`--fs-xs` 13（檢查代碼、行號、圖例這類標記）、`--fs-sm` 14（次要文字與標籤）、`--fs-md` 14（表格與清單）、`--fs-base` 15（內文、按鈕與輸入框）、`--fs-lg` 17（小標題）、`--fs-xl` 20（詳情標題）、`--fs-2xl` 24（頁面標題）。行高：內文 `--lh-body` 1.65、說明與長段落 `--lh-prose` 1.7、標題與控制項 `--lh-heading` 1.4。
  - CJK 斷行：`word-break: normal`（不拆英數，不用 `break-all`）、`overflow-wrap: break-word`（太長的字才換行）、`line-break: strict`（標點避頭尾）；中英間距與全形標點擠壓（`text-autospace`、`text-spacing-trim`）是漸進增強。不加字距：`letter-spacing` 只能是 0（標題也是），字重 600（有測試）。
  - chip（`.chip`）與滑過的提示（`.tooltip`）可以換行：chip 不縮小（`flex-shrink: 0`，短的仍是一列，不會被擠成逐字直排），長文字在容器寬度內換行；提示最寬 320px（不超出視窗）。
  - 表格內的識別字（IP、MAC、VLAN 清單）不逐字斷行，寬於欄位時在 `.table-scroll` 內橫向捲動。
  - 窄螢幕的清單（「檢視」，`.inv-table`）：表格依內容寬度排開（`width: max-content`），儲存格不換行，在 `.table-scroll` 內橫向捲動，並顯示滑動提示（`.inv-scroll-hint`）；只有第一欄可以換行。各清單的欄序把關鍵欄放在前三欄（例如 MAC 清單是 MAC、廠商、IP）。
  - 控制項高度 `--control-h`：滑鼠 36px，觸控（`pointer: coarse`）44px；已選檔案的移除鈕在觸控時也至少 44px。
  - 文字輸入框、日期欄、select、textarea 共用同一條基底規則，邊框用 `--line-input`（對白底與表面色至少 3:1）；按鈕、連結、清單列與表格列的焦點是 `--focus-outline`（2px 實線，強調色至少 3:1），都有測試。
- **CSS token**（`assets/app.css` 的 `:root`）：`:root` 之外的規則只用 `var(--*)`，不寫色值或數字的層級、時長與圓角。分類如下：
  - 顏色：中性面與框線（`--bg` 頁面底、`--panel` 抬升面、`--surface` 次要面、`--*-soft` 淺底、`--line*` 框線）；強調色（`--accent`、`--accent-strong` 按下／hover、`--accent-soft`、`--on-accent`）；狀態（`--err`／`--warn`／`--info`／`--ok` 的 `-soft` 淺底、`-text` 文字、`-line` 框線，`--sev-*` 標記）；危險操作（`--danger-text`、`--danger-line`）；設備類型 chip（`--kind-*-bg`／`-fg`）；次要文字（`--chip-text`、`--th-text`、`--heading-text`）；表格錯誤列與原文高亮（`--row-bad`、`--row-bad-hover`、`--hl-bg`）；浮層（`--overlay`、`--overlay-soft`、`--tooltip-bg`／`-fg`、`--dialog-line`、`--backdrop`）；L4 框線（`--l4-line*`）；焦點內圈（`--focus-ring-inner`）；品牌圖示的節點（`--brand-leaf`；index.html 的 SVG 以 class 上色，不寫色碼）；強制色彩下保留亮色的趨勢圖（`--fixed-light-bg`／`-text`，深色時也不變）。
  - 陰影：`--shadow-sm`、`--shadow-md`，以及單一用途的 `--shadow-xs`（按鈕）、`--shadow-header`、`--shadow-lg`（歡迎卡）、`--shadow-dialog`、`--shadow-primary`（主要按鈕，hover 用 `-hover`）。
  - 疊放順序 `--z-*`（由下而上）：`base` 0 拓樸圖、`sticky` 1 表頭、`raised` 2 聚焦的控制項、`layer` 4 歡迎畫面與 L4、`overlay` 5 工具列與圖例、`work` 6 工作畫面與抽屜、`header` 7 頁首與通知、`float` 8 L4 浮動說明、`banner-top` 9、`tooltip` 20、`dropdown` 50、`menu` 60。
  - 動效時長 `--dur-*`：`row` .12s 清單列、`fast` .14s 按鈕與輸入框、`progress` .15s、`fade` .4s 淡出、`loop` 1.2s 不確定進度、`instant` 減少動態效果時的覆寫。
  - 圓角 `--radius-*`：`lg` 12、預設 8、`sm` 5、`chip` 11、`cell` 4（L4 格子）、`xs` 3、`2xs` 2、`mark` 1、`pill` 999；另可用 0 與 50%（圓形）。
  - 停用：按鈕、篩選選項、流程步驟與輸入框共用 `--disabled-opacity` 與 `cursor: not-allowed`。危險操作（例如清除基準）用 `.danger` 修飾，不用 ID 規則上色。
  - 靜態檢查（`tests/ui/steps/14-style-a11y.js`「樣式 token」）：`:root`（含 `@media` 內的 `:root` 與深色的 `:root[data-theme="dark"]`）之外不寫 hex、`rgb()`／`rgba()`、`hsl()`／`hsla()` 等色彩函式與具名色（`white`、`black`…；`transparent`、`currentColor`、`inherit` 與強制色彩的系統色可以用）；index.html 的 inline style 與 SVG 的 `fill`／`stroke` 等也不寫色碼（分頁圖示的 data URI 在頁面之外，不算）；`z-index` 只用 `--z-*`；`transition`／`animation` 的時長與延遲（`*-delay`）只用 `--dur-*`；`border-radius` 與分邊寫法（`border-top-left-radius` 等）只用 `--radius-*`、0 或 50%；每個變數至少被 `:root` 之外的 `var()` 用到一次（只被其他變數引用時，要那個變數本身有用到才算），只供測試與 `theme.js` 比對的設備類型色（`--fw`、`--sw`、`--rt`、`--host`、`--unk`）列在例外清單；對話框有 `aria-labelledby`，✕ 關閉鈕有 `aria-label`。
- **鍵盤、觸控與系統偏好**（`src/view/graph/canvas.js`、`assets/app.css`）：拓樸圖可取得焦點，可用鍵盤操作（按鍵見[使用說明「檢視」](使用說明.md#step-view)）；移到的設備以滑過的樣式標示，並讀給螢幕閱讀器（`#graph-live`）。滑鼠、觸控與觸控筆共用 pointer 事件；觸控沒有 hover，命中範圍較大，點兩下等同雙擊。觸控與觸控筆的節點點擊半徑在螢幕上至少 `TOUCH.hitPx`（22px），且至少是節點半徑外加 `slopPx`；在同一個節點 `tapMs`／`tapPx` 內點兩下才算雙擊。兩指同時按著時是雙指縮放（以兩指中點為中心，同時平移），放開一指後剩下的手指接著平移、不觸發點選。界線集中在 `GraphView.LIMITS`（`ZOOM`、`FIT`、`FOCUS`、`TOUCH`、`MOUSE`，唯讀，測試核對）。強制色彩模式（Windows 高對比）下，焦點與「選取中」改用系統色的 outline；偏好減少動態效果時取消轉場，「力導向排列」一次算完、不播動畫。

- **亮色與暗色配色**：外形、線寬、虛線、透明度、字型與尺寸只寫一次；顏色另有兩組形狀相同的配色 `theme.palettes.light`／`dark`（葉節點路徑與 theme 相同，已凍結）。亮色就是 theme.js 寫的值；暗色是亮色複本套上覆寫表 `DARK`（只寫要改的葉節點，路徑寫錯或不是顏色時載入就丟錯）。`theme.apply(mode)` 原地改寫顏色的葉節點、不換掉物件或陣列（canvas.js 等在載入時存下子物件），`theme.mode` 唯讀，未知的模式丟 `RangeError`。
  - 暗色的設計規則（`DARK` 與 `assets/app.css` 的 `:root[data-theme="dark"] { … }` 一起改）：
    - 底色：頁面 `--bg` #0f141a、抬升面 `--panel` #1c232c、次要面與畫布 `--surface` #151b23；`theme.canvas.surface` 等於深色的 `--surface`，亮色的白底（L2 設備框、L3 網段、徽章、未收集設備）改成深色的 `--panel`。亮色的「淺底配深字」（`--*-soft` 配 `--*-text`）改成「深底配淺字」。深色 `:root` 正好重新定義亮色的每個顏色變數（`--fixed-light-*` 除外），文字色、設備類型色、嚴重度色與畫布底色和 `palettes.dark` 一致，都有測試。
    - 對比：文字對其底色至少 4.5:1、圖形標記與欄位邊框對畫布底色至少 3:1；冒煙測試的對比、一致性斷言都對亮暗兩組各跑一次。
    - 連線速率色階反轉：亮色越快越深，暗色越快越亮（1G 暗、40G 最亮），線寬的編碼兩組相同。
    - 色相：設備類型、嚴重度、連線、標示、廠商、趨勢與 L4 狀態保留亮色的色相，調整明度與彩度；以 CVD（紅色盲、綠色盲、藍色盲）模擬後每組的最小色差不低於亮色。
    - 別名：亮色以參照共用的值（`vlan.*.c` 等於 `mark.good`／`bad`、`l3.overlap` 與 `l3.badge` 等於 `text.warn`、`firewall.action.*` 與 `diff.effect.*` 等於 `text.*`、`l3.subnet.stroke`、`l4.badge.border` 等等於 `keyInk`、`trend.single` 等於 `mark.select`）在覆寫表也用同一個常數，兩組都相等（有測試）；兩組的 `mark` 沒有共同的值，圖上存下的標示色才分得出屬於哪一組。
  - **配色偏好**：設定「一般」的「配色」單選群組（`panels/settings-general.js`：`<fieldset>`＋`<legend>`，三個原生 radio：跟隨系統（預設）／淺色／深色，選項取自 `S.store.theme.VALUES`）。窄螢幕是同一個入口。`A.setThemePref(pref)` 存進 store（`S.store.theme`，見[第 3 節](#3-樣式儲存與檢視狀態)「儲存集中在 `src/view/store.js`」）、以 `A.syncSettingsControls()` 更新設定裡的勾選並套用；`A.themePref()` 讀目前的偏好。
  - **CSS 只跟著 `<html data-theme>`**：值是實際的深淺（`light`／`dark`），由 `A.applyColorScheme(mode)` 寫入，永遠等於 `theme.mode`。深色變數只寫在 `:root[data-theme="dark"]` 一份，CSS 不寫 `prefers-color-scheme`：選擇器清單不能帶 media 條件，「`@media` 裡的 `:root:not([data-theme="light"])`」加「`:root[data-theme="dark"]`」一定要把整組深色變數寫兩次；`light-dark()` 雖然只寫一次，但要改寫全部的變數，較舊的瀏覽器整組失效。跟隨系統時改由 JS 的 `matchMedia` 判斷系統深淺再寫屬性，代價是畫面的深淺需要 JS（這個工具本來就需要 JS）。`:root` 宣告 `color-scheme: light`、深色 `:root` 宣告 `color-scheme: dark`，捲軸與原生控制項跟著畫面；index.html 的 `<meta name="color-scheme" content="light dark">` 表示頁面兩種都支援。靜態檢查確認 app.css 沒有 `prefers-color-scheme`、只有一個 `:root[data-theme="dark"]`，且每個顏色變數正好在亮色與深色兩個 `:root` 各定義一次。
  - **首次繪製不閃**：index.html 在 `</head>` 之前、所有 `<script src>` 之後有一段 inline script，只呼叫 `SSOT.view.app.paintScheme()`（經 `S.store.theme.get()` 讀偏好、`A.resolveScheme` 換成實際深淺，寫 `data-theme`）。head 的腳本都是同步的，body 還沒解析、畫面還沒畫，所以第一次繪製就是對的深淺。CSP 的 `script-src` 是 `'self'` 加上這段 inline script 的 `sha256`（不用 `'unsafe-inline'`）：改了這段要同步更新 index.html 的雜湊，冒煙測試會比對雜湊與實際內容。因為沒有 `'unsafe-inline'`，index.html 不用 `onclick=` 等內嵌事件屬性（瀏覽器會擋），事件都在 `src/view` 綁定：歡迎畫面的「建立基準…」（`#welcome-input`）與「用範例資料試試看」（`#welcome-sample`）在 `app-input.js` 的 `bindInputDialog`，原文對話框的「自動換行」（`#raw-wrap`）與關閉（`#raw-close`）在 `app-select.js` 第一次 `App.openRaw` 時綁定（冒煙測試掃描 index.html 不得有 `on*=` 屬性）。偏好放 localStorage 而不是 IndexedDB 就是為了這一步能同步讀到。Canvas、圖例與面板的 theme 仍在啟動時的 `A.bindColorScheme()` 套用（在建立圖例之前）。
  - 啟動時 `A.bindColorScheme()` 讀回偏好並套用（設定畫面開啟時才畫單選，畫的時候讀 `A.themePref()`）；監聽系統的 change，只綁一次，只在偏好是跟隨系統時套用，淺色、深色時忽略系統的變更。沒有 `matchMedia` 時跟隨系統視為亮色。`matchMedia` 沒有監聽 API（`addEventListener`、`addListener` 都沒有）時跟隨系統也維持亮色，以 `console.warn` 告知，跟隨系統時另以通知告知（可改成固定的淺色或深色），不中止啟動。
  - change（或切換偏好）時依序：`theme.apply` → 換算圖上存下的顏色（廠商色依名次，`A.recolorVendors`；高亮與疊加線依 `mark` 的舊值→新值換算，所以同一組 `mark` 的值不可重複，有測試）→ 重建圖例（保留展開與焦點）→ 有基準時只重畫在渲染時從 theme 讀 inline 顏色的面板（詳情、改善趨勢、`A.renderCenter()` 的工作畫面），不重建左側清單，打到一半的處理紀錄（備註、豁免原因）才不會消失；拓樸圖只標記重畫，下一個畫格畫一次。匯出 PNG 暫時換成亮色（`withScheme`）時，換色本身也在 `try` 內，換色或繪圖失敗都會還原成目前的深淺，並以通知說明匯出失敗；`withScheme` 只換 theme、不改 `data-theme`，匯出時頁面不閃。強制色彩模式仍由 CSS 處理。

## 7. 拓樸版面

- 共用步驟在 `src/view/graph/layout.js`：
  - `prepare()`：分群、終端（排在所屬設備下方）與 BFS 分層
  - `shelf()`：各群以書架方式排列
  - `wrapRows(items, w, h, portrait)`：同一層太多台時折成多列，內建與 ELK 共用同一個規則（`WRAP`）。先依目標寬高比算出每列的台數並限制在上下限之間（橫式目標約 1.4、6–24 台；直式目標約 0.8、2–6 台），再把這一層平均分成幾列，所以一列可能少於下限；橫式一層 6 台以下不折。
- 兩種版面：
  - **快速（內建）**：同步計算，用一輪重心排序，太寬的層以 `wrapRows` 折行。
  - **分層（ELK，預設）**：`src/view/graph/elk-layout.js` 對每群的核心設備執行 ELK layered（方向一律 `DOWN`），依 `prepare()` 的層級決定邊的方向，再做多輪交叉最小化與 network-simplex 節點擺放。之後依 ELK 排好的左右順序以 `wrapRows` 折行（`foldLayers`：每段置中放在原本那一層，下面的層依多出的列數往下移）。節點框會預留終端方陣與標籤的空間。
- 載入流程：
  - 載入基準時先以快速版面出圖。
  - 沒有儲存位置時，再於背景套用分層版面。
  - 網路設備超過 `App.ELK_MAX`（1500）、逾時或失敗時，維持快速版面並說明原因：設備圖用 banner；L2 埠圖與 L3 網段圖寫在圖上方的層級說明（`#layer-note`，計算中也寫在那裡），不另開通知，兩段文字不會疊在畫布底部。
  - 設備圖套用成功時 banner 寫「已套用分層版面（N 台網路設備）」，台數和基準狀態卡同一個口徑（`Q.coverageSummary().network`），不寫耗時；L2、L3 套用成功不通知。
- ELK 在 `file://` 下沒有 Worker，會在主執行緒計算，所以每群之間會讓出主執行緒。約 1000 台網路設備時約 2.4 秒。
- **直長版面**：`A.isPortrait()`（`src/view/app-graph.js`）在窄螢幕、而且拓樸圖可放圖的範圍（`GraphView.viewport()`，扣掉疊在上面的元素）高大於寬時為 true；畫布還沒有尺寸時才看視窗。這時設備圖的內建版面與 ELK 都以 `wrapRows` 的直式規則折行（仍由上往下，每列較少台），`shelf(boxes, { portrait })` 的書架寬度係數由 1.4 改為 0.8，全圖時才不會又扁又小。只在載入與重新排列時判斷；L2 埠圖也依它折行（見下一項），L3 不受影響。
- **L2 埠圖**：設備是容器框、埠是框邊上的節點。`portPrepare` 決定設備的層級與每個埠在框的上緣或下緣（對端在較上層的埠放上緣）；內建版面 `portLayout(devs, ports, edges, { portrait })` 依層級排開設備框，一層太多台時以 `wrapRows` 折行（每列另不超過 2600），同一邊的埠依對端設備的 x 排序。分層版面 `elkPorts(…, { portrait })` 以 ELK 的 port 計算（埠固定在 `portPrepare` 決定的那一邊，同一邊由 ELK 排序以減少交叉），之後同樣以 `foldLayers` 折行（埠的位置相對於框，跟著框移動）；分群與內建版面相同，各群各算一次再以書架排列。沒有折行時一層幾十台的接取交換器排成一列，全圖會是一條扁平橫條（1440 寬約 640×60px），折行後全圖時設備框在螢幕上約 11px 高、看得出結構。
- **L3 網段圖**：網段與設備都是節點，沿用設備圖的分群（網段歸到接在它上面最多設備的那一群），各群分別以 ELK 計算。基準有兩個以上的 VRF 時改依 VRF 分群，每個 VRF（含 main）一群（見[第 4 節](#4-拓樸圖的層級與-l4)的「L3 與 VRF」）。
- **畫布**（`src/view/graph/canvas.js`，`GraphView`）：L2／L3 用的節點與邊，以及標示、讓位與分群標籤：
  - `node.box { w, h }`：容器框（L2 的設備）或長條（L3 的網段）；命中範圍與標示環是矩形，只在沒有點到框上的其他節點時命中。
  - `node.anchor { parent, dx, dy }`：位置跟著 parent（L2 的埠）；位置不另外儲存，拖曳它等於拖曳 parent。
  - `edge.style { c, w, dash }`：取代依類別的連線樣式；`edge.arrow`：在 b 端附近畫箭頭（L3 的路由）。
  - 高亮（`setHighlight`）的值可以是物件，帶線型與外形（VLAN 篩選用），不只是顏色。
  - `setEmphasis(devKeys)`：與多數不同的設備，以 `theme.canvas.deviation` 的虛線外圈另外標出，和選取、高亮並存；`emphasis` 是唯讀的 Set。
  - `setOccluders([{ el, max, when }])`：疊在畫布上的元素（工具列、圖例、操作提示、層級說明、通知、窄螢幕的詳情抽屜）。`viewport()` 回傳沒被遮住的範圍（螢幕座標）：上半部的元素推下上緣、下半部的推上下緣；元素隱藏、沒有大小、`when()` 為 false，或高度超過畫布的 `max` 倍（省略時 0.4，例如展開的圖例）時不計。
  - `fit(ids, pad, maxScale)` 放進 `viewport()`；全圖（不給 `ids`）且顯示分群時，群框也一併放進來，上緣另留一列分群標籤的高度；畫布還沒有尺寸（例如窄螢幕切到其他工作區）時延到 resize 再做，`syncSize()` 在畫布剛顯示、ResizeObserver 還沒通知時先同步大小。`focus(ids, { neighbors })` 的倍率上限是 `FOCUS.maxScale`（1.5，埠名在 1.25 倍以上才畫），`neighbors` 時一併納入可見的一跳鄰居（選一台設備、或檢查結果只標出一台設備時）；納入鄰居後倍率低於 `FOCUS.minScale`（0.9）時，改為只放進設備本身（`fit()` 的第 4 個參數 `fallback`，延後的 fit 也帶著它），再把畫面往鄰居的重心移動，最多可視範圍的 `FOCUS.lean`（0.3）倍（`_lean`），設備偏到鄰居的另一側；偏移不會把選取節點的框推出畫面（埠很多的寬框也一樣），框離畫面邊緣至少留 fit 的邊距（`FOCUS.pad` 64，畫布小時取寬高的 1/4 以內），框本身已經超出可視範圍時不偏移。連線的線寬是世界座標，放大超過 100% 時除以倍率，螢幕上維持 100% 的粗細。分群標籤在群框的上緣或左緣不在可用範圍內時不標（滑過才標）；群框窄到放不下簡稱時，簡稱可以超出群框（仍在畫布內），排在尾段之前；每個候選都試放上方與框內，放不下才換下一個。L3 網段長條的文字與標籤（世界座標 11、10）在螢幕上小於 `font.minPx` 時不畫（滑過、選取時照畫）。`reveal(ids)` 只平移不縮放，有節點在 `viewport()` 外時把它們移到中央（抽屜開啟時用）。
  - **分群標籤**在螢幕座標排版（`groupLabels` 是上次畫的標籤矩形，唯讀）：依群大小排序，先放群框上方，和已放的重疊時改放框內左上，兩處都不行就不標；群框頂邊在 `viewport()` 上緣之外（放大、聚焦後頂邊在工具列底下或畫面外）時不標，否則標籤只能貼著工具列、壓在節點與埠名上；寬度不超過群框可見的部分，放不下全名時依序用簡稱（括號前）、簡稱的尾段（空白分隔的最後一段）、截斷加「…」，並跳過畫面上別的群已用的文字。滑過的群（`hoverGroup`，指到標籤或群框，巢狀時取面積最小者）最先放、顯示全名、畫在最上層。群框至少 220 單位寬（等於版面的群間距），只有一兩台的小群也放得下簡稱。只有一台的群（`frame` 為 false）不畫框也不標（看起來像空群），滑過那台設備時（`soloGroupOf`）才顯示群名。以上兩種不標的情況，滑過時仍顯示。可用範圍是畫布左右各留 `EDGE_INSET`（4px）、上緣在 `viewport()` 之下，標籤不被切到，也不放在工具列底下；滑過時的全名超出右緣就往左挪。
  - **設備名稱與埠名**：設備名稱靠邊時往內推，不出畫布左右邊緣。倍率低於 `LABEL_MIN.all`（0.18）時只畫已收集的防火牆與路由器的名稱，低於 `LABEL_MIN.core`（0.06）時都不畫（選取、滑過與標示的除外）。埠名在螢幕上固定 `theme.font.portPx`，一般在倍率大於 1.25 時畫。滑過、選取的鏈路（及滑過節點的連線）不受倍率限制，先畫，和設備名稱與彼此重疊時沿線往外挪 `PORT_SLIDE`（14px）再試，最多 `PORT_TRIES`（6）次；都不行時，選取或滑過的那條仍畫在最後一個位置（一定看得到），滑過節點的其他連線才略過。一般埠名最後畫，與設備名稱或已畫的埠名重疊就略過（讓位）。上次畫的設備名稱與埠名矩形留在 `nodeLabels`、`portLabels`（螢幕座標，唯讀，給測試用）。
- 使用的版本是 `vendor/elkjs-0.11.1/`（EPL-2.0，未修改），不屬於核心載入順序。檔案約 1.6 MB，不放在 `index.html`；第一次需要分層版面時才由 `elk-layout.js` 以 `<script>` 載入。選擇「快速（內建）」或網路設備超過上限時不會載入。

## 8. 終端的畫法

終端埠的判定在核心（[設計說明 §5.3「終端埠」](設計說明.md#終端埠210-新增)），畫法只在檢視層：基準的設備、鏈路、檢查結果完全不變（有測試），虛擬節點只存在於畫面。核心的欄位仍叫 `unknownPeer`，畫面一律稱「終端」（`V.TERMS.endpoint`）。

| 情況 | 畫法 |
|---|---|
| 一個埠一個 MAC，且非 Wi-Fi | 圓點，顏色依廠商（避開紅、橘黃、綠，以免和狀態混淆），標 IP；近看顯示廠商縮寫。廠商色最多 8 色，依終端數量取前 8 個廠商（同數量依名稱），其餘與不明廠商歸「其他」的中性色；數量取自全部終端（含推定位置的終端），不受展開／收合影響 |
| 有線介面一埠多個 MAC，或任一 Wi-Fi 介面 | 有線多 MAC 不列為終端埠；Wi-Fi 介面不列為終端埠，但每個 Wi-Fi MAC 觀察位置列入終端清單並可作圖面提示（多 MAC 為菱形），Wi-Fi 位置不參與 A02 |
| 介面 `rawType=veth`（容器虛擬網路卡，`type=virtual`） | 連到該終端的鏈路用專用線型（長線加兩個點），顏色維持鏈路類別色，節點外觀不變；提示與介面詳細標「容器 veth」 |
| 介面 `type=wireless` | 鏈路用另一種專用線型（長線加一個點），標「Wi-Fi」 |
| 同一台設備超過 8 個，或全網超過 800 個 | 收合成一個「終端 ×N」；雙擊或在右側按「在圖上展開」 |

依介面類型的線型定義於 `theme.js` 的 `endpoint.byType`（鍵為 `rawType` 或 `type`，以 `endpoint.styleOf(介面)` 查詢），只識別連線（收合成「終端 ×N」群組時連線維持預設線型），僅視覺識別，不改變判定與檢查。

## 9. 匯出

`src/view/export.js` 只讀傳入的 Snapshot，在本機以 Blob 下載，不經過網路。

- **介面**：匯出的組字函式都收 Q，不讀 Snapshot 的欄位。`V.exporter.KINDS[k]` 是每種匯出的 `name(Q)`（檔名）、`text(Q, opts)`（內容）與 MIME，畫面的按鈕都經過這裡；基準 JSON 要原樣序列化整份 Snapshot，所以由 `opts.snapshot` 傳入，只序列化、不讀欄位。其他：`V.exporter.findingsCsv(Q, opts)`、`findingsMarkdown(Q, opts)`、`baseName(Q)`，`V.remediation.devicesCsvDraft(Q)`；圖的資料 `A.graphData(Q)` 與檢查結果清單的 `V.lists.findings.openFirst(Q)` 也收 Q。
- 基準 JSON：Snapshot 原樣序列化，不增刪欄位；可再載入作為新舊比對的舊基準。
- 檢查結果 CSV：一筆 finding 一列，欄位依序為 `severity,id,title,message,entities,evidence,acknowledged,ack_kind,ack_note,device,action,status,note,waiver_reason,waiver_until,facet,與多數不同（推論）`，共 17 欄。新欄位一律加在最後，既有欄位的位置不變。
  - 最後一欄（欄名是 `V.DEVIATION_LABEL`）是與多數不同的設備名（`finding.deviation`，推論，以「; 」分隔），和畫面同樣以 `V.majorityDeviating` 判斷；平手寫 `V.NO_MAJORITY`（「沒有多數」），不是多數決的檢查空白。Markdown 每筆底下另加一行「與多數不同（推論）：」，設備名以「、」分隔。
  - `entities` 是 `type:key`、`evidence` 是 `檔名:行號`，多筆以「; 」分隔。
  - 舊的確認欄位保留名稱與位置，改由處理紀錄對應：已處理（狀態不是 open、regressed）時，`acknowledged` 是使用者最後一次變更的時間（UTC ISO），`ack_kind` 是狀態（`scheduled`／`accepted`／`false-positive`／`fixed`），`ack_note` 是備註；待處理時三欄都是空白。
  - `device` 是所屬設備鍵（`Q.findingDevice`），不屬於任何設備時為空白。
  - `action` 是檢查的處理建議（`V.remediation.advice`），照 `CATALOG` 原文、保留反引號；檢查沒有處理建議時為空白。沒有 `causes` 欄：同一段多句文字會在每一列重複，合在一格也不好篩選，常見原因放在 Markdown 報表與畫面上。
  - `status` 是處理紀錄的狀態（`open`／`scheduled`／`accepted`／`false-positive`／`fixed`／`regressed`），不在處理紀錄中時空白；`note` 是備註（不論狀態）；`waiver_reason`、`waiver_until` 是接受風險的豁免原因與到期日（UTC ISO）。
  - `facet` 是 `finding.facet` 的原值（比對對象，會進入 findingKey，見 [設計說明 §7](設計說明.md#7-一致性檢查)），例如 A12 的 `dns`／`ntp`；檢查沒有 facet 時空白。放原值而不是畫面的顯示文字，方便在試算表篩選與對照 findingKey。Markdown 報表不加這一欄，因為訊息已經寫出項目。
  - 開頭有 UTF-8 BOM，換行為 CRLF；含逗號、引號、換行或頭尾空白的儲存格依 RFC 4180 加引號；以 `=`、`+`、`-`、`@`、Tab、CR 開頭的儲存格前面加 `'`，避免試算表當成公式執行。
- 檢查結果 Markdown：預設依嚴重度、檢查分組，每項檢查的段落開頭先列「處理建議」與逐條的「常見原因」（反引號內轉成行內程式碼）；含證據原文與行號。開頭有一行「處理紀錄」列出各狀態（open 以外）的筆數。已處理的項目前面標出狀態與時間，復發的標「復發」，豁免與備註另起一行。
- 「依設備排序」：CSV 改依所屬設備排序，Markdown 改依設備分組（每組標題是設備名稱與筆數，不屬於任何設備的最後一組），組內保留原順序。同一項檢查會出現在很多台設備，所以依設備分組時，處理建議與常見原因集中在報表最後的「附錄：處理建議與常見原因」，只列這份基準有出現的檢查，每項一次，依 `CATALOG` 的順序。
- 網路文件：`V.exporter.KINDS.siteMarkdown`／`siteCsv`（`sitedoc-<baseName>.md`／`.csv`），內容由核心的 `S.report.siteDocMarkdown`／`siteDocCsv` 產生（[設計說明第 3 節「網路文件」](設計說明.md#3-模組)），畫面另外只傳兩個選項：`ledgerOf`（同檢查結果，`App.exportAs` 加上）與 `zones`（和 L4 畫面同一份 `V.l4.zoneOpts(App).opts`）。工作包不放網路文件。
- 預期現況：`S.compare.expectedFrom(Q)` 的結果（`ssot-expected/1`）。
- devices.csv 草稿：見上，不加 BOM、換行用 LF（`collect.sh` 以 bash 逐行讀取）。
- 修正計畫：每台設備三個 `.rsc` 與總表 Markdown，見[第 5 節](#5-各面板的資料來源)的「修正計畫」。
- 處理紀錄：`ledger-<目前時間>.json`，見上。
- 工作包：`workpack-<baseName>.zip`（`A.workpackName()`，例如 `workpack-20260101T000000Z-42dev.zip`），由 `S.workpack.build` 產生（[設計說明 第 10A 節](設計說明.md#10a-工作包ssot-workpack1)）。各角色在 manifest 的 `name`（ZIP 內的路徑由核心依 `safeSegment` 產生）沿用各匯出的檔名：

  | 角色 | 檔名 |
  |---|---|
  | `source` | 收集檔的來源名稱（貼上的內容是 `(貼上的內容)`，半形括號；畫面顯示成全形，見 `V.fileName`） |
  | `snapshot` | `baseline-<baseName>.json`（和「基準 JSON」相同） |
  | `ledger` | `ledger-<建立時間>.json` |
  | `profile` | `profile-<id>.json`（沒有 id 時 `profile-unnamed.json`） |
  | `expected-data` | `expected-data.json` |
  | `expected` | 載入預期現況時的檔名 |
  | `report` | `findings-<baseName>.csv`、`findings-<baseName>.md` |
  | `patch` | 修正計畫每台設備的 `<base>.rsc`、`<base>-rollback.rsc`、`<base>-verify.rsc`，加上 `patch-summary-<baseName>.md` |

  JSON 都以兩格縮排寫出；基準 JSON 和下載的相同（`V.exporter.snapshotJson`）。
- 檔名含建立時間與設備數，例如 `findings-20260101T000000Z-42dev.csv`、`devices-draft-20260101T000000Z-42dev.csv`。
- 拓樸圖 PNG（`A.exportPng`）固定用亮色（多半貼進報告或列印）：暫時套亮色畫一次、取得圖檔後還原目前的配色並重畫，畫面不受影響。PNG 畫的是目前的層級，檔名依層級：設備圖 `topology.png`、L2 埠圖 `topology-l2.png`、L3 網段圖 `topology-l3.png`（`A.layerPngName`）。L4 可達性沒有 PNG，以提示列說明。
- L4 zone 矩陣 CSV：`l4-matrix-<baseName>.csv`，選了單一服務時加上服務（例如 `l4-matrix-<baseName>-tcp-443.csv`），有 VRF 篩選時再加上 `-vrf-<VRF>`（VRF 名稱中英數字、`.`、`-`、`_` 以外的字元換成 `_`）。每一格一列，欄位依序是來源 zone、目的 zone、zone 內、狀態、結果不一、允許、拒絕、無法判斷、總數、代表規則、無法判斷的原因；zone 在兩個以上的 VRF 時，最後多「來源 VRF」「目的 VRF」兩欄（其他欄位的位置不變）。有 VRF 篩選時只有篩選後的格子。BOM、換行與儲存格的處理和檢查結果 CSV 相同。
