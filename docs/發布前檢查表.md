# 發布前檢查表（真實瀏覽器）

`npm test` 的畫面測試（`tests/ui-smoke.js`）用的是模擬 DOM，以下這些只有真實瀏覽器才有的行為測不到：

- Canvas 繪圖、縮放與高解析度螢幕
- 鍵盤焦點、觸控與系統的顯示偏好（強制色彩、減少動態效果）
- `index.html` 的 Content-Security-Policy
- 用 `file://` 直接開啟時的載入行為
- ELK.js 的動態 `<script>` 載入
- IndexedDB 的儲存與還原
- Blob 下載（匯出檔案、修正計畫的 `.rsc`、處理紀錄）
- 剪貼簿（修正指令的「複製」）
- 部署到 GitHub Pages 後實際發布了哪些檔案

本專案零相依、可離線，不引入 Playwright 這類工具，改在發布前由人照這份清單手動檢查。每一項都寫了操作步驟與預期結果；結果與預期不符就是失敗，請把畫面、Console 訊息與瀏覽器版本記下來開 issue。

畫面上各功能的完整說明見 [README 的「使用」](../README.md#使用)，這份清單只列要檢查的地方。

## 0. 準備

1. 在要發布的 commit 上先執行 `npm test`，全部通過再開始。
2. 準備兩個乾淨的瀏覽器設定檔，或先清掉這個頁面的網站資料（Chrome／Edge：開發者工具 → Application → Storage → Clear site data；Firefox：開發者工具 → Storage → 在 Indexed DB 的 `topo-mikrotik` 上按右鍵刪除）。舊的儲存會讓「第一次開啟」的項目看不出結果。
3. 大型資料項目（第 9 節）需要先執行 `npm run gen:large`，產生 `samples/large-1000.txt`（約 16 MB，不提交）。
4. 每個瀏覽器都從第 1 節做到第 9 節，結果填進第 11 節的紀錄表。第 10 節只在 main 部署到 GitHub Pages 之後做一次。
5. 準備一段小型輸入，下稱「EDGE 輸入」。它有名稱含 `WAN` 的 interface list 但沒有成員，用來看第 7、8 節範例資料沒有的情況（會得到 C02 與 F08）：

   ```
   EDGE (10.0.0.1):
   ### /export terse
   /interface list add name=WAN
   /ip address add address=10.0.0.1/24 interface=ether1 network=10.0.0.0
   /ip firewall filter add action=accept chain=input protocol=tcp dst-port=22
   _____
   ```

## 1. 用 `file://` 開啟、CSP 與載入

**1.1 開啟頁面**

- 步驟：在檔案總管雙擊 `index.html`（網址列應為 `file:///…/index.html`）。開發者工具先開好 Console 與 Network 分頁，再重新整理一次。
- 預期：
  - 出現「建立網路基準」的歡迎卡片；頁尾顯示「RouterOS 網路基準 <版本>」，版本與 `src/core/ns.js` 的 `S.VERSION` 相同。
  - Console 沒有任何紅色錯誤：沒有 `Content-Security-Policy`／`Refused to…` 訊息，也沒有 `net::ERR_FILE_NOT_FOUND`、`Failed to load resource` 或 `… is not defined`。
  - Network 只有 `file://` 的本機檔案（`assets/app.css`、`src/…`、`profiles/…`、`samples/sample-bundle.js`）與 `data:` 的網站圖示，沒有任何 `http(s)://` 請求。
  - 這時還沒有載入 `vendor/elkjs-…/elk.bundled.js`（ELK 要等第一次需要分層版面時才載入）。

**1.2 CSP 確實生效**

- 步驟：在 Console 執行 `fetch('https://example.com/')`。
- 預期：請求被擋下，Console 出現違反 `connect-src 'none'` 的訊息，Promise 以錯誤結束（Chrome／Edge 訊息為 `Refused to connect to …`，Firefox 為「內容安全政策」相關訊息）。如果請求真的送出去，代表 CSP 沒有生效，算失敗。

**1.3 本機儲存可用**

- 步驟：看畫面中央上方是否出現提示列。
- 預期：沒有出現「這個瀏覽器無法使用本機儲存，關閉頁面後基準不會保留。」。若出現（例如某些瀏覽器的 `file://` 或隱私模式不提供 IndexedDB），第 3、4、5 節的「重新整理後保留」會全部不成立；請在紀錄表註明，並確認這個提示確實有顯示（不靜默失敗）。

## 2. 範例資料與兩段式版面

**2.1 建立範例基準**

- 步驟：按歡迎卡片的「用範例資料試試看」（或「建立基準…」→「載入範例資料」），再按對話框右下的「建立基準」。
- 預期：
  - 進度條走完後對話框關閉，提示列顯示「已建立基準：… 台已收集設備、… 條鏈路；錯誤 …、警告 …（… 秒）」。
  - 頂端出現基準摘要（錯誤／警告筆數、收集完整度與四個入口按鈕）；左側「檢查結果」第一個錯誤或警告群組自動展開。
  - 頁尾列出建立時間、設備與鏈路數、命名規則、輸入指紋與版本。
  - 右側的「總覽」有「基準鍵」一列（16 位十六進位）。

**2.2 先內建版面，再套用 ELK**

- 步驟：建立後立刻看拓樸圖與提示列；同時看 Network 分頁。
- 預期：
  - 圖馬上出現（內建版面），提示列先顯示「分層版面計算中…」。
  - Network 出現一次 `vendor/elkjs-0.11.1/elk.bundled.js`（路徑以 `src/view/graph/elk-layout.js` 的 `ENGINE_SRC` 為準）；Console 沒有錯誤。
  - 數秒內節點位置改變並自動「全圖」，提示列改為「已套用分層版面（N 台網路設備，M ms）」。
  - 若顯示「分層版面未套用：…，維持快速版面」，記下原因；範例資料不應出現這個提示，出現就算失敗。

**2.3 切換版面模式**

- 步驟：工具列的版面選單改成「快速（內建）」，再改回「分層（ELK）」。
- 預期：改成快速時節點立即重排、不出現 ELK 提示；改回分層時再出現「分層版面計算中…」→「已套用分層版面…」，Network 不會再載入一次 `elk.bundled.js`。

## 3. Canvas 繪圖與操作

**3.1 繪圖與互動**

- 步驟：滾輪縮放、拖曳空白處平移、按「全圖」；滑過一條連線與一個節點；點一台設備；雙擊一台設備。展開左下「圖例」。
- 預期：
  - 縮放、平移流暢，沒有殘影或空白區塊；「全圖」把整張圖放進畫面。
  - 滑過時出現浮動說明（連線顯示兩端設備與埠名，節點顯示名稱與類型）；滑過的節點本身有一圈深色細環。
  - 點設備時右側顯示詳細資料，節點有藍色粗環；雙擊時圖面聚焦到那台設備。
  - 圖例分「設備」「終端」「連線」「連線註記」「標示」五類。
  - 有錯誤的設備在右上角是**方形**標記、有警告的是**三角形**，主機與終端也有；有問題的連線在中點有同樣的外形。圖例「標示」的外形與圖上相同。
  - 推論鏈路是長虛線，單側觀察是點線，顏色仍依連線類別；1G、10G、40G 的線寬依序變粗。同兩台設備間有多條鏈路時是中間有細縫的雙線。與圖例對照，樣式一致。
  - 圖例「終端」最多列 8 個廠商，其餘寫成「其他廠商（N 家）／不明」（沒有其他廠商時是「其他廠商／不明」）。
  - 過長的設備名稱在圖上截斷並加「…」，滑過時的說明是完整名稱。

**3.2 高解析度與視窗大小**

- 步驟：在縮放比例 150% 以上的螢幕（或瀏覽器縮放 200%）檢視；拖曳視窗變窄再變寬；拖曳左右欄邊緣的分隔線。
- 預期：線條與文字清晰不模糊；改變視窗或欄寬後圖面跟著重繪，不變形、不留白邊。視窗寬度 900 px 以下時畫面上方出現「拓樸」「檢查／清單」「詳細資料」三個工作區按鈕，可切換。

**3.3 匯出 PNG**

- 步驟：按工具列「匯出 PNG」，用圖片檢視器開啟（最好是會用棋盤格顯示透明背景的檢視器）。
- 預期：下載 `topology.png`，內容是目前圖面（與畫面看到的範圍相同），背景是畫布的淺色底色，**不是透明**。

**3.4 鍵盤操作**

- 步驟：
  1. 按 Tab 直到焦點移到拓樸圖（或點一下拓樸圖的空白處）。
  2. 按 N 數次，再按 Shift+N。
  3. 按 Enter；再按 N 移到另一台，按 Shift+Enter；再按 Esc。
  4. 按方向鍵、Shift＋方向鍵、+、-、0。
  5. 開啟螢幕閱讀器（Windows 朗讀程式或 NVDA、macOS VoiceOver），重複第 2 步。
- 預期：
  - 第 1 步：用 Tab 移到拓樸圖時有明顯的焦點框。
  - 第 2 步：N 依畫面位置（由上而下、由左而右）移到下一台設備，以滑過的深色細環標示並顯示浮動說明；設備在畫面外時圖面自動平移到它；Shift+N 往回。
  - 第 3 步：Enter 選取這台並在右側開啟詳情；Shift+Enter 聚焦到那台設備（同雙擊）；Esc 取消選取。
  - 第 4 步：方向鍵平移，按住 Shift 移動較多；+／- 以畫面中央為中心縮放；0 回到全圖。按這些鍵時頁面本身不捲動。
  - 第 5 步：螢幕閱讀器讀出移到的設備，結尾是「按 Enter 開啟詳情」。
- 也檢查：檢查結果分頁的篩選標籤（嚴重度、只看新出現的等）可以用 Tab 聚焦，按 Enter 或空白鍵切換。

**3.5 觸控**

- 步驟：在觸控螢幕（或開發者工具的裝置模擬並啟用觸控）上：拖曳空白處；拖曳一台設備；點一下一台設備；快速點兩下一台設備；點兩下一個「終端 ×N」群組。
- 預期：拖曳空白處平移、拖曳設備移動位置；點一下選取並在右側顯示詳細資料；點兩下聚焦到那台設備；點兩下群組會展開。小的終端節點也點得到。平移時頁面本身不捲動、不縮放。

**3.6 強制色彩（Windows 高對比）**

- 步驟：Windows 設定 → 協助工具 → 對比佈景主題，選一個佈景主題後回到頁面（或在 Chrome／Edge 開發者工具的 Rendering 分頁模擬 `forced-colors: active`）。用 Tab 移動焦點，並按下幾個切換按鈕（例如工具列的「分群」、檢查結果的「依設備」）。
- 預期：焦點與「選取中」的按鈕都有系統色的外框，看得出目前在哪裡；嚴重度標記與圖例色塊仍保留原本的顏色與外形；文字都看得到。

**3.7 減少動態效果**

- 步驟：開啟系統的「減少動態效果」（Windows：協助工具 → 視覺效果 → 動畫效果關閉；macOS：輔助使用 → 顯示器 → 減少動態效果；或開發者工具 Rendering 分頁模擬 `prefers-reduced-motion: reduce`），重新整理後按工具列「力導向排列」，並展開、收合幾個區塊。
- 預期：「力導向排列」不播動畫，節點直接移到結果位置；展開、收合沒有轉場動畫。關閉這個設定後，「力導向排列」恢復逐步移動的動畫。

## 4. 節點位置與「清除」

**4.1 拖曳後重新整理**

- 步驟：等 2.2 的分層版面套用完成。把一台設備拖到明顯不同的位置，放開後等 1 秒以上，按 F5 重新整理。
- 預期：
  - 提示列顯示「已還原上次建立的基準（<建立時間>）」。
  - 剛才拖曳的設備仍在新位置，其他節點維持分層版面的位置。
  - 這次不會再出現「分層版面計算中…」（有儲存位置時不重新計算）。
- 也檢查：開發者工具的 IndexedDB `topo-mikrotik` → `kv` 有 `last` 與 `ledger` 這兩個鍵。

**4.2 「清除」只清除基準與輸入**

- 步驟：先完成第 5.1 節，讓至少一筆檢查結果不是待處理，並拖曳左右欄寬度。然後按頁首「清除」→ 在確認對話框按「確定」。
- 預期：
  - 畫面回到歡迎卡片，搜尋、路由追蹤、清除按鈕停用。
  - IndexedDB `kv` 裡 `last` 不見了；`ledger` 仍在；若調過欄寬或切換過版面模式，`layout`／`layoutMode` 也仍在。
  - 重新整理後仍是歡迎卡片，沒有還原提示；欄寬維持調整後的寬度。
  - 再用範例資料建立一次基準：之前變更過狀態的檢查結果仍是同樣的狀態；節點位置是新算的（會再出現分層版面的提示）。
- 也檢查：在確認對話框按「取消」時什麼都不清除。

## 5. 檢查結果：處理、分組與處理建議

**5.1 處理狀態與備註**

- 步驟：
  1. 在左側「檢查結果」展開 K01（LLDP 單向，警告）的群組，按其中一筆旁邊的「處理」。記下頂端摘要的錯誤／警告筆數。
  2. 出現狀態選單與備註欄：狀態選「可接受（豁免）」，不填豁免原因，按「儲存」。
  3. 豁免原因填「測試」，到期日維持預設，按「儲存」。
  4. 展開「可接受（豁免）」群組，按這一筆的「處理」，狀態改成「已排程修復」，備註填「測試 11/30」，按「儲存」（在備註欄按 Enter 也可以；按 Esc 或「取消」不儲存）。
  5. 另找一筆待處理的，按「處理」，狀態選「已修好」，按「儲存」。
  6. 按 F5 重新整理。
- 預期：
  - 第 1 步：狀態選單只列目前的狀態與可以改成的狀態（待處理可以改成已排程修復、可接受（豁免）、誤報、已修好）；選「可接受（豁免）」時才出現豁免原因與到期日，到期日預設約半年後。
  - 第 2 步：欄位下方顯示「可接受需要填寫原因」，資料沒有改變。
  - 第 3 步：那一筆移到下方「可接受（豁免）」群組，原本的群組筆數少 1（只有一筆時整個群組消失），頂端摘要的對應筆數也少 1，摘要註明「（另有 1 項已處理）」。群組中這一筆顯示狀態標籤、「可接受（豁免）：<時間>」與「豁免原因：測試・到期 <日期>」。
  - 第 4 步：這一筆改列在「已排程修復」群組，顯示「已排程修復：<時間>」與「備註：測試 11/30」，時間是這次修改的時間。
  - 第 5 步：欄位下方顯示「無法變更：這個項目仍出現在最新一輪基準中，不能手動標為 fixed…」，那一筆維持待處理。
  - 第 6 步：狀態、備註與時間都不變，摘要筆數與重新整理前相同。
  - 這一筆保持「已排程修復」，第 5.4、6、7 節會用到。
- 也檢查：點這一筆，右側詳情的檢查結果下方顯示「已排程修復」與備註。

**5.2 依設備分組**

- 步驟：在檢查結果上方按「依設備」，展開幾個群組，再按「依規則」切回。
- 預期：群組標題是設備名稱，依名稱順序排列；每筆前面標出規則代碼；不屬於任何設備的檢查結果（如果有）在最後一組「不屬於任何設備」。切回「依規則」後恢復原本的分組。

**5.3 常見原因與處理**

- 步驟：
  1. 點一筆 K01 或 F07，在右側詳情的檢查結果展開「常見原因與處理」。
  2. 在左側下方展開「通過」或「沒有資料可檢查」，再展開其中一條規則的「常見原因與處理」。
- 預期：
  - 預設收合；展開後先列「處理：」再列「常見原因：」（逐條），內容與 [基準檢查規則](基準檢查規則.md) 該規則的「處理」「常見原因」一致。
  - RouterOS 指令與欄位（例如 `/ip neighbor discovery-settings`、`available-from`）以等寬字型顯示、有淺色底，**看不到反引號**（`` ` ``）。看到反引號或 HTML 標籤原樣出現，就算失敗。
  - 規則清單的展開狀態在切換篩選、重新繪製後仍保留。

**5.4 處理紀錄分頁與收斂趨勢**

- 步驟：
  1. 切到左側「處理紀錄」分頁。
  2. 製造第二輪：按「建立基準…」→「載入範例資料」，在輸入框最後加一行註解 `# round 2`，按「建立基準」。
  3. 回到「處理紀錄」分頁。把滑鼠移到折線圖上，再用 Tab 移到圖上的每一輪。展開「表格檢視」。
- 預期：
  - 第 1 步：上方列出各狀態的筆數（至少有「已排程修復 1」）；「修復追蹤」的「已排程修復」列出第 5.1 節那一筆，標示「目前基準仍有」；「收斂趨勢」寫「目前只有一輪，下一輪基準建立後才會畫出趨勢。」並列出待處理、回歸、已豁免、覆蓋率、未知對端五個數字。
  - 第 2 步：輸入不同，所以是新的一輪；檢查結果沒有改變，所以本輪變化的新出現、已修好、回歸都是 0。

## 6. 匯出檔案

先保留第 5.1 節那一筆「已排程修復」，以便檢查匯出的處理紀錄欄位。下列 `<時間>` 是基準建立時間（UTC）去掉分隔符號，例如 `20260101T000000Z`；`<N>` 是設備數（頁尾「設備 N」）。

| 操作 | 預期檔名 | 預期內容 |
|---|---|---|
| 工具列「匯出 JSON」 | `baseline-<時間>-<N>dev.json` | 可用文字編輯器開啟的 JSON，`meta.schema` 是 `ssot-snapshot/2`，`meta.version` 與頁尾版本相同，另有 `meta.baselineKey` |

| 檢查結果分頁「Markdown」 | `findings-<時間>-<N>dev.md` | 見 6.2 |

三種瀏覽器都要確認：檔名完全相同（不是 `download`、不是亂碼、沒有被加上 `.txt`），下載不需要網路，Console 沒有錯誤。

**6.1 CSV 用 Excel 開啟**

- 步驟：在 Windows 的 Excel 直接雙擊 `findings-….csv`（不要用「資料 → 從文字匯入」）。
- 預期：
  - 第一列是 `severity, id, title, message, entities, evidence, acknowledged, ack_kind, ack_note, device, action, status, note, waiver_reason, waiver_until` 十五欄，中文標題與訊息正常顯示，沒有亂碼。
  - 資料列數等於 Markdown 報表「檢查結果：錯誤 …、警告 …、提醒 …」三個數字的總和（CSV 含已處理的項目）。
  - 含逗號或換行的訊息仍在同一格，沒有被拆成多欄。
  - 已排程修復的那一列：`acknowledged` 是 UTC 時間、`ack_kind` 是 `scheduled`、`ack_note` 是「測試 11/30」，`status` 是 `scheduled`、`note` 是「測試 11/30」；待處理的列 `acknowledged`、`ack_kind`、`ack_note` 空白，`status` 是 `open`。
  - 屬於某台設備的列，`device` 是設備鍵（範例資料中就是設備名稱）；每一列的 `action` 都有處理建議，指令保留反引號（例如 `` `/ip neighbor` ``），沒有被拆成多欄。
- 也檢查：按檢查結果分頁的「依設備排序」後再匯出 CSV，資料列依 `device` 排序，`device` 空白的列在最後。

**6.2 Markdown 報表**

- 步驟：用文字編輯器開啟 `findings-….md`；再按「依設備排序」匯出一次，開啟新檔。
- 預期：
  - 開頭是「# 基準檢查報表」，有一行 `- 處理紀錄：已排程修復 1`（有其他狀態時一併列出）。
  - 已排程修復的那一筆寫成 `- **已排程修復**（<時間>） <訊息>`，下一行是 `  - 備註：測試 11/30`。
  - 預設（依規則）：每條規則的段落開頭有「- 處理建議：」與「- 常見原因：」，常見原因逐條列成子項目，指令寫成行內程式碼（`` `…` ``）。
  - 依設備：各設備一段「## <設備名>（<筆數>）」，不屬於任何設備的在最後；報表最後有「## 附錄：處理建議與常見原因」，每條有出現的規則只列一次。各設備段落裡不再重複處理建議。

**6.3 預期資料讀回**

**6.4 devices.csv 草稿**

  - 第 2 步：「選取檢查結果（已選 1 項）」；摘要是「可產生指令 1 項（1 台設備）」；TPE_CORE_RT_01 那一段列出修改前（基準的原文，含檔名與行號，點一下開啟原始輸出）與修改後（套用指令）、說明與「風險 低」。只有一台設備時，直接有三個下載按鈕。
  - 第 3 步：兩台設備（TPE_CORE_RT_01、TPE_CORE_RT_02）各一段；F02 列在「沒有產生指令的項目」，分組標題是中文說明（不是 `ambiguous-find` 這類代碼），內容說明 find 無法區分；選 TPE_CORE_RT_01 的全部之後，其他規則的項目依「需要選擇處理方式」「需要人工判斷」等原因分組列出。
  - 第 4 步：套用檔的前置檢查（`:if ([:len [… find where …]] != 1) do={ :error … }`）全部在 `# ---- apply` 之前；回復檔把 `disabled=yes` 改回 `disabled=no`；驗證檔是 `print where …`，註解寫出預期結果。檔案內容只有 ASCII（沒有中文）。下載的檔名是 `<設備>.rsc`、`<設備>-rollback.rsc`、`<設備>-verify.rsc`，內容與畫面相同。複製時提示列顯示「已複製<檔名>；執行前請逐行核對。」。
  - 第 5 步：每台設備三個 `.rsc`，加上 `patch-summary-<時間>-<N>dev.md`；瀏覽器可能會詢問是否允許下載多個檔案，允許後全部下載完成。總表列出每台設備的檔名、項目數與最高風險，以及沒有產生指令的項目與原因。
  - 第 6 步：勾選的那一筆出現在計畫中；從防火牆畫面開啟時，選取的是那台設備可修正的檢查結果。
- 也檢查：建立另一份基準（例如 EDGE 輸入）後再開啟修正計畫，選取已經清空。

## 9. 大型資料（約 1000 台）

- 步驟：
  1. 執行 `npm run gen:large`。
  2. 在頁面按「建立基準…」→「選擇檔案…」，選 `samples/large-1000.txt`，按「建立基準」。用手錶或提示列的秒數記錄時間。
  3. 建立完成後操作：滾輪縮放、拖曳平移、在搜尋輸入一台設備名稱並選取、點左側一筆檢查結果、雙擊一個「終端 ×N」群組節點展開；在拓樸圖上按住 N 鍵幾秒。
  4. 按 F5 重新整理。
- 預期：
  - 建立過程中進度條與狀態文字持續更新，分頁沒有被瀏覽器判定為「沒有回應」。提示列的建立秒數記入紀錄表，作為和上一次發布比較的基準（Node 上的參考數字見 [設計說明 §9](設計說明.md#9-規模)）。
  - 先出現內建版面；之後出現「已套用分層版面（約 1000 台網路設備，… ms）」，或因超過 20 秒顯示「分層版面未套用：分層版面超過 20 秒，維持快速版面…」。兩者都算通過（不是當機），記下是哪一個與毫秒數。若顯示「超過分層版面上限」，與 [設計說明 §12](設計說明.md#12-未知對端210-新增) 不符（該節寫明約 1000 台網路設備時約 2.4 秒可套用），算失敗。
  - 主機數量超過 300 台，所以工具列「主機」按鈕預設沒有按下、圖上不畫主機。
  - 縮放、平移沒有明顯卡頓（每次操作 1 秒內有反應）；搜尋下拉選單 1 秒內出現；展開群組後新節點排在所屬設備下方；按住 N 鍵時移動與自動平移跟得上。
  - 這份資料是乾淨網路，左側沒有錯誤與警告。
  - 重新整理後還原同一份基準；若提示「基準太大，無法存入瀏覽器；關閉頁面後需要重新建立。」，記在紀錄表（這是明確告知，不算失敗，但要記下是哪個瀏覽器）。

## 10. GitHub Pages 上線後

main 合併後，等 Actions 的「Deploy site to GitHub Pages」完成，再用一個瀏覽器做一次。網站只發布畫面需要的檔案（見 [README 的 CI](../README.md#ci)）。

**10.1 開啟與 ELK**

- 步驟：開啟 <https://sinnoken.github.io/topo-mikrotik/>，開發者工具先開好 Console 與 Network，重新整理後按「用範例資料試試看」並建立基準。
- 預期：
  - 頁尾版本與這次發布的 `S.VERSION` 相同（不是舊版的快取；不同時強制重新整理一次）。
  - Console 沒有紅色錯誤；Network 只有 `sinnoken.github.io` 的檔案，全部是 200（或快取的 304），沒有 404。
  - Network 出現一次 `vendor/elkjs-0.11.1/elk.bundled.js`（路徑以 `ENGINE_SRC` 為準），狀態 200；提示列最後顯示「已套用分層版面（…）」。

**10.2 不該發布的路徑**

- 步驟：在網址列逐一開啟下列網址。
  - `https://sinnoken.github.io/topo-mikrotik/tests/run.js`
  - `https://sinnoken.github.io/topo-mikrotik/tools/collect.sh`
  - `https://sinnoken.github.io/topo-mikrotik/docs/`
  - `https://sinnoken.github.io/topo-mikrotik/package.json`
  - `https://sinnoken.github.io/topo-mikrotik/README.md`
  - `https://sinnoken.github.io/topo-mikrotik/.claude/agents/ownership.json`
- 預期：每一個都是 GitHub Pages 的 404 頁面。有任何一個顯示出內容就算失敗。
- 也檢查：`https://sinnoken.github.io/topo-mikrotik/samples/sample-bundle.txt` 仍然可以開啟（`samples/` 是畫面需要的檔案，應該發布）。
