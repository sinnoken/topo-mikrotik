# topo-mikrotik 設計說明（MikroTik RouterOS 專用版）

> 這是 topo-ssot 的 **MikroTik 專用版**：核心架構、模型、檢查、畫面與多廠牌版相同，只有「輸入解析器」、設備類型推論與少數檢查不同。差異見第 13 節。以下內容以本版為準。

範圍：MikroTik RouterOS（7.x 為主）｜規模：約 1000 台已收集設備｜一次貼完、在瀏覽器即時產生｜不需網路、不需後端

---

## 1. 目的

由設備 CLI 輸出建立一份**可信的網路現況基準（Snapshot）**，並回答：

1. 網路結構是什麼？
2. 某個 MAC／IP／VLAN 在哪裡？
3. 哪些地方資料互相矛盾、哪些地方沒有收集到？

圖、表、路由追蹤都只是檢視這份基準的方式。

## 2. 原則

| # | 原則 | 實作方式 |
|---|---|---|
| P1 | 一次建立、不增量合併 | `SSOT.build(sources, options) → Snapshot`；同輸入同結果（有測試） |
| P2 | 核心與外掛分離 | 輸入格式（readers）、命名規則（profile）、比對（compare）都可拔除 |
| P3 | 依賴單向 | 外掛讀核心；核心不讀外掛；比對只透過查詢介面讀基準 |
| P4 | 每筆事實帶來源 | 事實帶「區塊、行號」；畫面可開啟原文並標示該行 |
| P5 | 不靜默失敗 | 無法辨識的內容、辨識成功卻解析不出東西的段落列入 I01；已解析的區塊中認不得的行列入 I03 |
| P6 | 核心不碰畫面與儲存 | 核心可在 Node 執行（測試即如此） |

## 3. 模組

```
        ┌──────────── 外掛（可拔除）─────────────┐
        │ readers/   bundle-v1、files-v1         │
        │ profile/   命名規則引擎＋profiles/*.js  │
        │ compare/   預期資料比對、新舊基準比對    │
        └──────┬────────────┬──────────┬────────┘
               ▼            ▼          ▼ 只讀
        ┌──────────────────── 核心 ─────────────────────┐
        │ adapters/  辨識＋解析 → 事實（fact）             │
        │ model/     build.js 事實→實體；infer.js 推論     │
        │ check/     一致性檢查、覆蓋率                     │
        │ core/      keys.js 唯一鍵、ip.js、ns.js           │
        │ pipeline.js  ①讀取→②辨識→③解析→④建模→⑤推論→⑥檢查 │
        │ query/     唯讀查詢、路由追蹤                     │
        └──────────────────────┬──────────────────────────┘
                               ▼
                           Snapshot（純 JSON）
                               ▼ 只讀（SSOT.query）
        ┌──────────── 下游（只讀基準）──────────────────┐
        │ remediate/ 修正 patch（ssot-patch/1，只產生文字）│
        │ ledger/    處理紀錄（ssot-ledger/1，不在基準內） │
        └──────────────────────┬──────────────────────────┘
                               ▼
              view/（單一畫面：檢查結果｜拓樸圖｜詳細資料）
```

`remediate/` 與 `ledger/` 也是核心檔案（列在 `tools/core-files.js`，不碰畫面與儲存），但它們在 Snapshot 的下游：只透過 `SSOT.query()` 讀基準，不修改基準，也不被上游的 pipeline 使用。修正 patch 見[第 15 節](#15-修正-patchssot-patch1)，處理紀錄見[第 16 節](#16-處理紀錄ssot-ledger1)。

所有檔案都是一般 `<script>`，以 `globalThis.SSOT` 命名空間串接；載入順序定義在 `tools/core-files.js`，測試會檢查 `index.html` 與它一致。這樣 `index.html` 可以直接雙擊開啟（瀏覽器在 `file://` 下不允許 ES module 與 Web Worker）。

`check/` 分成兩個檔案：`catalog.js` 是規則目錄（`S.check.CATALOG`：編號、嚴重度、類別、標題、需要的資料、常見原因 `causes` 與處理方式 `action`），`checks.js` 是判斷。`catalog.js` 必須在 `checks.js` 之前載入；順序錯了，`checks.js` 載入時會直接丟出錯誤，不會在沒有規則目錄的情況下執行。`causes`、`action` 只在 `CATALOG`，不複製到 finding，也不進 Snapshot；畫面與匯出透過 `V.remediation.advice()` 讀取（見[第 14 節](#14-檢視狀態與匯出)）。

## 4. 輸入

```
原始輸入 ─Reader─▶ Block[] ─辨識─▶ Block＋adapter ─Adapter─▶ Fact[]
```

- **Block**：`{ device, mgmtIp, command, lines, origin:{file,startLine,endLine} }`；有 SSH 收集器的註解時另有 `collectedAt`（指令開始的 UTC 時間）、`failure`（`{ reason, exitCode, text, line }`），註解寫錯時記在 `issues`（由 I01 列出）。註解格式見[收集清單 §2「其他規則」](收集清單與輸入格式.md#其他規則)。
- **Reader**：`bundle-v1`（設備標頭＋`_____`）、`files-v1`（檔名＝設備名）。介面：`accepts(text,file)`、`read(text,file)`。
- **指令標記**：`### 指令`、RouterOS 提示字元 `[user@id] > /指令`（須為絕對路徑）。有標記時依指令選 adapter，否則依內容判斷。
- 所有 `print` 指令都要用 `detail without-paging`（key=value 格式）。詳見 `docs/收集清單與輸入格式.md`。
- **Adapter 介面**（`src/adapters/index.js`）：`{ id, vendor, dataType, label, command, detect(lines), parse(block, emit, ignore) }`。`parse` 只把文字轉成事實，每筆事實帶 `line`；`ignore(line, why)` 宣告這一行依該指令的格式本來就不產生事實（說明行、續行、停用的項目等），`why` 是簡短原因。
- **每一行都要有去處**：`S.adapters.parse(block, adapters, decorate)` 以辨識出的 adapter 解析區塊，回傳 `{ facts, usage, ignored, unrecognized }`。已解析區塊中的每個非空行，不是產生事實的行，就是 adapter 宣告可忽略的行；**兩者都不是，就是無法辨識**，記在 `blocks[].unrecognizedLines` 並列為 I03。所以 adapter 只宣告可忽略的行，沒處理到的行一定會被列出。多個 adapter 時，任一個產生事實或宣告可忽略就算有處理。
- **RouterOS 錯誤訊息**：`S.adapters.util.rosError(line)` 判斷一行是不是 RouterOS 的錯誤回應（行首的 `bad command name`、`syntax error`、`no such item`、`failure:` 等）。這種行一律算無法辨識，即使 adapter 宣告可忽略。
- **I01 與 I03**：整段沒有進入基準（沒有設備標頭、沒有解析器認得、辨識成功卻解析不出任何資料；整段只有 RouterOS 錯誤訊息時訊息改為「指令執行錯誤」）列為 I01；已解析出事實的區塊中個別認不得的行列為 I03。條件與可忽略的行見[基準檢查規則 I03](基準檢查規則.md#i03)。測試的不變式「每一行輸入都有被處理」逐行檢查範例資料與 `tests/fixtures/`：每個非空行都是結構行、產生事實、可忽略、I03 或 I01，而且 fixtures 不可有 I03。

**detail 輸出的解析**：以「列」為單位。列首是 `序號 旗標 key=value…`（序號、旗標可省略）；直接以 key=value 開頭的行是終端機換行的續行，併入上一列；`;;; 註解` 屬於它所在或下一列。只有序號與旗標、欄位在下一行的列首（例如「13  R 」）也開新列；2.8.0 以前這種行會讓下一列被併進上一列（範例中 bond100 失去介面狀態、bridge1 拿到 bond100 的註解）。旗標必須是 `Flags:` 說明行列出的字元（沒有說明行時只接受英文字母），雜訊不會被當成列首。
新增廠牌：新增一支 `adapters/<vendor>.js` 呼叫 `S.adapters.register()`，其他部分不需修改。

### 5.2 實體（Snapshot.model，schema `ssot-snapshot/2`）

欄位命名參考 NetBox 的 DCIM／IPAM 模型（Device、Interface、VLAN、IPAddress、Prefix），但不照搬：只儲存能從 RouterOS 輸出取得或明確推論的內容。

| inferredLinks | key、a、b、bases（依據）、confidence（`high`／`medium`）、evidence（每項依據的說明與來源行）；推論，見 §5.3 |
| ospfAdjacencies | dev、localEp、peerDev、peerEp、peerIp、peerId、reciprocal、src |

**防火牆規則的鍵與簽章**

- `signature`：設備＋位址族＋表＋chain＋比對條件（清單值排序後的正規形式），不含動作與編號，供比對與重複判斷使用。
- `key`：`設備|位址族|表|chain|簽章雜湊`；同一個簽章在同一個 chain 第二次以後出現時加 `#n`。在 chain 中插入一條規則時，其他規則的鍵不變（除非新規則的簽章與後面某條相同）。

**Snapshot 的其他部分**

| 欄位 | 內容 |
|---|---|
| `blocks[]` | id、device、devKey、command、reader、adapters、how、file、start、end、empty、collectedAt（指令開始的 UTC 時間，沒有註解時為 null）、failure（`{ reason: timeout｜exit-code｜connection｜other, exitCode, text, line }`，沒有失敗時為 null）、unrecognizedLines（已解析區塊中無法辨識的行號，遞增；沒有時、以及整段列為 I01 的區塊為 `[]`，見 I03） |
| `coverage[]` | dev、collected、kind、data、missing（依類型應有、沒收到的資料類別）、interfaces、links、macs、failures（該設備收集失敗的區塊：`{ block, line, command, reason, exitCode, text, dataTypes }`，連線失敗的 command 為 null）、firewall（有設定資料的設備為 `{ rules, wan }`，wan 是 firewallZones 的 status；否則為 null） |
| `meta.stats` | 各實體筆數（含 `firewallRules`）與 findings 各嚴重度筆數 |
| `meta.inputHash` | 輸入指紋：所有來源的名稱與內容的雜湊，判斷是不是同一份輸入 |
| `meta.baselineKey` | 基準鍵：`hash(JSON [inputHash, 'major.minor', 命名規則的雜湊或 null, 預期資料的雜湊或 null])`。命名規則與預期資料是 build 選項 `profile`、`expectedData` 的內容，以鍵排序後的 JSON（`S.util.canonicalJson`）計算，所以同一個 id 與版本、內容不同的命名規則也能區分。版本只取 major.minor（patch 版不改變 Snapshot，見 [ADR-005](架構決策/005-版本升級規則.md)）；不含 createdAt 等與執行環境有關的欄位。和 inputHash 的差別：同一份輸入以不同的程式版本、命名規則或預期資料建立時，inputHash 相同、baselineKey 不同。用途是處理紀錄判斷「這份基準是否已經推進過」（[第 16 節](#16-處理紀錄ssot-ledger1)）。2.8.0 以前的基準沒有這個欄位 |

**只在內部模型、不序列化的組態**

跨設備組態一致性檢查（V06、V07、A06–A12、R06）用到的部分設定只存在內部模型 M，不寫進 Snapshot，§5.2 的欄位不變。這些檢查的 finding 以 `evidence` 指回 export 的原始行，多數決的推定結果放在 finding 的 `deviation`（見 §7）。

| 事實（adapter） | 內部模型 | 內容 |
|---|---|---|
| `ipBind` | `M.ipBinds` | dev、section（選單）、name、value，另有比對鍵 nameKey（trim＋小寫；DHCP 租約為正規化 MAC）、valueKey（/32 去遮罩、網段取網路位址）；供 A10、A11 |
| `dnsServers`、`ntpServers` | 設備的 `dnsServers`、`ntpServers` | `{ values, src }`，多個設定行取聯集；供 A12 |
| `dhcpNet` 的 `dns`、`ntp` | `M.dhcpNets[].dns`、`ntp` | dns-server、ntp-server；供 R06。Snapshot 的 `dhcpNetworks` 只輸出 gateways |

**設備身分**

- `deviceType`（型號）、`softwareVersion`、`platform`、`caps` 是事實。來源依序是設備自己的 `/system resource`，其次是鄰居回報；設備自報優先。
- `manufacturer` 是推論：資料來自 MikroTik adapter，或 platform 為 MikroTik／RouterOS 時為 `mikrotik`。
- `kind` 是設備類型推論。不使用 NetBox 的 `role`，因為 `role` 保留給命名規則的註解。

**介面**

- 欄位：
  - `type` 是封閉列舉 `S.IFC_TYPES`：`physical`、`lag`、`bridge`、`vlan`、`wireless`、`virtual`、`loopback`、`other`。原始 RouterOS 類型保留在 `rawType`，例如 veth 屬於 `virtual`，但 `rawType` 仍是 `veth`。
  - `typeBasis` 說明類型的依據：`rawType`、`member`（有聚合成員）、`name`（名稱慣例）或 `default`（缺資料，預設為實體埠）。
  - `enabled` 為 `false` 表示任一來源停用；為 `null` 表示沒有資料。
- 介面之間的關係都存 ep 鍵，分為三種，不共用欄位：
  - 聚合：`lag`／`lagMembers`
  - bridge port：`bridge`
  - VLAN 子介面：`parent`＋`encapVlan`
- VLAN 成員：
  - 欄位：`pvid`（bridge port 的 ingress 預設 VLAN）、`untaggedVlans`、`taggedVlans`，三者分開儲存。
  - 介面承載的全部 VLAN 用 `S.util.ifcVlans(i)` 取得；V01 以這個聯集（含所屬聚合）比較。
  - 不是數字的 VLAN 記在 `unresolvedVlans`，不丟棄。
- `mode` 是推論：有 tagged VLAN 為 `tagged`（trunk），只有 PVID／untagged 為 `access`，都沒有則為 `null`。

**IP 位址與前綴**

- 每個介面上的每個位址是一筆 `ipAddresses`，帶來源行。
- OSPF 鄰居位址以 `/32`、`hearsay: true` 儲存。
- `prefixes` 是推論，由設備自有、長度小於 32 的位址推導出直連網段。鄰居宣告的位址不產生前綴。
- 查詢介面：
  - `Q.ipOwner(ip)`
  - `Q.ipsOf(ep)`
  - `Q.addressesOf(ep)`
  - `Q.subnets()`
  - `Q.prefixes()`

**檢查結果與覆蓋的查詢**

- `Q.findingKey(f)`：finding 的穩定鍵，見[第 8 節](#8-比對獨立模組)。
- `Q.findingBaseKey(f)`（也可用 `SSOT.query.findingBaseKey`）：不含 facet 的鍵（id＋實體），也就是 2.9.0 之前的 findingKey；沒有 facet 的 finding 與 `Q.findingKey` 相同。給處理紀錄等轉換舊鍵用。
- `Q.findingDevice(f)`：finding 所屬的設備鍵。取第一個 `device` 實體；沒有時，取第一個能對到設備的介面、鏈路一端、防火牆規則、管理服務或設備自有的 IP。都對不到（例如沒有設備標頭的 I01、只涉及 MAC 或 VLAN 的檢查）時為 null。畫面的分組、匯出與修正 patch 都用它。
- `Q.coverage()`：Snapshot 的 `coverage[]`（每台設備收集了哪些資料、缺漏與收集失敗），沒有時為空陣列。處理紀錄用它判斷能不能判定已修好。

**相容性**

- 讀取 `ssot-snapshot/1` 的舊基準時：有儲存輸入就重新建立；沒有輸入就提示格式不相容，不會靜默略過。

每個由輸入事實產生的實體都帶 `src`（`[區塊, 行號]` 清單）。`src` 為空時，設備、介面、VLAN 另帶 `srcNone` 說明原因：`seen-only`（只由鄰居看到的設備）、`hearsay`（單側觀察的介面）、`implicit`（預設 VLAN）；有來源時為 `null`。`unrecorded` 代表應有來源卻漏記，測試禁止出現；已收集設備上的介面（含由 MAC 表隱式建立的）一定有來源。

### 5.3 關鍵推論

- **LLDP 配對與 bridge**：反向配對只採用對端的 LLDP／CDP 證據，MNDP 不算回報（對端只有 MNDP 仍是 K01）。兩端介面名稱比對時，bridge 本身（依 `rawType=bridge`，缺資料時依 `bridge*` 名稱）在兩端分別以 `bridge` 或 `bridge/成員` 回報，視為同一介面。
- **LLDP 對端埠名**：RouterOS bridge 成員的 `interface-name` 形如 `bridge/ether2`，adapter 取最後一段（`ether2`）作為對端實體埠，與本機 `interface=ether3,bridge` 取非 bridge 成員的規則對稱；原文保留在來源行。
- **鄰居邊語意**：LLDP／CDP 的觀察走介面鄰接推論；本機介面名稱是本機端依據，對端回報的 `interface-name` 是對端埠證據，無法配對時的平行埠排序配對仍屬推測。只有 MNDP 證據時，edge 表示兩台設備在同一 L2 broadcast domain 可達，不表示兩者直連，也不將回報的對端埠名視為實際配對埠；不套用直連專用的 K01／K02／K03／V01 檢查。`evidenceScope` 使用 `interface-adjacency`、`broadcast-domain` 或 `routing-adjacency`；`observations` 保留觀察介面及來源行。MNDP 沒有 domain ID，因此模型不宣稱完整廣播網域成員清單。同一對設備可因多個本機介面或雙向回報各有一條 MNDP link（Snapshot 保留全部以便追溯）；設備詳情的「鄰居」表由 `Q.neighborRows()` 併成每個對端設備一列，觀察介面合併列出。
- **自動群組名稱**：未套用 profile 分群的設備依拓樸鏈路分成連通元件，標為「自動群組 N」。這是版面分群提示，不是依 IP prefix 推導的子網名稱，也不表示群內設備都以實體線路直接相連；純 MNDP 證據同樣可能使設備位於同一群組。
- **鄰居配對**：LLDP／CDP 對端也有可配對的鄰居資料時雙向配對（`verified`）；對端有 LLDP／CDP 鄰居輸出但未回報此介面鄰接為單向（K01；只看雙方的 LLDP／CDP 證據，MNDP 不算回報）；對端沒提供鄰居資料則為單側觀察（hearsay，只計入覆蓋率）。鄰居 identity 對不上收集檔設備名時，用管理 IP 對回同一台。
- **OSPF 鄰接**：OSPF 是 IP 層鄰接證據，不加入 `links`，不作為拓樸直連 edge，也不與相同端點的 L2 edge 合併。單獨存於 `ospfAdjacencies`，設備詳細資料列出本機介面、鄰居、雙向回報狀態與來源。鄰居位址 → 擁有該 IP 的介面；找不到再用 router-id、管理 IP；都找不到建立以鄰居 ID 命名的未知設備（R02）。
- **設備類型**：型號（CRS／CSS→交換器；CCR／RB／hAP／hEX／CHR→路由器）→ 已收集設備依資料（有 OSPF→路由器；有 MAC 表且無路由→交換器）→ 未收集設備依鄰居回報的功能（router／bridge／station）→ 對端埠名像網路卡→主機。命名規則可覆寫並標示依據。
- **推論鏈路**（`inferredLinks`，推論，不寫進 `links`、不影響任何檢查）：給沒有 LLDP 的設備用，例如只支援 MNDP、也無法用 SSH 收集的 SwOS 交換器（CSS106、CSS610）。
  - **依據**：
    - `fdb`：MAC 表。A 的 p 埠學到 X 的 MAC，而 p 這側其他已知設備都能排除：
      - 已收集交換器在「不朝向 A」的埠看到它，代表它在那台交換器後面。
      - 它不轉送二層（沒有 bridge、沒有 MAC 表），不可能夾在中間。
      - X 有 MAC 表時，X 朝向 A 的埠不能和 A 這側看到同一台設備，否則兩者之間還有設備。

      X 是未收集的交換器時，同一埠學到、沒有 MAC 表的已收集設備（例如沒有 bridge 的路由器）推定接在 X 後面；p 這側還有其他未收集設備時不推論。已知 MAC 包括已收集設備的 `ownMacs`、介面 MAC，以及鄰居表回報的 MAC。
    - `stp`：埠的 RSTP 角色是 root／alternate／backup 時，`designated-bridge-id` 是這段網路上的上游橋接器。那個 MAC 屬於已知設備（例如以 MNDP 發現的 CSS106）時，推論這個埠接到它。對方也有 RSTP 資料時，用 `designated-port-id` 對回確切的埠。BPDU 會穿過不跑 STP 的未管理交換器，所以意義同樣是「直接相連，或中間只有未管理設備」。
    - `subnet-p2p`：兩台已收集設備的介面位址在同一個 /30 或 /31。/24 這類共用網段只證明在同一廣播網域，不採用。
    - `mndp-mutual`／`mndp-unique`：MNDP 雙向回報對方的埠，或某埠只看到一台 MNDP 鄰居。MNDP 會穿過未管理交換器，所以**只當佐證**：至少要有一項 `fdb`、`stp` 或 `subnet-p2p` 才成立，MNDP 同時成立時信心為 `high`。
  - **合併**：所有依據推論完後，同一條鏈路併成一筆，而且在過濾「只有 MNDP」之前做，所以 MNDP 佐證不會遺失。
    - 聚合成員埠歸到所屬的聚合介面。
    - 對端埠不明的代號依合併後的本機埠重新產生；任何依據知道對端埠名時，取代「埠不明」那一筆。
    - 只設在 VLAN／bridge 介面上的 /30 證據：同一對設備另外剛好只有一條實體埠的推論時，併進那一條；有多條時無法確定是哪一條，不合併。
  - **意義**：推論的是「直接相連，或中間只有未管理設備」。
  - **不推論的情況**：已有 LLDP／CDP 鏈路的設備對；埠（含所屬聚合）已有 LLDP／CDP 鄰接到已收集設備時，該埠後面的設備。
  - **對端埠**：未收集設備的埠用它在 MNDP 回報的埠名，沒有就標為不明。
  - **圖面**：同一對設備的鏈路與推論鏈路由 `Q.devicePairs()` 併成一條線，並給出唯一的證據強度 `evidence`，線型依它從 `theme.weakEdge` 取得：介面鄰接（一般線型）＞ 單側觀察 ＞ 推論（長虛線）＞ 只有 MNDP；弱證據只改線型與透明度，保留速率色。只有 MNDP 的設備對不畫線：MNDP 只證明同一廣播網域，可以推定相鄰的情況已由推論鏈路涵蓋；MNDP 鏈路仍保留在基準，列在設備鄰居表、介面與鏈路詳情。
  - **選取**：選介面時一併標示它的推論鏈路（`Q.inferredLinksOfEp`，查成員埠也會找到記在聚合上的推論鏈路），介面詳情列出這些推論鏈路；選 VLAN 時，已收集的各端都帶這個 VLAN 的推論鏈路（`Q.vlan(id).inferred`）也標成綠色。
- **VLAN 區塊**（`Q.vlan(id).domains`，推論，不存進 Snapshot）：VLAN ID 只在一台設備內有意義，不同站點常重用同一個 ID（NetBox 也以 VLAN group 劃定 VID 的範圍）。
  - **分塊方式**：帶這個 VLAN 的設備，以「兩端都帶此 VLAN 的鏈路」（`carry`）與「已收集各端都帶此 VLAN 的推論鏈路」（`inferred`）相連者為同一塊；只經由同一台未收集設備（例如 CSS106）相連也算同一塊，但那台設備不列在區塊內。純 MNDP 鏈路不帶 VLAN 資料，不算相連。
  - **意義**：分成多塊表示鏈路證據上互不相連，可能是各自獨立的廣播網域，也可能中間有沒收集、沒有 LLDP 的設備，所以只是提示。
  - **鍵**：`<VLAN ID>@<區塊內自然排序第一台設備>`；`Q.vlan(id, key)` 只回傳那一塊的設備、鏈路與 VLAN 定義，鍵不存在時回到整體結果。
  - **畫面**：VLAN 詳情在分成多塊時標示區塊數並列出各塊，點選後圖上只標示那一塊；搜尋 VLAN ID 的結果也標示區塊數。
  - **共用**：分塊規則只有一份（`S.infer.vlanSpan`），查詢（`Q.vlan`）與檢查都用它；A02、V06、A06 只比較同一塊內的位置（檢查端共用 `byDomain`）。
- **未收集交換器底下的終端**（`macs[].behind`，推論，精確到設備、埠不明）：終端接在收不到資料的交換器（例如 SwOS 的 CSS106）時，只有上一跳 RouterOS 的 MAC 表看得到它。
  - **錨點**：已收集、有 MAC 表的設備 A 的埠 p，需同時符合：
    - p 沒有 LLDP 鄰接到已收集設備。
    - p 學到未收集的交換器或路由器的 MAC。
    - 那台設備沒有被證明在別台已收集交換器後面。
  - **哪些 MAC 算在它底下**：p 學到的其他 MAC，但排除下列幾種：
    - 已知設備自己的 MAC。
    - 已有確切位置的 MAC（終端埠、Wi-Fi）。
    - 在 p 這側其他已收集交換器「不朝向 A」的埠上出現的 MAC。
  - **位置**：p 這側只有一台未收集設備時，`dev` 為它；有多台（例如 CSS106 再串 CSS610）時 `dev` 為 null，`via` 列出全部，畫面顯示「在 X、Y 或其下游」。
  - **多個錨點**：同一 MAC 有多個錨點時，取那一側已收集交換器最少者（最靠近終端）。
  - **畫面**：主機畫在該交換器節點下，連線用推論樣式。
  - **與推論鏈路的對應**：推定位置與「錨點埠 ⇄ 該交換器」的推論鏈路是同一段路徑，基準不另存關聯，查詢時以錨點埠（含所屬聚合）與設備對回（`Q.behindVia(mac)`、`Q.behindUnder(推論鏈路 key)`）。MAC 詳情列出經由的推論鏈路，推論鏈路詳情列出後面推定的終端，選取終端時圖上標示整段路徑。
  - **A04**：錨點埠不報 A04，因為下面接的是已知設備。
- **Wi-Fi 客戶端位置**（`macs[].wifi`，推論）：MAC 表無法說明 Wi-Fi 客戶端連在哪台 AP，因為同一個 MAC 會出現在 AP 的無線介面、AP 上行與沿途 trunk，且會漫遊。依證據強度取位置，`basis` 標示依據：`registration`（關聯表，最強；多台 AP 時取 `last-activity` 最近者，其餘為 `candidates`，`roaming` 為真）→ `bridge-wifi`（已收集設備的 MAC 表在 `type=wireless` 介面學到）→ `via-ap-port`（交換器埠的鄰居是沒有收集資料的 AP，無法區分有線或無線）。已判定為有線終端埠的 MAC、AP 自己的 MAC 不套用 `via-ap-port`。因為用到終端埠判定，在推論算出終端埠之後才由 `S.infer.wifiLocations()` 計算。沒有 Wi-Fi 證據的 MAC，`wifi` 為 null。
- **終端位置**：這是依已收集證據推定的「未知對端」位置，不代表已證明對端是終端主機。核心 `unknownPeer` 介面必須恰好學到一個 MAC、不是 Wi-Fi、狀態非 down、不是虛擬介面，且沒有 LLDP／CDP 介面鄰接連到其他已收集網路設備；學到多個 MAC 的有線介面不符合此條件。Wi-Fi 介面本身不視為終端介面，但清單會將每個 Wi-Fi MAC／介面觀察位置列為終端位置；同一 MAC 出現在多個 Wi-Fi 介面可能是漫遊，因此 Wi-Fi 觀察不參與 A02。純 MNDP 只證明同一 L2 broadcast domain 可達，不會當作直連鄰接排除終端埠。若 bridge host 有多個 VLAN 觀察，MAC 的 `seen` 會各自保留 `{ep,vlan}`，不會互相覆蓋。
- **虛擬介面**（`S.infer.isVirtualIfc`）：有 RouterOS 原始類型 `rawType` 時，`bridge`、`vlan`、`loopback`、`vrrp` 是虛擬介面；沒有時依名稱推測，以 `irb`、`vlan`、`bridge` 或 `lo` 加數字開頭的是虛擬介面。終端埠、A04 與查詢的 Wi-Fi 觀察位置共用這一條規則。
- **推論全部在檢查之前完成**：`S.infer.infer()` 依序算出設備類型、鏈路分類與兩端 VLAN（含 `links[].vlanMismatch`）、推論鏈路、VLAN 區塊，套用命名規則、分群，再算終端埠（`edgeLocations`：`interfaces[].edge`／`unknownPeer`、`macs[].edge`，用到命名規則覆寫後的設備類型與推論鏈路）、Wi-Fi 客戶端位置（`wifiLocations`）、未收集交換器底下的終端（`behindLocations`）與防火牆的 WAN／LAN 分類。⑥ 檢查只讀取模型產生 findings，不寫回模型。
- **K01、K04、R02 由檢查判定**：建模時只記下配對結果，這兩個欄位只在內部模型、不序列化：每筆 LLDP／CDP 觀察的 `pairing`（`reciprocal`、`one-way`、`hearsay`），以及 OSPF 鄰接的 `peerBasis`（`address`、`router-id`、`router-id-address`、`mgmt-ip`，都找不到為 null）。檢查時依此列出 K01（`one-way`）、K04（`reciprocal` 但對端埠名不同）與 R02（`peerBasis` 為 null）。
- **覆蓋率**：`S.check.coverage(M, expectedData, blocks)` 依與 C02 同一份應收集資料表計算 `missing`，並由區塊的 `failure` 列出 `failures`。
- **防火牆**（推論與比對語意在 `S.infer.fw`，檢查與查詢共用）：
  - **WAN／LAN**：只看 interface list，不看介面名稱。已定義、名稱符合 `/(^|[^a-z])wan([^a-z]|$)/i`（含獨立的 `WAN` 字樣、不分大小寫，例如 `WAN`、`ISP-WAN`、`wan2`；`WANLINK` 不算；LAN 同理）的清單，展開 `include`／`exclude` 後的成員就是 WAN（LAN）介面；`all`、`none` 依 RouterOS 語意，`dynamic` 等內建清單或未定義的清單無法展開，含這種清單的清單整個略過。沒有這種清單時為 `no-wan-list`，有清單但沒有可確定的成員時為 `empty-wan-list`，兩者都不猜（F08）。
  - **IPv6 是否在用**（`firewallZones[].ipv6`，供 F07 的 IPv6 部分）：export 的 `/ipv6 settings` 設了 `disable-ipv6=yes` 為 `disabled`；否則有啟用中的 `/ipv6 address`、`/ipv6 dhcp-client`，或有任何 `/ipv6 firewall` 規則，為 `used`（`src` 是依輸入順序的第一個證據行）；都沒有為 `unknown`。export 只列非預設值，看不出有沒有自動產生的位址，所以 unknown 時不猜。
  - **涵蓋（`covers`）**：F01 用來判斷前面的規則是否涵蓋後面的規則；帶 `random`、`limit` 等不確定比對的規則一律不涵蓋。
  - **走 chain（`evalChain`、`evalFilter`）**：模擬「從 WAN 進來的新連線」依序走過 chain（含 jump、return，jump 深度上限 16）。每個條件的結果是成立、不成立或無法判斷；只有全部成立的規則才算命中，**含無法判斷條件的規則直接略過**（例如 `dst-address-list`、時間或標記類條件），所以前面這類 drop 規則擋不下，結果可能多報。`evalFilter` 先看 raw 的 prerouting，再走 filter 的內建 chain；**內建 chain 沒有規則決定時視為放行**（RouterOS 的預設）。來源視為任意公網位址：`src-address` 要涵蓋整個位址空間，或是只排除私有位址的否定，才算成立；`src-address-list` 只有否定才成立；`src-port` 由攻擊者選，accept 規則視為成立。
  - **`/ip service`**：export 沒寫的服務以 RouterOS 7 的出廠設定補上（`basis: 'default'`），待真機確認；清單在 `infer.js` 的 `SERVICE_DEFAULTS`。

## 7. 一致性檢查

共 41 項規則，分成輸入（I）、覆蓋（C）、鏈路（K）、VLAN（V）、位址（A）、路由（R）、防火牆（F）七類。每項規則的判斷條件、使用的資料、不檢查的情況與處理建議，集中在 **[docs/基準檢查規則.md](基準檢查規則.md)**，本文件不再另列一份規則表，以免兩份內容不一致。規則目錄在 `src/check/catalog.js`，判斷在 `src/check/checks.js`（見[第 3 節](#3-模組)）。

每筆：`{ id, severity, cat, title, message, entities:[{type,key}], facet?, evidence:[{block,line,text,file}], deviation? }`。entity 的 type 有 `device`、`interface`、`link`、`vlan`、`ip`、`mac`、`rule`（防火牆規則，key 是 `firewallRules[].key`）與 `service`（管理服務，key 是「設備|服務名稱」）。`evidence` 預設最多 6 筆，規則可在 `CATALOG` 以 `evidenceLimit` 覆寫（目前只有 C02 不限）。

`facet` 是可選欄位，只有同一組 id＋實體可能產生多筆 finding 的規則才有（`CATALOG` 宣告了 `facet` 的 12 條），標示這筆檢查的是哪一個項目，例如 A12 的 `dns`／`ntp`。有宣告的規則每筆都有、沒宣告的都沒有，`add()` 強制檢查。值只取自設定項目的固定字樣與正規化後的設定值，不取自訊息、設備名稱或行號；多段以 `|` 分隔。facet 會進入 findingKey（[第 8 節](#8-比對獨立模組)）。各規則的取值見[基準檢查規則「每筆結果的內容」](基準檢查規則.md#每筆結果的內容)。

`deviation` 是可選欄位，只有跨設備組態一致性中做多數決的規則（V06、V07、A06–A08、A10–A12、R06）才有：`{ basis: 'majority', deviating: [設備 key…] }`。`deviating` 是依多數推定偏離的設備（推論），依設備名稱自然排序，平手時為空陣列。判斷條件見[基準檢查規則「跨設備組態一致性」](基準檢查規則.md#跨設備組態一致性)。

## 8. 比對（獨立模組）

下列三個功能都只透過查詢介面讀取，不修改基準（有測試確認比對前後 Snapshot 完全相同）。

**預期資料比對**：`SSOT.compare(SSOT.query(snapshot), expected) → DiffReport`

- 預期資料格式 `ssot-expected/1`（設備、鏈路、VLAN），用「設備名」「設備名 介面名」指向實體，不共用 Snapshot 結構。端點以**最後一個空白**分隔，所以設備名可以含空白（介面鍵不含空白）。
- 結果分 ok／missing／different／unexpected（`strictDevices`、`strictLinks` 開啟時才列多出）。
- 預期的鏈路以這組介面本身的證據為準：有 LLDP／CDP 鄰接時照常比對；這組介面沒有介面鄰接、只有同一對設備的 MNDP 觀察時，才回報「只有 MNDP 的 L2 廣播網域可達證據」。

**由基準產生預期資料**：`SSOT.compare.expectedFrom(Q, { strict }) → ssot-expected/1`

- 內容：已收集的設備（含 `kind`）、已雙向確認的 LLDP／CDP 介面鄰接鏈路、各設備的 VLAN。名稱經正規化後仍對回同一個鍵時用名稱，否則用鍵本身。
- 和同一份基準比對時全部是 ok。`strict` 會加上 `strictDevices`／`strictLinks`；未經雙向確認的鏈路不在預期資料內，所以這時同一份基準的這些鏈路也會列為 unexpected。

**新舊基準比對**：`SSOT.compare.snapshots(Q舊, Q新) → ssot-snapdiff/1`

- 回傳 `{ schema, errors, warnings, summary, items }`；`summary` 是新增、移除、改變的總數，以及各類別（`byCategory`）的筆數。
- `warnings[]`：`{ kind, before, after, message }`，依 `version`、`profile` 的順序，兩份相同時不列。schema 相同時照常比對，但提示部分差異可能來自程式或命名規則，不是網路改變：
  - `version`：兩份的 `meta.version` 不同（沒有時為 null）。新版才有的檢查會顯示為新出現。
  - `profile`：兩份的 `meta.profile`（`{ id, version }` 或 null）不同。設備名稱、類型與分群可能因此不同。
  - schema 不同而不比對時，`warnings` 為空。
- `items[]`：`{ category, change, key, field, before, after, message, effect }`；`change` 為 `added`／`removed`／`changed`，新增時 `before` 為 null，移除時 `after` 為 null。

  | 類別 | key | 比較的內容 |
  |---|---|---|
  | `device` | 設備鍵 | 新增／移除；`kind`、`deviceType`、`softwareVersion` 改變 |
  | `link` | 鏈路鍵 | 只比 LLDP／CDP 介面鄰接的新增／移除（MNDP 只證明廣播網域可達，不比） |
  | `vlan` | `設備\|VLAN ID` | 設備上新增／移除 |
  | `ip` | IP（不含遮罩） | 只比設備自有的位址（不含鄰居宣告）；新增／移除，或改到別的介面（`field: interface`）、遮罩改變（`field: address`） |
  | `firewall` | 規則鍵 | 新增／移除；`action`、`disabled` 改變；同 chain、同動作、新舊條件互相涵蓋的「移除＋新增」併成一筆 `match` 改變（條件變窄或變寬） |
  | `finding` | `findingKey`（退回時是 `findingBaseKey`） | 以鍵的多重集合比對：同一個鍵先配對訊息相同的，其餘依順序配對，配不到的才是新出現／已消失 |

- **finding 的鍵退回**：2.8.0 以前的基準沒有 facet，直接用 findingKey 比對，有 facet 的規則會變成「消失＋新出現」。所以先收集兩份基準中至少有一筆 finding 沒有 facet 的規則，這些規則在兩邊都改用 `Q.findingBaseKey` 比對，`item.key` 也是 findingBaseKey；其他規則照常用 findingKey。同一份基準內，一條規則的 finding 不是都有 facet 就是都沒有（`add()` 強制檢查），沒有 facet 的規則兩種鍵相同，所以同版本的比對不會退回。
- `effect`：只有 `firewall` 類別有值，其他為 null。`new-exposure` 是新基準才有的 F03／F04／F05／F07 指向的規則；其餘依放行方向判斷為 `less-restrictive`（放寬）或 `more-restrictive`（收緊）。accept、dst-nat、netmap 算放行，drop、reject、tarpit 算擋下；jump、log、src-nat 等不影響放行的動作為 null。
- **排序**：依類別（上表順序）、鍵、變更種類（移除、新增、改變）、欄位排序，同樣的輸入一定得到同樣的順序。
- **schema 不同**：兩份基準的 schema 不同，或不是本工具的 `ssot-snapshot/2` 時不比對，`errors` 說明原因、`items` 為空；請用同一版工具從原始輸入重新建立。

**finding 的穩定鍵**：`Q.findingKey(f)`（也可用 `SSOT.query.findingKey`）＝ `JSON.stringify([id, "facet:"+facet（有 facet 時）, 排序並去重的 "type:key"…])`，例如 `["A12","facet:dns","device:VA","device:VB"]`。facet 固定在第 2 個元素、不參與排序；沒有 facet 的規則，鍵與 2.9.0 之前相同（`Q.findingBaseKey`）。不含訊息、證據與行號，所以訊息文字或行號改變時，兩份基準仍對得上。同一份基準內仍可能碰撞（id、facet 與 entities 都相同、只差訊息）：同一台設備的多段 I01、I03，沒有設備的 I01，以及少數 facet 也分不開的情況，例如同一台設備重複設定同一個 DHCP 網段（R05）、同一介面重複連到同一個 router-id（R02）；需要逐筆對應時以多重集合處理，如上。組成的取捨見 [ADR-003](架構決策/003-findingKey的組成.md)。

## 9. 規模

實測（Node，產生的 1041 台已收集設備、3921 個節點、5920 條鏈路、約 1 萬個 MAC、約 1400 萬字元輸入）：建立約 3.7 秒、乾淨網路零誤報。

| 問題 | 做法 |
|---|---|
| 解析卡畫面 | 分段執行並顯示進度（`buildAsync`）；`file://` 不能用 Web Worker，故不採用 |
| 物理模擬太慢 | 預設不跑。先以分群＋分層的快速版面一次算完出圖，再於背景套用 ELK 分層版面（約 1000 台網路設備約 2.4 秒；超過 1500 台不執行）。「力導向排列」為選用的格網加速力導向 |
| 整張網路連成一片 | 沒有命名規則時，以標籤傳播依連線密度自動切出「區域」分區排列（只影響畫面，不寫回基準） |
| 主機把層拉得很寬 | 只連到一台設備的未收集終端，排在該設備正下方的小方陣 |
| 節點太多 | 主機超過 300 個時預設隱藏；只畫畫面內物件；縮小時不畫標籤與埠名 |
| 儲存空間 | IndexedDB，不用 localStorage，不自動過期 |

## 12. 未知對端（2.1.0 新增）

**要解決的問題**：接取交換器下面接了幾十台沒有 LLDP 的設備（PC、印表機、IoT），只看 LLDP 的拓樸會顯示成「這台交換器只有上行」，實際上它下面有一大片沒被看見的東西。MNDP 只提供同一 L2 廣播網域可達線索，並不能指出直接鄰居埠，因此不會將有 MAC 的埠排除在未知對端之外。舊版工具會在這種埠畫出虛擬節點；這一版保留這個意圖，但改成不污染基準。

**判定（核心，寫進基準）**：`interfaces[].unknownPeer = true`，條件是同時成立
1. 設備是已收集的；介面恰好學到一個 MAC、不是 Wi-Fi，狀態不是 down，也不是虛擬介面（規則見 [§5.3](#53-關鍵推論)）
2. 該介面（含所屬聚合與聚合成員）沒有任何 LLDP／CDP 介面鄰接鏈路；純 MNDP 廣播網域可達邊不作為鄰接排除條件
3. 該介面（含所屬聚合與聚合成員）沒有推論鏈路（推論接到未收集的網路設備，例如 SwOS 交換器）

有 LLDP／CDP 介面鄰接至已收集網路設備的伺服器埠、上行聚合埠都不算；學到多個 MAC 的有線介面可能連著下游交換器或 AP，因此不列為核心終端介面。Wi-Fi 介面是一對多的 MAC 觀察位置，`Q.inventory().rows.endpoints` 會逐一列出其 MAC／介面位置，但不會將 Wi-Fi 標為 `unknownPeer`／`edge`，也不會把 Wi-Fi 觀察送入 A02。純 MNDP 廣播網域可達不算直連鄰接，不會因此排除一般終端埠。查詢介面：`Q.unknownDevices()`、`Q.unknownPeers(設備)`（一般終端埠附 MAC、ARP 的 IP、OUI 廠商、VLAN）與 `Q.inventory()`（列及數字的單一來源）。

**畫面（檢視層，不寫進基準）**：基準的設備、鏈路、檢查結果完全不變（有測試），虛擬節點只存在於畫面。所有顏色、線型、透明度與字型集中在 `src/view/theme.js`，Canvas 繪圖與圖例都讀它（圖例分「設備／終端／連線／連線註記／標示」五類，預設收合，說明文字放提示；外形、連線色、線寬、虛線、弱證據透明度與標示色由 theme 產生，有測試比對）；CSS 的設備類型、嚴重度色與它的一致性也有測試。連線依速率是同一色相由淺到深的色階，線寬隨速率遞增（1G → 10G → 40G，聚合最粗）；1G 是由介面名稱推估的分類，不代表實際協商速率，圖例提示會說明此限制。「單側觀察」是點線、「推論鏈路」是長虛線，兩者只改線型與透明度，保留速率色；只有 MNDP 的設備對不畫線。選取或 hover 高亮時維持完整不透明度。一般 UI 採冷白背景與一致的圓角、控制項高度及陰影層級；操作按鈕依優先級呈現，狀態 chip 使用對應色彩及邊框，清單表格使用斑馬列與 hover 高亮，互動元件提供鍵盤焦點樣式，並尊重減少動態效果的系統偏好。

| 情況 | 畫法 |
|---|---|
| 一個埠一個 MAC，且非 Wi-Fi | 圓點，顏色依廠商（避開紅、橘黃、綠，以免和狀態混淆），標 IP；近看顯示廠商縮寫。廠商色最多 8 色，依終端數量取前 8 個廠商（同數量依名稱），其餘與不明廠商歸「其他」的中性色；數量取自全部未知對端與推定終端，不受展開／收合影響 |
| 有線介面一埠多個 MAC，或任一 Wi-Fi 介面 | 有線多 MAC 不列為終端埠；Wi-Fi 介面不列為終端埠，但每個 Wi-Fi MAC 觀察位置列入終端清單並可作圖面提示（多 MAC 為菱形），Wi-Fi 位置不參與 A02 |
| 介面 `rawType=veth`（容器虛擬網路卡，`type=virtual`） | 連到該終端的連線用專用線型（長線加兩個點），顏色維持連線類別色，節點外觀不變；提示與介面詳細標「容器 veth」 |
| 介面 `type=wireless` | 連線用另一種專用線型（長線加一個點），標「Wi-Fi」 |

**版面**

- 共用步驟在 `src/view/graph/layout.js`：
  - `prepare()`：分群、終端（排在所屬設備下方）與 BFS 分層
  - `shelf()`：各群以書架方式排列
- 兩種版面：
  - **快速（內建）**：同步計算，用一輪重心排序並對太寬的層折行。
  - **分層（ELK，預設）**：`src/view/graph/elk-layout.js` 對每群的核心設備執行 ELK layered，依 `prepare()` 的層級決定邊的方向，再做多輪交叉最小化與 network-simplex 節點擺放。節點框會預留終端方陣與標籤的空間。
- 載入流程：
  - 載入基準時先以快速版面出圖。
  - 沒有儲存位置時，再於背景套用分層版面。
  - 網路設備超過 `App.ELK_MAX`（1500）、逾時或失敗時，維持快速版面，並以 banner 說明原因。
- ELK 在 `file://` 下沒有 Worker，會在主執行緒計算，所以每群之間會讓出主執行緒。約 1000 台網路設備時約 2.4 秒。
- 使用的版本是 `vendor/elkjs-0.11.1/`（EPL-2.0，未修改），不屬於核心載入順序。檔案約 1.6 MB，不放在 `index.html`；第一次需要分層版面時才由 `elk-layout.js` 以 `<script>` 載入。選擇「快速（內建）」或網路設備超過上限時不會載入。

依介面類型的線型定義於 `theme.js` 的 `endpoint.byType`（鍵為 `rawType` 或 `type`，以 `endpoint.styleOf(介面)` 查詢），只識別連線（收合成「終端 ×N」群組時連線維持預設線型），僅視覺識別，不改變判定與檢查。
| 同一台設備超過 8 個，或全網超過 800 個 | 收合成一個「終端 ×N」群組；雙擊或在右側按「在圖上展開」 |

- 點節點或群組：右側顯示每個埠的 MAC、IP、廠商、VLAN；點一列跳到該介面。設備頁也有同樣的清單。
- 搜尋 MAC／IP 時，圖上會標出它所在的那個終端；點檢查結果 A03 會顯示該設備的終端清單。
- 左右欄邊緣可拖曳調整寬度（最小 240px，中間圖面至少 320px；雙擊還原），寬度存在獨立的 `layout` 鍵，只屬檢視狀態，不進基準。
- 工具列「未知對端」可整個關閉。位置會跟著其他節點一起儲存。
- 1000 台實測：880 台設備各收成一個群組（全網超過上限），展開一台約 0.4 秒。

**刻意沒做**：「介面 up 但沒有學到任何 MAC」（閒置埠）。要可靠判斷需要 `show interfaces terse` 的狀態，不在必要收集清單內。

## 13. 與多廠牌版（Juniper＋Fortinet）的差異

| 項目 | 多廠牌版 | MikroTik 版 |
|---|---|---|
| 解析器 | 12 個（Junos 8、FortiOS 4） | 13 個（RouterOS） |
| 輸出格式 | 各廠牌不同（表格、display set、config 區塊） | 一律 `detail`（key=value）＋ export |
| 介面名稱 | 去掉 Junos 的 `.0` | 不處理（RouterOS 沒有這個慣例） |
| 鄰居對端埠 | LLDP 表格的 Port info | `interface-name`；沒有時用順序配對 |
| VLAN | 名稱＋ID | bridge VLAN 只有 ID（無名稱）；只在 `vlan-filtering=yes` 的 bridge 才有意義。V06、V07 比較的是 VLAN 介面名稱與說明 |
| 檢查 | 16 項 | 41 項（不使用 V02、V03） |
| 設備類型 | 廠牌＋資料 | 型號＋資料＋鄰居回報的功能 |
| 新增的處理 | — | 鄰居 identity 對不上收集檔設備名時用管理 IP；OSPF 沒有 interface 時用網段解析；未知埠名時的鏈路配對 |
| 瀏覽器儲存 | `topo-ssot` | `topo-mikrotik`（兩版可並存） |

## 14. 檢視狀態與匯出

畫面只透過 `SSOT.query()` 讀取 Snapshot。下列都是檢視狀態、使用者的資料或衍生輸出，不改寫基準：

- **處理紀錄（取代確認標記）**：使用者對每個 finding 的決定與歷程，資料模型與規則在核心 `S.ledger`（[第 16 節](#16-處理紀錄ssot-ledger1)），畫面接線在 `src/view/app-ledger.js`。
  - 存在 store 的獨立鍵 `'ledger'`，和基準 `'last'` 分開：按「清除」不影響它，重新建立同一份網路的基準時仍然有效。
  - 每次建立或還原基準後，以目前時間呼叫 `S.ledger.advance` 推進一輪；同一份基準（基準鍵相同）已推進過時不顯示本輪變化。
  - **舊確認標記的轉換**：啟動時 store 沒有 `'ledger'`、但有舊的 `'acks'`（`{ findingKey: { at, kind, note } }`）時，先記下，等第一份基準載入時以 `S.ledger.fromAcks` 轉換（含推進一輪），提示列顯示轉換的筆數。`'ledger'` 寫入成功後才刪除 `'acks'`；寫入失敗時保留 `'acks'`，下次開啟再轉換一次。store 已經有 `'ledger'` 時不讀 `'acks'`。
  - **無法使用時停用**：store 中的 `'ledger'` 格式不正確（`S.ledger.validate` 不通過），或舊確認標記無法轉換時，處理紀錄停用：不寫入 store、不丟資料，畫面說明原因與錯誤。可以匯出原資料、匯入正確的處理紀錄，或以空白的處理紀錄重新開始（舊的 `'acks'` 保留不刪）。
  - **匯出與匯入**：匯出 `ledger-<目前時間>.json`（停用時匯出 store 中的原資料）。匯入先以 `S.ledger.validate` 檢查，不合法時列出錯誤、目前的處理紀錄不變；合法時等使用者確認後**整份覆蓋**目前的處理紀錄（只覆蓋、不合併），再以目前的基準推進一輪。
  - **待處理與已處理**：處理紀錄的狀態是 open、regressed，或不在處理紀錄中時算待處理；其餘（scheduled、accepted、false-positive、fixed）算已處理。已處理的錯誤與警告不計入頂端摘要的筆數，但摘要註明另有幾項已處理。摘要另有回歸、因收集失敗而無法判斷、豁免到期的提示，點一下開啟「處理紀錄」分頁。
  - **變更狀態**：檢查結果每筆的「處理」開啟編輯欄位。狀態選單只列目前的狀態與 `S.ledger.USER_TO` 允許的轉換，另有備註；選「可接受」時要填豁免原因（畫面要求必填）與到期日（預設 `S.ledger.WAIVER_DAYS` 天後，日期以 UTC 0 時計）。儲存交給 `S.ledger.set`；不合法的變更（例如把仍出現在最新一輪基準的項目標為已修好）在欄位下方顯示核心的錯誤訊息，資料不變。
  - 已處理的項目依狀態各列一組（已排程修復、可接受（豁免）、誤報、已修好，預設收合）；有標為誤報的規則時，另列「誤報率最高的規則」（`S.ledger.ruleStats`，最多 5 條）。詳情的檢查結果列出狀態、豁免原因與到期日、備註。
- **處理紀錄分頁**（`src/view/panels/ledger.js`）：數字全部來自核心（`S.ledger.summary` 與 `advance` 的結果），分頁只排版與畫圖。
  - 各狀態的筆數；豁免沒寫原因時提醒補上（例如由舊確認標記轉換而來）。
  - **本輪變化**：新出現、已修好、回歸、豁免到期、因收集失敗而無法判斷的筆數與清單（每組最多列 300 筆）；目前基準有這一筆時，點一下定位。
  - **修復追蹤**：已排程修復的項目（標示目前基準仍有或沒有），以及累計已修好的項目。取代 2.7.0 在新舊基準比對上方的修復追蹤。
  - **收斂趨勢**：只有一輪時列出目前的數字；兩輪以上畫三張小倍數折線圖（SVG）：待處理、回歸與已豁免的筆數（三條線另以圓形、方形、三角形標記區分，線尾有數值）、覆蓋率（已收集／應收集）、未知對端數。每一輪可用指標或鍵盤聚焦顯示該輪的數值，另有「表格檢視」列出同樣的數字。顏色取自 `theme.trend`。
- **修正計畫對話框**（`#dlg-patch`，`src/view/panels/patch.js`）：計畫與 `.rsc` 文字全部由核心 `S.remediate` 產生（[第 15 節](#15-修正-patchssot-patch1)），畫面只負責選取、預覽與下載。
  - 從檢查結果分頁的「修正計畫…」，或防火牆畫面的「在修正計畫中開啟」開啟。
  - 選取：依規則（可產生指令的規則排前面，點一下選取或取消這條規則的全部）、依設備（「加入這台的全部」）、展開規則逐筆勾選（每條最多列 200 筆），或「全部清除」。逐筆勾選以 findingKey 為單位，facet 不同的（例如同一組設備的 A12 DNS 與 NTP）各自一列，並標示檢查項目；仍共用一個鍵的只有依輸入區塊產生的 I01、I03。選取是 findingKey 的集合，只在記憶體，不存進 store；換了基準（inputHash 不同）時清空。
  - 計畫：依設備列出每一項的修改前（證據的原文，可開啟原始輸出）與修改後（這一項的套用指令，取自 `S.remediate.renderRsc`），以及說明、風險與警告。每台設備可切換檢視套用、回復、驗證三個檔案，可複製或下載。只有一台設備時直接下載三個 `.rsc`；多台時可「逐檔下載全部」（每台三個 `.rsc`，加上總表 `patch-summary-<建立時間>-<N>dev.md`），或只下載總表。沒有產生指令的項目依原因分組列出。
  - 目前沒有 ZIP 下載（計畫第二階段提供）；多檔下載時瀏覽器可能會詢問是否允許。
- **檢查項目的顯示**：詳情的檢查結果在標題旁標示「檢查項目：…」，修正計畫的逐筆勾選也標示同一段文字；滑過時顯示 facet 原值。顯示文字的對應表只在畫面層的 `V.remediation.facetText`（`src/view/remediation.js`），找不到對應或格式不符時顯示原值，不隱藏；沒有 facet 的檢查結果不標示。
- **規則的常見原因與處理**：畫面與匯出要讀 `CATALOG` 的 `causes`／`action`，只能透過 `V.remediation.advice(id)`。它每次從 `S.check.CATALOG` 讀取、不複製文字，回傳 `{ action, causes }`：沒有 `action` 時為 null，`causes` 一律是字串陣列（單一字串視為一條）。
  - 反引號標出的 RouterOS 指令與欄位，由 `src/view/dom.js` 的 `V.codeParts` 切成 `[{ text, code }]`（沒有成對的反引號保留為一般文字），`V.codeText` 再組成文字節點與 `<code>` 元素，都以 textContent 寫入，不用 innerHTML。Markdown 匯出用同一個切法，把反引號內的部分轉成行內程式碼。
  - 共用元件是 `V.details.parts.adviceBlock(id, opt)`：預設收合的 `<details>`（兩者都有時標題為「常見原因與處理」，只有一種時為「處理建議」或「常見原因」），用在詳情的檢查結果、規則清單的「通過」「沒有資料可檢查」，以及終端 MAC 位置畫面的 A03。`causes` 與 `action` 都沒有時不顯示。
- **檢查結果的分組與篩選**（`src/view/panels/lists.js`）：都是檢視狀態，不存進 store。
  - **依設備分組**：所屬設備由 `Q.findingDevice` 判斷（規則見 [§5.2](#52-實體snapshotmodelschema-ssot-snapshot2)），都對不到時歸入最後的「不屬於任何設備」。設備依名稱自然排序，組內保留基準的順序。匯出的「依設備排序」用同一個判斷（`V.remediation.sortByDevice`）。
  - **只看新出現的**：讀取「比對」分頁載入的舊基準，以 `S.compare.snapshots` 中 `category: 'finding'`、`change: 'added'` 的項目（以 `findingKey` 對應）為新出現的。兩份基準的版本不同時（`warnings` 有 `version`），旁邊提示新出現的可能來自新版檢查。沒有載入舊基準、比對失敗（例如 schema 不同），或建立、載入了新的基準（舊基準比對隨之清空）時，這個選項停用並說明原因。
- **新舊基準比對的結果不保存**：舊基準是使用者載入、之前匯出的 Snapshot JSON；比對結果與舊基準的查詢介面只放在記憶體（`src/view/panels/baseline-diff.js`），不寫進 store。比對結果上方逐筆列出核心的 `warnings`（版本、命名規則不同）。
- **防火牆畫面的修正**：設備的防火牆畫面有「修正（停用規則）」一節，列出指向規則、而且核心有修正方式（`S.remediate.levelOf` 不是 manual）的檢查結果。計畫由 `S.remediate.plan` 產生：可產生指令的列出套用指令、find 的依據、風險與警告，可複製；不能產生的（例如 F03 要選擇處理方式、F02 的 find 無法區分）列出核心給的原因。定位到某條規則時只列這條、預設展開，否則列這台設備的全部、預設收合。完整的 `.rsc` 在修正計畫對話框。
- **devices.csv 草稿**（`V.remediation.devicesCsvDraft`）：由 C01（只被鄰居發現、沒有收集資料的網路設備）產生 `tools/collect.sh` 的設備清單，格式 `name,address,user,port,extra`。
  - `address` 依序取設備的管理 IP、鄰居回報的位址；`user` 一律是佔位值 `CHANGE_ME`（`collect.sh` 擋不下佔位值，檔頭註解會提醒先改成實際的 SSH 帳號）；`port` 為 22，`extra` 留空。
  - 不能直接使用的設備寫成註解列（開頭 `#`，`collect.sh` 會略過）並註明原因：沒有任何位址、位址含空白或逗號、名稱不符合 `collect.sh` 的名稱規則，或名稱重複。修正後移除 `#` 即可。
  - 檔頭註解另寫基準建立時間、輸入指紋，以及建議先執行 `tools/collect.sh devices.csv --dry-run`。
- **樣式**（`src/view/theme.js`，唯一來源；配色以 dataviz 的 validator 在亮色、底色 `#f8fafc` 驗證）：
  - 狀態色（`sev`、`mark.bad`／`good`）只表示狀態，而且一律搭配外形或文字；類別色（設備、連線、廠商）不用紅、橘黃、綠。
  - `text`：文字色（body、muted、err、warn、ok、info），對其底色至少 4.5:1，與 `assets/app.css` 的對應變數一致。防火牆的動作色與比對的 effect 色都取自它。
  - `sevShape`：嚴重度的外形，錯誤是方形、警告是三角形；節點右上角、連線中點與圖例共用（`V.sevMark`）。比對的 effect 標籤前也加上同樣的外形（`diff.effectSev`）。
  - `multi`：同一對設備有多條鏈路時，線加寬（`widen`）並在中間留一條底色細縫（`gap`），看起來是雙線。
  - `font`：Canvas 的字型清單（`ui`、`mono`），與 CSS 的 body、`--mono` 相同。過長的節點標籤與埠名截斷加「…」。
  - `canvas.surface`：畫布底色（與 `--surface` 相同）。每次繪圖先填滿，所以匯出的 PNG 不是透明背景；多條鏈路的中縫也用它。
  - `trend`：處理紀錄趨勢圖的線色、外形標記、格線與座標軸色。
  - 其他：防火牆畫面的動作色、停用規則透明度與定位列（`firewall`），新舊比對的 effect 色與新暴露底色（`diff`）。
- **鍵盤、觸控與系統偏好**（`src/view/graph/canvas.js`、`assets/app.css`）：拓樸圖可取得焦點，可用鍵盤操作（按鍵見 [README「畫面」](../README.md#畫面)）；移到的設備以滑過的樣式標示，並讀給螢幕閱讀器（`#graph-live`）。滑鼠、觸控與觸控筆共用 pointer 事件；觸控沒有 hover，命中範圍較大，點兩下等同雙擊。強制色彩模式（Windows 高對比）下，焦點與「選取中」改用系統色的 outline；偏好減少動態效果時取消轉場，「力導向排列」一次算完、不播動畫。
- **匯出**（`src/view/export.js`）：只讀傳入的 Snapshot，在本機以 Blob 下載，不經過網路。
  - 基準 JSON：Snapshot 原樣序列化，不增刪欄位；可再載入作為新舊比對的舊基準。
  - 檢查結果 CSV：一筆 finding 一列，欄位依序為 `severity,id,title,message,entities,evidence,acknowledged,ack_kind,ack_note,device,action,status,note,waiver_reason,waiver_until,facet`，共 16 欄。新欄位一律加在最後，既有欄位的位置不變。
    - `entities` 是 `type:key`、`evidence` 是 `檔名:行號`，多筆以「; 」分隔。
    - 舊的確認欄位保留名稱與位置，改由處理紀錄對應：已處理（狀態不是 open、regressed）時，`acknowledged` 是使用者最後一次變更的時間（UTC ISO），`ack_kind` 是狀態（`scheduled`／`accepted`／`false-positive`／`fixed`），`ack_note` 是備註；待處理時三欄都是空白。
    - `device` 是所屬設備鍵（`Q.findingDevice`），不屬於任何設備時為空白。
    - `action` 是規則的處理建議（`V.remediation.advice`），照 `CATALOG` 原文、保留反引號；規則沒有處理建議時為空白。沒有 `causes` 欄：同一段多句文字會在每一列重複，合在一格也不好篩選，常見原因放在 Markdown 報表與畫面上。
    - `status` 是處理紀錄的狀態（`open`／`scheduled`／`accepted`／`false-positive`／`fixed`／`regressed`），不在處理紀錄中時空白；`note` 是備註（不論狀態）；`waiver_reason`、`waiver_until` 是可接受的豁免原因與到期日（UTC ISO）。
    - `facet` 是 `finding.facet` 的原值（檢查項目，會進入 findingKey，見 [§7](#7-一致性檢查)），例如 A12 的 `dns`／`ntp`；規則沒有 facet 時空白。放原值而不是畫面的顯示文字，方便在試算表篩選與對照 findingKey。Markdown 報表不加這一欄，因為訊息已經寫出項目。
    - 開頭有 UTF-8 BOM，換行為 CRLF；含逗號、引號、換行或頭尾空白的儲存格依 RFC 4180 加引號；以 `=`、`+`、`-`、`@`、Tab、CR 開頭的儲存格前面加 `'`，避免試算表當成公式執行。
  - 檢查結果 Markdown：預設依嚴重度、規則分組，每條規則的段落開頭先列「處理建議」與逐條的「常見原因」（反引號內轉成行內程式碼）；含證據原文與行號。開頭有一行「處理紀錄」列出各狀態（open 以外）的筆數。已處理的項目前面標出狀態與時間，回歸的標「回歸」，豁免與備註另起一行。
  - 「依設備排序」：CSV 改依所屬設備排序，Markdown 改依設備分組（每組標題是設備名稱與筆數，不屬於任何設備的最後一組），組內保留原順序。同一條規則會出現在很多台設備，所以依設備分組時，處理建議與常見原因集中在報表最後的「附錄：處理建議與常見原因」，只列這份基準有出現的規則，每條一次，依 `CATALOG` 的順序。
  - 預期資料：`S.compare.expectedFrom(Q)` 的結果（`ssot-expected/1`）。
  - devices.csv 草稿：見上，不加 BOM、換行用 LF（`collect.sh` 以 bash 逐行讀取）。
  - 修正計畫：每台設備三個 `.rsc` 與總表 Markdown，見上面的修正計畫對話框。
  - 處理紀錄：`ledger-<目前時間>.json`，見上。
  - 檔名含建立時間與設備數，例如 `findings-20260101T000000Z-42dev.csv`、`devices-draft-20260101T000000Z-42dev.csv`。

## 15. 修正 patch（ssot-patch/1）

核心 [src/remediate/patch.js](../src/remediate/patch.js) 由基準的 finding 產生結構化的修正計畫，再輸出成 RouterOS `.rsc` 文字。**工具維持唯讀**：只產生文字，不連線、不套用到設備，也沒有套用用的工具（[ADR-001](架構決策/001-工具維持唯讀.md)）。計畫只用 Snapshot 的事實，相同的基準與選取一定得到相同的計畫與文字（有黃金檔測試 `tests/golden/sample-patch*`）。

**計畫**：`S.remediate.plan(Q, selection)` 回傳

```
{ schema: 'ssot-patch/1', baseline: { inputHash, createdAt, version }, devices: [{ key, name }], items: [...], skipped: [...] }
```

- **selection**：省略或 null 為全部 finding；字串陣列為 findingKey 清單；物件 `{ keys?, ids?, devices? }` 為三者的交集（`devices` 可以是設備鍵或名稱）。有不認得的欄位，或不是字串陣列時，丟出 TypeError；基準中沒有的 findingKey 放進 `skipped`（reason 為 `not-found`）。
- **level**（`S.remediate.LEVEL`、`levelOf(id)`）：`auto` 可直接產生指令（F01、F02、F06）；`choice` 要使用者選擇處理方式（F03、V01、V08、R06、A06–A12，第二階段實作）；其他都是 `manual`，需要人工判斷。
- **item**（目前只有停用規則）：`{ key: 'disable-rule:<規則鍵>', findingKey, id, dev, level: 'auto', target: { type: 'rule', key, family, table, chain, position, by }, ops, evidence, risk: { level, text }, note, warnings }`。
  - `ops[]` 是結構化的修改 `{ op: 'set', path, where, expect: 1, props: { disabled: 'yes' }, before: { disabled: 'no' } }`；`before` 是基準中的值，供回復使用。
  - `where` 是 `find where` 的條件，不用規則編號。依序嘗試 comment、比對條件（action、比對欄位與參數）、兩者合併，取同一個 chain 中沒有其他規則也符合的第一種（`target.by` 是 `comment`、`match` 或 `comment+match`）。comment 只在編碼是 ASCII 或 UTF-8 時使用，其他編碼無法確定與設備內的文字相同。
  - `risk.level` 是 `low`（F01、F02）或 `medium`（F06）；`note` 是中文說明；`warnings` 是需要注意的事，例如註解編碼不明、find 條件含非 ASCII 文字。
- **skipped**：`{ findingKey, id, dev, level, reason, detail, rule?, item? }`，`detail` 是給使用者看的原因。reason 有：
  - `choice`、`manual`：這個等級目前不產生指令。
  - `no-rule`：找不到 finding 指向的規則。`already-disabled`：基準中這條規則已經停用。
  - `ambiguous-find`：每一種 find 條件都會符合同一個 chain 的其他規則（前置檢查一定會中止），改為人工處理。說明文字（`SKIP_TEXT`）是「find 條件可能符合多條規則，無法確定只停用這一條；先為這條規則加上可區分的 comment，再重新收集」；`detail` 另寫出同一個 chain 中也符合的規則編號，F02 的兩條規則完全相同時就是這種情況。
  - `unsafe-property`：屬性名稱不是 RouterOS 的屬性格式，無法安全地寫成 find 條件。
  - `same-target`：同一條規則已由前面的項目停用（`item` 是那一項的鍵）。
  - `not-found`：基準中沒有這個 findingKey（`id`、`dev`、`level` 為 null）。
- **排序**：`items` 依設備（名稱的自然順序，再依鍵），同一台設備內依 finding 在基準中的順序；`skipped` 同樣排序，不屬於任何設備的在後，基準中沒有的鍵最後。`devices` 是有 item 的設備，依 `items` 的順序。

**.rsc 文字**：每台設備三個檔案。檔頭寫出格式、設備、基準（inputHash、建立時間、版本），並註明工具不會連線或改動設備。

- **套用**（`renderRsc(plan, dev)`）：所有前置檢查集中在最前面，每個 op 一條 `:if ([:len [<path> find where …]] != 1) do={ :error … }`，任一失敗就中止。RouterOS 的 `/import` 逐行執行到第一個錯誤為止、沒有交易，所以前置檢查不通過時不會改到任何設定。之後才依序 `set [find where …] disabled=yes`，每一行前面以註解寫出修改前的值。
- **回復**（`renderRollback`）：套用的反向，項目與 op 都倒序、`props` 與 `before` 互換，同樣先做前置檢查。
- **驗證**（`renderVerify`）：每個 op 一條 `print where …`，註解寫出預期結果（應只列出一條、是否帶 `X` 停用旗標）。
- **只用 ASCII**：手冊沒有說明 `/import` 對非 ASCII 位元組的處理，所以字串一律加引號（`where` 才是字串比對），`"`、`\`、`$` 依手冊跳脫，`?`、控制字元與非 ASCII 位元組寫成 `\XX`；註解中的非 ASCII 字元寫成 `<U+XXXX>`。中文說明只放在計畫的 note、risk、warnings。
- **多台設備**：`S.remediate.files(plan)` 依 `devices` 的順序，回傳每台的 `{ dev, name, base, apply, rollback, verify }`，檔名是 `base.rsc`、`base-rollback.rsc`、`base-verify.rsc`。設備鍵只含 `A-Z a-z 0-9 _ . -`，而且不會和其他設備替換後的名稱重複時，直接當 `base`；否則替換不合格的字元，再加上鍵的雜湊前 8 碼。

RouterOS 語法的依據（`find where`、`:if`、`:error`、字串跳脫、`/import` 的行為）寫在 `patch.js` 開頭的註解，附官方手冊的網址。

## 16. 處理紀錄（ssot-ledger/1）

核心 [src/ledger/ledger.js](../src/ledger/ledger.js) 記錄使用者對每個 finding 的決定與每一輪的歷程，讓一輪輪收集的結果互相銜接、逐漸收斂。這是使用者的資料，**不放進 Snapshot**（[ADR-002](架構決策/002-處理紀錄放在基準之外.md)）；只透過查詢介面讀基準，不修改基準。全部是純函式：不碰 DOM 與 IndexedDB、不讀目前時間（`now` 由呼叫端傳入，必須是 ISO 8601）、不修改傳入的物件。

**資料格式**

```
{
  schema: 'ssot-ledger/1',
  items: { '<findingKey>': {
    status, id, dev, devs?, firstSeen, lastSeen, patch, waiver: { reason, until } | null, note,
    history: [{ at, from, to, by: 'user' | 'advance', baseline, reason, waiver?, ack?, fromKey?, superseded? }] } },
  iterations: [{ baseline: { inputHash, baselineKey?, createdAt }, at, counts, coverage: { collected, expected }, unknownPeers }]
}
```

- `items` 以 findingKey 為鍵（見 [ADR-003](架構決策/003-findingKey的組成.md)），依鍵排序。碰撞的 finding 共用同一個項目。
- `dev`：findingKey 只涉及一台設備時是該設備（取自 device 實體，以及介面、規則、服務鍵與鏈路兩端的設備部分），否則為 null。
- `devs`（選用）：只有 findingKey 推不出設備的項目才有（例如只涉及 IP、MAC 的 A01）。是這個問題最後一次出現時，證據所在區塊的設備（排序；同一個鍵的每筆 finding 都算）；`[]` 表示證據都在沒有設備標頭的區塊，`null` 表示推不出來（沒有證據，或證據的區塊對不到）。用來判斷能不能判定已修好。較早的紀錄沒有這個欄位。
- `firstSeen`／`lastSeen`：第一次與最後一次出現的基準鍵；`history[].baseline` 是當時最新一輪的基準鍵。
- `waiver` 只在 accepted 時有值；離開 accepted 時，原本的豁免記在那一筆歷程的 `waiver`，不遺失。
- `patch`：對應的修正 patch 鍵（字串）或 null。
- `history[].reason`：`advance` 寫入 `new`、`disappeared`、`reappeared`、`waiver-expired` 與舊鍵轉換的 `facet-split`；使用者變更是 `edit`，舊確認標記是 `from-ack`。
- `history[].fromKey`、`history[].superseded`（選用）：只有舊鍵轉換的那一筆歷程才有。`fromKey` 是轉換前的舊鍵；`superseded` 只在新鍵已有項目時出現，保存被取代的舊項目完整內容。見下方「舊鍵轉換」。
- `S.ledger.validate(obj)` 逐項回報格式錯誤（`{ ok, errors }`），不修改、不丟棄資料；不認得的欄位（較新版本寫入的）保留，不算錯誤。其他函式收到格式不正確的處理紀錄時丟出錯誤，不靜默修正。

**狀態**：`open`（待處理）、`scheduled`（已排程修復）、`fixed`（已修好）、`accepted`（可接受，附豁免）、`false-positive`（誤報）、`regressed`（回歸：修好後又出現）。

**推進一輪**：`S.ledger.advance(ledger, Q, { now })` 回傳 `{ ledger, changes, unobserved, split, skipped }`（`split` 見下方「舊鍵轉換」；`skipped` 時為空陣列）。下表的「出現」是基準中有這個 findingKey；「消失」是沒有，而且可以判定；「無法判定」是沒有，但不能判定是否已修好。

| 目前狀態 | 出現 | 消失 | 無法判定 |
|---|---|---|---|
| （不在處理紀錄中） | 新增為 open（`new`） | — | — |
| open、scheduled、regressed | 不變 | fixed（`disappeared`） | 不變，列在 `unobserved` |
| fixed | regressed（`reappeared`） | 不變 | 不變 |
| accepted | 不變 | 不變 | 不變 |
| false-positive | 不變 | 不變 | 不變 |

- accepted 不論是否出現，豁免到期（`until` 早於 now）時改回 open（`waiver-expired`）。false-positive 不變，因為判斷的是規則本身，不是網路現況，保留給規則品質統計。
- 出現在基準中的項目更新 `lastSeen`（第一次出現時也補 `firstSeen`）。`changes` 是 `[{ key, from, to, reason }]`，依鍵排序。
- **能不能判定已修好**：
  - **findingKey 推得出設備**：涉及的每台設備都要可以判定，也就是已收集且沒有任何收集失敗，或只在鄰居資料中出現、沒有收集（它的問題不依賴它自己的輸出）。已收集但有收集失敗、或整台不在基準中時不判定，因為問題消失可能只是沒收到資料。
  - **findingKey 推不出設備、`devs` 有設備**：`devs` 的設備都已收集、而且沒有收集失敗，才判定；否則列為 unobserved。換成另一個網路時，這些設備不在基準中，所以不會誤判成 fixed。
  - **`devs` 是 `[]`**（證據都在沒有設備標頭的區塊）：基準中沒有任何收集失敗才判定。
  - **沒有 `devs`（舊紀錄）或為 `null`**：保守地列為 unobserved。
  - 每筆 finding 最多附 6 筆證據，所以證據超過上限時，`devs` 只涵蓋前 6 筆證據所在的設備。
- **冪等**：依基準鍵判斷是不是同一份基準。基準鍵是 `meta.baselineKey`（[§5.2](#52-實體snapshotmodelschema-ssot-snapshot2)）；2.8.0 以前的基準與處理紀錄沒有 baselineKey，一律退回用 inputHash，不改寫舊資料。已經推進過的基準回傳 `skipped: true`，處理紀錄原樣不動、不新增一輪。
- **每一輪的摘要** `iterations[]`：`baseline` 記 inputHash、baselineKey（有時）與建立時間，`at` 是推進的時間。只存摘要，不存整份 Snapshot。`counts` 的意義：
  - `new`、`fixed`、`waiverExpired`、`unobserved`：這一輪新增、判定已修好、豁免到期、無法判定的筆數。
  - `open`、`scheduled`、`regressed`、`accepted`、`falsePositive`：推進後各狀態的總筆數。
  - `coverage`：`collected` 是已收集的設備數，`expected` 是已收集數加上 C01（應收集但未收集）的筆數。`unknownPeers` 是未知對端的總數。

**舊鍵轉換**（`S.ledger.KEY_MIGRATIONS`）：findingKey 的組成改變時（[ADR-003](架構決策/003-findingKey的組成.md)），把舊鍵項目的決定帶到新鍵。決策見 [ADR-002](架構決策/002-處理紀錄放在基準之外.md) 的「修訂」。

- **規則**：每條是 `{ reason, oldKeys(Q, f) }`，給新基準的一筆 finding，回傳它可能對應到的舊鍵（可以是空陣列）。目前只有一條 `facet-split`（2.9.0）：有 facet 的 finding，舊鍵是 `Q.findingBaseKey(f)`。規則依陣列順序套用，新鍵與舊鍵相同時不算轉換。
- **時機**：`advance` 在判定狀態之前轉換，所以舊項目不會被判為消失。只轉換處理紀錄有這個舊鍵、而且舊鍵不在新基準中的項目。`fromAcks` 推進時套用同一套轉換。
- **舊項目的處置**：
  - 新鍵還沒有項目：複製整個舊項目（狀態、`note`、`waiver`、`patch`、`firstSeen`、歷程與不認得的欄位），`dev` 依新鍵重新推得，歷程加一筆 `{ from: 狀態, to: 狀態, by: 'advance', baseline, reason, fromKey: 舊鍵 }`。一個舊鍵對應到幾個新鍵就複製幾份。
  - 新鍵已經有項目：以新鍵的項目為準，歷程加一筆同樣的紀錄，並在 `superseded` 保存舊項目的完整內容。
  - 轉換完後刪除舊項目：它的內容已在每一筆新項目中，留著會被判為 fixed 或重複計數。
  - 轉換後的新項目再照上表判定，例如舊項目是 fixed、新鍵出現時改為 regressed。
- **回傳**：`split` 是 `[{ from: 舊鍵, to: [新鍵…], reason }]`，依舊鍵排序，`to` 也排序。
- **冪等**：舊項目轉換後就刪除，每個舊鍵只轉換一次；同一份基準再推進時依基準鍵略過。
- **擴充方式**：在 `KEY_MIGRATIONS` 加一條規則即可，轉換流程（`migrateKeys`）不用改。例如 M3 的 VRF（[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）讓實體鍵多了 VRF 時，再加一條把新鍵對回舊鍵的規則。

**使用者變更**：`S.ledger.set(ledger, key, change, { now })`，`change = { status?, note?, waiver?, patch? }`，省略的欄位不變。

| 目前狀態 | 使用者可以改為 |
|---|---|
| open | scheduled、accepted、false-positive、fixed |
| scheduled | open、accepted、false-positive、fixed |
| accepted | open、scheduled、false-positive、fixed |
| false-positive | open、scheduled、accepted、fixed |
| regressed | open、scheduled、accepted、false-positive、fixed |
| fixed | 不能改狀態（之後若再出現，`advance` 會標為 regressed）；仍可修改備註與 patch |

- regressed 只能由 `advance` 判定。手動標為 fixed 只允許在項目已不在最新一輪基準時（例如設備已移除）；仍出現時丟出錯誤，請修好後重新收集，由 `advance` 判定。
- accepted 一定要有豁免：`until` 省略時是 now 加 182 天（`S.ledger.WAIVER_DAYS`），而且必須晚於 now；其他狀態不能有豁免。
- 有任何欄位改變時寫入一筆歷程（狀態不變時 from＝to、reason 為 `edit`；被取代或移除的豁免記在歷程）；完全沒有改變時原樣回傳。不合法的轉換、不存在的鍵、格式不對的欄位都丟出錯誤。

**從舊確認標記轉換**：`S.ledger.fromAcks(acks, Q, { now })` 把畫面舊版的確認標記（`{ findingKey: { at, kind, note } }` 或同內容的 Map）轉成處理紀錄，接著以 Q 推進一輪，回傳與 `advance` 相同的結果。

- 分類：`accepted`、`scheduled`、`false-positive` 對應同名狀態；未分類（null）與不認得的分類視為 accepted。
- accepted 的豁免原因取 note，到期日是 now 加 182 天（從轉換時起算，避免很久以前的確認一轉換就到期）。
- 每一項的第一筆歷程是 `{ at: 確認時間, from: null, to, by: 'user', baseline: null, reason: 'from-ack', ack: 原始紀錄 }`，原始內容不遺失。
- 任何一筆格式不對（鍵不是 findingKey、`at` 不是 ISO 時間、`kind`／`note` 型別不對）就丟出錯誤並列出全部問題，不略過。

**統計**

- `S.ledger.summary(ledger)`：趨勢圖用的時間序列 `series`（每一輪的 counts、待處理＝open＋regressed、覆蓋與比率、未知對端），以及目前狀態 `current`（各狀態筆數、豁免總數與沒寫原因的筆數）。
- `S.ledger.ruleStats(ledger)`：各規則的處理結果與誤報比率（標為 false-positive 的筆數／該規則的總筆數），依規則編號排序，供規則品質的閉環使用。
