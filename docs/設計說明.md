# topo-mikrotik 設計說明（MikroTik RouterOS 專用版）

> 這是 topo-ssot 的 **MikroTik 專用版**：核心架構、模型、檢查、畫面與多廠牌版相同，只有「輸入解析器」、設備類型推論與少數檢查不同。差異見[附錄 B](#附錄-b與多廠牌版juniperfortinet的差異)。以下內容以本版為準。

範圍：MikroTik RouterOS（7.x 為主）｜規模：約 1000 台已收集設備｜一次貼完、在瀏覽器即時產生｜不需網路、不需後端

**章節安排**：原則（第 1–3 節）→ 上游：輸入、模型與推論、命名規則、檢查（第 4–7 節）→ 下游：比對、修正 patch、處理紀錄、工作包（第 8–10A 節）→ 檢視層架構（第 11 節；畫面操作在[使用說明](使用說明.md)，第 12 節只留連結）→ 附錄。

## 1. 目的

由設備 CLI 輸出建立一份**可信的網路現況基準（Snapshot）**，並回答：

1. 網路結構是什麼？
2. 某個 MAC／IP／VLAN 在哪裡？
3. 哪些地方資料互相矛盾、哪些地方沒有收集到？

圖、表、路由追蹤都只是檢視這份基準的方式。

## 2. 原則

| # | 原則 | 實作方式 |
|---|---|---|
| P1 | 一次建立、不增量合併 | `SSOT.build(sources, options) → Snapshot`；同輸入同結果（有測試） |
| P2 | 核心與外掛分離 | 輸入格式（readers）、命名規則（profile）、比對（compare）都可拔除 |
| P3 | 依賴單向 | 外掛讀核心；核心不讀外掛；比對只透過查詢介面讀基準 |
| P4 | 每筆事實帶來源 | 事實帶「區塊、行號」；畫面可開啟原文並標示該行 |
| P5 | 不靜默失敗 | 無法辨識的內容、辨識成功卻解析不出東西的段落列入 I01；已解析的區塊中認不得的行列入 I03 |
| P6 | 核心不碰畫面與儲存 | 核心可在 Node 執行（測試即如此） |

## 3. 模組

```
        ┌──────────── 外掛（可拔除）─────────────┐
        │ readers/   bundle-v1、files-v1         │
        │ profile/   命名規則引擎＋profiles/*.js  │
        │ compare/   預期資料比對、新舊基準比對    │
        └──────┬────────────┬──────────┬────────┘
               ▼            ▼          ▼ 只讀
        ┌──────────────────── 核心 ─────────────────────┐
        │ adapters/  辨識＋解析 → 事實（fact）             │
        │ model/     build.js 事實→實體；infer.js 推論     │
        │ check/     一致性檢查、覆蓋率                     │
        │ core/      keys.js 唯一鍵、ip.js、ns.js           │
        │ pipeline.js  ①讀取→②辨識→③解析→④建模→⑤推論→⑥檢查 │
        │ query/     唯讀查詢、路由追蹤、L4 可達性          │
        └──────────────────────┬──────────────────────────┘
                               ▼
                           Snapshot（純 JSON）
                               ▼ 只讀（SSOT.query）
        ┌──────────── 下游（只讀基準）──────────────────┐
        │ remediate/ 修正 patch（ssot-patch/1，只產生文字）│
        │ ledger/    處理紀錄（ssot-ledger/1，不在基準內） │
        │ workpack/  工作包（ssot-workpack/1）與 ZIP 讀寫 │
        └──────────────────────┬──────────────────────────┘
                               ▼
              view/（單一畫面：檢查結果｜拓樸圖｜詳細資料）
```

`remediate/`、`ledger/` 與 `workpack/` 也是核心檔案（列在 `tools/core-files.js`，不碰畫面與儲存），但它們在 Snapshot 的下游：只透過 `SSOT.query()` 讀基準（工作包另外在呼叫時使用 `S.build`、`S.ledger` 與 `S.profile`），不修改基準，也不被上游的 pipeline 使用。修正 patch 見[第 9 節](#9-修正-patchssot-patch1)，處理紀錄見[第 10 節](#10-處理紀錄ssot-ledger1)，工作包見[第 10A 節](#10a-工作包ssot-workpack1)。

所有檔案都是一般 `<script>`，以 `globalThis.SSOT` 命名空間串接；載入順序定義在 `tools/core-files.js`，測試會檢查 `index.html` 與它一致。這樣 `index.html` 可以直接雙擊開啟（瀏覽器在 `file://` 下不允許 ES module 與 Web Worker）。

`check/` 分成兩個檔案：`catalog.js` 是規則目錄（`S.check.CATALOG`：編號、嚴重度、類別、標題、需要的資料、常見原因 `causes` 與處理方式 `action`），`checks.js` 是判斷。`catalog.js` 必須在 `checks.js` 之前載入；順序錯了，`checks.js` 載入時會直接丟出錯誤，不會在沒有規則目錄的情況下執行。`causes`、`action` 只在 `CATALOG`，不複製到 finding，也不進 Snapshot；畫面與匯出透過 `V.remediation.advice()` 讀取（見[第 11 節](#111-資料來源與檢視狀態)）。

## 4. 輸入

```
原始輸入 ─Reader─▶ Block[] ─辨識─▶ Block＋adapter ─Adapter─▶ Fact[]
```

- **Block**：`{ device, mgmtIp, command, lines, origin:{file,startLine,endLine} }`；有 SSH 收集器的註解時另有 `collectedAt`（指令開始的 UTC 時間）、`failure`（`{ reason, exitCode, text, line }`），註解寫錯時記在 `issues`（由 I01 列出）。註解格式見[收集清單 §2「其他規則」](收集清單與輸入格式.md#其他規則)。
- **Reader**：`bundle-v1`（設備標頭＋`_____`）、`files-v1`（檔名＝設備名）。介面：`accepts(text,file)`、`read(text,file)`。
- **指令標記**：`### 指令`、RouterOS 提示字元 `[user@id] > /指令`（須為絕對路徑）。有標記時依指令選 adapter，否則依內容判斷。
- 所有 `print` 指令都要用 `detail without-paging`（key=value 格式）。詳見 `docs/收集清單與輸入格式.md`。
- **Adapter 介面**（`src/adapters/index.js`）：`{ id, vendor, dataType, label, command, detect(lines), parse(block, emit, ignore) }`。`parse` 只把文字轉成事實，每筆事實帶 `line`；`ignore(line, why)` 宣告這一行依該指令的格式本來就不產生事實（說明行、續行、停用的項目等），`why` 是簡短原因。
- **每一行都要有去處**：`S.adapters.parse(block, adapters, decorate)` 以辨識出的 adapter 解析區塊，回傳 `{ facts, usage, ignored, unrecognized }`。已解析區塊中的每個非空行，不是產生事實的行，就是 adapter 宣告可忽略的行；**兩者都不是，就是無法辨識**，記在 `blocks[].unrecognizedLines` 並列為 I03。所以 adapter 只宣告可忽略的行，沒處理到的行一定會被列出。多個 adapter 時，任一個產生事實或宣告可忽略就算有處理。
- **RouterOS 錯誤訊息**：`S.adapters.util.rosError(line)` 判斷一行是不是 RouterOS 的錯誤回應（行首的 `bad command name`、`syntax error`、`no such item`、`failure:` 等）。這種行一律算無法辨識，即使 adapter 宣告可忽略。
- **I01 與 I03**：整段沒有進入基準（沒有設備標頭、沒有解析器認得、辨識成功卻解析不出任何資料；整段只有 RouterOS 錯誤訊息時訊息改為「指令執行錯誤」）列為 I01；已解析出事實的區塊中個別認不得的行列為 I03。條件與可忽略的行見[基準檢查規則 I03](基準檢查規則.md#i03)。測試的不變式「每一行輸入都有被處理」逐行檢查範例資料與 `tests/fixtures/`：每個非空行都是結構行、產生事實、可忽略、I03 或 I01，而且 fixtures 不可有 I03。

**detail 輸出的解析**：以「列」為單位。列首是 `序號 旗標 key=value…`（序號、旗標可省略）；直接以 key=value 開頭的行是終端機換行的續行，併入上一列；`;;; 註解` 屬於它所在或下一列。只有序號與旗標、欄位在下一行的列首（例如「13  R 」）也開新列；2.8.0 以前這種行會讓下一列被併進上一列（範例中 bond100 失去介面狀態、bridge1 拿到 bond100 的註解）。旗標必須是 `Flags:` 說明行列出的字元（沒有說明行時只接受英文字母），雜訊不會被當成列首。
新增廠牌：新增一支 `adapters/<vendor>.js` 呼叫 `S.adapters.register()`，其他部分不需修改。

**防火牆規則的鍵與簽章**

- `signature`：設備＋位址族＋表＋chain＋比對條件（清單值排序後的正規形式），不含動作與編號，供比對與重複判斷使用。
- `key`：`設備|位址族|表|chain|簽章雜湊`；同一個簽章在同一個 chain 第二次以後出現時加 `#n`。在 chain 中插入一條規則時，其他規則的鍵不變（除非新規則的簽章與後面某條相同）。

**不重建也能使用的公開函式**

|---|---|---|
| `ipBind` | `M.ipBinds` | dev、section（選單）、name、value，另有比對鍵 nameKey（trim＋小寫；DHCP 租約為正規化 MAC）、valueKey（/32 去遮罩、網段取網路位址）；供 A10、A11 |
| `dhcpNet` 的 `dns`、`ntp` | `M.dhcpNets[].dns`、`ntp` | dns-server、ntp-server；供 R06。Snapshot 的 `dhcpNetworks` 只輸出 gateways |

**設備身分**

- `deviceType`（型號）、`softwareVersion`、`platform`、`caps` 是事實。來源依序是設備自己的 `/system resource`，其次是鄰居回報；設備自報優先。
- `manufacturer` 是推論：資料來自 MikroTik adapter，或 platform 為 MikroTik／RouterOS 時為 `mikrotik`。
- `kind` 是設備類型推論。不使用 NetBox 的 `role`，因為 `role` 保留給命名規則的註解。

**DNS／NTP 伺服器**（`devices[].dnsServers`、`ntpServers`，事實；供 A12，之後的修正指令依來源決定寫法）

- 形狀：`null`（沒有設定）或 `{ values, menu, param, src }`。`values` 是伺服器清單，`menu`／`param` 是收集到的來源選單與參數，`src` 是各設定行。
- 來源有四種組合（`src/adapters/mikrotik.js`）：

  | menu | param | 說明 |
  |---|---|---|
  | `/ip dns` | `servers` | DNS |
  | `/system ntp client` | `servers` | RouterOS 7 |
  | `/system ntp client servers` | `address` | RouterOS 7 的子選單，每筆 `add` 一個伺服器；略過停用的項目 |
  | `/system ntp client` | `primary-ntp/secondary-ntp` | RouterOS 6 的兩個固定欄位，記成同一個 param |

- 同一台設備有多個來源時：`values` 依出現順序合併並去重；`menu`／`param` 依 `src/model/build.js` 的 `SERVER_SOURCE_RANK`（上表的順序）取優先序最高的那一個，同序取先出現的。RouterOS 7 的子選單會同時列出 `servers=` 設定的靜態項目與動態項目，所以 `servers=` 優先於子選單。
- `/ip dns` 的 `dynamic-servers` 是唯讀的（DHCP client 等服務學到的），不是設定值，不收集。
- 查詢：`Q.serversOf(devKey)` 回傳 `{ dns, ntp }`，各為上面的形狀或 null（沒有設定或找不到設備）。

**介面**

- 欄位：
  - `type` 是封閉列舉 `S.IFC_TYPES`：`physical`、`lag`、`bridge`、`vlan`、`wireless`、`virtual`、`loopback`、`other`。原始 RouterOS 類型保留在 `rawType`，例如 veth 屬於 `virtual`，但 `rawType` 仍是 `veth`。
  - `typeBasis` 說明類型的依據：`rawType`、`member`（有聚合成員）、`name`（名稱慣例）或 `default`（缺資料，預設為實體埠）。
  - `enabled` 為 `false` 表示任一來源停用；為 `null` 表示沒有資料。
- 介面之間的關係都存 ep 鍵，分為三種，不共用欄位：
  - 聚合：`lag`／`lagMembers`
  - bridge port：`bridge`
  - VLAN 子介面：`parent`＋`encapVlan`
- VLAN 成員：
  - 欄位：`pvid`（bridge port 的 ingress 預設 VLAN）、`untaggedVlans`、`taggedVlans`，三者分開儲存。
  - 介面承載的全部 VLAN 用 `S.util.ifcVlans(i)` 取得；V01 以這個聯集（含所屬聚合）比較。
  - 不是數字的 VLAN 記在 `unresolvedVlans`，不丟棄。
  - **VLAN 子介面讓 parent 承載**：`/interface vlan` 解析時，把它的 VLAN 記成 parent 的 `taggedVlans`（設定的事實：parent 收送帶這個 VLAN ID 的 tagged 訊框）；停用的子介面不算。依 parent 的種類：
    - 實體埠：埠本身以 tagged 承載，例如單臂路由（router-on-a-stick）的實體埠。
    - 聚合（bond）：聚合介面帶這個 VLAN，成員埠經所屬聚合承載（同 `effVlans`）。
    - bridge：只有 bridge 本身（CPU 埠）帶這個 VLAN，bridge 的成員埠不帶。
- `mode` 是推論：有 tagged VLAN 為 `tagged`（trunk），只有 PVID／untagged 為 `access`，都沒有則為 `null`。
- **vlan-filtering**：
  - `vlanFiltering`（事實）：bridge 介面的 `vlan-filtering`，true／false；不是 bridge，或沒有這個 bridge 的設定資料時為 null。依 export 判斷：terse export 不寫預設值，`add` 沒寫就是 no（false）；`set` 只有寫了才改。
  - `vlanUnfiltered`（推論）：介面在 `vlanFiltering` 為 false 的 bridge 上，包括 bridge 本身、bridge port，以及 bridge port 的聚合成員（`S.infer.bridgeOf`）。依手冊，這時 bridge 不看也不改 VLAN 標籤，`pvid`、`frame-types`、`ingress-filtering` 都沒有作用，所以這一端承載哪些 VLAN 無法由設定確認。只由其他輸出知道、`vlanFiltering` 為 null 的 bridge，不當成未過濾。
- **鏈路兩端的 VLAN**（`S.infer` 的 `linkVlans`，V01、`Q.vlan`、`Q.vlanCarriers` 共用）：
  - `vlansA`／`vlansB`：兩端的有效 VLAN（介面本身加上所屬聚合）；`vlansCommon`：交集。
  - `vlanComparable`：兩端都有 VLAN 資料、不是單側觀察，而且兩端都不是 `vlanUnfiltered`。
  - `vlansDiff`：可比較時，只在一端、計入 V01 的 VLAN。一端不在任何 bridge 上、也沒有 PVID 時（例如單臂路由的實體埠，VLAN 只靠子介面），對端只以 untagged 承載、這一端沒有的 VLAN（通常是 PVID 1）不算：這一端的 untagged 訊框由介面本身處理，沒有 VLAN ID。「不在任何 bridge 上」要有那台設備的 export 才能確定。不可比較時為空陣列。
  - `vlanMismatch`：`vlansDiff` 不是空的。
- **已知的限制**：
  - 兩台以上未過濾的交換器串接時，它們之間的鏈路兩端都是 `vlanUnfiltered`，不算透通鏈路（見 §5.3「VLAN 區塊」），所以不會把兩側連成同一塊。
  - `use-service-tag=yes`（S-tag，802.1ad）仍當作同一個 VLAN ID 比較。
  - VLAN 子介面直接建在 bridge 的成員埠上時，沒有特別處理（依上面的規則，由那個成員埠以 tagged 承載）。

**IP 位址與前綴**

- 每個介面上的每個位址是一筆 `ipAddresses`，帶來源行。
- OSPF 鄰居位址以 `/32`、`hearsay: true` 儲存。
- `prefixes` 是推論，由設備自有、長度小於 32 的位址推導出直連網段。鄰居宣告的位址不產生前綴。
- 查詢介面：
  - `Q.ipOwner(ip)`
  - `Q.ipsOf(ep)`
  - `Q.addressesOf(ep)`
  - `Q.subnets()`
  - `Q.prefixes()`
  - `Q.subnetGraph(opts)`：L3 子網圖（M1），見下方。

**L3 子網圖**：`Q.subnetGraph({ nodes, hearsay, routes })` → `{ subnets, nodes, edges, routes }`。子網節點、設備或介面節點，以及「在這個子網有位址」的邊。

- **參數**：`nodes` 為 `'device'`（預設，每台設備一個節點）或 `'interface'`（每個介面一個節點；管理 IP 的節點 id 是「設備鍵|」）。`hearsay` 預設 true，加入推論的邊：鄰居宣告的位址（`basis: 'neighbor'`）與沒有列在介面位址的管理 IP（`basis: 'mgmt'`），都只以最長相符接到已知網段，不產生新網段。`routes` 預設 false，為 true 時加入靜態路由（含黑洞）與預設路由；目的網段不是已知網段時，新增 `basis: 'route'` 的子網節點。
- `subnets[]`：`{ id, prefix, net, len, family, vrf, basis（connected／route）, vlan, vlans, eps, devices, routers, gateways, overlaps, duplicateIps }`。`routers` 是接在這裡的路由設備，`gateways` 是 DHCP 網路設定的閘道（`{ ip, dev, src }`）。
  - `overlaps`：和這個網段互相包含的其他網段 id（例如 `10.0.0.0/16` 與 `10.0.1.0/24`）。`routes` 為 true 時，路由新增的子網（例如彙總路由）也參與比對；預設路由 /0 包含所有網段，不列。
  - `duplicateIps`：同一個 IP 設在這個網段的多個介面上（VRRP 位址除外，鄰居宣告的不算）。
- `nodes[]`：`{ id, type, dev, ep, name, label, kind, collected, vrf, subnets, router, routerBasis, multihomed, hostAddresses }`。`hostAddresses` 是 /32 的自有位址（loopback 等，不形成網段）。
  - **路由設備是推論**：接到 2 個以上的子網，而且有路由表資料（`routerBasis: 'routes'`），或設備類型是路由器或防火牆（`'kind'`）。只是多張網卡的主機不算（`multihomed` 為 true、`router` 為 false）。interface 節點的 `router` 是所屬設備的值。
- `edges[]`：`{ id, subnet, node, dev, eps, addresses: [{ address, ip, ep, role, hearsay, seenBy, src }], basis（address／neighbor／mgmt）, inferred, vrf }`。`inferred` 為 `basis` 不是 `address`。
  - **管理 IP 的邊以 `seenBy` 追溯**：`mgmtIp` 在 Snapshot 沒有來源行，所以 `src` 是設備的 `src`（只由鄰居看到的設備為空），`seenBy` 列出看到這台設備的已收集設備。
- `routes[]`：`{ id, dev, subnet（目的網段 id）, prefix, len, default, proto, distance, blackhole, nh, via（下一跳所在、這台設備直連的網段 id）, vrf, src }`。interface 模式也接在設備上。
- **vrf 目前固定為 null**：M3（[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）之前全部視為 main。同一個網段即使在不同 VRF 或不同站點，也會併成同一個子網節點，這是已知的限制。
- **只有 IPv4**：核心沒有收集 IPv6 的 prefix 與路由，所以子網與路由都是 IPv4。

**L2 視圖的查詢**（M1）

- `Q.vlanIds()`：基準中出現的所有 VLAN ID（VLAN 定義與介面的 PVID／untagged／tagged），由小到大。VLAN 篩選的選項用。
- `Q.vlanCarriers(vid, domain)`：承載這個 VLAN 的鏈路，VLAN 篩選時高亮用；給 `domain`（`Q.vlan` 的區塊鍵，見 [§5.3「VLAN 區塊」](#53-關鍵推論)）時只含那一塊。回傳 `{ id, domain, devices, links, counts: { carry, partial, oneSide, inferred }, eps }`。
  - `links[]`：`{ key, kind（link／inferred）, status, inferred, hearsay, reason, a, b, src }`，依 status（下表的順序）再依鍵排序。`kind` 表示用 `Q.getLink` 還是 `Q.getInferredLink` 取回原始實體；`inferred` 為 true 表示這一列是推論；`hearsay` 表示鏈路本身只有單側觀察。判斷依據和 `Q.vlan` 相同：兩端的有效 VLAN（介面本身加上所屬聚合的 PVID／untagged／tagged）。

    | status | 意義 | 事實或推論 |
    |---|---|---|
    | `carry` | 兩端都帶這個 VLAN | 事實 |
    | `partial` | 兩端都有 VLAN 資料，只有一端帶（兩端不一致，V01）；只含 `vlansDiff` 中的 VLAN，例如單臂路由的實體埠對上 PVID 1 不算 | 事實 |
    | `oneSide` | 只有一端帶，另一端無從得知；`reason` 是 `unfiltered`（任一端在未開 vlan-filtering 的 bridge 上，VLAN 原樣轉送；就是 `Q.vlan(id).transparent`，參與區塊劃分）、`peer-uncollected`（對端沒有收集）、`peer-no-vlan-data`（對端沒有 VLAN 設定資料）或 `hearsay`（鏈路是單側觀察）。後三種不參與 `Q.vlan` 的區塊劃分 | 推論 |
    | `inferred` | 推論鏈路，已收集的各端都帶這個 VLAN（同 `Q.vlan(id).inferred`） | 推論 |

  - `a`／`b`：`{ ep, dev, port, has, via, mode, collected, vlanData }`。`has` 為 true／false 是事實（這台設備有 VLAN 設定資料）；為 null 表示無從得知（沒有收集、沒有 VLAN 資料，或這一端是 `vlanUnfiltered`）。`via` 是帶這個 VLAN 的位置：`self`（介面本身）、`lag`（所屬聚合介面）或 `member`（推論鏈路記在聚合上，由成員埠帶）；`mode` 是 `tagged`、`untagged` 或 `both`。
  - `eps`：帶這個 VLAN 的鏈路端點（`has` 為 true），排序後的 ep 鍵。
  - 只算介面鄰接（LLDP／CDP）；MNDP 只證明同一廣播網域，不列入。
  - VLAN 子介面讓 parent 以 tagged 承載（停用的不算；parent 是 bridge 時只有 bridge 本身帶），和 V01 相同，所以單臂路由的實體埠也會被高亮。規則與已知的限制見上方「介面」的「VLAN 子介面讓 parent 承載」「vlan-filtering」與「已知的限制」。
- `Q.portGraph({ lag, ports, inferred, devices })`：埠層級的 L2 圖（給 ELK 的 port），回傳 `{ devices, ports, edges, omitted }`。
  - **參數**：`lag` 為 `'collapse'`（預設，聚合成員併進聚合埠，成員列在 `members`）或 `'expand'`（成員各自是埠，`lag` 指向所屬聚合）；`ports` 為 `'linked'`（預設，只列有邊的埠）或 `'all'`（另列範圍內已收集設備的實體、聚合與無線介面）；`inferred` 預設 true，是否包含推論鏈路；`devices` 是設備鍵的陣列，給了就只取至少一端在其中的邊（另一端的設備也會出現，`focus` 為 false）。
  - `devices[]`：`{ id, label, kind, collected, focus, ports, bridges: [{ ep, name, ports, vlanIfcs }] }`。**bridge 不是埠**，放在 `devices[].bridges`，列出它的埠與掛在它上面的 VLAN 介面。
  - `ports[]`：`{ id（ep 鍵）, dev, name, ifc, unknown, type, rawType, status, enabled, hearsay, lag, members, bridge, mode, pvid, vlans, subIfcs, unknownPeer, macCount, edges }`。**VLAN 子介面不是埠**，列在掛載的埠（或其成員）的 `subIfcs`。推論鏈路未收集端的未知埠，`ifc` 為 null、`unknown` 為 true。
  - `edges[]`：`{ id, a, b（埠 id，a < b）, aDev, bDev, links, inferredLinks, count, evidence, inferred, cls, vlansCommon, src }`。`evidence` 依強弱是 `adjacency`（有雙側的 LLDP／CDP 介面鄰接）、`hearsay`（只有單側觀察，推論）、`inferred`（只有推論鏈路，推論）；`inferred` 為 `evidence` 不是 `adjacency`。
  - 只算 interface-adjacency 的鏈路。`omitted` 是沒有畫成邊的筆數：`domainOnly`（MNDP 鏈路，只證明同一廣播網域，不當直連）、`sameDevice`（收合後兩端是同一個埠）、`inferred`（`inferred` 為 false 時略過的推論鏈路）。
- **共通規則**（`vlanCarriers`、`portGraph`、`subnetGraph`，以及 `vlanIds`）：第一次呼叫時才計算，依參數快取，同樣的參數第二次呼叫直接回傳同一個物件；回傳的物件是 Q 新建的，深層凍結。`portGraph`、`subnetGraph` 的參數值不認得時丟出 TypeError；`vlanCarriers` 的 vid 轉成數字比對。

### 5.3 關鍵推論

- **LLDP 配對與 bridge**：反向配對只採用對端的 LLDP／CDP 證據，MNDP 不算回報（對端只有 MNDP 仍是 K01）。兩端介面名稱比對時，bridge 本身（依 `rawType=bridge`，缺資料時依 `bridge*` 名稱）在兩端分別以 `bridge` 或 `bridge/成員` 回報，視為同一介面。
- **LLDP 對端埠名**：RouterOS bridge 成員的 `interface-name` 形如 `bridge/ether2`，adapter 取最後一段（`ether2`）作為對端實體埠，與本機 `interface=ether3,bridge` 取非 bridge 成員的規則對稱；原文保留在來源行。
- **鄰居邊語意**：LLDP／CDP 的觀察走介面鄰接推論；本機介面名稱是本機端依據，對端回報的 `interface-name` 是對端埠證據，無法配對時的平行埠排序配對仍屬推測。只有 MNDP 證據時，edge 表示兩台設備在同一 L2 broadcast domain 可達，不表示兩者直連，也不將回報的對端埠名視為實際配對埠；不套用直連專用的 K01／K02／K03／V01 檢查。`evidenceScope` 使用 `interface-adjacency`、`broadcast-domain` 或 `routing-adjacency`；`observations` 保留觀察介面及來源行。MNDP 沒有 domain ID，因此模型不宣稱完整廣播網域成員清單。同一對設備可因多個本機介面或雙向回報各有一條 MNDP link（Snapshot 保留全部以便追溯）；設備詳情的「鄰居」表由 `Q.neighborRows()` 併成每個對端設備一列，觀察介面合併列出。
- **自動群組名稱**：未套用 profile 分群的設備依拓樸鏈路分成連通元件，標為「自動群組 N」。這是版面分群提示，不是依 IP prefix 推導的子網名稱，也不表示群內設備都以實體線路直接相連；純 MNDP 證據同樣可能使設備位於同一群組。
- **鄰居配對**：LLDP／CDP 對端也有可配對的鄰居資料時雙向配對（`verified`）；對端有 LLDP／CDP 鄰居輸出但未回報此介面鄰接為單向（K01；只看雙方的 LLDP／CDP 證據，MNDP 不算回報）；對端沒提供鄰居資料則為單側觀察（hearsay，只計入覆蓋率）。鄰居 identity 對不上收集檔設備名時，用管理 IP 對回同一台。
- **OSPF 鄰接**：OSPF 是 IP 層鄰接證據，不加入 `links`，不作為拓樸直連 edge，也不與相同端點的 L2 edge 合併。單獨存於 `ospfAdjacencies`，設備詳細資料列出本機介面、鄰居、雙向回報狀態與來源。鄰居位址 → 擁有該 IP 的介面；找不到再用 router-id、管理 IP；都找不到建立以鄰居 ID 命名的未知設備（R02）。
- **設備類型**：型號（CRS／CSS→交換器；CCR／RB／hAP／hEX／CHR→路由器）→ 已收集設備依資料（有 OSPF→路由器；有 MAC 表且無路由→交換器）→ 未收集設備依鄰居回報的功能（router／bridge／station）→ 對端埠名像網路卡→主機。命名規則可覆寫並標示依據。
- **推論鏈路**（`inferredLinks`，推論，不寫進 `links`、不影響任何檢查）：給沒有 LLDP 的設備用，例如只支援 MNDP、也無法用 SSH 收集的 SwOS 交換器（CSS106、CSS610）。
  - **依據**：
    - `fdb`：MAC 表。A 的 p 埠學到 X 的 MAC，而 p 這側其他已知設備都能排除：
      - 已收集交換器在「不朝向 A」的埠看到它，代表它在那台交換器後面。
      - 它不轉送二層（沒有 bridge、沒有 MAC 表），不可能夾在中間。
      - X 有 MAC 表時，X 朝向 A 的埠不能和 A 這側看到同一台設備，否則兩者之間還有設備。

      X 是未收集的交換器時，同一埠學到、沒有 MAC 表的已收集設備（例如沒有 bridge 的路由器）推定接在 X 後面；p 這側還有其他未收集設備時不推論。已知 MAC 包括已收集設備的 `ownMacs`、介面 MAC，以及鄰居表回報的 MAC。
    - `stp`：埠的 RSTP 角色是 root／alternate／backup 時，`designated-bridge-id` 是這段網路上的上游橋接器。那個 MAC 屬於已知設備（例如以 MNDP 發現的 CSS106）時，推論這個埠接到它。對方也有 RSTP 資料時，用 `designated-port-id` 對回確切的埠。BPDU 會穿過不跑 STP 的未管理交換器，所以意義同樣是「直接相連，或中間只有未管理設備」。
    - `subnet-p2p`：兩台已收集設備的介面位址在同一個 /30 或 /31。/24 這類共用網段只證明在同一廣播網域，不採用。
    - `mndp-mutual`／`mndp-unique`：MNDP 雙向回報對方的埠，或某埠只看到一台 MNDP 鄰居。MNDP 會穿過未管理交換器，所以**只當佐證**：至少要有一項 `fdb`、`stp` 或 `subnet-p2p` 才成立，MNDP 同時成立時信心為 `high`。
  - **合併**：所有依據推論完後，同一條鏈路併成一筆，而且在過濾「只有 MNDP」之前做，所以 MNDP 佐證不會遺失。
    - 聚合成員埠歸到所屬的聚合介面。
    - 對端埠不明的代號依合併後的本機埠重新產生；任何依據知道對端埠名時，取代「埠不明」那一筆。
    - 只設在 VLAN／bridge 介面上的 /30 證據：同一對設備另外剛好只有一條實體埠的推論時，併進那一條；有多條時無法確定是哪一條，不合併。
  - **意義**：推論的是「直接相連，或中間只有未管理設備」。
  - **不推論的情況**：已有 LLDP／CDP 鏈路的設備對；埠（含所屬聚合）已有 LLDP／CDP 鄰接到已收集設備時，該埠後面的設備。
  - **對端埠**：未收集設備的埠用它在 MNDP 回報的埠名，沒有就標為不明。
  - **圖面**：同一對設備的鏈路與推論鏈路由 `Q.devicePairs()` 併成一條線，並給出唯一的證據強度 `evidence`，線型依它從 `theme.weakEdge` 取得：介面鄰接（一般線型）＞ 單側觀察 ＞ 推論（長虛線）＞ 只有 MNDP；弱證據只改線型與透明度，保留速率色。只有 MNDP 的設備對不畫線：MNDP 只證明同一廣播網域，可以推定相鄰的情況已由推論鏈路涵蓋；MNDP 鏈路仍保留在基準，列在設備鄰居表、介面與鏈路詳情。
  - **選取**：選介面時一併標示它的推論鏈路（`Q.inferredLinksOfEp`，查成員埠也會找到記在聚合上的推論鏈路），介面詳情列出這些推論鏈路；選 VLAN 時，已收集的各端都帶這個 VLAN 的推論鏈路（`Q.vlan(id).inferred`）也標成綠色。
- **VLAN 區塊**（`Q.vlan(id).domains`，推論，不存進 Snapshot）：VLAN ID 只在一台設備內有意義，不同站點常重用同一個 ID（NetBox 也以 VLAN group 劃定 VID 的範圍）。
  - **分塊方式**：帶這個 VLAN 的設備，以「兩端都帶此 VLAN 的鏈路」（`carry`）、「已收集各端都帶此 VLAN 的推論鏈路」（`inferred`）與「透通鏈路」（`transparent`）相連者為同一塊；只經由同一台未收集設備（例如 CSS106）或未過濾的 bridge 相連也算同一塊，但那台設備本身沒有這個 VLAN 時不列在區塊內。純 MNDP 鏈路不帶 VLAN 資料，不算相連。
  - **透通鏈路**（`Q.vlan(id).transparent`，推論）：只有一端帶這個 VLAN、另一端在未開 vlan-filtering 的 bridge 上（`vlanUnfiltered`）的介面鄰接鏈路。未過濾的 bridge 把 VLAN 原樣轉送，所以兩側可能是同一個廣播網域，但無從確認。給區塊鍵時，`transparent` 和 `carry`、`partial`、`inferred` 一樣只含那一塊。
  - **意義**：分成多塊表示鏈路證據上互不相連，可能是各自獨立的廣播網域，也可能中間有沒收集、沒有 LLDP 的設備，所以只是提示。
  - **鍵**：`<VLAN ID>@<區塊內自然排序第一台設備>`；`Q.vlan(id, key)` 只回傳那一塊的設備、鏈路與 VLAN 定義，鍵不存在時回到整體結果。
  - **畫面**：VLAN 詳情在分成多塊時標示區塊數並列出各塊，點選後圖上只標示那一塊；搜尋 VLAN ID 的結果也標示區塊數。
  - **共用**：分塊規則只有一份（`S.infer.vlanSpan`），查詢（`Q.vlan`）與檢查都用它；A02、V06、A06 只比較同一塊內的位置（檢查端共用 `byDomain`）。
- **未收集交換器底下的終端**（`macs[].behind`，推論，精確到設備、埠不明）：終端接在收不到資料的交換器（例如 SwOS 的 CSS106）時，只有上一跳 RouterOS 的 MAC 表看得到它。
  - **錨點**：已收集、有 MAC 表的設備 A 的埠 p，需同時符合：
    - p 沒有 LLDP 鄰接到已收集設備。
    - p 學到未收集的交換器或路由器的 MAC。
    - 那台設備沒有被證明在別台已收集交換器後面。
  - **哪些 MAC 算在它底下**：p 學到的其他 MAC，但排除下列幾種：
    - 已知設備自己的 MAC。
    - 已有確切位置的 MAC（終端埠、Wi-Fi）。
    - 在 p 這側其他已收集交換器「不朝向 A」的埠上出現的 MAC。
  - **位置**：p 這側只有一台未收集設備時，`dev` 為它；有多台（例如 CSS106 再串 CSS610）時 `dev` 為 null，`via` 列出全部，畫面顯示「在 X、Y 或其下游」。
  - **多個錨點**：同一 MAC 有多個錨點時，取那一側已收集交換器最少者（最靠近終端）。
  - **畫面**：主機畫在該交換器節點下，連線用推論樣式。
  - **與推論鏈路的對應**：推定位置與「錨點埠 ⇄ 該交換器」的推論鏈路是同一段路徑，基準不另存關聯，查詢時以錨點埠（含所屬聚合）與設備對回（`Q.behindVia(mac)`、`Q.behindUnder(推論鏈路 key)`）。MAC 詳情列出經由的推論鏈路，推論鏈路詳情列出後面推定的終端，選取終端時圖上標示整段路徑。
  - **A04**：錨點埠不報 A04，因為下面接的是已知設備。
- **Wi-Fi 客戶端位置**（`macs[].wifi`，推論）：MAC 表無法說明 Wi-Fi 客戶端連在哪台 AP，因為同一個 MAC 會出現在 AP 的無線介面、AP 上行與沿途 trunk，且會漫遊。依證據強度取位置，`basis` 標示依據：`registration`（關聯表，最強；多台 AP 時取 `last-activity` 最近者，其餘為 `candidates`，`roaming` 為真）→ `bridge-wifi`（已收集設備的 MAC 表在 `type=wireless` 介面學到）→ `via-ap-port`（交換器埠的鄰居是沒有收集資料的 AP，無法區分有線或無線）。已判定為有線終端埠的 MAC、AP 自己的 MAC 不套用 `via-ap-port`。因為用到終端埠判定，在推論算出終端埠之後才由 `S.infer.wifiLocations()` 計算。沒有 Wi-Fi 證據的 MAC，`wifi` 為 null。
- **終端位置**：這是依已收集證據推定的「未知對端」位置，不代表已證明對端是終端主機。核心 `unknownPeer` 介面必須恰好學到一個 MAC、不是 Wi-Fi、狀態非 down、不是虛擬介面，且沒有 LLDP／CDP 介面鄰接連到其他已收集網路設備；學到多個 MAC 的有線介面不符合此條件。Wi-Fi 介面本身不視為終端介面，但清單會將每個 Wi-Fi MAC／介面觀察位置列為終端位置；同一 MAC 出現在多個 Wi-Fi 介面可能是漫遊，因此 Wi-Fi 觀察不參與 A02。純 MNDP 只證明同一 L2 broadcast domain 可達，不會當作直連鄰接排除終端埠。若 bridge host 有多個 VLAN 觀察，MAC 的 `seen` 會各自保留 `{ep,vlan}`，不會互相覆蓋。
- **虛擬介面**（`S.infer.isVirtualIfc`）：有 RouterOS 原始類型 `rawType` 時，`bridge`、`vlan`、`loopback`、`vrrp` 是虛擬介面；沒有時依名稱推測，以 `irb`、`vlan`、`bridge` 或 `lo` 加數字開頭的是虛擬介面。終端埠、A04 與查詢的 Wi-Fi 觀察位置共用這一條規則。
- **推論全部在檢查之前完成**：`S.infer.infer()` 依序算出設備類型、鏈路分類與兩端 VLAN（含 `links[].vlanMismatch`）、推論鏈路、VLAN 區塊，套用命名規則、分群，再算終端埠（`edgeLocations`：`interfaces[].edge`／`unknownPeer`、`macs[].edge`，用到命名規則覆寫後的設備類型與推論鏈路）、Wi-Fi 客戶端位置（`wifiLocations`）、未收集交換器底下的終端（`behindLocations`）與防火牆的 WAN／LAN 分類。⑥ 檢查只讀取模型產生 findings，不寫回模型。
- **K01、K04、R02 由檢查判定**：建模時只記下配對結果，這兩個欄位只在內部模型、不序列化：每筆 LLDP／CDP 觀察的 `pairing`（`reciprocal`、`one-way`、`hearsay`），以及 OSPF 鄰接的 `peerBasis`（`address`、`router-id`、`router-id-address`、`mgmt-ip`，都找不到為 null）。檢查時依此列出 K01（`one-way`）、K04（`reciprocal` 但對端埠名不同）與 R02（`peerBasis` 為 null）。
- **覆蓋率**：`S.check.coverage(M, expectedData, blocks)` 依與 C02 同一份應收集資料表計算 `missing`，並由區塊的 `failure` 列出 `failures`。
- **防火牆**（推論與比對語意在 `S.infer.fw`，檢查與查詢共用）：
  - **WAN／LAN**：只看 interface list，不看介面名稱。已定義、名稱符合 `/(^|[^a-z])wan([^a-z]|$)/i`（含獨立的 `WAN` 字樣、不分大小寫，例如 `WAN`、`ISP-WAN`、`wan2`；`WANLINK` 不算；LAN 同理）的清單，展開 `include`／`exclude` 後的成員就是 WAN（LAN）介面；`all`、`none` 依 RouterOS 語意，`dynamic` 等內建清單或未定義的清單無法展開，含這種清單的清單整個略過。沒有這種清單時為 `no-wan-list`，有清單但沒有可確定的成員時為 `empty-wan-list`，兩者都不猜（F08）。
  - **IPv6 是否在用**（`firewallZones[].ipv6`，供 F07 的 IPv6 部分）：export 的 `/ipv6 settings` 設了 `disable-ipv6=yes` 為 `disabled`；否則有啟用中的 `/ipv6 address`、`/ipv6 dhcp-client`，或有任何 `/ipv6 firewall` 規則，為 `used`（`src` 是依輸入順序的第一個證據行）；都沒有為 `unknown`。export 只列非預設值，看不出有沒有自動產生的位址，所以 unknown 時不猜。
  - **涵蓋（`covers`）**：F01 用來判斷前面的規則是否涵蓋後面的規則；帶 `random`、`limit` 等不確定比對的規則一律不涵蓋。
  - **走 chain（`evalChain`、`evalFilter`）**：模擬「從 WAN 進來的新連線」依序走過 chain（含 jump、return，jump 深度上限 16）。每個條件的結果是成立、不成立或無法判斷；只有全部成立的規則才算命中，**含無法判斷條件的規則直接略過**（例如 `dst-address-list`、時間或標記類條件），所以前面這類 drop 規則擋不下，結果可能多報。`evalFilter` 先看 raw 的 prerouting，再走 filter 的內建 chain；**內建 chain 沒有規則決定時視為放行**（RouterOS 的預設）。來源視為任意公網位址：`src-address` 要涵蓋整個位址空間，或是只排除私有位址的否定，才算成立；`src-address-list` 只有否定才成立；`src-port` 由攻擊者選，accept 規則視為成立。
  - **`/ip service`**：export 沒寫的服務以 RouterOS 7 的出廠設定補上（`basis: 'default'`），待真機確認；清單在 `infer.js` 的 `SERVICE_DEFAULTS`。
  - **三值判斷（`decide`）**：給 L4 可達性用（見下方「L4 可達性與 zone」）。和 `evalChain` 一樣依序走過 chain，但條件無法判斷的規則**不略過**，而是列出所有可能的結果；只有一種結果時才算決定。
- **防火牆命中次數**：`print stats` 的每一列對應到 export 的規則（`model/build.js` 的 `matchFirewallStats`），規則見 §5.2 的 `firewallStats` 與 [F09](基準檢查規則.md#f09)。

#### L4 可達性與 zone（2.11.0 新增）

M2 的資料層：端到端可達性 `Q.reach`、zone、zone 矩陣與規則影響，實作在 `src/query/trace.js`（`S.reach.engine`），查詢函式見 [§5.2「防火牆命中次數與 L4 的查詢」](#52-實體snapshotmodelschema-ssot-snapshot2)。全部是推論；規則比對的語意只在 `S.infer.fw`（`decide`），逐跳的轉送決定和路由追蹤 `S.trace` 共用 `lookup`、`nextOwner`，不另寫一份。

**逐跳的處理順序**（依 RouterOS 的封包流程）：

1. raw prerouting。被 drop 就是 deny。
2. nat dstnat。dst-nat 改寫目的位址與埠後，以新的目的**重新查路由**。
3. 目的是這台設備自己的位址時走 filter input（另列 `/ip service` 是否接受）；否則依路由決定出介面（ECMP 時每個出介面一條分支），走 filter forward。設備自己送出的封包（來源是網路設備自己的位址）先走 raw output，再走 filter output。
4. nat srcnat，再交給下一跳的設備。

起點：來源是網路設備自己的位址時，從那台設備送出；否則找包含來源的最長網段，閘道依序取 DHCP 網路設定的閘道、這個網段上有路由表的設備、這個網段上已收集的設備。來源與目的在同一個網段時不經過路由器。來源不在任何網段時，可用 `entry` 指定封包進入的介面。

**zone**（`Q.zones`）：每個 IPv4 直連網段依下列順序，取第一個有結果的來源（`S.query.zoneSources()`）：

| 順序 | 來源（`source`） | zone id | 事實或推論 |
|---|---|---|---|
| 1 | 命名規則的 `zones` 標籤（`profile`，見[命名規則](命名規則.md#zones選用2110-新增)） | `tag:<名稱>` | 註解，`inferred: false` |
| 2 | interface list（`interface-list`）：設定這個網段的介面是哪些已定義清單的成員；同時屬於多個清單時取成員最少的，同數再依名稱 | `list:<清單>` | 成員是事實，以清單當 zone 是推論 |
| 3 | VLAN（`vlan`）：網段的 `prefixes[].vlan`；各設備設在不同 VLAN（A07）時取介面數最多的 VLAN，平手時沒有結果 | `vlan:<ID>` | 推論 |
| 4 | 網段本身（`subnet`），一定有結果 | `subnet:<網段>` | 推論 |

- 命名規則排在 interface list 之前，因為它是使用者明確寫下的意圖。interface list 與命名規則的 `interface` 比對只看已收集設備的介面；interface list 另外要那台設備有 export。
- 每個網段記錄 `basis`（依據的說明，例如屬於哪個清單、也屬於哪些清單）與 `alternatives`（其他來源會得到的 zone），所以可以檢查分組是否合理。
- `sources` 參數可以只用其中幾種來源，`subnet` 一定包含。
- **命名規則的核對**：`profile` 參數要是建立基準時用的同一份命名規則。`Q.zones` 與用到 zone 的查詢（`Q.zoneMatrix`、`Q.zoneCell`、`Q.ruleImpact` 等）核對 `id`、`version` 與內容雜湊（`S.profile.hash`，和 `meta.profile.hash` 比對）；id 或版本不同、建立基準時沒有套用命名規則、內容雜湊不同（例如改了 `zones` 段卻沒改 version），或基準沒有記錄雜湊（2.11.0 以前建立）時，丟出說明原因的 TypeError，不改用別的分法。

**zone 矩陣**（`Q.zoneMatrix`、`Q.zoneCell`）：不對每個位址各算一次，而是用等價類：

- **位址等價類**：所有 IPv4 規則的 `src-address`、`dst-address`、`to-addresses` 的區間邊界，加上網段的邊界，把位址空間切成區段；同一區段內的位址對所有規則的位址條件結果相同。每個區段取一個代表位址：優先用 ARP 表中不屬於網路設備的位址，沒有時取區段內第一個可用的位址（`basis: 'arp'`／`'synthetic'`）。
- **service 等價類**：規則提到的協定各自一類，其他協定依有沒有埠分兩類；埠依規則的 `dst-port`、`port` 邊界分段。同一類的 service 只算一次。
- **dst-nat 的入口另外當成目的**：啟用中、`to-addresses` 是單一位址的 IPv4 dst-nat 規則，入口位址（`dst-address`，或符合 `in-interface`／`in-interface-list` 的介面位址）另外加進目的；只有真的被改寫時才算。格子的目的 zone 以 **NAT 之後的位址**為準。
- **格子的狀態**：`allow`（全通）、`deny`（全擋）、`partial`（有通有擋）、`unknown`（有無法判斷、沒有通擋混合）、`empty`（沒有代表位址）；`heterogeneous` 為 true 表示同一個目的與 service，不同來源代表的結果不同（或同一個來源對不同目的不同），可能是 zone 分得不對；`diagonal` 是同一個 zone 內。
- `Q.zoneCell` 把結果相同的來源代表併成一列（`groups`），並列出牽涉的規則；再往下一層是對某個代表位址呼叫 `Q.reach`。
- **造成差異的組**（`groups[].divergent`、`divergentServices`）：和 `heterogeneous` 同一個依據。把「同一個目的與 service、不同來源」或「同一個來源與 service、不同目的」的記錄各看成一條線（unknown 不算）；一條線上同時有 allow 與 deny 時，結果是少數的那些記錄造成差異，平手時兩邊都算。含有這種記錄的組 `divergent` 為 true，所以格子異質 ⇔ 至少有一組 divergent。不採用「整格的多數」當基準，是因為 dst-nat 的入口會讓 allow 的筆數變多，反而把正常被拒絕的來源標成異常。
- **分段計算**（`Q.zoneMatrixSteps`）：依序是 `reps`（找代表位址）、`evaluate`（逐一判斷：來源代表 × 目的 × service 等價類）、`summary`（整理每一格）三個階段。每處理 8 個單位（一次判斷或一筆記錄）看一次經過的時間，超過約 25 ms 就讓出一次；時間只決定在哪裡讓出，不影響結果。`Q.zoneMatrix` 就是把它跑完，兩者共用同一份快取，已算過時第一次 `next()` 就結束。參數錯誤在第一次 `next()` 時丟出 TypeError；全部跑完才寫進快取，中途放棄（`return()`）不會留下快取。
- **規則影響**（`Q.ruleImpact`）：矩陣中牽涉到這條規則的路徑（決定結果、條件無法判斷或只是經過），加上這台設備本身的 input／output，以及把它當成停用時結果改變的路徑（`ifDisabled`）。

**判斷的前提**（`S.query.reachAssumptions()`，每次 `Q.reach` 都附在 `assumptions`）：

- 只判斷**新連線**（`connection-state=new`，視為確定）；回程由連線追蹤放行，不另外判斷。
- 只套用 RouterOS 的 raw、nat、filter；mangle（標記、策略路由）、bridge filter、主機與服務本身的防火牆不在範圍內。
- 只算 IPv4 與 main 路由表；`vrf` 固定為 null，傳入其他值時丟出 TypeError（VRF 在 M3，[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）。
- 來源埠由用戶端自選，比對來源埠的條件無法判斷。
- address-list 的內容不在基準中（export 只有名稱與靜態項目，不展開，也沒有動態項目），一律無法判斷。

**「確定」的定義**：

- 一關（表＋chain）的結果：列出所有可能的結果，只有一種時才算確定（nat 另外要是同一條規則，因為改寫的位址可能不同）。所以條件無法判斷的規則，如果命中與不命中的結果都一樣，仍算確定。
- 一條路徑：任一關確定是 drop 就是 deny；有一跳無法判斷，但之後有確定的 deny 時，整條就是 deny；否則有任何無法判斷就是 unknown。
- 多條路徑（ECMP、來源網段有多個閘道）的結果不同時是 unknown（`branches-differ`）。
- deny 的原因（不是 unknown）：規則 drop、沒有符合的路由（`no-route`）、黑洞路由（`blackhole`）、路由迴圈（`loop`），列在 `decisive`。

**unknown 的原因代碼**（`reasons[].code`，每筆另有 `dev`、`message`，與規則有關的另有 `rule`）。全部的代碼（25 個，包括路徑結束的代碼 `paths[].end.code`）以 `S.query.reachReasonCodes()` 為準：凍結的陣列 `[{ code, kind（reason：只出現在原因與說明／end：路徑結束的代碼，結果不是允許時也會出現在原因）, note }]`。引擎產生清單以外的代碼時直接丟出錯誤，`tests/core/reach.js` 也會掃描 `src/query/trace.js` 確認兩者一致；畫面把 `note` 放在原因的提示裡，`tests/ui-smoke.js` 確認每個代碼在 `V.REACH_REASON` 都有中文。下表是 unknown 的原因：

| 代碼 | 意義 |
|---|---|
| `rule-condition` | 規則的條件無法判斷，而且會影響結果；`keys` 列出條件（address-list 的內容、介面不明、mangle 標記、來源埠、IPsec、速率或機率等） |
| `device-uncollected` | 路徑上的設備沒有收集，不知道它的路由與防火牆 |
| `no-firewall-data` | 設備沒有設定資料（`/export`），防火牆規則不明 |
| `no-route-data` | 設備沒有路由表資料 |
| `next-hop-outside` | 下一跳不在基準內，之後的路徑無法判斷 |
| `dst-device-uncollected` | 目的屬於沒有收集的網路設備，它自己的防火牆不明 |
| `src-device-uncollected` | 來源屬於沒有收集的網路設備 |
| `src-location-unknown` | 找不到包含來源的網段，不知道封包從哪台設備進入（可用 `entry` 指定） |
| `no-gateway` | 來源網段上沒有可當閘道的已收集設備 |
| `nat-ambiguous` | dstnat 可能由不同的規則改寫，改寫後的目的不明 |
| `nat-target` | dst-nat 改寫後的位址或埠不明（`to-addresses`／`to-ports` 是範圍、轉給設備自己但沒有已知位址，或動作不在可判斷的範圍） |

| `raw-notrack` | raw 的 notrack 規則不追蹤連線，之後以 connection-state 比對的規則結果不明 |

**不進 Snapshot**：zone、矩陣與可達性都在查詢時計算，依參數快取在記憶體，不寫進 Snapshot，也不進黃金基準與新舊比對（[ADR-014](架構決策/014-L4-zone矩陣在查詢時計算.md) 的選項 B；ADR 仍是提議）。同一份基準與參數一定得到相同結果，有沒有快取都一樣。1000 台規模的耗時見 [§11.6](#116-規模)。

#### 未知對端（2.1.0 新增）

**要解決的問題**：接取交換器下面接了幾十台沒有 LLDP 的設備（PC、印表機、IoT），只看 LLDP 的拓樸會顯示成「這台交換器只有上行」，實際上它下面有一大片沒被看見的東西。MNDP 只提供同一 L2 廣播網域可達線索，並不能指出直接鄰居埠，因此不會將有 MAC 的埠排除在未知對端之外。舊版工具會在這種埠畫出虛擬節點；這一版保留這個意圖，但改成不污染基準：判定寫進基準，畫法只在檢視層（[§11.4](#114-未知對端的畫法)）。

**判定（核心，寫進基準）**：`interfaces[].unknownPeer = true`，條件是同時成立
1. 設備是已收集的；介面恰好學到一個 MAC、不是 Wi-Fi，狀態不是 down，也不是虛擬介面（規則見上方「虛擬介面」）
2. 該介面（含所屬聚合與聚合成員）沒有任何 LLDP／CDP 介面鄰接鏈路；純 MNDP 廣播網域可達邊不作為鄰接排除條件
3. 該介面（含所屬聚合與聚合成員）沒有推論鏈路（推論接到未收集的網路設備，例如 SwOS 交換器）

有 LLDP／CDP 介面鄰接至已收集網路設備的伺服器埠、上行聚合埠都不算；學到多個 MAC 的有線介面可能連著下游交換器或 AP，因此不列為核心終端介面。Wi-Fi 介面是一對多的 MAC 觀察位置，`Q.inventory().rows.endpoints` 會逐一列出其 MAC／介面位置，但不會將 Wi-Fi 標為 `unknownPeer`／`edge`，也不會把 Wi-Fi 觀察送入 A02。純 MNDP 廣播網域可達不算直連鄰接，不會因此排除一般終端埠。查詢介面：`Q.unknownDevices()`、`Q.unknownPeers(設備)`（一般終端埠附 MAC、ARP 的 IP、OUI 廠商、VLAN）與 `Q.inventory()`（列及數字的單一來源）。

**刻意沒做**：「介面 up 但沒有學到任何 MAC」（閒置埠）。要可靠判斷需要 `show interfaces terse` 的狀態，不在必要收集清單內。

## 7. 一致性檢查

共 42 項規則，分成輸入（I）、覆蓋（C）、鏈路（K）、VLAN（V）、位址（A）、路由（R）、防火牆（F）七類。每項規則的判斷條件、使用的資料、不檢查的情況與處理建議，集中在 **[docs/基準檢查規則.md](基準檢查規則.md)**，本文件不再另列一份規則表，以免兩份內容不一致。規則目錄在 `src/check/catalog.js`，判斷在 `src/check/checks.js`（見[第 3 節](#3-模組)）。

每筆：`{ id, severity, cat, title, message, entities:[{type,key}], facet?, evidence:[{block,line,text,file}], deviation? }`。entity 的 type 有 `device`、`interface`、`link`、`vlan`、`ip`、`mac`、`rule`（防火牆規則，key 是 `firewallRules[].key`）與 `service`（管理服務，key 是「設備|服務名稱」）。`evidence` 預設最多 6 筆，規則可在 `CATALOG` 以 `evidenceLimit` 覆寫（目前只有 C02 不限）。

`facet` 是可選欄位，只有同一組 id＋實體可能產生多筆 finding 的規則才有（`CATALOG` 宣告了 `facet` 的 12 條），標示這筆檢查的是哪一個項目，例如 A12 的 `dns`／`ntp`。有宣告的規則每筆都有、沒宣告的都沒有，`add()` 強制檢查。值只取自設定項目的固定字樣與正規化後的設定值，不取自訊息、設備名稱或行號；多段以 `|` 分隔。facet 會進入 findingKey（[第 8 節](#8-比對獨立模組)）。各規則的取值見[基準檢查規則「每筆結果的內容」](基準檢查規則.md#每筆結果的內容)。

`deviation` 是可選欄位，只有跨設備組態一致性中做多數決的規則（V06、V07、A06、A07、A08、A10、A11、A12、R06）才有：`{ basis: 'majority', deviating: [設備 key…], groups: [{ value, key, devs }], main }`。`deviating` 是依多數推定偏離的設備（推論），依設備名稱自然排序，平手時為空陣列。`groups` 是多數決實際用的分組（順序與訊息相同）：`value` 是該組第一台設備的設定值（陣列，依它的設定順序），`key` 是同位置的正規化比對值，`devs` 依名稱自然排序。`main` 是多數組在 `groups` 中的索引，沒有多數時為 null。判斷條件見[基準檢查規則「跨設備組態一致性」](基準檢查規則.md#跨設備組態一致性)。

## 8. 比對（獨立模組）

下列三個功能都只透過查詢介面讀取，不修改基準（有測試確認比對前後 Snapshot 完全相同）。

**預期資料比對**：`SSOT.compare(SSOT.query(snapshot), expected) → DiffReport`

- 預期資料格式 `ssot-expected/1`（設備、鏈路、VLAN），用「設備名」「設備名 介面名」指向實體，不共用 Snapshot 結構。端點以**最後一個空白**分隔，所以設備名可以含空白（介面鍵不含空白）。
- 結果分 ok／missing／different／unexpected（`strictDevices`、`strictLinks` 開啟時才列多出）。
- 預期的鏈路以這組介面本身的證據為準：有 LLDP／CDP 鄰接時照常比對；這組介面沒有介面鄰接、只有同一對設備的 MNDP 觀察時，才回報「只有 MNDP 的 L2 廣播網域可達證據」。

**由基準產生預期資料**：`SSOT.compare.expectedFrom(Q, { strict }) → ssot-expected/1`

- 內容：已收集的設備（含 `kind`）、已雙向確認的 LLDP／CDP 介面鄰接鏈路、各設備的 VLAN。名稱經正規化後仍對回同一個鍵時用名稱，否則用鍵本身。
- 和同一份基準比對時全部是 ok。`strict` 會加上 `strictDevices`／`strictLinks`；未經雙向確認的鏈路不在預期資料內，所以這時同一份基準的這些鏈路也會列為 unexpected。

**新舊基準比對**：`SSOT.compare.snapshots(Q舊, Q新) → ssot-snapdiff/1`

- 回傳 `{ schema, errors, warnings, summary, items }`；`summary` 是新增、移除、改變的總數，以及各類別（`byCategory`）的筆數。
- `warnings[]`：`{ kind, before, after, message }`，依 `version`、`profile`／`profile-unverified` 的順序，兩份相同時不列。schema 相同時照常比對，但提示部分差異可能來自程式或命名規則，不是網路改變：
  - `version`：兩份的 `meta.version` 不同（沒有時為 null）。新版才有的檢查會顯示為新出現。
  - `profile`：兩份的 `meta.profile` 的 id、版本或內容雜湊不同（有一邊沒有套用命名規則也算）。設備名稱、類型與分群可能因此不同。
  - `profile-unverified`：id 與版本相同，但有一邊沒有 `meta.profile.hash`（2.11.0 以前建立），無法確認內容是否相同；不當成相同，也不當成不同。和 `profile` 最多出現一個。
  - `profile` 與 `profile-unverified` 的 `before`／`after` 是 `{ id, version, hash }`（沒有 hash 時為 null）或 null。
  - schema 不同而不比對時，`warnings` 為空。
- `items[]`：`{ category, change, key, field, before, after, message, effect }`；`change` 為 `added`／`removed`／`changed`，新增時 `before` 為 null，移除時 `after` 為 null。

  | 類別 | key | 比較的內容 |
  |---|---|---|
  | `device` | 設備鍵 | 新增／移除；`kind`、`deviceType`、`softwareVersion` 改變 |
  | `link` | 鏈路鍵 | 只比 LLDP／CDP 介面鄰接的新增／移除（MNDP 只證明廣播網域可達，不比） |
  | `vlan` | `設備\|VLAN ID` | 設備上新增／移除 |
  | `ip` | IP（不含遮罩） | 只比設備自有的位址（不含鄰居宣告）；新增／移除，或改到別的介面（`field: interface`）、遮罩改變（`field: address`） |
  | `firewall` | 規則鍵 | 新增／移除；`action`、`disabled` 改變；同 chain、同動作、新舊條件互相涵蓋的「移除＋新增」併成一筆 `match` 改變（條件變窄或變寬） |
  | `finding` | `findingKey`（退回時是 `findingBaseKey`） | 以鍵的多重集合比對：同一個鍵先配對訊息相同的，其餘依順序配對，配不到的才是新出現／已消失 |

- **finding 的鍵退回**：2.8.0 以前的基準沒有 facet，直接用 findingKey 比對，有 facet 的規則會變成「消失＋新出現」。所以先收集兩份基準中至少有一筆 finding 沒有 facet 的規則，這些規則在兩邊都改用 `Q.findingBaseKey` 比對，`item.key` 也是 findingBaseKey；其他規則照常用 findingKey。同一份基準內，一條規則的 finding 不是都有 facet 就是都沒有（`add()` 強制檢查），沒有 facet 的規則兩種鍵相同，所以同版本的比對不會退回。
- `effect`：只有 `firewall` 類別有值，其他為 null。`new-exposure` 是新基準才有的 F03／F04／F05／F07 指向的規則；其餘依放行方向判斷為 `less-restrictive`（放寬）或 `more-restrictive`（收緊）。accept、dst-nat、netmap 算放行，drop、reject、tarpit 算擋下；jump、log、src-nat 等不影響放行的動作為 null。
- **排序**：依類別（上表順序）、鍵、變更種類（移除、新增、改變）、欄位排序，同樣的輸入一定得到同樣的順序。
- **schema 不同**：兩份基準的 schema 不同，或不是本工具的 `ssot-snapshot/2` 時不比對，`errors` 說明原因、`items` 為空；請用同一版工具從原始輸入重新建立。

**finding 的穩定鍵**：`Q.findingKey(f)`（也可用 `SSOT.query.findingKey`）＝ `JSON.stringify([id, "facet:"+facet（有 facet 時）, 排序並去重的 "type:key"…])`，例如 `["A12","facet:dns","device:VA","device:VB"]`。facet 固定在第 2 個元素、不參與排序；沒有 facet 的規則，鍵與 2.9.0 之前相同（`Q.findingBaseKey`）。不含訊息、證據與行號，所以訊息文字或行號改變時，兩份基準仍對得上。同一份基準內仍可能碰撞（id、facet 與 entities 都相同、只差訊息）：同一台設備的多段 I01、I03，沒有設備的 I01，以及少數 facet 也分不開的情況，例如同一台設備重複設定同一個 DHCP 網段（R05）、同一介面重複連到同一個 router-id（R02）；需要逐筆對應時以多重集合處理，如上。組成的取捨見 [ADR-003](架構決策/003-findingKey的組成.md)。

## 9. 修正 patch（ssot-patch/1）

核心 [src/remediate/patch.js](../src/remediate/patch.js) 由基準的 finding 產生結構化的修正計畫，再輸出成 RouterOS `.rsc` 文字。**工具維持唯讀**：只產生文字，不連線、不套用到設備，也沒有套用用的工具（[ADR-001](架構決策/001-工具維持唯讀.md)）。計畫只用 Snapshot 的事實，相同的基準與選取一定得到相同的計畫與文字（有黃金檔測試 `tests/golden/sample-patch*`，涵蓋範例資料的 F01、F02、F06 與 A12，A12 的選擇見[開發指南 §3](開發指南.md#3-測試)）。

**計畫**：`S.remediate.plan(Q, selection, opts)` 回傳

```
{ schema: 'ssot-patch/1', baseline: { inputHash, createdAt, version }, devices: [{ key, name }], items: [...], skipped: [...], choices: [...] }
```

- **selection**：省略或 null 為全部 finding；字串陣列為 findingKey 清單；物件 `{ keys?, ids?, devices? }` 為三者的交集（`devices` 可以是設備鍵或名稱）。有不認得的欄位，或不是字串陣列時，丟出 TypeError；基準中沒有的 findingKey 放進 `skipped`（reason 為 `not-found`）。
- **opts**：省略或 null；`{ choices?: { findingKey: 選項 id } }`，傳入使用者對 choice 等級的選擇（見下方「choice：A12」）。有不認得的欄位、`choices` 的值不是字串時丟出 TypeError；選項 id 不存在時丟出 RangeError；選取範圍外的 findingKey 不使用。
- **level**（`S.remediate.LEVEL`、`levelOf(id)`）：`auto` 可直接產生指令（F01、F02、F06）；`choice` 要使用者選擇處理方式（F03、V01、V08、R06、A06–A12；目前只有 A12 產生指令，其他仍列為 `choice` 不產生）；其他都是 `manual`，需要人工判斷。
- **item**（停用規則）：`{ key: 'disable-rule:<規則鍵>', findingKey, id, dev, level: 'auto', target: { type: 'rule', key, family, table, chain, position, by }, ops, evidence, risk: { level, text }, note, warnings }`。A12 的 item 見下方。
  - `ops[]` 是結構化的修改 `{ op: 'set', path, where, expect: 1, props: { disabled: 'yes' }, before: { disabled: 'no' } }`；`before` 是基準中的值，供回復使用。
  - `where` 是 `find where` 的條件，不用規則編號。依序嘗試 comment、比對條件（action、比對欄位與參數）、兩者合併，取同一個 chain 中沒有其他規則也符合的第一種（`target.by` 是 `comment`、`match` 或 `comment+match`）。comment 只在編碼是 ASCII 或 UTF-8 時使用，其他編碼無法確定與設備內的文字相同。
  - `risk.level` 是 `low`（F01、F02）或 `medium`（F06）；`note` 是中文說明；`warnings` 是需要注意的事，例如註解編碼不明、find 條件含非 ASCII 文字。
- **skipped**：`{ findingKey, id, dev, level, reason, detail, rule?, item? }`，`detail` 是給使用者看的原因。reason 有：
  - `choice`：尚未支援選擇修正的 choice 規則（A12 以外），說明文字是「這條規則尚未支援選擇修正，沒有產生指令；處理方式見規則的處理建議」。`manual`：需要人工判斷，說明文字是「這項檢查需要人工判斷，沒有自動修正；處理方式見規則的處理建議」。
  - `no-rule`：找不到 finding 指向的規則。`already-disabled`：基準中這條規則已經停用。
  - `ambiguous-find`：每一種 find 條件都會符合同一個 chain 的其他規則（前置檢查一定會中止），改為人工處理。說明文字（`SKIP_TEXT`）是「find 條件可能符合多條規則，無法確定只停用這一條；先為這條規則加上可區分的 comment，再重新收集」；`detail` 另寫出同一個 chain 中也符合的規則編號，F02 的兩條規則完全相同時就是這種情況。
  - `unsafe-property`：屬性名稱不是 RouterOS 的屬性格式，無法安全地寫成 find 條件。
  - `same-target`：同一條規則已由前面的項目停用（`item` 是那一項的鍵）。
  - `not-found`：基準中沒有這個 findingKey（`id`、`dev`、`level` 為 null）。
  - A12 專用（見下方）：`needs-choice`（沒有多數、也沒有指定選項；附 `options`）、`accepted-choice`（選了不修改）、`ntp-v6`（RouterOS 6 的 NTP 寫法）、`unsafe-value`（值含 `@vrf`、`%介面` 等無法確認寫法的字元）、`no-servers`（基準中沒有這台設備的伺服器來源）、`no-groups`（finding 沒有 `deviation.groups`）。A12 的 `skipped` 每台設備各一筆，`dev` 是那台設備。
- **排序**：`items` 依設備（名稱的自然順序，再依鍵），同一台設備內依 finding 在基準中的順序；`skipped` 同樣排序，不屬於任何設備的在後，基準中沒有的鍵最後。`devices` 是有 item 的設備，依 `items` 的順序。`choices` 依 finding 在基準中的順序。

**choice：A12（DNS／NTP 伺服器）**：一筆 A12（facet 為 `dns` 或 `ntp`）是一個選擇，選項取自 finding 的 `deviation.groups`／`main`（[§7](#7-一致性檢查)）。

- **選項**（`choices[].options`，依序）：
  - `majority`：改成多數組的值。只在有多數時才有，`inferred: true`，`basis: { agree, total, devs }`；多數決是推論，多數也可能是錯的。
  - `device:<該組第一台>`：每一組一個，改成這組的值（指定組內任一台也可以，會換成第一台）。
  - `accept`：不修改。
- **預設**：沒有指定時，有多數就用 `majority`（`chosenBy: 'default'`）；沒有多數時是 `needs-choice`，不產生指令，`skipped` 附上 `options`。選 `accept` 時是 `accepted-choice`，也不產生指令。標為可接受由畫面寫進處理紀錄，`S.remediate` 不依賴 `S.ledger`。
- **`choices[]`**：`{ findingKey, id, facet, title, options: [{ id, label, value?, devs?, basis?, inferred? }], chosen, chosenBy: 'user' | 'default' | null, value, items: [item key], reason: null | 'needs-choice' | 'accepted-choice' }`。`value` 是目標值，`needs-choice`、`accept` 時為 null。
- **item**：值和目標不同的設備每台一個，`{ key: 'set-servers:<facet>:<設備>', findingKey, id: 'A12', dev, level: 'choice', choice, target: { type: 'servers', key: 設備, facet, menu, param }, ops, evidence, risk, note, warnings }`。依這台設備的來源（`Q.serversOf` 的 `menu`／`param`，[§5.2](#52-實體snapshotmodelschema-ssot-snapshot2)）決定寫法：
  - `/ip dns`、`/system ntp client` 的 `servers`：一個 `set-list` op，整份清單 `set servers=…`。
  - `/system ntp client servers` 的 `address`（子選單）：逐筆改子選單本身。要換掉的項目 `set [find where address=舊] address=新`，多的 `remove`，少的 `add`。這樣保留每筆的 `min-poll`、`max-poll`、`iburst`、`auth-key` 等屬性；不改用 client 的 `servers=`，因為它以整份清單取代靜態項目，手冊沒有說明子選單項目的其他屬性會不會保留。限制：被 `remove` 的項目，rollback 只能以 `address` 加回，其他屬性不在基準中，會回到預設值（`warnings` 會說明）。
  - RouterOS 6 的 `primary-ntp`／`secondary-ntp`：目前的官方手冊（v7）查不到這兩個參數，列為 manual（`ntp-v6`）。值含 `@vrf`、`%介面` 等字元時也列為 manual（`unsafe-value`）。
  - `risk.level`：DNS 是 `medium`，NTP 是 `low`。
- **op 的四種**：
  - `set`：`{ op, path, where, expect: 1, props, before }`，`path set [find where …] props`。
  - `remove`：`{ op, path, where, expect: 1, before }`，`before` 是被移除項目的屬性。
  - `add`：`{ op, path, where, expect: 0, props }`，前置檢查確認還沒有這一筆，避免重複。
  - `set-list`：`{ op, path, param, value, before }`，`path set param=value`；`before` 是基準中的清單。

**.rsc 文字**：每台設備三個檔案。檔頭寫出格式、設備、基準（inputHash、建立時間、版本），並註明工具不會連線或改動設備。

- **套用**（`renderRsc(plan, dev)`）：所有前置檢查集中在最前面，`set`、`remove`、`add` 每個 op 一條 `:if ([:len [<path> find where …]] != <expect>) do={ :error … }`，任一失敗就中止。`set-list` 先比 `[:len [<path> get <param>]]`，再以 `[:tostr [:pick … <n>]]` 逐項比對基準中的值；手冊沒有陣列轉字串的分隔規則，所以不比整串。這個寫法手冊沒有完整範例，`.rsc` 的註解與 item 的 `warnings` 都註明要先在測試機確認。RouterOS 的 `/import` 逐行執行到第一個錯誤為止、沒有交易，所以前置檢查不通過時不會改到任何設定。之後才依序執行各 op（例如 `set [find where …] disabled=yes`），每一行前面以註解寫出修改前的值。
- **回復**（`renderRollback`）：套用的反向，項目與 op 都倒序，同樣先做前置檢查。`set` 互換 `props` 與 `before`，`where` 中被改到的鍵換成套用後的值（例如子選單的 `address`，套用後要用新值才找得到）；`remove` 與 `add` 互換；`set-list` 互換 `value` 與 `before`。
- **驗證**（`renderVerify`）：每個 op 一條 `print where …`（`where` 用套用後的值），註解寫出預期結果（應列出幾筆、是否帶 `X` 停用旗標；`remove` 預期沒有）；`set-list` 改為 `:put [<path> get <param>]`，註解寫出預期的清單與順序。
- **只用 ASCII**：手冊沒有說明 `/import` 對非 ASCII 位元組的處理，所以字串一律加引號（`where` 才是字串比對），`"`、`\`、`$` 依手冊跳脫，`?`、控制字元與非 ASCII 位元組寫成 `\XX`；註解中的非 ASCII 字元寫成 `<U+XXXX>`。中文說明只放在計畫的 note、risk、warnings。
- **多台設備**：`S.remediate.files(plan)` 依 `devices` 的順序，回傳每台的 `{ dev, name, base, apply, rollback, verify }`，檔名是 `base.rsc`、`base-rollback.rsc`、`base-verify.rsc`。設備鍵只含 `A-Z a-z 0-9 _ . -`，而且不會和其他設備替換後的名稱重複時，直接當 `base`；否則替換不合格的字元，再加上鍵的雜湊前 8 碼。

RouterOS 語法的依據（`find where`、`:if`、`:error`、字串跳脫、`/import` 的行為，以及 A12 用到的 `servers`、子選單、`get`、`:len`、`:pick`、`:tostr`）寫在 `patch.js` 的註解，附官方手冊的網址。

## 10. 處理紀錄（ssot-ledger/1）

核心 [src/ledger/ledger.js](../src/ledger/ledger.js) 記錄使用者對每個 finding 的決定與每一輪的歷程，讓一輪輪收集的結果互相銜接、逐漸收斂。這是使用者的資料，**不放進 Snapshot**（[ADR-002](架構決策/002-處理紀錄放在基準之外.md)）；只透過查詢介面讀基準，不修改基準。全部是純函式：不碰 DOM 與 IndexedDB、不讀目前時間（`now` 由呼叫端傳入，必須是 ISO 8601）、不修改傳入的物件。

**資料格式**

```
{
  schema: 'ssot-ledger/1',
  items: { '<findingKey>': {
    status, id, dev, devs?, firstSeen, lastSeen, patch, waiver: { reason, until } | null, note,
    history: [{ at, from, to, by: 'user' | 'advance', baseline, reason, waiver?, ack?, fromKey?, superseded? }] } },
  iterations: [{ baseline: { inputHash, baselineKey?, createdAt }, at, counts, coverage: { collected, expected }, unknownPeers }]
}
```

- `items` 以 findingKey 為鍵（見 [ADR-003](架構決策/003-findingKey的組成.md)），依鍵排序。碰撞的 finding 共用同一個項目。
- `dev`：findingKey 只涉及一台設備時是該設備（取自 device 實體，以及介面、規則、服務鍵與鏈路兩端的設備部分），否則為 null。
- `devs`（選用）：只有 findingKey 推不出設備的項目才有（例如只涉及 IP、MAC 的 A01）。是這個問題最後一次出現時，證據所在區塊的設備（排序；同一個鍵的每筆 finding 都算）；`[]` 表示證據都在沒有設備標頭的區塊，`null` 表示推不出來（沒有證據，或證據的區塊對不到）。用來判斷能不能判定已修好。較早的紀錄沒有這個欄位。
- `firstSeen`／`lastSeen`：第一次與最後一次出現的基準鍵；`history[].baseline` 是當時最新一輪的基準鍵。
- `waiver` 只在 accepted 時有值；離開 accepted 時，原本的豁免記在那一筆歷程的 `waiver`，不遺失。
- `patch`：對應的修正 patch 鍵（字串）或 null。
- `history[].reason`：`advance` 寫入 `new`、`disappeared`、`reappeared`、`waiver-expired` 與舊鍵轉換的 `facet-split`；使用者變更是 `edit`，舊確認標記是 `from-ack`。
- `history[].fromKey`、`history[].superseded`（選用）：只有舊鍵轉換的那一筆歷程才有。`fromKey` 是轉換前的舊鍵；`superseded` 只在新鍵已有項目時出現，保存被取代的舊項目完整內容。見下方「舊鍵轉換」。
- `S.ledger.validate(obj)` 逐項回報格式錯誤（`{ ok, errors }`），不修改、不丟棄資料；不認得的欄位（較新版本寫入的）保留，不算錯誤。其他函式收到格式不正確的處理紀錄時丟出錯誤，不靜默修正。

**狀態**：`open`（待處理）、`scheduled`（已排程修復）、`fixed`（已修好）、`accepted`（可接受，附豁免）、`false-positive`（誤報）、`regressed`（回歸：修好後又出現）。

**推進一輪**：`S.ledger.advance(ledger, Q, { now })` 回傳 `{ ledger, changes, unobserved, split, skipped }`（`split` 見下方「舊鍵轉換」；`skipped` 時為空陣列）。下表的「出現」是基準中有這個 findingKey；「消失」是沒有，而且可以判定；「無法判定」是沒有，但不能判定是否已修好。

| 目前狀態 | 出現 | 消失 | 無法判定 |
|---|---|---|---|
| （不在處理紀錄中） | 新增為 open（`new`） | — | — |
| open、scheduled、regressed | 不變 | fixed（`disappeared`） | 不變，列在 `unobserved` |
| fixed | regressed（`reappeared`） | 不變 | 不變 |
| accepted | 不變 | 不變 | 不變 |
| false-positive | 不變 | 不變 | 不變 |

- accepted 不論是否出現，豁免到期（`until` 早於 now）時改回 open（`waiver-expired`）。false-positive 不變，因為判斷的是規則本身，不是網路現況，保留給規則品質統計。
- 出現在基準中的項目更新 `lastSeen`（第一次出現時也補 `firstSeen`）。`changes` 是 `[{ key, from, to, reason }]`，依鍵排序。
- **能不能判定已修好**：
  - **findingKey 推得出設備**：涉及的每台設備都要可以判定，也就是已收集且沒有任何收集失敗，或只在鄰居資料中出現、沒有收集（它的問題不依賴它自己的輸出）。已收集但有收集失敗、或整台不在基準中時不判定，因為問題消失可能只是沒收到資料。
  - **findingKey 推不出設備、`devs` 有設備**：`devs` 的設備都已收集、而且沒有收集失敗，才判定；否則列為 unobserved。換成另一個網路時，這些設備不在基準中，所以不會誤判成 fixed。
  - **`devs` 是 `[]`**（證據都在沒有設備標頭的區塊）：基準中沒有任何收集失敗才判定。
  - **沒有 `devs`（舊紀錄）或為 `null`**：保守地列為 unobserved。
  - 每筆 finding 最多附 6 筆證據，所以證據超過上限時，`devs` 只涵蓋前 6 筆證據所在的設備。
- **冪等**：依基準鍵判斷是不是同一份基準。基準鍵是 `meta.baselineKey`（[§5.2](#52-實體snapshotmodelschema-ssot-snapshot2)）；2.8.0 以前的基準與處理紀錄沒有 baselineKey，一律退回用 inputHash，不改寫舊資料。已經推進過的基準回傳 `skipped: true`，處理紀錄原樣不動、不新增一輪。
- **每一輪的摘要** `iterations[]`：`baseline` 記 inputHash、baselineKey（有時）與建立時間，`at` 是推進的時間。只存摘要，不存整份 Snapshot。`counts` 的意義：
  - `new`、`fixed`、`waiverExpired`、`unobserved`：這一輪新增、判定已修好、豁免到期、無法判定的筆數。
  - `open`、`scheduled`、`regressed`、`accepted`、`falsePositive`：推進後各狀態的總筆數。
  - `coverage`：`collected` 是已收集的設備數，`expected` 是已收集數加上 C01（應收集但未收集）的筆數。`unknownPeers` 是未知對端的總數。

**這份基準是第幾輪**：`S.ledger.roundOf(ledger, meta)` 回傳 `iterations` 的索引（0 起算），沒有推進過這份基準時為 -1。`meta` 是基準的 `meta`（或 `iterations[].baseline` 的形式）；判斷方式和 `advance` 的冪等相同，依基準鍵，沒有 baselineKey 時退回 inputHash。所以有 baselineKey 的一輪不會只憑 inputHash 對上。處理紀錄格式不正確，或 `meta` 沒有 baselineKey 也沒有 inputHash 時丟出錯誤。工作包用它確認處理紀錄和基準是同一輪（[§10A](#10a-工作包ssot-workpack1)）。

**兩份處理紀錄的差異**：`S.ledger.diff(cur, next)` 比較兩份處理紀錄，例如讀入工作包或匯入處理紀錄之前，判斷目前的 `cur` 有沒有 `next` 沒有的內容。兩份都要通過 `S.ledger.validate`，否則丟出錯誤。回傳：

- `onlyInCur`、`onlyInNext`：只在其中一份的項目鍵；`changed`：兩份都有、內容不同的項目鍵。都依鍵排序。
- `roundsOnlyInCur`、`roundsOnlyInNext`：只在其中一份的輪次；`roundsChanged`：兩份都有這一輪、內容不同（例如推進的時間或筆數不同）。內容是基準鍵，依各自的 `iterations` 順序。輪次以基準鍵對應，和 `advance` 的冪等判斷相同；舊紀錄沒有 baselineKey 時退回 inputHash。
- `lossIfReplaced`：以 `next` 整份取代 `cur` 會不會遺失 `cur` 的內容，也就是 `onlyInCur`、`changed`、`roundsOnlyInCur`、`roundsChanged` 任一不是空的。
- `same`：兩份內容完全相同。
- 「內容相同」以 `S.util.canonicalJson` 比較：物件的鍵順序不算差異；陣列的順序算差異（例如 `history` 是依時間附加的歷程，順序本身就是內容）；不認得的欄位（較新版本寫入的）也參與比較，不同就算 `changed`。

**舊鍵轉換**（`S.ledger.KEY_MIGRATIONS`）：findingKey 的組成改變時（[ADR-003](架構決策/003-findingKey的組成.md)），把舊鍵項目的決定帶到新鍵。決策見 [ADR-002](架構決策/002-處理紀錄放在基準之外.md) 的「修訂」。

- **規則**：每條是 `{ reason, oldKeys(Q, f) }`，給新基準的一筆 finding，回傳它可能對應到的舊鍵（可以是空陣列）。目前只有一條 `facet-split`（2.9.0）：有 facet 的 finding，舊鍵是 `Q.findingBaseKey(f)`。規則依陣列順序套用，新鍵與舊鍵相同時不算轉換。
- **時機**：`advance` 在判定狀態之前轉換，所以舊項目不會被判為消失。只轉換處理紀錄有這個舊鍵、而且舊鍵不在新基準中的項目。`fromAcks` 推進時套用同一套轉換。
- **舊項目的處置**：
  - 新鍵還沒有項目：複製整個舊項目（狀態、`note`、`waiver`、`patch`、`firstSeen`、歷程與不認得的欄位），`dev` 依新鍵重新推得，歷程加一筆 `{ from: 狀態, to: 狀態, by: 'advance', baseline, reason, fromKey: 舊鍵 }`。一個舊鍵對應到幾個新鍵就複製幾份。
  - 新鍵已經有項目：以新鍵的項目為準，歷程加一筆同樣的紀錄，並在 `superseded` 保存舊項目的完整內容。
  - 轉換完後刪除舊項目：它的內容已在每一筆新項目中，留著會被判為 fixed 或重複計數。
  - 轉換後的新項目再照上表判定，例如舊項目是 fixed、新鍵出現時改為 regressed。
- **回傳**：`split` 是 `[{ from: 舊鍵, to: [新鍵…], reason }]`，依舊鍵排序，`to` 也排序。
- **冪等**：舊項目轉換後就刪除，每個舊鍵只轉換一次；同一份基準再推進時依基準鍵略過。
- **擴充方式**：在 `KEY_MIGRATIONS` 加一條規則即可，轉換流程（`migrateKeys`）不用改。例如 M3 的 VRF（[ADR-015](架構決策/015-支援VRF並升級ssot-snapshot-3.md)）讓實體鍵多了 VRF 時，再加一條把新鍵對回舊鍵的規則。

**使用者變更**：`S.ledger.set(ledger, key, change, { now })`，`change = { status?, note?, waiver?, patch? }`，省略的欄位不變。

| 目前狀態 | 使用者可以改為 |
|---|---|
| open | scheduled、accepted、false-positive、fixed |
| scheduled | open、accepted、false-positive、fixed |
| accepted | open、scheduled、false-positive、fixed |
| false-positive | open、scheduled、accepted、fixed |
| regressed | open、scheduled、accepted、false-positive、fixed |
| fixed | 不能改狀態（之後若再出現，`advance` 會標為 regressed）；仍可修改備註與 patch |

- regressed 只能由 `advance` 判定。手動標為 fixed 只允許在項目已不在最新一輪基準時（例如設備已移除）；仍出現時丟出錯誤，請修好後重新收集，由 `advance` 判定。
- accepted 一定要有豁免：`until` 省略時是 now 加 182 天（`S.ledger.WAIVER_DAYS`），而且必須晚於 now；其他狀態不能有豁免。
- 有任何欄位改變時寫入一筆歷程（狀態不變時 from＝to、reason 為 `edit`；被取代或移除的豁免記在歷程）；完全沒有改變時原樣回傳。不合法的轉換、不存在的鍵、格式不對的欄位都丟出錯誤。

**從舊確認標記轉換**：`S.ledger.fromAcks(acks, Q, { now })` 把畫面舊版的確認標記（`{ findingKey: { at, kind, note } }` 或同內容的 Map）轉成處理紀錄，接著以 Q 推進一輪，回傳與 `advance` 相同的結果。

- 分類：`accepted`、`scheduled`、`false-positive` 對應同名狀態；未分類（null）與不認得的分類視為 accepted。
- accepted 的豁免原因取 note，到期日是 now 加 182 天（從轉換時起算，避免很久以前的確認一轉換就到期）。
- 每一項的第一筆歷程是 `{ at: 確認時間, from: null, to, by: 'user', baseline: null, reason: 'from-ack', ack: 原始紀錄 }`，原始內容不遺失。
- 任何一筆格式不對（鍵不是 findingKey、`at` 不是 ISO 時間、`kind`／`note` 型別不對）就丟出錯誤並列出全部問題，不略過。

**統計**

- `S.ledger.summary(ledger)`：趨勢圖用的時間序列 `series`（每一輪的 counts、待處理＝open＋regressed、覆蓋與比率、未知對端），以及目前狀態 `current`（各狀態筆數、豁免總數與沒寫原因的筆數）。
- `S.ledger.ruleStats(ledger)`：各規則的處理結果與誤報比率（標為 false-positive 的筆數／該規則的總筆數），依規則編號排序，供規則品質的閉環使用。

## 10A. 工作包（ssot-workpack/1）

核心 [src/workpack/workpack.js](../src/workpack/workpack.js) 把一整輪的資料（收集檔、基準、處理紀錄、命名規則、預期資料、報表與修正 patch）放進一個不壓縮的 ZIP，帶走後再帶回來。ZIP 的讀寫在 [src/workpack/zip.js](../src/workpack/zip.js)，零相依。決策與取捨見 [ADR-017](架構決策/017-工作包ssot-workpack-1.md)。

兩個檔案都是純函式：只處理 `Uint8Array`，不碰 DOM、Blob、IndexedDB，不讀目前時間（時間由呼叫端傳入），不修改傳入的物件。核心不讀 store，要放進工作包的內容由畫面提供。工作包在 Snapshot 的下游，不被 pipeline 使用；`read` 會呼叫 `S.ledger` 與 `S.profile` 核對內容，`validate` 會呼叫 `S.build` 重建基準。

**不壓縮 ZIP**（`S.zip`）

- `S.zip.write([{ path, bytes }], { mtime? }) → Uint8Array`：依陣列順序寫入，每個項目都是 stored（method 0）、旗標只有 bit 11（檔名是 UTF-8）。`mtime` 是 ISO 8601，以 UTC 的年月日時分秒寫成 MS-DOS 時間（2 秒精度，1980–2107 年）；省略時用固定的 `S.zip.FIXED_MTIME`（`1980-01-01T00:00:00Z`）。相同的 entries 與 mtime 一定得到相同的 bytes。路徑不安全或重複、`bytes` 不是 `Uint8Array`、時間超出範圍、需要 ZIP64（超過 65534 個項目、單檔或總大小達 4 GiB）時丟錯。
- `S.zip.read(bytes) → { entries: [{ path, bytes, crc32, mtime }], dirs: [path] }`：依 central directory 的順序；`bytes` 是複本；`mtime` 視為 UTC，不合法時為 null；目錄項目（以 `/` 結尾、大小 0）只列在 `dirs`。驗證全部結構，有問題時丟出 `ZipError`（`name` 為 `'ZipError'`，`errors` 是全部問題 `[{ code, path, message }]`），不略過、不猜測。代碼見下方的表。
- 其他：`S.zip.crc32(bytes)`（多項式 0xEDB88320）、`S.zip.utf8.encode`／`decode`（嚴格：落單的 UTF-16 代理字元、不合法的 UTF-8 都丟出 TypeError；讀回時保留開頭的 BOM）、`S.zip.checkPath(path, dir)`、`S.zip.safeSegment(name)`、`S.zip.CODES`。格式依據 PKWARE APPNOTE，章節寫在 `zip.js` 的註解。

**路徑規則**

- `S.zip.checkPath(p, dir)`：安全時回傳 null，否則回傳中文原因。讀與寫用同一套規則：以 `/` 分隔的相對路徑；不可空白、以 `/` 開頭、含 `\`、以磁碟代號（`C:`）開頭、含控制字元或 Windows 不允許的字元（`< > : " | ? *`）；每個段落不可空白、不可是 `.` 或 `..`、不可以空白或 `.` 結尾、不可是 Windows 保留名稱（CON、PRN、AUX、NUL、COM1–9、LPT1–9，含副檔名）。`dir` 為 true 時要求結尾的 `/`，否則不可以 `/` 結尾。
- 重複的檔名不分大小寫：解壓到不分大小寫的檔案系統時會互相覆蓋。
- `S.zip.safeSegment(name)`：把任意名稱轉成一個安全的段落。只保留 Unicode 字母、數字與 `_ . -`，其他換成 `_`；開頭的 `.` 與結尾的 `.` 換成 `_`；Windows 保留名稱前加 `_`；最長 120 個字元；空字串變成 `_`。轉換後仍可能和其他名稱相同，由呼叫端處理。
- 工作包內的路徑是 `<角色目錄>/<安全名稱>`：名稱經 `safeSegment` 改過時，在副檔名前加上原名雜湊（`S.util.hash`）的前 8 碼；和已用的路徑重複（不分大小寫）時，改用角色、原名與序號的雜湊。原名保存在 manifest 的 `name`，讀回時不變。

**`S.workpack` 的介面**

- `S.workpack.build(parts, { now }) → Uint8Array`
  - `parts`：`[{ role, name, text }` 或 `{ role, name, bytes }]`，`text` 是字串、`bytes` 是 `Uint8Array`，兩者恰好一個。`role` 見下表；`name` 是非空字串，收集檔的 `name` 就是 `S.build` 的來源名稱，報表與 patch 是下載的檔名。
  - `now` 必須明確給，是 ISO 8601；寫進 manifest 的 `createdAt` 與 ZIP 的修改時間。相同的 parts 與 now 一定得到相同的 bytes。
  - 檔案依角色（下表的順序）排列，同一角色保留呼叫端的順序（收集檔的順序決定 inputHash）。`manifest.json` 是 ZIP 的第一個項目。
  - 參數形狀不對丟出 TypeError；內容的問題全部列出後丟出 `WorkpackError`（`errors`、`warnings`，同 `read`）。build 不回傳警告，需要時以 `read` 讀回成品取得。
- `S.workpack.read(bytes) → pack`：`{ manifest, files, sources, snapshot, ledger, profile, expectedData, expected, warnings }`。
  - `manifest` 原樣保留，含不認得的欄位。`files` 是 `[{ role, path, name, bytes }]`，依 manifest 的順序，大小與 SHA-256 都已驗證；報表與 patch 只在 `files` 中，不解讀。
  - `sources` 是 `[{ name, text }]`，可以直接交給 `S.build`；`snapshot`、`ledger`、`profile`、`expectedData`、`expected` 是解析後的 JSON，沒有時為 null。
  - ZIP 結構錯誤原樣丟出 `ZipError`；其他問題全部列出後丟出 `WorkpackError`。
- `S.workpack.validate(pack, { now, profile, expectedData }) → { ok, errors, warnings, snapshot }`：以工作包的收集檔重新 `S.build`，核對是不是同一份基準。三個選項都要明確給（`profile`、`expectedData` 不使用時傳 null）；通常傳 `pack.profile` 與 `pack.expectedData`，畫面也可以換成使用者目前的命名規則。`snapshot` 是重建的基準，呼叫端可以直接使用，不必再建一次；重建失敗時為 null。
- `S.workpack.validateAsync(pack, opts, onProgress?) → Promise<同 validate>`：參數與回傳值都和 `validate` 相同，改用 `S.buildAsync` 重建，每個階段讓出主執行緒，畫面不會停住；`onProgress` 收到的進度格式和 `S.buildAsync` 相同。判斷邏輯和 `validate` 共用同一份。參數形狀不對（含 `onProgress` 不是函式）時 Promise 以 TypeError 拒絕。
- 其他：`S.workpack.sha256(bytes)`（FIPS 180-4，回傳 64 位小寫十六進位）、`SCHEMA`、`ROLES`、`ERRORS`、`WARNINGS`、`MANIFEST`（`'manifest.json'`）。

**角色**（`S.workpack.ROLES`，封閉列舉）

| 角色 | ZIP 內的目錄 | 份數 | 內容 | 讀回時 |
|---|---|---|---|---|
| `source` | `sources/` | 至少 1 | 收集檔（原始輸入） | UTF-8 文字，放進 `pack.sources` |
| `snapshot` | `baseline/` | 恰好 1 | 基準（Snapshot JSON） | 解析 JSON |
| `ledger` | `ledger/` | 最多 1 | 處理紀錄（`ssot-ledger/1`） | 解析 JSON |
| `profile` | `profile/` | 最多 1 | 命名規則（`ssot-profile`） | 解析 JSON |
| `expected-data` | `build/` | 最多 1 | `S.build` 的 `expectedData` 選項（各類設備應有的資料，`{ 設備類型: [資料類別…] }`），是 baselineKey 的組成之一 | 解析 JSON，放進 `pack.expectedData` |
| `expected` | `expected/` | 最多 1 | 預期資料 `ssot-expected/1`（`S.compare` 用，[第 8 節](#8-比對獨立模組)） | 解析 JSON |
| `report` | `reports/` | 任意 | 報表（CSV、Markdown…） | 不解讀 |
| `patch` | `patches/` | 任意 | 修正 patch（`.rsc`…） | 不解讀 |

「預期資料」有兩種，不要混用：`expected-data` 是建立基準的選項，改了基準鍵就不同；`expected` 是和基準比對的預期資料，不影響基準。

**manifest**（`manifest.json`）

```
{ schema: 'ssot-workpack/1', toolVersion, createdAt, inputHash, baselineKey,
  baseline: { schema, version, createdAt, profile },
  files: [{ role, path, name, bytes, sha256 }] }
```

- `toolVersion` 是建立時的 `S.VERSION`，`createdAt` 是 build 的 `now`。
- `inputHash`、`baselineKey`（沒有時為 null）與 `baseline` 取自基準的 `meta`；`baseline.profile` 是 `meta.profile`（`{ id, version, hash }` 或 null；2.11.0 以前的基準沒有 hash）。
- `files[]`：`bytes` 是檔案的位元組數，`sha256` 是內容的 SHA-256，可以用 `sha256sum` 等一般工具核對。`name` 是畫面提供的原始名稱，`path` 是 ZIP 內的安全路徑。

**核對的內容**（build 與 read 共用同一套）

- **份數與格式**：每個角色的份數；文字與 JSON 角色必須是合法的 UTF-8；JSON 角色必須是合法的 JSON。
- **基準**：要有 `meta.inputHash`；`meta.baselineKey` 有值時必須是非空字串。`meta.schema` 不是目前的 `S.SCHEMA` 時是警告（validate 會重建）。
- **收集檔**：
  - 和基準的 `meta.sources`（[§5.2](#52-實體snapshotmodelschema-ssot-snapshot2)）逐一比對份數、順序、名稱、`bytes` 與 `hash`。基準沒有 `meta.sources` 時是警告：只是不能逐一核對單一檔案。
  - 以 `S.inputHashOf` 算出全部收集檔（名稱、內容與順序）的 inputHash，和基準的 `meta.inputHash` 核對；不需要重建。不同時是錯誤。
- **命名規則**：附上時要能以 `S.profile.compile` 編譯。基準用過命名規則（`meta.profile`）時一定要附上，而且是同一份：id、版本與內容雜湊（`S.profile.hash`，和 `meta.profile.hash` 比對）都相同；基準沒用卻附上也是錯誤。2.11.0 以前的基準沒有內容雜湊，只核對 id 與版本，另列警告 `profile-unverified`；validate 重建時會再以基準鍵核對（內容不同時重建的基準鍵也不同）。
- **expectedData** 必須是 `{ 設備類型: [字串…] }`；**預期資料**的 `schema` 必須是 `ssot-expected/1`。
- **處理紀錄**：要通過 `S.ledger.validate`，而且推進過這份基準（`S.ledger.roundOf`，[第 10 節](#10-處理紀錄ssot-ledger1)）。沒有推進過是錯誤；推進過、但之後又推進了其他基準（不是最後一輪）是警告。

**read 另外檢查的內容**

- 要有 `manifest.json`，內容是合法的 UTF-8 JSON 物件。`schema` 必須是 `ssot-workpack/<整數>`：比 1 新的 major 明確拒絕，請用新版工具開啟；其他不認得的版本也拒絕。
- manifest 的欄位：`toolVersion` 非空、`createdAt` 是 ISO 8601、`inputHash` 非空、`baselineKey` 是非空字串或 null、`baseline` 是物件、`files` 是陣列；`files[]` 每筆的 `role`、`name` 非空，`bytes` 是非負整數，`sha256` 是 64 位小寫十六進位，`path` 通過 `checkPath`。
- `files[]` 列出的每個檔案都要在 ZIP 中，路徑不重複，大小與 SHA-256 和 manifest 相同。
- 收集檔的 inputHash（`S.inputHashOf(pack.sources)`）要和 manifest 的 `inputHash` 相同；manifest 的 `inputHash`、`baselineKey` 也要和基準的 `meta` 相同。
- 不認得的角色（可能是較新版本寫入的）是警告：檔案照樣驗證大小與雜湊、保留在 `files`，但不解讀。ZIP 中有 manifest 沒列出的檔案也是警告，不讀入。建立的版本和目前的 `S.VERSION` 不同時是警告。

**validate 的判斷**（`validateAsync` 相同）

- 重建失敗（例如呼叫端給的命名規則無法編譯）列為錯誤，不丟例外。
- 重建的 inputHash 和 manifest 不同是錯誤：inputHash 只由收集檔的名稱與內容決定，收集檔已通過 SHA-256 驗證，不同表示基準與處理紀錄不屬於這些收集檔，不能當成同一輪帶回。`read` 已經以 `S.inputHashOf` 核對過，所以 `read` 的結果不會在這裡出錯；保留這一步是為了呼叫端自己組的 pack，以及 `S.build` 與 `S.inputHashOf` 萬一不一致時仍抓得到。
- inputHash 相同、baselineKey 不同時：程式的 major.minor、命名規則或 expectedData 和建立時不同，是警告，並說明是哪一項；處理紀錄會把它當成新的一輪，這是預期的行為。三者都相同、基準鍵卻不同時是錯誤，表示工作包的內容自相矛盾；基準沒有命名規則的內容雜湊時，錯誤訊息另外提示最可能的原因是附的命名規則內容和建立時不同（id 與版本相同）。

**錯誤與警告代碼**

`S.zip.CODES`（`ZipError` 的 `errors[].code`）：

| 代碼 | 意義 |
|---|---|
| `not-bytes` | 輸入不是 `Uint8Array` |
| `no-eocd` | 找不到結尾紀錄（end of central directory）：不是 ZIP 或檔案不完整 |
| `multi-disk` | 分割成多個檔案的 ZIP，或項目在另一個分割檔 |
| `zip64` | ZIP64，不支援 |
| `out-of-range` | central directory、local header 或資料的位置與大小超出範圍 |
| `bad-central` | central directory 的格式錯誤，或筆數和大小對不上 |
| `bad-local` | local header 的簽章不對 |
| `local-mismatch` | local header 的檔名、壓縮方式、CRC 或大小和 central directory 不同 |
| `name-encoding` | 檔名標示為 UTF-8 卻不合法，或沒有標示 UTF-8 而含有非 ASCII 位元組 |
| `unsafe-path` | 路徑不安全（`checkPath`） |
| `duplicate` | 檔名重複（不分大小寫） |
| `encrypted` | 項目有加密 |
| `compressed` | 項目是壓縮過的，只支援 stored |
| `size-mismatch` | 不壓縮的項目壓縮前後大小不同，或目錄項目有內容 |
| `crc` | CRC-32 不符，內容損毀或被修改 |
| `overlap` | 兩個項目的資料範圍重疊 |

`S.workpack.ERRORS`（`WorkpackError` 的 `errors[].code`，validate 的 `errors[].code`）：

| 代碼 | 時機 | 意義 |
|---|---|---|
| `no-manifest` | read | 沒有 `manifest.json`，不是工作包 |
| `manifest` | read | manifest 不是合法的 JSON 物件，或欄位格式不對 |
| `schema` | read | `schema` 不是 `ssot-workpack/<整數>`，或是不認得的版本 |
| `schema-newer` | read | 比本工具新的 major 版本 |
| `missing-file` | read | manifest 列出的檔案不在 ZIP 中 |
| `size`、`hash` | read | 大小或 SHA-256 和 manifest 不同 |
| `duplicate-path` | read | manifest 重複列出同一個路徑 |
| `count` | build、read | 角色的份數不對 |
| `encoding`、`json` | build、read | 不是合法的 UTF-8 或 JSON |
| `snapshot` | build、read | 基準沒有 `meta.inputHash`，或 `meta.baselineKey` 格式不對 |
| `baseline-mismatch` | read | 基準的 inputHash 或 baselineKey 和 manifest 不同 |
| `source-mismatch` | build、read | 收集檔和基準的 `meta.sources` 不同（份數、順序、名稱、長度或內容） |
| `ledger` | build、read | 處理紀錄沒有通過 `S.ledger.validate` |
| `ledger-baseline` | build、read | 處理紀錄沒有推進過這份基準 |
| `profile` | build、read | 命名規則無法編譯，或是空的 |
| `profile-mismatch` | build、read | 基準用的命名規則和附上的不同（id、版本或內容雜湊）、沒有附上，或基準沒用卻附上 |
| `expected-data` | build、read | expectedData 的格式不對 |
| `expected` | build、read | 預期資料的 schema 不是 `ssot-expected/1` |
| `rebuild` | validate | 以收集檔重建失敗 |
| `input-hash` | build、read、validate | 收集檔的 inputHash 和基準的 `meta.inputHash` 不同（build、read，以 `S.inputHashOf` 計算，不重建）、和 manifest 不同（read），或重建後和 manifest 不同（validate） |
| `baseline-key` | validate | 程式版本、命名規則與 expectedData 都相同，基準鍵卻不同 |

`S.workpack.WARNINGS`（`pack.warnings` 與 validate 的 `warnings`）：

| 代碼 | 時機 | 意義 |
|---|---|---|
| `unknown-role` | read | 不認得的角色，檔案保留但不解讀 |
| `unlisted-file` | read | ZIP 中有 manifest 沒列出的檔案，沒有讀入 |
| `tool-version` | read | 建立工作包的版本和目前不同 |
| `snapshot-schema` | read | 基準的 schema 不是目前的 `S.SCHEMA` |
| `snapshot-sources` | read | 基準沒有 `meta.sources`，無法逐一核對單一收集檔；全部收集檔的 inputHash 仍然會核對 |
| `ledger-newer` | read | 處理紀錄推進過這份基準，之後又推進了其他基準 |
| `profile-unverified` | read | 基準沒有命名規則的內容雜湊（2.11.0 以前建立），只核對了 id 與版本；validate 重建時再以基準鍵核對 |
| `baseline-key` | validate | 程式版本、命名規則或 expectedData 和建立時不同，基準鍵因此不同 |

build 不回傳警告（只在丟出 `WorkpackError` 時附在 `warnings`），要以 `read` 讀回成品取得。`baseline-key` 同時在錯誤與警告中，依上面「validate 的判斷」區分。

## 11. 檢視層架構

檢視層是 `src/view/` 底下的一般 `<script>`，在 `index.html` 中排在核心、命名規則與嵌入的範例之後載入。這一節只寫架構與資料的去向；畫面怎麼操作見[使用說明](使用說明.md)。

- **只讀基準**：畫面只透過 `SSOT.query(snapshot)`（Q）與 `S.query.*` 的靜態查詢（[§5.2](#52-實體snapshotmodelschema-ssot-snapshot2)）讀取 Snapshot 與規則目錄，不讀 Snapshot 的欄位、不讀內部模型 M，也不改寫 Snapshot（[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）。比對、修正計畫與處理紀錄的結果都由核心（`S.compare`、`S.remediate`、`S.ledger`）產生，畫面只負責選取、排版與下載。
  - **允許使用的 `S.*` 成員**以 `tests/ui-smoke.js` 的邊界掃描（`VIEW_S_ALLOW`、`VIEW_S_ONLY`）為準，目前是：查詢 `query`、`trace`、`util`、`keys`；常數 `VERSION`、`SCHEMA`、`LINK_SCOPE`、`KIND_LABEL`；輸入 API `build`、`buildAsync`、`inputHashOf`、`profiles`、`samples`，以及只允許一個成員的 `S.readers.PASTE`、`S.profile.compile`；下游 `compare`、`remediate`、`ledger`、`workpack`、`zip`；畫面自己的 `view`、`store`。
  - 禁止的寫法：`S.check.*`（改用 `S.query.rule`／`rules`／`dataLabel`、`S.util.fmtVlans`）、`S.adapters`（改用 `S.query.adapterLabel`）、計算的成員名稱 `S[…]`、從 `S` 解構，以及讀 `snap.`／`snapshot.` 的欄位（`findings`、`meta`、`coverage`、`blocks`、`model` 等，改用 Q 的函式；還沒建立 Q 的 JSON 用 `S.query.metaOf`）與 `Q.snapshot`。
  - 畫面需要新的資料時，由 data-model 新增查詢函式，畫面不繞過。
- **這一輪的資料集中在 `App.round`**（`src/view/app.js`）：`{ sources, profile, expectedData, snapshot, Q, expected: { name, data, error }, origin: { kind, name?, createdAt? }, get ledger() }`。
  - `sources` 是收集檔 `[{ name, text }]`（順序決定 inputHash）；`profile` 是建立基準時用的命名規則；`expectedData` 是 `S.build` 的建立選項（目前只會由工作包帶入）；`snapshot`、`Q` 是基準與它的查詢介面。
  - `expected` 是比對用的預期資料（`ssot-expected/1`；無法解析時 `data` 為 null、`error` 寫原因），沒有時為 null。
  - `origin` 是這份基準怎麼來的：`kind` 為 `build`、`restore` 或 `workpack`，由工作包帶回時另有工作包的檔名與建立時間。
  - `ledger` 是唯讀的 getter，讀的是 `src/view/app-ledger.js` 的狀態（處理紀錄停用時為 null）；處理紀錄的停用、轉換與寫入 store 仍由 app-ledger.js 管理。
  - 只能經 `A.load(snap, positions, inputs)`（換基準，可以同時換輸入，不會出現基準換了、收集檔還是舊的中間狀態）、`A.setRoundInputs(inputs)`（只換輸入）與 `A.clearRound()`（「清除」）改變。`App.snap`、`App.Q`、`App.sources`、`App.profileJson` 改為它的唯讀存取器，直接指定在嚴格模式下會丟錯。
  - 選取、展開、版面、縮放與位置是檢視狀態，不放在 `App.round`。上一輪的基準（新舊基準比對的舊基準）也不在這裡，仍在 `src/view/panels/baseline-diff.js` 的記憶體中，因為它在工作包沒有角色。
- **流程步驟與中間的工作畫面**（`src/view/app-panes.js`，版面重整 3）：頁首的流程步驟（① 輸入 ② 檢視 ③ 分診 ④ 修正 ⑤ 驗證）取代原本的左側五個分頁與中間四個分頁。每一步同時決定左側清單與中間的工作畫面；右側的詳細資料不變。

  | 步驟 | 左側 | 中間 |
  |---|---|---|
  | ① 輸入（`input`） | —（資料中心蓋住主畫面） | 資料中心：這一輪的輸入、覆蓋率與輸出 |
  | ② 檢視（`view`） | 清單（`#pane-inventory`：設備、介面、IP、網段、MAC、VLAN） | 拓樸圖 |
  | ③ 分診（`triage`，預設） | 檢查結果（`#pane-findings`） | 拓樸圖 |
  | ④ 修正（`fix`） | 沒有，中間全寬 | 修正計畫（`#view-patch`，「要修正哪些」在它自己的左欄） |
  | ⑤ 驗證（`verify`） | 沒有，中間全寬 | 驗證（`#view-verify`）：本輪變化 `#round-body`、處理紀錄 `#ledger-body`、修復追蹤 `#tracking-body`、收斂趨勢 `#trend-body`、比對 `#compare-body` |

  - **狀態**：`App.step` 是主畫面那一步（②–⑤，預設 ③）；資料中心開著時目前的一步是 ①（`A.currentStep()`），關閉後回到 `App.step`。`App.centerView` 是中間的工作畫面：`graph`、`patch` 或 `verify`。步驟與工作畫面都是檢視狀態，不存進 store；store 的鍵沒有變。
  - **切換**：`App.showStep(step, { focus, scroll, workspace, opener, section })`。① 開啟資料中心（`section` 是要捲到的區塊，`opener` 是開啟它的按鈕）；②–⑤ 先關閉資料中心再切換。`focus` 為 true 時焦點移到這一步的標題（②、③ 是左側清單的標題 `#left-title`，④、⑤ 是工作畫面的標題）；為字串時移到 ⑤ 的區塊（`round`、`ledger`、`tracking`、`trend`、`compare`）或 `graph`（畫布）；省略時焦點不動。`scroll` 只捲到同樣的目標、不移焦點。`workspace` 是窄螢幕要顯示的工作區，預設有左側清單時先看清單，否則看工作畫面。
  - **其他模組的入口**：`App.showView(view, { focus })` 換成對應的一步：`graph` 是「在圖上定位」（目前不在拓樸圖時，回到上一次看圖的 ② 或 ③），`patch` 是 ④，`verify` 是 ⑤，`compare`、`trend` 是 ⑤ 並捲到那個區塊。搜尋與路由追蹤用它回到拓樸圖。
  - **步驟列**（`A.renderSteps`）：`<nav>` 中的按鈕，目前的一步是 `aria-current="step"`。每一步寫出狀態文字（① 已收集台數、② 拓樸圖的層級、③ 待處理筆數、④ 已選項目、⑤ 處理紀錄的第幾輪與回歸數），不只靠顏色。沒有基準時 ④、⑤ 以 `aria-disabled` 停用（仍可聚焦與朗讀原因），點了以提示列說明；停在 ④、⑤ 時清除基準會回到 ③（`A.syncSteps`）。
  - **工作畫面的疊放**：④、⑤ 疊在 `#stage` 上的拓樸圖（`#view-graph`）上面，同一格：畫布的大小不變，切換時不重新排列，位置、縮放與選取都保留，PNG 照常匯出。拓樸圖被蓋住時設為 `inert`。④、⑤ 沒有左側清單，左欄寬度為 0（記住的寬度不變）。只重繪目前顯示的工作畫面（`A.renderCenter`）。
  - **點選**：在 ④、⑤ 點選檢查結果或比對的項目時，步驟不切換，詳情在右側顯示；圖的選取也更新。
  - **層級切換**仍在拓樸圖的工具列，② 和 ③ 都看得到；② 的步驟狀態寫出目前的層級。
  - **窄螢幕**：三個工作區依流程排列（左側清單 → 中間的工作畫面 → 詳細資料），標籤跟著目前的一步（`A.syncWorkspaces`）；④、⑤ 沒有清單工作區。
  - **資料中心就是 ①**：它是蓋住整個主畫面的另一層，有自己的 `inert`、Esc 與焦點規則（見 §11.1「資料中心」）。
- **樣式的唯一來源**：顏色、線型、透明度與 Canvas 字型都定義在 `src/view/theme.js`（[§11.2](#112-樣式theme)）。
- **儲存集中在 `src/view/store.js`**：IndexedDB 資料庫 `topo-mikrotik` 的 `kv`；無法使用 IndexedDB 時退回記憶體，畫面會提示。使用的鍵：
  - `last`：最後一次的基準、輸入（收集檔、命名規則、`expectedData`）與節點位置，由 `A.saveLast` 從 `App.round` 寫入；按「清除」只刪這個鍵。
  - `ledger`：處理紀錄（舊版的 `acks` 轉換後刪除，見 [§11.1](#111-資料來源與檢視狀態)）。
  - `layout`、`layoutMode`：左右欄寬度與版面模式。
  - `profiles`：使用者載入的命名規則。
- **檢視狀態不進基準**：畫布上的節點位置、選取、展開、縮放、篩選、修正計畫的選取與新舊比對的結果，都不寫回 Snapshot。
  - 設備圖的節點位置（`'last'.positions`）與 `'layout'` 的格式都不變。L2 埠圖與 L3 子網圖的位置與縮放**只放在記憶體**（`App.layers`），不另外佔 store 的鍵：這兩層可以由 ELK 重新算出來，而且埠的 id 會隨聚合收合與焦點改變，存起來還要處理失效。
- **版面引擎**：內建版面與分層版面（ELK）共用 `src/view/graph/layout.js` 的分群與分層，見 [§11.3](#113-拓樸版面)。
- **拓樸圖的層級**（`src/view/app-layers.js`，M1）：設備圖、L2 埠圖（`Q.portGraph`）、L3 子網圖（`Q.subnetGraph`）共用同一張畫布 `App.graph`，切換時換掉圖資料；L4 可達性（M2）也是工具列的一層，但不是畫布，見下方「L4 可達性」。app-layers.js 負責層級切換、VLAN 篩選，以及 L2／L3 的圖資料、版面與標示；設備圖的資料仍在 app-graph.js。
  - **狀態**（都是檢視狀態，不寫進基準）：`App.layer`（`device`／`l2`／`l3`／`l4`）；`App.devicePos`（設備圖的位置，存進 store 的 `'last'`）；`App.layers`（L2／L3 的圖資料、位置與縮放，鍵是「層級＋選項」，例如 L2 的聚合收合、全部的埠、範圍與焦點；換基準或清除時清空）；`App.layerJob`（L2／L3 背景版面的工作，測試可以等待）；`App.vlanFilter`（`{ id, domain }`，VLAN 篩選）；`App.L2_MAX`（300）。
  - 切換層級（`App.showLayer`）時，各層的平移與縮放分開保存、不互相覆蓋；選取保留，在新的一層重新標示。只有設備圖拖曳後的位置寫進 store。
  - **VLAN 篩選**：`App.vlanFilter` 在每一層都持續標示，直到選「不篩選」；選 VLAN 時也會設為篩選。標示來自 `Q.vlanCarriers`（`A.vlanMarks`）：設備圖標在設備對的線上，L2 標在埠對埠的邊上，同一條線有多條鏈路時取最需要注意的狀態（只有一端帶 > 承載 > 推論承載 > 只有一端可確認）；L3 標出屬於這個 VLAN 的子網。換基準時，新的基準沒有這個 VLAN 就取消篩選。
  - **L2 的大型資料**：埠讓 ELK 的計算量比設備圖大很多，所以 `App.L2_MAX`（300 台）低於 `App.ELK_MAX`。超過時只畫焦點設備與它的鄰居，並停用「整張圖」。焦點是選取的設備；沒有選取時，取連線最多的路由器、防火牆或交換器。選了不在圖上的設備時，改以那一台為中心重畫（`A.recenterL2`）。
- **L4 可達性**（`src/view/panels/l4.js`，M2）：zone 矩陣（L0）、下鑽（L1 位址組、L2 牽涉的規則、L3 逐跳路徑）與可達性查詢。資料全部來自查詢層（`Q.zoneMatrixSteps`、`Q.zoneMatrix`、`Q.zoneCell`、`Q.reach`、`Q.zones`，以及 `S.query.l4Services`、`reachAssumptions`、`reachReasonCodes`；[§5.3「L4 可達性與 zone」](#l4-可達性與-zone2110-新增)），畫面不自己判斷規則或路由。操作見[使用說明「② 檢視」](使用說明.md#step-view)。
  - **疊在畫布上**：L4 的內容在 `#view-l4`，選了 L4 時疊在畫布上、工具列下面（層級切換仍在工具列，Tab 順序在矩陣之前）。`App.showLayer('l4')` 不換畫布的資料、不記縮放；畫布設為 `inert`，圖例與操作說明不顯示，回到其他層級時照原樣還原。只對畫布有用的工具列群組（VLAN 篩選、全圖與重新排列、主機、匯出 PNG）在 L4 隱藏。
  - **入口與介面**：`V.l4`（`show`、`zoneOpts`、`state`、`openCell`、`openGroup`、`runReach`、`timings`、`runs`、`MATRIX_MAX`）。`V.l4.runs(Q)` 是這份基準上各服務分段計算的紀錄（`{ ms, wallMs, steps, maxStepMs, maxGapMs }`：計算本身、含讓出的總時間、段數、一段最久佔住主執行緒多久、兩段之間最長的間隔），大型冒煙測試讀它。`App.l4Job` 是矩陣的計算，`App.l4ImpactJob` 是規則詳情的「計算 L4 影響」，都是 Promise，測試可以等待。
  - **「在圖上定位」**（搜尋、路由追蹤，`App.showView('graph')`）在 L4 時改回設備圖，因為矩陣沒有圖。
  - **匯出**：L4 不匯出 PNG（`A.exportPng` 以提示列說明），矩陣改用 L4 畫面的「下載 CSV」（目前的服務，每一格一列，開頭有 UTF-8 BOM、換行 CRLF，儲存格經 `V.exporter.csvCell` 處理）。
  - **矩陣用 HTML 表格**：`<table role="grid">` 加 CSS 自製，不用 SVG 或 Canvas。理由是可及性：鍵盤（roving tabindex，只有目前的格子在 Tab 順序裡）、螢幕閱讀器（每格的 `aria-label` 寫出狀態、筆數與代表規則）與強制色彩都比較容易做好。
  - **顏色**：取自 `theme.l4`（[§11.2](#112-樣式theme)），五種狀態一律有符號與文字（`V.L4_STATUS`），不只靠顏色。
  - **上限**：矩陣最多畫 `MATRIX_MAX`（60）個 zone，超過時只有表格檢視；表格檢視最多列 3000 格，完整內容在 CSV。下鑽的表格最多列 300 筆。
  - **檢視狀態**：服務、檢視方式（矩陣／表格）、下鑽到哪裡、「收起全部拒絕的組」與異質格的「顯示全部」都只在記憶體，不存進 store，換基準時清掉。矩陣與規則影響的計算結果由查詢層快取；畫面記下這份基準算過哪些服務，再開時直接畫、不顯示忙碌提示。規則影響的結果依基準與規則保留，到換基準為止。
  - **第一次計算**：用 `Q.zoneMatrixSteps` 分段計算（[§5.3](#l4-可達性與-zone2110-新增)）。先顯示忙碌提示，稍後才開始；段與段之間以 `setTimeout(0)` 讓出主執行緒，所以計算期間畫面仍可操作。同時最多一個計算；只換檢視方式時沿用進行中的計算。換服務、換基準或離開 L4 時以 `it.return()` 放棄，不畫過期的結果，查詢層也不留快取；離開 L4 而放棄的，回到 L4 時重新計算。算過的服務在狀態列寫出計算時間與段數。
  - **進度的可及性**：說明文字放在狀態列（live region），只朗讀一次；進度條（`role="progressbar"`）每段更新 `aria-valuenow` 與 `aria-valuetext`（階段與筆數，例如「第 2／3 段：逐一判斷 …」），畫面上的數字設為 `aria-hidden`，不在 live region 反覆朗讀。
  - **異質格的下鑽**：L1 預設只列 `groups[].divergent` 的組，可切換顯示全部；造成差異的服務（`divergentServices`）在按鈕上另標「≠ 差異」文字，不只靠顏色。不異質的格子仍是全部拒絕的組預設收起。
  - **命名規則**：建立基準時用的命名規則（`App.profileJson`）有 `zones` 段時，才以 `profile` 參數傳給查詢層（`V.l4.zoneOpts`，規則影響共用）。核對失敗時（[§5.3](#l4-可達性與-zone2110-新增)）不套用 `zones` 段（zone 改由其他來源決定），並在狀態列與「zone 的依據」寫出核心的錯誤訊息，不靜默改用別的分法。

### 11.1 資料來源與檢視狀態

下列都是檢視狀態、使用者的資料或衍生輸出，不改寫基準：

- **處理紀錄（取代確認標記）**：使用者對每個 finding 的決定與歷程，資料模型與規則在核心 `S.ledger`（[第 10 節](#10-處理紀錄ssot-ledger1)），畫面接線在 `src/view/app-ledger.js`。
  - 存在 store 的獨立鍵 `'ledger'`，和基準 `'last'` 分開：按「清除」不影響它，重新建立同一份網路的基準時仍然有效。
  - 每次建立或還原基準後，以目前時間呼叫 `S.ledger.advance` 推進一輪；同一份基準（基準鍵相同）已推進過時不顯示本輪變化。
  - **舊確認標記的轉換**：啟動時 store 沒有 `'ledger'`、但有舊的 `'acks'`（`{ findingKey: { at, kind, note } }`）時，先記下，等第一份基準載入時以 `S.ledger.fromAcks` 轉換（含推進一輪），提示列顯示轉換的筆數。`'ledger'` 寫入成功後才刪除 `'acks'`；寫入失敗時保留 `'acks'`，下次開啟再轉換一次。store 已經有 `'ledger'` 時不讀 `'acks'`。
  - **無法使用時停用**：store 中的 `'ledger'` 格式不正確（`S.ledger.validate` 不通過），或舊確認標記無法轉換時，處理紀錄停用：不寫入 store、不丟資料，畫面說明原因與錯誤。可以匯出原資料、匯入正確的處理紀錄，或以空白的處理紀錄重新開始（舊的 `'acks'` 保留不刪）。

- **devices.csv 草稿**（`V.remediation.devicesCsvDraft`）：由 C01（只被鄰居發現、沒有收集資料的網路設備）產生 `tools/collect.sh` 的設備清單，格式 `name,address,user,port,extra`。

  - 不能直接使用的設備寫成註解列（開頭 `#`，`collect.sh` 會略過）並註明原因：沒有任何位址、位址含空白或逗號、名稱不符合 `collect.sh` 的名稱規則，或名稱重複。修正後移除 `#` 即可。
  - 檔頭註解另寫基準建立時間、輸入指紋，以及建議先執行 `tools/collect.sh devices.csv --dry-run`。

### 11.2 樣式（theme）

所有顏色、線型、透明度與字型集中在 `src/view/theme.js`，Canvas 繪圖與圖例都讀它（圖例分「設備／終端／連線／連線註記／標示」五類，預設收合，說明文字放提示；外形、連線色、線寬、虛線、弱證據透明度與標示色由 theme 產生，有測試比對）；CSS 的設備類型、嚴重度色與它的一致性也有測試。連線依速率是同一色相由淺到深的色階，線寬隨速率遞增（1G → 10G → 40G，聚合最粗）；1G 是由介面名稱推估的分類，不代表實際協商速率，圖例提示會說明此限制。「單側觀察」是點線、「推論鏈路」是長虛線，兩者只改線型與透明度，保留速率色；只有 MNDP 的設備對不畫線。選取或 hover 高亮時維持完整不透明度。一般 UI 採冷白背景與一致的圓角、控制項高度及陰影層級；操作按鈕依優先級呈現，狀態 chip 使用對應色彩及邊框，清單表格使用斑馬列與 hover 高亮，互動元件提供鍵盤焦點樣式，並尊重減少動態效果的系統偏好。

- **theme 的內容**（配色以 dataviz 的 validator 在亮色、底色 `#f8fafc` 驗證）：
  - 狀態色（`sev`、`mark.bad`／`good`）只表示狀態，而且一律搭配外形或文字；類別色（設備、連線、廠商）不用紅、橘黃、綠。
  - `text`：文字色（body、muted、err、warn、ok、info），對其底色至少 4.5:1，與 `assets/app.css` 的對應變數一致。防火牆的動作色與比對的 effect 色都取自它。
  - `sevShape`：嚴重度的外形，錯誤是方形、警告是三角形；節點右上角、連線中點與圖例共用（`V.sevMark`）。比對的 effect 標籤前也加上同樣的外形（`diff.effectSev`）。
  - `multi`：同一對設備有多條鏈路時，線加寬（`widen`）並在中間留一條底色細縫（`gap`），看起來是雙線。
  - `font`：Canvas 的字型清單（`ui`、`mono`），與 CSS 的 body、`--mono` 相同。過長的節點標籤與埠名截斷加「…」。
  - `canvas.surface`：畫布底色（與 `--surface` 相同）。每次繪圖先填滿，所以匯出的 PNG 不是透明背景；多條鏈路的中縫也用它。
  - `vlan`：VLAN 篩選的四種線型：`carry` 實線、`inferred` 長虛線（同推論鏈路）、`partial` 錯誤色實線加垂直短刻度（`ticks`：沿線每 `gap` 一道、全長 `len`、粗 `w`）並在中點加錯誤外形（方形）、`oneSide` 淡色點線。都保留外形或線型，不只靠顏色。
    - `partial` 的錯誤色與 `carry` 的正常色在紅綠色盲下分不出來（validator 的 CVD 檢查 deutan ΔE 5.0 不通過），所以顏色不變，改以線型與外形作第二種編碼；設備圖、L2 埠圖、圖例與 PNG 匯出都有刻度。
    - 不用雙線，是因為會和「多條鏈路」（`multi`）的雙線撞在一起；不用鋸齒線，是因為在短邊上不好辨認。其他線型都是沿線方向的虛線、點線或雙線，垂直的刻度不會和它們混淆。
  - `l2`：L2 埠圖的設備框（`box`，外框用設備類型色，未收集的用虛線）與埠（`port`，聚合埠較寬，推論鏈路未收集端的未知埠用虛線）。
  - `l3`：L3 子網圖的子網長條（`subnet`，只由路由得知的目的網段用虛線外框）、路由（`route`，虛線加箭頭）、網段重疊（`overlap`，警告文字色的虛線，中點加警告外形）與重疊、重複 IP 的標籤（`badge`）。
  - `trend`：處理紀錄趨勢圖的線色、外形標記、格線與座標軸色，以及線型 `lineWidth`（1.5）、`markerSize`（外形標記的半徑 3）、`markerRing`（標記外圈的底色環 1.5）。待處理、回歸、已豁免三色以 dataviz 的 validator 檢查全部通過，色覺差異模擬下最差的 ΔE 是 18.4。
  - `l4`：L4 zone 矩陣與可達性的五種狀態（`status`，鍵和 `Q.zoneMatrix` 的格子 `status`、`Q.reach` 的 `verdict` 相同），每種有符號色 `mark`、底色 `bg` 與符號 `glyph`；另有格子的文字色（`text.body`）、異質徽章（`badge`）、對角線（zone 內）的虛線外框（`diagonal`）與焦點色。
    - allow（✓）、deny（✕）、partial（◐）的 `mark` 以 dataviz 的 validator 檢查全部通過，色覺差異模擬下最差的 ΔE 是 13.2（deutan）。
    - unknown（?）與 empty（–）刻意用中性色：「無法判斷」與「沒有可算的組合」不是一種結果。empty 另加斜線底紋（`hatch`），和 unknown 的實心灰底分開。
    - 格子的文字對每種底色至少 4.5:1，符號對格子底色與畫布底色至少 3:1。強制色彩模式下底色被系統色取代，狀態仍靠符號與文字辨識，焦點改用 `Highlight` 的 outline。
  - 其他：防火牆畫面的動作色、停用規則透明度與定位列（`firewall`），新舊比對的 effect 色與新暴露底色（`diff`）。
- **鍵盤、觸控與系統偏好**（`src/view/graph/canvas.js`、`assets/app.css`）：拓樸圖可取得焦點，可用鍵盤操作（按鍵見[使用說明「② 檢視」](使用說明.md#step-view)）；移到的設備以滑過的樣式標示，並讀給螢幕閱讀器（`#graph-live`）。滑鼠、觸控與觸控筆共用 pointer 事件；觸控沒有 hover，命中範圍較大，點兩下等同雙擊。強制色彩模式（Windows 高對比）下，焦點與「選取中」改用系統色的 outline；偏好減少動態效果時取消轉場，「力導向排列」一次算完、不播動畫。

### 11.3 拓樸版面

- 共用步驟在 `src/view/graph/layout.js`：
  - `prepare()`：分群、終端（排在所屬設備下方）與 BFS 分層
  - `shelf()`：各群以書架方式排列
- 兩種版面：
  - **快速（內建）**：同步計算，用一輪重心排序並對太寬的層折行。
  - **分層（ELK，預設）**：`src/view/graph/elk-layout.js` 對每群的核心設備執行 ELK layered，依 `prepare()` 的層級決定邊的方向，再做多輪交叉最小化與 network-simplex 節點擺放。節點框會預留終端方陣與標籤的空間。
- 載入流程：
  - 載入基準時先以快速版面出圖。
  - 沒有儲存位置時，再於背景套用分層版面。
  - 網路設備超過 `App.ELK_MAX`（1500）、逾時或失敗時，維持快速版面，並以 banner 說明原因。
- ELK 在 `file://` 下沒有 Worker，會在主執行緒計算，所以每群之間會讓出主執行緒。約 1000 台網路設備時約 2.4 秒。
- **L2 埠圖**：設備是容器框、埠是框邊上的節點。`portPrepare` 決定設備的層級與每個埠在框的上緣或下緣（對端在較上層的埠放上緣）；內建版面 `portLayout` 依層級逐列排開設備框，同一邊的埠依對端設備的 x 排序。分層版面 `elkPorts` 以 ELK 的 port 計算（埠固定在 `portPrepare` 決定的那一邊，同一邊由 ELK 排序以減少交叉），分群與內建版面相同，各群各算一次再以書架排列。
- **L3 子網圖**：子網與設備都是節點，沿用設備圖的分群（子網歸到接在它上面最多設備的那一群），各群分別以 ELK 計算。
- **畫布**（`src/view/graph/canvas.js`）為 L2／L3 新增的節點與邊：
  - `node.box { w, h }`：容器框（L2 的設備）或長條（L3 的子網）；命中範圍與標示環是矩形，只在沒有點到框上的其他節點時命中。
  - `node.anchor { parent, dx, dy }`：位置跟著 parent（L2 的埠）；位置不另外儲存，拖曳它等於拖曳 parent。
  - `edge.style { c, w, dash }`：取代依類別的連線樣式；`edge.arrow`：在 b 端附近畫箭頭（L3 的路由）。
  - 高亮（`setHighlight`）的值可以是物件，帶線型與外形（VLAN 篩選用），不只是顏色。
- 使用的版本是 `vendor/elkjs-0.11.1/`（EPL-2.0，未修改），不屬於核心載入順序。檔案約 1.6 MB，不放在 `index.html`；第一次需要分層版面時才由 `elk-layout.js` 以 `<script>` 載入。選擇「快速（內建）」或網路設備超過上限時不會載入。

### 11.4 未知對端的畫法

未知對端的判定在核心（[§5.3「未知對端」](#未知對端210-新增)），畫法只在檢視層：基準的設備、鏈路、檢查結果完全不變（有測試），虛擬節點只存在於畫面。

| 情況 | 畫法 |
|---|---|
| 一個埠一個 MAC，且非 Wi-Fi | 圓點，顏色依廠商（避開紅、橘黃、綠，以免和狀態混淆），標 IP；近看顯示廠商縮寫。廠商色最多 8 色，依終端數量取前 8 個廠商（同數量依名稱），其餘與不明廠商歸「其他」的中性色；數量取自全部未知對端與推定終端，不受展開／收合影響 |
| 有線介面一埠多個 MAC，或任一 Wi-Fi 介面 | 有線多 MAC 不列為終端埠；Wi-Fi 介面不列為終端埠，但每個 Wi-Fi MAC 觀察位置列入終端清單並可作圖面提示（多 MAC 為菱形），Wi-Fi 位置不參與 A02 |
| 介面 `rawType=veth`（容器虛擬網路卡，`type=virtual`） | 連到該終端的連線用專用線型（長線加兩個點），顏色維持連線類別色，節點外觀不變；提示與介面詳細標「容器 veth」 |
| 介面 `type=wireless` | 連線用另一種專用線型（長線加一個點），標「Wi-Fi」 |
| 同一台設備超過 8 個，或全網超過 800 個 | 收合成一個「終端 ×N」群組；雙擊或在右側按「在圖上展開」 |

依介面類型的線型定義於 `theme.js` 的 `endpoint.byType`（鍵為 `rawType` 或 `type`，以 `endpoint.styleOf(介面)` 查詢），只識別連線（收合成「終端 ×N」群組時連線維持預設線型），僅視覺識別，不改變判定與檢查。

### 11.5 匯出

`src/view/export.js` 只讀傳入的 Snapshot，在本機以 Blob 下載，不經過網路。

- **介面**：匯出的組字函式都收 Q，不讀 Snapshot 的欄位。`V.exporter.KINDS[k]` 是每種匯出的 `name(Q)`（檔名）、`text(Q, opts)`（內容）與 MIME，畫面的按鈕都經過這裡；基準 JSON 要原樣序列化整份 Snapshot，所以由 `opts.snapshot` 傳入，只序列化、不讀欄位。其他：`V.exporter.findingsCsv(Q, opts)`、`findingsMarkdown(Q, opts)`、`baseName(Q)`，`V.remediation.devicesCsvDraft(Q)`；圖的資料 `A.graphData(Q)` 與檢查結果清單的 `V.lists.findings.openFirst(Q)` 也收 Q。
- 基準 JSON：Snapshot 原樣序列化，不增刪欄位；可再載入作為新舊比對的舊基準。
- 檢查結果 CSV：一筆 finding 一列，欄位依序為 `severity,id,title,message,entities,evidence,acknowledged,ack_kind,ack_note,device,action,status,note,waiver_reason,waiver_until,facet`，共 16 欄。新欄位一律加在最後，既有欄位的位置不變。
  - `entities` 是 `type:key`、`evidence` 是 `檔名:行號`，多筆以「; 」分隔。
  - 舊的確認欄位保留名稱與位置，改由處理紀錄對應：已處理（狀態不是 open、regressed）時，`acknowledged` 是使用者最後一次變更的時間（UTC ISO），`ack_kind` 是狀態（`scheduled`／`accepted`／`false-positive`／`fixed`），`ack_note` 是備註；待處理時三欄都是空白。
  - `device` 是所屬設備鍵（`Q.findingDevice`），不屬於任何設備時為空白。
  - `action` 是規則的處理建議（`V.remediation.advice`），照 `CATALOG` 原文、保留反引號；規則沒有處理建議時為空白。沒有 `causes` 欄：同一段多句文字會在每一列重複，合在一格也不好篩選，常見原因放在 Markdown 報表與畫面上。
  - `status` 是處理紀錄的狀態（`open`／`scheduled`／`accepted`／`false-positive`／`fixed`／`regressed`），不在處理紀錄中時空白；`note` 是備註（不論狀態）；`waiver_reason`、`waiver_until` 是可接受的豁免原因與到期日（UTC ISO）。
  - `facet` 是 `finding.facet` 的原值（檢查項目，會進入 findingKey，見 [§7](#7-一致性檢查)），例如 A12 的 `dns`／`ntp`；規則沒有 facet 時空白。放原值而不是畫面的顯示文字，方便在試算表篩選與對照 findingKey。Markdown 報表不加這一欄，因為訊息已經寫出項目。
  - 開頭有 UTF-8 BOM，換行為 CRLF；含逗號、引號、換行或頭尾空白的儲存格依 RFC 4180 加引號；以 `=`、`+`、`-`、`@`、Tab、CR 開頭的儲存格前面加 `'`，避免試算表當成公式執行。
- 檢查結果 Markdown：預設依嚴重度、規則分組，每條規則的段落開頭先列「處理建議」與逐條的「常見原因」（反引號內轉成行內程式碼）；含證據原文與行號。開頭有一行「處理紀錄」列出各狀態（open 以外）的筆數。已處理的項目前面標出狀態與時間，回歸的標「回歸」，豁免與備註另起一行。
- 「依設備排序」：CSV 改依所屬設備排序，Markdown 改依設備分組（每組標題是設備名稱與筆數，不屬於任何設備的最後一組），組內保留原順序。同一條規則會出現在很多台設備，所以依設備分組時，處理建議與常見原因集中在報表最後的「附錄：處理建議與常見原因」，只列這份基準有出現的規則，每條一次，依 `CATALOG` 的順序。
- 預期資料：`S.compare.expectedFrom(Q)` 的結果（`ssot-expected/1`）。
- devices.csv 草稿：見上，不加 BOM、換行用 LF（`collect.sh` 以 bash 逐行讀取）。
- 修正計畫：每台設備三個 `.rsc` 與總表 Markdown，見上面的修正計畫。
- 處理紀錄：`ledger-<目前時間>.json`，見上。
- 工作包：`workpack-<baseName>.zip`（`A.workpackName()`，例如 `workpack-20260101T000000Z-42dev.zip`），由 `S.workpack.build` 產生（[第 10A 節](#10a-工作包ssot-workpack1)）。各角色在 manifest 的 `name`（ZIP 內的路徑由核心依 `safeSegment` 產生）沿用各匯出的檔名：

  | 角色 | 檔名 |
  |---|---|
  | `source` | 收集檔的來源名稱（貼上的內容是 `(貼上的內容)`） |
  | `snapshot` | `baseline-<baseName>.json`（和「基準 JSON」相同） |
  | `ledger` | `ledger-<建立時間>.json` |
  | `profile` | `profile-<id>.json`（沒有 id 時 `profile-unnamed.json`） |
  | `expected-data` | `expected-data.json` |
  | `expected` | 載入預期資料時的檔名 |
  | `report` | `findings-<baseName>.csv`、`findings-<baseName>.md` |
  | `patch` | 修正計畫每台設備的 `<base>.rsc`、`<base>-rollback.rsc`、`<base>-verify.rsc`，加上 `patch-summary-<baseName>.md` |

  JSON 都以兩格縮排寫出；基準 JSON 和下載的相同（`V.exporter.snapshotJson`）。
- 檔名含建立時間與設備數，例如 `findings-20260101T000000Z-42dev.csv`、`devices-draft-20260101T000000Z-42dev.csv`。
- 拓樸圖 PNG（`A.exportPng`）畫的是目前的層級，檔名依層級：設備圖 `topology.png`、L2 埠圖 `topology-l2.png`、L3 子網圖 `topology-l3.png`（`A.layerPngName`）。L4 可達性沒有 PNG，以提示列說明。
- L4 zone 矩陣 CSV：`l4-matrix-<baseName>.csv`，選了單一服務時加上服務（例如 `l4-matrix-<baseName>-tcp-443.csv`）。每一格一列，欄位依序是來源 zone、目的 zone、zone 內、狀態、異質、允許、拒絕、無法判斷、總數、代表規則、無法判斷的原因；BOM、換行與儲存格的處理和檢查結果 CSV 相同。

### 11.6 規模

實測（Node，產生的 1041 台已收集設備、3921 個節點、5920 條鏈路、約 1 萬個 MAC、約 1400 萬字元輸入）：建立約 3.7 秒、乾淨網路零誤報。

M1 的查詢（`npm run test:large` 的約 1000 台資料，第一次呼叫；`tests/large.js` 會印出時間，上限是壓力測試上限的四分之一）：`Q.vlanCarriers` 一個 VLAN（VLAN 20）約 190 ms；`Q.portGraph()` 預設約 181 ms，`ports: 'all'` 約 259 ms；`Q.subnetGraph({ routes: true })` 約 86 ms。同樣的參數第二次呼叫因為快取，約 0 ms。`Q.vlan` 約 106 ms。

M2 的查詢（同一份資料與量法，第一次呼叫，上限同上；數字以 `npm run test:large` 印出的為準，下面是幾次量測的範圍）：`Q.zones()` 約 27 ms（4 個 zone、200 個網段）；`Q.reach` 一次約 3–13 ms；`Q.zoneMatrix()` 約 2.3–2.7 秒（120 個代表位址、約 10 萬次判斷）；`Q.zoneCell` 一格約 170–200 ms；`Q.ruleImpact` 量的是一條真的有影響的規則（input 鏈的「!LAN 一律丟棄」，2178 筆判斷；乾淨網路的 forward 規則影響都是 0 筆，量不出成本），約 980–1230 ms。

| 問題 | 做法 |
|---|---|
| 解析卡畫面 | 分段執行並顯示進度（`buildAsync`）；`file://` 不能用 Web Worker，故不採用 |
| 物理模擬太慢 | 預設不跑。先以分群＋分層的快速版面一次算完出圖，再於背景套用 ELK 分層版面（約 1000 台網路設備約 2.4 秒；超過 1500 台不執行）。「力導向排列」為選用的格網加速力導向 |
| 整張網路連成一片 | 沒有命名規則時，以標籤傳播依連線密度自動切出「區域」分區排列（只影響畫面，不寫回基準） |
| 主機把層拉得很寬 | 只連到一台設備的未收集終端，排在該設備正下方的小方陣 |
| 節點太多 | 主機超過 300 個時預設隱藏；只畫畫面內物件；縮小時不畫標籤與埠名 |
| 儲存空間 | IndexedDB，不用 localStorage，不自動過期 |

- 1000 台實測：880 台設備各收成一個群組（全網超過上限），展開一台約 0.4 秒。
- 1000 台的 L2／L3 畫面：L2 埠圖（超過 `App.L2_MAX`，只畫焦點設備與鄰居）約 552 ms；第一次切到 L3 子網圖（含 ELK）約 3475 ms，之後再切回約 139 ms。
- 1000 台的 L4 畫面（大型冒煙測試印出的時間）：第一次開矩陣分段計算，一次實測分 159 段，一段最久 48 ms，兩段之間最長 61 ms；計算本身 2754 ms，含讓出共 4259 ms（期間顯示分段進度，畫面仍可操作）。同一份基準再開時使用快取；選單一服務時分 17 段；規則詳情的「計算 L4 影響」約 785 ms。`tests/large.js` 另外直接量 `Q.zoneMatrixSteps` 每一段的時間，斷言 p95 不超過 `max(50, 壓力測試上限 / 100)` ms，而且超過 10 段。

## 附錄 A：與 v0.1 草案的差異

| 項目 | v0.1 | 實作 | 原因 |
|---|---|---|---|
| 背景執行 | Web Worker | 主執行緒分段＋進度 | `file://` 不允許 Worker；實測 1000 台約 3 秒可接受 |

## 附錄 B：與多廠牌版（Juniper＋Fortinet）的差異
