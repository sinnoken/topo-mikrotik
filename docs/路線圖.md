# 路線圖

這份文件回答「接下來要做什麼、依什麼順序、做到什麼程度算完成」。

**維護方式**

- 排程改變或完成一項時更新這份文件。
- 完成的項目移到[「已完成」](#已完成)，只留一句摘要與 PR 編號。
- 已實作的設計寫在[設計說明](設計說明.md)，不寫在這裡；這裡只連結過去。
- 決策的理由寫在 [ADR](架構決策/README.md)，這裡只寫編號。
- 負責的 agent 依 [ownership.json](../.claude/agents/ownership.json) 的檔案歸屬；改介面時的順序依 [ADR-013](架構決策/013-新增workflow-agent依上下游分工.md)：data-model → workflow → frontend → docs（collector 在 data-model 之前，提供新的收集指令）。

狀態代號：

| 狀態 | 意義 |
|---|---|
| 進行中 | 已有 agent 在 worktree 開發 |
| 已排程 | 使用者已決定要做，排在主線或旁支中等待前一項 |
| 待決定 | 對應的 ADR 還是「提議」，或範圍要使用者決定 |
| 等資料 | 要使用者提供真實設備的資料才能進行 |

### L2 埠依鏈路方向選邊

- **狀態**：已完成（第 16 輪，3.7.0；9159df5）。拖曳中即時換邊沒有做：畫布只在放開時發出事件，現在是放開後換邊。做法見[畫面架構 §7](畫面架構.md#7-拓樸版面)。
- **目的**：L2 埠圖的埠目前只在框的上、下緣，而且在設備排位置之前就依層級決定（`V.layout.portPrepare`：對端全在上層放上緣，其餘放下緣）。同一層的設備互連時兩端都在下緣，線繞成 U 形；拖曳設備後埠也不會換邊。
- **做法**：
  - 設備位置排好後，每個埠取框中心到對端框中心的向量 (dx, dy)：|dy|/|dx| 大於框的 h/w 時放上或下緣（依 dy 正負），否則放左或右緣（依 dx 正負）。多個對端（LAG、一埠看到多台）取平均位置。
  - 同一邊依對端在該邊的投影排序：上下緣依 x，左右緣依 y。這是現有上下緣排序的推廣。
  - 選邊函式放在 `src/view/graph/layout.js`，內建版面、ELK（只用它決定設備位置）與拖曳共用，結果一致。拖曳時即時重算，接近對角線時加遲滯，避免埠來回跳。
  - 左右邊埠較多時框高跟著加。儲存的手動位置照常可用：載入後依設備位置重新選邊，不另外存邊。
- **範圍**：只改畫面的檢視狀態，Snapshot 不變。既有「埠在上或下緣」的測試一起改；附改前與改後的截圖對照（`ux-review`）。
- **負責**：frontend → docs（畫面架構 §7）

### L4 由外而內與閱讀順序

- **狀態**：已排程，在 [L2 埠依鏈路方向選邊](#l2-埠依鏈路方向選邊)之後（2026-11-06 使用者決定）
- **目的**：L4 的內容正確，但閱讀順序和使用者想問的相反。使用者想一眼看出「從 WAN 進來，連得到哪些 IP、哪些服務」；L4 是阻擋的管控，原則上從最外面開始思考。第六次 UX 評審後的截圖看到的問題：
  - 答案在最後：先是說明、判斷的前提、控制項、圖例與計算說明，矩陣在第一個畫面只露出兩列。
  - WAN 只是矩陣的第一列；格子的「17/86」是代表位址 × 目的 × 服務的次數，不是使用者的單位。
  - 明細裡唯一的允許（例如 `tcp/8443 → 10.1.20.11:443`）夾在十幾個拒絕之間。
  - 「結果不一」的說明偏技術；左右兩側與 L4 無關，「路由追蹤…」和 L4 的關係看不出來。
- **原則**：
  - 先答案、再原因、前提放最後：第一句就是結論（例如「從 WAN 進來，連得到 1 個服務：tcp/8443 → 10.1.20.11:443（經 dst-nat，推論）」）；前提收成一行連結。
  - 先列開放的，拒絕的收成「其餘 N 個組合拒絕」。
  - 用 IP:埠說話，次數留在提示文字。
  - 不在 L4 或右側新增分頁或切換；選規則一律 `App.select({ type: 'rule' })`，右側照舊。
- **由外而內的結構**（由上往下）：
  1. 外部 → 路由器本身：邊界路由器的 input 與 `/ip service`（對應 F07、F10–F14）。
  2. 外部 → 內部（dst-nat）：哪個公網埠轉到哪台主機的哪個埠（對應 F04）。
  3. 外部 → 內部（直接路由）：沒有 NAT 的路徑，IPv4 的公網網段與 IPv6 的 LAN（對應 F03、F05）。
  4. 內部互通：現有的 zone 矩陣，降為進階、預設收合。
  5. 內部 → 外部：之後再討論。
- **步驟**：
  1. frontend：只針對 L4 的 UX 評審（`ux-review`），以截圖逐段標出閱讀順序，確定新結構的畫面稿。（已完成，第 16 輪；報告不進 repo）
  2. data-model：
     - **回程的前提**（已完成，第 16 輪：`Q.policyBaseline` 與 [F15](基準檢查.md#f15)，3.7.0）：逐台判斷 input／forward 是否放行 established/related、丟棄 invalid，以及最後的預設動作。沒有的設備，路徑標「回程未保證」，並新增一條檢查（findings 改變，依 [ADR-005](架構決策/005-版本升級規則.md) 升 minor，範例資料放對應的問題）。
     - **暴露清單的查詢**：WAN 入口取自現有的 WAN 判斷。候選服務是預設服務、從 WAN 進來的放行規則的目的埠、dst-nat 的埠與 `/ip service` 的埠。候選目的是 WAN 設備本身、dst-nat 的目標與內部網段的代表位址。逐一以 `Q.reach` 判斷，與 zone 矩陣共用快取。查詢時計算（[ADR-014](架構決策/014-L4-zone矩陣在查詢時計算.md)），Snapshot 不變。
  3. frontend：依畫面稿重排 L4。上述 1–3 段在最上面，矩陣、位址組、逐跳路徑保留但換順序；明細先列允許與無法判斷。
  4. data-model：IPv6 第一階段。不做 IPv6 路由，只看邊界路由器：從 WAN 進入時，以 IPv6 的 input／forward 規則判斷能到哪些 LAN 網段（取自已解析的 `/ipv6 address`），補進第 3 段。完成前畫面寫明「只有 IPv4」並連到 F05。
  5. docs：使用說明、畫面架構、查詢介面、基準檢查、版本紀錄。
- **之後再決定**：防火牆層級（規則瀏覽器、規則組成、規則順序一覽），看的是「規則寫得好不好」，另案討論；完整的 IPv6 L4 要收集 `/ipv6 route` 並改 Snapshot。
- **負責**：frontend（評審）→ data-model → frontend → data-model（IPv6）→ docs
