# 開發指南

這份文件寫給要修改程式的人：專案結構、指令、測試、擴充方式、外部資產與 CI。開發原則與 agent 分工見 [CLAUDE.md](../CLAUDE.md) 與 [.github/copilot-instructions.md](../.github/copilot-instructions.md)；模組與資料模型見[設計說明](設計說明.md)，查詢函式見[查詢介面](查詢介面.md)，檢視層架構見[畫面架構](畫面架構.md)。

## 1. 專案結構

這一節是檔案放在哪裡的唯一清單。各模組的責任與依賴方向見[設計說明 §3](設計說明.md#3-模組)，檔案歸哪個 agent 見 [ownership.json](../.claude/agents/ownership.json)。


處理流程：reader 切成區塊（保留檔案與行號）→ adapter 解析為事實 → model 建立實體 → 推論 → 檢查 → Snapshot（`ssot-snapshot/3`）。畫面、比對、修正 patch、處理紀錄與工作包只透過 `SSOT.query()` 唯讀存取 Snapshot（工作包另外在呼叫時使用 `S.build` 重建）。細節見[設計說明](設計說明.md)。

## 2. 指令

只需要 Node.js（CI 使用 Node 22／24），不需安裝任何套件，也沒有 build、lint 或 format script。這一節是指令的唯一清單（[CLAUDE.md](../CLAUDE.md) 只留最常用的幾個並連到這裡）：

```bash
npm test                 # 全部：核心、文件、SSH 收集器、畫面冒煙測試（tools/run-all.js，四組都跑完再彙總）
npm run test:core        # 只跑核心測試（tests/core、tests/workflow；含收集器端到端測試，需要 bash 與 GNU timeout，Windows 用 Git Bash）
npm run test:docs        # 只跑文件與分工一致性（tests/docs.js）
npm run test:collector   # 只跑 SSH 收集器測試（tests/collect.sh，需要 bash 與 GNU timeout）
npm run test:ui          # 只跑畫面冒煙測試（tests/ui-smoke.js，模擬 DOM）
npm run test:large       # 核心測試加上約 1000 台的壓力測試
npm run test:core -- --grep A02   # 只跑名稱含 A02 的測試（區分大小寫，可與 --large 並用；沒有符合的測試時以失敗結束）
SSOT_LARGE_MAX_MS=30000 npm run test:large   # 覆寫壓力測試的時間上限（預設 20000 ms；非數字或 ≤0 直接失敗）
SMOKE_INPUT=samples/large-1000.txt node tests/ui-smoke.js   # 大型冒煙測試（先執行 npm run gen:large）
npm run golden:update    # 刻意改變 Snapshot 後更新黃金基準（tests/golden/），提交前用 git diff 檢視
npm run check:version -- origin/main   # 黃金基準的內容和 base 不同時，確認 S.VERSION 已升 minor（ADR-005）
npm run sample           # 重新產生範例收集檔並嵌入畫面，也依 tools/collector-commands.sh 產生 samples/collect-commands.js（核心測試會檢查 samples/ 和產生器一致，不一致時請執行這個）
npm run gen:large        # 產生約 1000 台的收集檔（samples/large-1000.txt，不提交）
npm run oui -- <index.json>      # 更新 OUI 廠商資料（步驟見「更新外部資產」）
npm run baseline -- 收集檔 -o out/   # 排程用的 CLI（tools/baseline.js），選項、輸出與結束碼見 README「排程執行（CLI）」
node tools/anonymize.js 收集檔.txt -o tests/fixtures/real/<版本>-<型號>.txt   # 真實輸出去識別化後當測試資料（見第 5 節）
git diff --check         # 提交前檢查行尾空白與衝突標記（CI 也會檢查）
```

`tests/run.js` 只是執行器：依檔名載入 `tests/core/*.js` 再載入 `tests/workflow/*.js`，`--large` 時最後載入 `tests/large.js`；共用的 helper 在 `tests/lib.js`。`--grep` 只跑名稱含該文字的測試，結尾註明「已篩選：N／總數」；沒有任何測試符合或參數不認得時以失敗結束。在 Node REPL 以 `require('./tests/load.js')()` 可以取得 `SSOT` 命名空間，直接呼叫 `S.build(...)`。

**維護分支用的工具**（`.claude/scripts/`，給主對話 lead 用，不進 CI；流程見 `branch-maintenance`、`ux-review` 兩個 skill）：

```bash
node .claude/scripts/slice-xref.js . slices.json      # 派工前：各切片的檔案交集與「A 用到 B 定義的成員」；程式檔有交集時結束碼 1
.claude/scripts/merge-slice.sh <worktree> <基準>      # 把 agent worktree 的切片以 git apply --3way 套用到目前分支（-text 檔案直接複製以保留 CRLF），不 commit
.claude/scripts/merge-slice.sh --cleanup <worktree> <基準>   # 切片都套用後才刪 worktree 與 worktree-agent-* 分支
node .claude/scripts/shot.js <commit> <輸出目錄>      # 截圖矩陣（亮／暗 × 1440／390）；本機選用，需自行安裝 puppeteer
```

## 3. 測試

`npm test` 由 `tools/run-all.js` 依序執行核心（`tests/run.js`）、文件（`tests/docs.js`）、收集器（`tests/collect.sh`）、畫面（`tests/ui-smoke.js`）四組，一組失敗也會把後面的跑完，最後列出每一組的結果；有任何一組失敗或無法執行（例如找不到 `bash`）時以 1 結束。不用 shell 的 `a || s=1` 串接，因為 Windows 的 cmd.exe 不支援。

`tests/run.js` 逐一執行測試並 `await` 每個測試函式的回傳值，所以測試可以是 async，Promise 裡的失敗會算成失敗（以前不等 Promise，失敗會被當成通過）。

畫面冒煙測試的入口是 `tests/ui-smoke.js`（`npm run test:ui`），它只依序載入下面的檔案：

| 檔案 | 內容 |
|---|---|
| `tests/ui/dom.js` | 極簡的模擬 DOM：載入 `index.html` 的 `<body>`、`document`／`window` 的替身、`<script>` 動態載入、`localStorage`、`requestAnimationFrame` |
| `tests/ui/harness.js` | 依 `index.html` 的順序載入核心與畫面；step 的登錄與執行器、`--grep` |
| `tests/ui/helpers.js` | step 共用的小工具（`text`、`$`、`goStep`、`buildInput`、`recordCanvas`、`captureDownloads` 等）；step 檔只從這裡取得名稱 |
| `tests/ui/boundary.js` | 畫面與資料的邊界掃描（`stripJs`、`VIEW_S_ALLOW`、`VIEW_S_ONLY`、`viewBoundaryViolations`） |
| `tests/ui/steps/*.js` | step，依主題分檔（啟動與輸入、拓樸圖、研判、L2／L3、L4、VRF、匯出、處理紀錄、修正、樣式與無障礙、設定、資料中心與本機資料……） |

step 之間共用畫面狀態（`App`、store、選取），`tests/ui-smoke.js` 的 `FILES` 順序就是執行順序，不可調換；`FILES` 和 `tests/ui/steps/` 不一致時直接失敗。新增 step 放進對應主題的檔案，名稱要和既有的 step 都不同（[發布前檢查表](發布前檢查表.md)逐字引用 step 名稱）。

- `node tests/ui-smoke.js --grep <文字>`（或 `npm run test:ui -- --grep <文字>`）只跑名稱含該文字的 step（區分大小寫），結尾註明「已篩選：N／總數」；沒有任何 step 符合或參數不認得時以失敗結束。可與 `SMOKE_INPUT=…` 並用。
- `--grep` 會**自動帶入前置 step**，標「（前置）」，依原本順序執行：`tests/ui/harness.js` 的 `FIXTURE`（啟動、載入範例並建立基準；排在符合的 step 前面的才帶入），以及 `NEEDS` 列出的依賴（遞移帶入）。`NEEDS` 是逐一單跑全部 step 實測出來的：只帶入 `FIXTURE` 時會失敗的 step 才列。新增的 step 單跑失敗、全部跑時通過，就是依賴了前面的 step，把它依賴的 step 加進 `NEEDS`（鍵與值都是 step 名稱的開頭，必須恰好對到一個排在前面的 step，否則直接失敗）。
- 第一個失敗之後的每個失敗都另標「（可能是連鎖失敗：前面的「…」已失敗）」：step 共用狀態，前面失敗時畫面可能沒回到預期的狀態，先修第一個失敗。

收集器測試（`tests/collect.sh`）開頭有一項靜態檢查：`tools/*.sh`、`tests/*.sh` 中 `$名稱` 後面直接接非 ASCII 字元（例如 `$board：`）時失敗並列出行號。macOS 內建的 bash 3.2 在 UTF-8 語系下會把後面的位元組算進變數名，`set -u` 時報 unbound variable；這種地方要寫成 `${名稱}`。

文件測試（`tests/docs.js`）另外檢查每個 Markdown 檔（不含報表的預期輸出 `tests/workflow/fixtures/`）的相對連結都指得到檔案、錨點都對得到標題；錨點依 GitHub 的規則由標題產生（全形標點去掉、中文保留，ATX 與 setext 標題都算，比對不分大小寫），改標題時要一起改引用。連結包括 `[文字](目標)`、角括號的 `[文字](<含空白的目標>)`、參考式定義與 Markdown 裡的 `<a href>`；網址中成對的括號算在網址裡，程式碼區塊與行內程式碼（含雙反引號）裡的不算。錨點規則與連結的取法只有一份，在 `tests/lib.js`，冒煙測試檢查畫面裡的文件連結也用它。

文件測試也檢查文件不再出現畫面已淘汰的說法（例如頁首「⋯」選單 → ⚙ 設定、「規則目錄」→「檢查目錄」）。淘汰用詞的清單也在 `tests/lib.js`：`RETIRED_TERMS` 畫面與文件共用，`RETIRED_UI_TERMS` 另外加上只在畫面擋的詞（文件可以寫內部 API、ADR 編號、規格書的「下鑽」等）。範圍是 `docs/`、README、CLAUDE.md、開發原則與 skills；版本紀錄、路線圖與架構決策是歷史敘述，不掃；程式碼、連結網址、HTML 標籤與刪除線不算，同一行寫明是舊說法（原本、取代、改名、舊稱、已淘汰、拿掉）時也不算。命中屬合理用法時，把清單的詞改成更精確的片語或移到 `RETIRED_UI_TERMS`。

除了逐項功能的測試，核心測試（`tests/run.js`）另有幾類跨元件的檢查：

- **收集器端到端契約**：用假的 `ssh` 實際執行 `tools/collect.sh`，把產生的 `bundle-v1` 交給核心，確認收集時間、失敗原因、設備與指令都讀得出來，收集器註解也不會被列為 I01。需要 `bash` 與 GNU `timeout`（coreutils）；Windows 請安裝 Git Bash 並放在 PATH 前面。缺少時這項測試會明確失敗並說明缺什麼，不會略過。
- **防火牆性質測試**：以固定種子的亂數產生數百組規則，檢查涵蓋判斷的自反、遞移，插入規則不改變其他規則的鍵，在 input 最前面插入 drop 不會增加 F03，不確定的比對不會產生 F01。失敗訊息附上種子與規則，用同一個種子就能重現。
- **比對性質測試**：以範例資料和刻意修改過的版本互相比對，檢查自己比自己沒有差異、A→B 與 B→A 的新增和移除互換、只改 finding 訊息不算差異、新增 WAN 放行標為新暴露。
- **每一行輸入都有被處理**：範例資料與 `tests/fixtures/` 的每個非空行，都要是結構行（設備標頭、指令標記、註解等）、產生事實的行、解析器宣告可忽略的行、I03 或 I01 區塊的一部分；`tests/fixtures/` 不可有 I03。規則見[設計說明 §4](設計說明.md#4-輸入)。
- **可重現**（`tests/core/sample.js`）：以四組時區與語系（`TZ` 為 UTC 或 Asia/Taipei，`LANG`／`LC_ALL` 為 C 或 zh_TW.UTF-8）的子行程各建一次範例基準，先確認環境確實生效，再確認去掉 `meta.createdAt`、`meta.timing` 後完全相同。另把範例依設備拆成多個檔案、正序與反序各建一次：去掉來源位置後模型、覆蓋率與 findingKey 的順序都相同；來源位置、inputHash 與少數檢查結果的列舉順序隨輸入順序改變，範圍由測試釘住。
- **非同步的核心函式**：`tests/run.js` 會等 async 測試完成，可以直接寫 `test('…', async () => { … })`。既有的 `S.workpack.validateAsync` 測試（`tests/workflow/workpack.js`）是在 `tests/run.js` 會等 Promise 之前寫的，以子行程（`child_process.execFileSync` 執行 `node -e`，在子行程中 `require('tests/load.js')`）跑完再把結果以 JSON 交回來比對。
- **工作包與 ZIP**（`tests/workflow/workpack.js`）：`S.zip` 和其他工具互通（讀得了 Python `zipfile` 寫出的 stored ZIP，壓縮過的明確拒絕；CRC-32 和 Node `zlib` 一致），以及加密、不安全路徑、重複檔名、CRC 不符等每一種拒絕。`S.workpack` 以範例資料建立再讀回，內容和匯出前相同；相同的 parts 與 now 得到完全相同的 bytes；被改過的 manifest、雜湊與大小、順序或內容不同的收集檔（以 `S.inputHashOf` 核對，不重建）、不是同一輪的處理紀錄都列出錯誤；`validate` 以固定時間重建的基準，和黃金基準測試用的範例基準（`tests/golden.js` 的 `goldenSnapshot`）完全相同。另含 `S.ledger.roundOf` 的測試。
- **模擬 DOM 的 NodeList**（`tests/ui/dom.js`）：和瀏覽器一致，`querySelectorAll` 回傳 NodeList（有 `length`、索引、`item`、`forEach` 與迭代，沒有 `find`、`map`、`some` 等陣列方法），`children` 是 HTMLCollection（連 `forEach` 都沒有）。畫面程式要用陣列方法時先 `Array.from(…)`。只給測試程式用的陣列版本是 `testAll(sel)`，畫面程式不可以用。
  - 冒煙測試另有一個靜態掃描步驟（「NodeList／HTMLCollection：…」），掃描 `src/view`，擋下對 `querySelectorAll(…)`、`children`、`childNodes` 直接呼叫陣列方法，以及使用 `testAll` 的寫法，涵蓋冒煙測試沒走到的分支。違規時照訊息改成 `Array.from(…)`。
- **畫面與資料的邊界**（`tests/ui/boundary.js` 與 `tests/ui/steps/01-boot-input.js` 的邊界掃描步驟，[ADR-018](架構決策/018-畫面只透過Q與S.query讀資料.md)）：
  - **邊界掃描**：去掉註解、字串與 regex 的內容後，掃描 `src/view` 的每個 `.js`。只允許 `VIEW_S_ALLOW`、`VIEW_S_ONLY` 列出的 `S.*` 成員，不可讀 `snap.`／`snapshot.` 的欄位、`Q.snapshot`，不可用計算的成員名稱 `S[…]` 或從 `S` 解構。違規時逐筆列出檔案、行號與建議的寫法（例如 `S.check.CATALOG` → `S.query.rule(id)`）。
  - **深層凍結**：把基準深層凍結後載入，跑過選設備、選鏈路、選每項檢查的結果、切換分頁、開修正計畫與全部匯出；畫面寫入基準時會因凍結出錯，測試也收集 `console.error`，最後確認基準 JSON 完全沒變。
  - **違規時怎麼修**：照訊息的建議改用 Q 或 `S.query.*`；沒有合適的函式時，請 data-model 在 `src/query/query.js` 新增，不要放寬允許清單。深層凍結失敗表示畫面改寫了基準，要把結果放進檢視狀態或複本。
- **CLI**（`tests/workflow/cli.js`）：以子行程（`child_process.spawnSync`）執行 `tools/baseline.js`，輸出到暫存目錄後讀回。涵蓋三種結束碼（第一輪有新的待處理項目、復發 → 1；同一份基準再推進或沒有新項目 → 0；壞的處理紀錄 JSON、處理紀錄／命名規則／預期現況格式錯誤、讀不到檔案、參數錯誤、收集檔沒有認到任何設備的資料（空檔、只有空白或註解、內容都認不得）→ 2，而且輸出目錄不留下任何檔案）；`sitedoc.md`／`sitedoc.csv` 與直接呼叫 `S.report.siteDocMarkdown`／`siteDocCsv` 的結果相同；「CLI 與畫面得到相同的處理紀錄」：同一份輸入（含使用者在兩輪之間改過狀態的處理紀錄），CLI 寫出的 `ledger.json` 和在 Node 中直接呼叫 `S.build`＋`S.ledger.advance` 的結果深度相等；相同輸入與 `--now` 兩次輸出的每個檔案位元組都相同。結束碼的值取自 `require('tools/baseline.js').EXIT`，不在測試裡另寫一份。
- **版本一致性**（`tests/core/version-rule.js`、`tools/check-version.js`）：依 [ADR-005](架構決策/005-版本升級規則.md)，同一份輸入建出的 Snapshot 內容改變就要升 minor。`node tools/check-version.js [base]`（預設 `origin/main`）比較 `git merge-base <base> HEAD` 與目前工作目錄的 `tests/golden/sample-snapshot.json`，忽略 `meta` 的 `version`、`baselineKey`、`createdAt`、`timing` 後內容不同、而 `src/core/ns.js` 的 `S.VERSION` 的 major.minor 沒變時以 1 結束並說明要升 minor；git 或檔案有問題時以 2 結束。核心測試涵蓋判斷函式：內容相同、只改版本欄位、升 minor 或 major 通過，內容不同而版本相同或只升 patch 號失敗。
- **修正 patch 黃金檔**：範例資料中 F01、F02、F06 與 A12 的修正計畫，以及每台設備的 `.rsc`，要和 `tests/golden/sample-patch.json`、`tests/golden/sample-patch/` 完全相同。A12 的選擇固定在 `tests/golden.js` 的 `PATCH_CHOICES`：DNS（沒有多數）選 TPE_CORE_RT_02 那一組，NTP 不指定、採多數；刻意改變時用 `npm run golden:update` 更新。

## 5. 用真實設備輸出驗證解析器

解析器目前只用依手冊撰寫與程式產生的資料測試過。若你有實機輸出，可以去識別化後放進 `tests/fixtures/real/` 當回歸測試：

```bash
node tools/anonymize.js 收集檔.txt -o tests/fixtures/real/<RouterOS版本>-<設備型號>.txt
```

MAC 保留廠商前綴、IP 與名稱換成一致的代號、密碼與序號換成 `REDACTED`。產生的 `*.map.json` 對照表不要提交；提交前請再人工檢查一次。詳見 [tests/fixtures/real/README.md](../tests/fixtures/real/README.md)。

## 6. 更新外部資產

兩份外部資產都放在 repo 裡，網頁執行時不連網；更新是開發時的步驟。建議每半年檢查一次有沒有新版，或在遇到版面問題、廠商顯示不明時更新。

**ELK.js（分層版面）**

1. 在暫存目錄執行 `npm pack elkjs@<版本>` 並解開，把 `lib/elk.bundled.js` 與 `LICENSE.md` 原樣複製到新的 `vendor/elkjs-<版本>/`，並照舊版寫一份 `README.md`（來源、版本、授權）。授權是 EPL-2.0，`LICENSE.md` 一定要一起放；檔案不要修改。
2. 把 `src/view/graph/elk-layout.js` 的 `ENGINE_SRC` 改成新路徑，刪掉舊的 `vendor/elkjs-<舊版本>/`。
3. 更新文件中寫到版本的地方（[畫面架構 §7「拓樸版面」](畫面架構.md#7-拓樸版面)、`CLAUDE.md` 的架構段）。
4. 執行 `npm run test:ui`（冒煙測試會實際載入 `ENGINE_SRC` 並排出分層版面）與 `npm test`；再用瀏覽器開啟 `index.html` 載入範例資料，確認分層版面正常。

**OUI 廠商資料**

MAC 前綴 → 廠商的資料來源是 npm 套件 [`oui-data`](https://www.npmjs.com/package/oui-data)（BSD-2-Clause，資料取自 IEEE）。在暫存目錄執行 `npm pack oui-data@<版本>` 並解開，再執行 `npm run oui -- <解開目錄>/package/index.json`。產生器會從同目錄的 `package.json` 讀出版本，寫進 `src/data/oui-data.js` 的檔頭與 `S.oui.source()`；收錄 6／7／9 碼前綴，查詢時取最長符合者。產生後執行 `npm test`，並用 `git diff --stat` 確認只有 `src/data/oui-data.js` 改變。

## 7. CI

[.github/workflows/ci.yml](../.github/workflows/ci.yml) 在 PR、合併到 main（push 到 main）、每週排程與手動執行時觸發；只 push 到其他分支不會觸發。第一個 job（`changes`）依 PR 改動的檔案決定要跑哪些 job；合併到 main、排程與手動執行不分流，一律跑全套與大型測試：

| job | PR 時什麼時候跑 | 做什麼 |
|---|---|---|
| 文件測試（`docs`） | 只改 Markdown、`.claude/`、`.github/skills/` 時（代替全套） | Node 24 執行 `npm run test:docs` 與 `git diff --check` |
| 全套（`test`） | 改到上面以外的任何檔案 | Node 22／24 執行 `npm test` 與 `git diff --check` |
| 大型測試（`test-large`） | 改到 `src/`、`samples/`、`tools/`、`tests/`、`profiles/`、`vendor/`、`index.html`、`package*.json` 或 `.github/workflows/` | Node 24 執行 `npm run test:large`（設定 `SSOT_LARGE_MAX_MS: 40000`，CI runner 較慢，只抓明顯退化），再以 `npm run gen:large` 產生的約 1000 台資料跑一次大型冒煙測試（`SMOKE_INPUT=samples/large-1000.txt node tests/ui-smoke.js`） |
| 版本一致性（`version`） | 改到 `src/` 或 `tests/golden/` 時；只在 PR 跑 | 以 PR 的 base 執行 `npm run check:version -- <base>`（見[測試](#3-測試)的「版本一致性」） |

main 上的部署前由 [deploy-pages.yml](../.github/workflows/deploy-pages.yml) 跑 `npm test` 後部署到 GitHub Pages，只在網站會發布的檔案改變時部署。提交前仍請先在本機執行 `npm test`。
- **行尾空白與衝突標記**：`ci.yml` 跑完 `npm test` 後，以 `git diff --check` 檢查整個 tree。RouterOS 原始輸出（`samples/`、`tests/fixtures/`）與 `vendor/` 的行尾空白是內容的一部分，由 [.gitattributes](../.gitattributes) 標為 `-whitespace`，不列入檢查。
- **Pages 只發布畫面需要的檔案**：部署時只複製 git 追蹤的 `index.html`、`assets/`、`src/`、`profiles/`、`samples/`、`vendor/`；`tests/`、`docs/`、`tools/`、`.claude/` 等不上站。部署前會確認 `index.html` 引用的每個檔案，以及 `src/view/graph/elk-layout.js` 的 `ENGINE_SRC`（ELK）都在網站裡，缺少任何一個就停止部署。
- `.gitignore` 排除 `.claude/worktrees/`（Claude Code subagent 的本機 git worktree）。

CI 的畫面測試用模擬 DOM，測不到 Canvas、CSP、`file://` 載入、ELK 動態載入、IndexedDB 與檔案下載；發布前請在真實瀏覽器照 [發布前檢查表](發布前檢查表.md) 手動檢查一次。
